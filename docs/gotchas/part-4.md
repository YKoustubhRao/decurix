# Gotchas, part 4

- **A worker gets cheaper at its work: every token is counted, and what it worked out once it does not work out again** (`decurix_agent/playbooks.py`, `tool_task.py`, `usage.py`, `computer/mimic.py`, TheBot `llm/meter.go`; `tasks.Summary.Tokens`). The goal, from the person running this (2026-10-12): the same intelligence, fewer tokens with time, with the scripts and logic it found saved - **in that order: correctness > intelligence >> efficiency**. The heavy model is used freely while a kind of work is new (recording, the questions after it, understanding, finding the pattern); a cheaper path is taken only once checked runs have earned it, a judgement is never handed to a smaller model to save tokens, and every result is still checked. **Tokens fall only when turns fall**: every operator turn re-reads its whole frame (about 3,000 tokens for shell work on a hosted brain, about 8,500 on the screen with its screenshot and element list), so what is kept has to remove turns, never add reading. Measured live on the app's own stack, one worker on Azure gpt-5.4, each result checked and each figure verified in the files, the Outbox or the application's own data:

  | the same kind of request, again and again | 1st (by hand) | 2nd | 3rd on |
  |---|---|---|---|
  | a workbook summarised from a CSV | 16,528 tok, 30 s | 8,250, 12 s | 2,185 / 2,194, 4-8 s |
  | figures counted and an email drafted with the file attached | 15,202, 21 s | 8,105, 7 s | 2,056 / 2,076 / 2,079, 4 s |
  | a supplier created in an ERP's web form | 134,607, 60 s | by the engine again until two runs agree: 110,660 and 115,173 | 6,012 / 6,001, 24-28 s |

  - **Counted.** A hosted brain's spend was invisible: soul reported no token counts, and of the agent's own model calls only the lesson study and the final check were added. `llm.Metered` (inside `llm.Limited`) adds each call to the `llm.Usage` its job's context carries (`llm.WithUsage` in `handleChat`), the job's snapshot reports `usage: {promptTokens, responseTokens, calls}`, and `thebot_harness._count` adds it to the task; `llm_client.chat` adds every hosted call itself, so `study`/`verify`/`azure_harness` no longer count their own. Cost stays unknown for a hosted model: **tokens are the measure**. The Tasks page has "Tokens per task" and a Tokens column, `/api/tasks/export` a `tokens` column (`tasks.FormatTokens`; nil is "not reported", never 0). soul's L1 judge after a job runs on its own context and is not counted.
  - **Kept, from a clean checked run only** (`playbooks.keep`, called from `skill_task._gate`'s DONE). The operator's commands that exited 0 (`Meta["worked"]`, with `turns`) are kept as `~/.decurix/playbooks/<name>.json` - what a script is written from, what a person is shown, and where each run's cost is counted; never something the engine is given - under the request's shape (its words without quotes, numbers and filler): looks left out, a command holding a credential replaced by a note, what `gui type`/`gui select` typed replaced by `<value>` unless the request itself holds it. Worth keeping is judged by turns (`MIN_TURNS` 3). Not kept as the way: a run the check sent back (a second soul job that is not a resume), a takeover, and **a run in which a person answered a question** (`playbooks.answered`, from `thebot_harness.continue_after_query` for any reply but an approval's) - found live, "open ... and sign in" stopped on a question, the answer asked for a supplier to be made, and all of it was kept as how to sign in.
  - **Shell and file work becomes a script of the worker's own** (`_distil`, `_prove`, `~/.decurix/tools/<name>.py|.sh`). Handing the kept commands back as a list made things worse (15,532 and 17,088 tokens by hand; 20,240 and 20,961 with the list: same turns, more reading), so such work is offered a tool or nothing. One hosted call (`DISTIL_SYSTEM`) turns the commands into ONE script; three rules are enforced with no model before it is kept:
    - **Sound** (`_sound`): it parses, holds no credential, and no line `commands.dangerous_reason` stops. A task that stopped for an approval gets no script (one command would not stop).
    - **Its arguments are what a request states, both ways** (`_stated`, `in_request`). Every example argument must be in the request's own words (a file by its name, an address, a quoted phrase): found live, a "period label" argument ("January", for `sales_jan.csv`) made the next reading guess. And a phrase the request quotes that the commands used must be an argument: found live, a script rebuilt the email's subject from the file's name, and a request stating its own subject could not use it.
    - **Proven** (`_prove`): run with those arguments in a private copy of the work folder (`HOME` moved there; the files the task itself wrote - `produced.files` - left out, so it has to make them; `DECURIX_OUTBOX_DRY` set, so an `office email` in the trial is written to a file and reaches no Outbox), what it writes must read the same as what the checked task left (`_same_reading`: same words, numbers equal however printed) and it must draft the same emails (`_same_drafts`: recipients, subject, body, attachment names, against the note `tools/outbox.py` now keeps of each task's drafts in `~/.decurix/computer/drafts/<task id>.jsonl`). The first script ever written was kept untested, required its output to exist and called `office update` wrongly - its first use failed.
    A script that fails any of these is sent back with what went wrong (`DISTIL_ATTEMPTS` 3), and a later clean run by hand may try once more (`MAX_DISTIL_SESSIONS` 2).
  - **A proven script is first run by the engine, then with no engine** (`tool_task.py`). Offered to the engine it costs two turns (8,100-8,250). Once it has done one request that way, checked (`DIRECT_AFTER` 1, `DECURIX_TOOL_DIRECT_AFTER`), the watcher dispatches the next request of that shape to `tool_task.perform` before the engine: one call to the worker's own model (`ARGS_SYSTEM` - not the fast one: whether a request is what the script does is a judgement, and a wrong yes writes a file or drafts an email before any check sees it) reads the request into the arguments, held to the request with no model (as many as the example has, each `in_request`; `fits: false`, a guess or an unsure reading hands the request to the engine); the script runs in the work folder; and `verify.judge` reads back the files and drafts it made (`produced.text` + `produced.drafts_text`) before anything is reported. A script that exits non-zero hands over to the engine with what it printed, and after `FAILURES_BEFORE_ENGINE_ONLY` (2) is not run directly again. A result the check cannot settle is not reported "not checked", as an engine's own file work is: nobody was reading along when the script ran, so the engine is given what it printed and told to compare it with the request and correct it where it is, without making a second copy.
  - **One wrong result ends a script** (`playbooks.tool_failed`, from `missed(why)` when the engine ran it and from `tool_task` when it ran directly). Proving a script on the request it came from cannot show what it took from that request: found live, a proven script had "January" fixed in the email body, drafted it for February, and the final check refused it. It is dropped at once, the check's words are kept (`tool_faults`) and told to the model that writes the next one (`_faults_note`), and after `MAX_TOOL_FAULTS` (2) that kind of request is left to the engine. The worker cannot withdraw the wrong draft (only a person discards from the Outbox), so that task ended by asking which draft stands.
  - **Screen work is replayed from the worker's own run** (`_mark_proven`, `mimic._candidates`, `mimic.load_skill`). **The commands are never handed back, for any kind of work** (`context` offers a tool or nothing): refs are not the same from one run to the next on an application that redraws itself, so the list named controls that were not there - four more suppliers with it cost 114,963, 139,710 and 129,400 tokens against 102,896 with nothing, and the first two-run comparison had only looked like help. What is kept of a run on the screen is its recording. **It is replayed only once two clean checked runs of the kind pressed the same controls in the same order** (`playbooks.skeleton`: each recorded action's kind and its control's role and name, from the task's own recording - not refs, not values; the last `KEEP_PATHS` (4) paths are remembered, so a run that wandered in between does not unlearn the way). One run shows a way that worked; two that agree show it was not that request's accident - and until then the engine does the work, on purpose. Live: three runs by the engine, the second and third agreed, the fourth and fifth were replayed. The agreeing run's task recording is marked `proven` (kept from pruning like a demonstration, one per shape), and `mimic` offers it beside a person's demonstrations: the next request of that shape is matched and its values placed by the existing no-model path (`skill_task.perform_mimic` -> `replay.run`), the final check judges the screen, and a replay that stops is taken over by the engine as any is. Two things a worker's own run needed that a person's does not: **its steps are held to their controls, not to what followed** (`load_skill` clears `expect` on every step that is not `consequential`, and marks the skill `own`) - an engine's look after a click is not a person waiting for a result; replayed as recorded it stopped at "expected link Contacts, which never appeared" and the engine redid the task for 98,221 tokens - and **a title that only says a page has not loaded is never an expected result** (`replay.NOT_LOADED_TITLE`: "Untitled", "New Tab", an address; a person's recordings gain from this too). A proven recording the engine has to take over `OWN_RETIRE_AFTER` (2) times running is un-proven (`playbooks.own_replayed`), so the next request is worked out afresh and becomes the new way.
  - **A request that names a file to work on is not DONE before a command has run** (TheBot `grounding.go` `namesFileWork`, in `unstartedScreenNudge`). Found by these measurements: the fourth request of a conversation was answered in three seconds, "summary_feb.xlsx is complete ... I verified the workbook by reading it back", no command run, no file written, the totals invented - and nothing checked it, because the check for file work reads back files and there were none. Pushed back once, then put to the person; a question that only names a file is still answered. **An email a task drafted is read back by the final check too** (`produced.drafts`): a task that only drafted an email used to go out unchecked.
  - **For a person** (`/skills/<id>`'s "Worked out by itself", `httpapi/playbooks.go` -> the agent's `/playbooks*`; `playbooks.listing/detail/forget`): one card per kind of request - how it is done now (its script, a replay of its own run, or the commands), first-time tokens against now, uses - with what it kept (the script, the commands) and Forget, which sends that kind of request back to being worked out. `backup.go`/`restore.go` take `playbooks` and `tools` beside `skills` and `memory` (a proven recording travels with the optional `recordings`).
  - **Switches.** `DECURIX_PLAYBOOKS=0` turns all of it off; `DECURIX_PLAYBOOKS_DIR`, `DECURIX_TOOLS_DIR`, `DECURIX_TOOL_DIRECT_AFTER`, `DECURIX_TOOL_SECONDS` (300).
  - **Not verified, and not done.** The page section and the three `/api/desktops/playbooks*` routes were written after the last build: rendered and unit-tested, never opened in a browser, and the agent's `/playbooks` API was exercised only from inside the worker. Backup and restore of the two new folders: unit tests of the existing path only. One screen task was measured (a web form, six fields' worth; seventeen suppliers in all, each once and right in the application's own data); a longer form, a form with rows, and a task that stops for an approval (a proven recording is not made from one) were not. A replayed own run reports "Done the way I did it before" and relies wholly on the final check - its steps confirm nothing. Whether the model writes a good script varies run to run: the email task got one on the first try in three sessions of five, none in one, and a wrong one in one. A taught skill with a value picked from a list still runs on the model every time (`_learning_by_model`). The Office (GPT) engine reports no command trace and keeps nothing. Left on the test stack by these runs: worker `econ`, about twenty unsent drafts to ops@example.com in the Outbox, and seventeen test suppliers in the ERP demo (Northwind Traders ... Quartz Hardware). `TestRAGQuerySendsFullChunkTextNotTruncated` needs a live embedding server.
- **A taught task run on documents, on a fresh build, and five faults it found** (2026-10-12; the app's own stack, one worker on Azure gpt-5.4, a business application as the web app; one bill demonstrated by a scripted person over VNC - 32 steps, every field named - and taught in four answers for 24,799 tokens; seven more bills sent one by one as "Enter this vendor bill" with the PDF attached; every record then read out of the application's own data). **Outcome:** three bills entered right with no question (138-264 s, 245,696-553,837 tokens each - the learning stage, the model driving); one with three lines of products the application does not have entered right after the one question the lesson asks for; one whose supplier the application does not have, and one with a line it has no item for, each ended in the right question with nothing created (the second only after the fixes below); and one that went wrong for 27 minutes and 3,087,000 tokens before it was put right by a person's words. Two bills charge two tax rates and the application has one template, so its total cannot equal the bill's: that is the application's setup, and what the worker did about it is the first fault. No run reported a success that was not one. The skill is still an apprentice (no clean streak), so nothing here ran as a replay.
  - **A figure the application computes is not the worker's to force** (`skill_task.NOT_YOURS_TO_FORCE`, in every second attempt's instructions and in `_retry_engine`). The rows were entered as the bill has them; the final check said the totals differ; and the second attempt, told to correct what was wrong, ticked "included in basic rate" on a tax row - against the person's own "leave the tax template as ERPNext sets it" - and left the draft wrong, then could not find its way back to the record and asked. Now: correct only what was entered from the request; a setting, template, rate or tick box the task never touched or the person said to leave is not changed to make a computed figure match; when the values are in as the document has them and the figure still differs, both are reported and the person is asked.
  - **A figure with its unit or its currency is its number** (`binding.as_number`, `FIGURE`, inside `as_written`). "20 Reams", "2 Chairs" and "Rs. 360.00" were read whole for fields the demonstration typed bare numbers into; the number check refused them and a person was asked three times for figures the bills state. One number with nothing around it but a currency mark before and unit words after is that number, only for a field whose example is a bare number; "20 x 30", "Invoice 20" and "PO 7731" are left as read.
  - **Typing another record's name into a field is refused like selecting it** (`core._typed_in_place_of`, in `act` for a named `type`). After a search of a field found nothing, `gui select` of another entry was refused and a click on one in the list was refused - and the engine typed another item's name into the field and pressed Tab, which a field that looks records up takes as the choice; the draft was saved with a database-hosting item on a server chassis' line. Typing what was searched for, or part of it, is still allowed; a person's reply lifts it as before.
  - **"Which should I use instead" is the person's** (`ANSWERED_SYSTEM`). That same question had first been answered for the person from a lesson kept from an earlier bill ("for our books paper is paper, a chair is a chair": use the existing item of the same kind) - which names no server and no entry for one. A rule about kinds answers such a question only when it names this very thing and an entry that is offered; a general "use the closest" never chooses a record for a thing the person has not spoken of. Seen working: the same bill then ended, in 181 s, in the question with the list of what is offered and nothing saved.
  - **The commands are not the evidence when a hosted model is judged by the host** (TheBot `operatorState.Hosted`; `unperformedScreenNudge` is skipped for a hosted brain). Sent back to a record it had entered correctly, the operator rightly changed nothing and said so, and "the task says to type, and nothing was typed" refused that DONE, the already-told gate answered the doubt twice, and a person was paged about a finished record - twice in this run.
  - **Not fixed, seen in this run.** The worker reported "I did not separately verify whether a bill with the same supplier invoice number already existed" - it was taught to, and no step of the demonstration shows how, so it does not. It could not reopen a record it had saved minutes before until given its address (its own report had the number). On the second attempt of one bill its report read "the bill was already entered ... no new invoice was created" about its own first attempt's draft. The host had 500 MB of memory free with both stacks running: the control plane and the application each stopped answering for a minute, twice, and one WSL command timed out. A lesson cannot yet say "these are the application's figures, expect them to differ from the document": the person had to say it per bill.
- **A taught task that runs the way it was shown, at another document's size** (2026-10-12/13; the same worker, skill and application as the run above; a bill demonstrated once and taught with the rule "before you start, search for a bill with the same supplier invoice number"; then bills of one, two and three lines sent one by one). What stood between "taught" and "done the way it was taught", each fixed where it starts:
  - **A replay is fitted to the run** (`skills.fit`, `run_rows`, called by `skills.expand`). The demonstration's rows were its rows: a bill of three lines replayed two and stopped. When the run's values have more rows than the demonstration, the last row's steps are written out again for each extra row (controls found by what they are, not by the demonstration's row); fewer, and the rows past the last are dropped with their values. A value the demonstration typed and then picked from the list that appeared (`chosen_from_list`), given another value this run, becomes one `select` of this run's value instead of typing and clicking the demonstration's entry. From the first step that is this run's own, results the demonstration's choices left on the screen are no longer waited for - only checks that follow one of this run's values.
  - **A field that exists only once its place is pressed is reached by pressing there** (`replay._appears_when_pressed`, `_field_appeared`, `CELL_SECONDS`). A table's cell is plain text until pressed, and the recorder named the press by the field that then appeared, so a replay looked for that field, did not find it, and stopped on the first row of every document. Only after the healing ladder found nothing, and only for a field role (`CELL_FIELD_ROLES`); a press that brings no such field halts as before.
  - **Typing after Ctrl+A replaces** (`replay._replaces_selection`): a pre-filled rate field was recorded as typed into a field holding text, the replay put the caret at the end, and "25,000.00" became "25,000.0030000".
  - **Opening an app from its desktop icon waits as long as `gui open` does** (`core.OPEN_SECONDS`); a replay gave up before the app's window was there. A window title that only says an unsaved record's slug (`new-purchase-invoice-xyz`) is not expected again (`_stable_title`), nor is one that says the page has not loaded (`NOT_LOADED_TITLE`).
  - **A crashed page is said to be one** (`core._dead_page_note`, `CRASHED_PAGE_NOTE`: Chrome's "Aw, Snap!" read by OCR in either theme): on a host with ~450 MB free the page crashed under a worker that went on clicking at it. The note says to reload (F5) and look again.
  - **"Purchase Invoice List" is a place** (`approval.RECORD_NAME` takes List/Report/... after the record noun): the link stopped a task for a yes.
  - **A task whose rules ask for more than its steps stays the model's** (`skill_task._asks_for_a_check_first`, `CHECK_FIRST`, `_supervise`). A trusted skill replays with no model; but "before you start, search for ..." is done by no recorded step, and a bare replay would enter the bill without it (the final check, rightly, would not confirm it). When the person's explanation, answers or corrections ask for a look first or a condition on doing it at all, or once a replay could not be confirmed, the model drives every run, with the replay as its tool. Correctness first: the cost stays the model's for such a task.
  - **The model is given the replay as numbered steps** (`skill_task._procedure`: read the documents; make the checks the person asked for; run `gui do NAME --param ...` with this run's values written out (`_do_line`), or - when the app is already open after a check - put it back on the page the steps begin on and run from the first step inside it (`_back_to_start`: `gui open <start page> && gui do ... --from N`, `_start_page`, `_first_step_inside`); carry on by hand from where it stops with `--from N`; verify). Before this, a worker whose check had left the app on the last task's record had `gui do --from 3` refused and asked a person what to do.
  - **A dialog's Yes to something permanent needs a yes from the person** (`approval.confirms_permanently`, `CONFIRM_ANSWER`, `PERMANENT_QUESTION`). After `gui do` had saved a draft, the engine pressed Ctrl+S once more "to make sure"; on a saved draft that application's next action is to submit it, and it asked "Confirm: Permanently Submit PINV-26-00021?". The engine answered No by itself - nothing would have stopped a Yes, because the gate reads a control's own label and this one says "Yes". A Yes/OK/Confirm/Continue inside a dialog whose name (as the element's path carries it) says permanent, cannot be undone, submit, send, pay, publish, post, transfer or delete is now stopped for approval; "Leave site?" and "Discard unsaved changes?" are not. Not covered: a dialog that is named only "Confirm" with the question in a paragraph, and an application that submits on a shortcut with no dialog at all. The procedure's step 5 now also says not to press the replay's last step again.
  - **The final check is shown what a check made along the way found, and judges a working rule from it** (`evidence.observed`: each action now carries what the screen did in answer, cut at `MAX_CHANGE`; `verify.JUDGE_SYSTEM`). On a cleared ERPNext the second bill was entered right, with the totals compared, and still paged a person: "no proof the duplicate check was made". The evidence listed the search typed into ERPNext's search box but not its answer ("No Results found"), and the check asked the final screen for proof of something done before it. A rule about how to work (search first, compare and say both totals) is now judged from the recorded actions and the report; only a result that shows the rule broken (two records with one reference, a submitted record) makes it not done.
  - **A value the application refuses is the person's, never dropped to get past the check** (TheBot `taskRules` in `operator.go`; `verify.JUDGE_SYSTEM`). A vendor form with an invalid GSTIN (a planted test case): ERPNext refused it, and the operator - told to "fix field errors and save again" - saved the vendor with no GSTIN as GST-unregistered, and the check passed a report that said exactly that. The rule now separates errors the worker made (a typo, a format) from the application refusing the source's own value, which is asked about with the message and the value; and a report that says a value was left out or replaced because it was refused is `not_done`.
  - **Updating means changing the record that holds the value; what the application knows is read, not asked** (TheBot `taskRules`). Given a supplier's revised price list, the operator set out to create new price records rather than change the existing ones, then asked a person which unit of measure to use - each item's unit is in ERPNext.
  - **A period the document gives is counted, not taken from a default** (TheBot `taskRules`; `verify.JUDGE_SYSTEM`). A quotation asked to be "valid for 30 days" was saved with ERPNext's default validity of one month (31 days), and passed the check.
  - **A helper that finds nothing is not the record's own word** (TheBot `taskRules`). Recording a customer's payment against the invoice its remittance names, ERPNext's "get outstanding invoices" found none (its own date filters) and the operator asked a person whether to book an advance - the invoice was outstanding in full. A record the document names by number is opened by that number before anything is concluded, and a reference table can be filled by hand.
  - **A document goes from one party to another, and the party to record is the other one** (TheBot `taskRules`). A remittance addressed "To: Example Inc - Accounts Receivable" (the company itself) was read as coming from that party: the operator searched the customer list for it, found nothing, and asked a person which customer to use. The operator is told to read who a document is from and to, and that the organisation whose application this is is one side.
  - **An entry the task's own documents name is never a stand-in** (`core._in_documents`, `task_context.current_files`). After that mistaken search, the substitute guard refused the payer the remittance itself names - the worker could not correct its own misreading. The guard now lets through an entry every telling word of whose name is in one of the request's attached documents (read with `office.read_document`, cached per process); the request's file paths are kept whole beside the request, which is cut at 500 characters.
  - **Typing into an application's search box is navigation, not a value** (TheBot `grounding.typesIntoSearch`). To reach a new Payment Entry the operator typed "Payment Entry" into ERPNext's search bar and was refused twice as typing "a value that appears nowhere", then asked a person where the words came from. A `gui type` into a field the operator was shown as a searchbox, or one named Search/Find/Filter/Go to (by its ref, in `observe`'s `e12 combobox "Search"` or an action's `combobox "Search" (e12)`), is not traced; any other field is guarded as before.
  - **One existing record named within the document's description is that record** (TheBot `taskRules`). With the search fixed, the operator found the one plausible item ("SKU001 T-shirt" for "Cotton T-shirts, round neck, assorted sizes") and still asked a person to confirm it: the rule said when to ask (several candidates) but not when not to. It now says that exactly one record whose name is contained in the description, the rest only detailing it, is the one - the rule `gui select` already applies - and the mapping is reported.
  - **A plural is searched in the singular, with its own punctuation and in its phrase** (`core._searches`, `_singular`). A customer's order line "Cotton T-shirts, round neck" was searched as `Tshirt` (the hyphen stripped) and "Ceramic coffee mugs 300 ml" never as `coffee mug`, so ERPNext's items "T-shirt" and "Coffee Mug" were never offered and the worker asked a person which item to use. A word keeps its inner punctuation, and each run of words ending in a plural is also tried in the singular right after it.
  - **A record made from a document carries the document's own reference** (TheBot `taskRules`; `verify.JUDGE_SYSTEM`). Two sales orders were saved with the right customer, lines and dates but without the customer's own PO number and date - the field is further down the form - and both passed the check. The operator is told to find and fill the field for the other party's reference; the check calls a record without it `not_done` when the record has a place for it.
  - **A total the application computes is not a reason to stop** (TheBot `taskRules`). Entering a customer's purchase order (its total stated before tax) as a sales order, the operator stopped half way to ask whether to go on "despite ERPNext adding taxes". The rule that a figure the application computes from its own template is the application's, and both are reported, had lived only in the bill skill's lesson; it is now the operator's for every task.
  - **What an earlier task left on the screen is not this task's** (TheBot `taskRules`). A vendor registration stopped at a question left an unsaved "New Supplier" form open; the next request, a sales order, found it, tried to save that supplier (and met its GSTIN error), and gave up on the order. The operator is told that a half-filled form, an error or a dialog on the screen at the start may be left over: never save, submit, change or fix a record it did not open in this task; open what the request needs, in a new tab if leaving is refused.
  - **What the report itself lists as left undone is read** (`verify.JUDGE_SYSTEM`). A sales order passed without the customer's own PO number and date, which the report listed as "left undone: no visible field on the part of the form I completed" - the field is further down. A value the document gives, left out for want of finding its field, is `not_done`; only a reason that stands (no place for it at all, the person said so) passes.
  - **A worker knows where things are from inside its desktop** (`identity._desktop_apps`, `launchers.address`). Registering a vendor untaught, the engine opened `http://localhost:8000` (the desktop itself), then `127.0.0.1:8000`, and ended an attempt with "the application never became available". The identity facts every engine reads now say that localhost is the desktop and the computer's servers are at host.docker.internal, and list the apps on the desktop with the address a web app's launcher opens (read from its wrapper's `APP=`), sorted, at most `MAX_APPS`.
  - **A launcher that brings its app forward has opened it** (`core._open`): with the app's window already open behind the browser, the launcher raised it and `gui open` reported "no new window appeared within 90 seconds". For a desktop launcher, a window that was open and is now in front counts.
  - **A reply that explains and then confirms is a confirmation** (`skill_task._confirms`, `CONFIRM_TAIL`). "An LLP is a partnership firm, not a company - keep Supplier Type as Partnership ...
