# Gotchas, part 1

- `CODE_MAP.md` is generated by `go run codemap_gen.go` (internal/codemap) from each tracked file's own header comment; never hand-edit it. `TestCodeMapIsCurrent` fails until it is regenerated after a file is added, removed or re-described.
- Go doc comments: every exported/significant func gets a one-line `// FuncName does X` summary directly above it — keep following that pattern for new functions.
- The agent's output must start with exactly one of `COMMAND:` / `DONE:` / `HELP:` (see `ollama_client.SYSTEM_PROMPT`) — `parser.parse_agent_response` searches for whichever marker appears first, so don't change that contract without updating both sides.
- The desktop agent (`vm_server.py`) is launched as a detached background process by `agent/start_agent_terminal.sh` (via `setsid ... &`), not inside a visible terminal — output goes to `/tmp/decurix-startup.log` inside the container. Don't reintroduce a foreground/`xfce4-terminal --hold` launch; it makes the agent visible as a window on the VNC desktop instead of running silently.
- `decurix_agent/state.py`'s module attributes (`current_task`, `waiting_for_query`, etc.) are the agent's only cross-module shared state. Mutate them as `state.current_task = x` after `from decurix_agent import state` — never `from decurix_agent.state import current_task`, which copies the value instead of sharing it.
- `EnsureImages` no longer pulls. `decurix-desktop:*` are local-only tags that exist in no registry, so the old `ImagePull` could only ever fail with "pull access denied" on a fresh machine; it now just reports which images are missing and points at `--build-images`. Don't reintroduce a pull unless the images actually get published somewhere.
- `embed.go` sits at the module root on purpose — `go:embed` cannot reference parent directories, and the desktop build context spans `docker/` and `agent/`. Anything a desktop image needs at *docker build* time must be under one of those two trees and matched by an `embed.go` pattern, or the image builds fine from the repo and fails from a released binary. `go:embed` also silently skips names starting with `_` or `.`, which is what keeps `agent/__pycache__` out — but would equally skip a real file you name that way.
- **`go:embed` also skips `agent/thebot`, silently, because it is a Go module of its own** (a directory with a `go.mod`). So a released binary's build context had no TheBot and `--build-images` failed at `COPY agent/thebot/go.mod` - found by the Windows app's first launch; the Linux/Mac scripts `docker build` from the repo and never met it. `go generate .` (`embed_gen.go`, `//go:build ignore`) packs it into `agent/thebot.tar.gz` (gitignored, picked up by the `agent` pattern) and `desktop.tarBuildContext` unpacks it back to `agent/thebot/...` in the stream. Everything that builds a binary to hand out runs it first (`scripts/release/release.*`, `scripts/windows/build-electron.ps1`, `docker/Dockerfile`), **before `GOOS` is set** (the generator runs on the build machine). A binary built without it says so (`errNoTheBotSource`) instead of failing in Docker, and `TestTheEmbeddedContextHasEverythingTheDockerfilesCopy` checks every Dockerfile `COPY` source against the embedded context (it skips when the archive was not generated).
- **`go:embed` also skips the agent's `_`-named files** (`decurix_agent/__init__.py`, `computer/__init__.py`, `computer/__main__.py`, `tools/__init__.py`, `browser-agent/*/_pathfix.py`): a directory pattern drops names starting with `_`, so every desktop image the app or a released binary built had no `computer/__main__.py`, and `gui` - every engine's way to the screen - failed with "No module named decurix_agent.computer.__main__" (found 2026-10-07; the scripts' `docker build` from a checkout never met it). `embed.go` names them by pattern, and `TestEveryAgentFileIsEmbedded` walks the checkout's `agent/` for any `_` file the context lacks.
- **`--build-images` rebuilds an image built from other sources, not only a missing one** (`desktop.contextHash`, label `decurix.context`). It used to skip any image that existed, so a freshly built app went on creating desktops from the image an earlier binary had built - agent code and all. The desktop image's hash covers the whole embedded context except the tools Dockerfile; the tools image's, its own Dockerfile only. The classic builder's layer cache keeps an unchanged layer, so a rebuild after an agent change is minutes, not the first build's tens. An image built by the scripts' `docker build` has no label and is rebuilt once by the app.
- **TheBot's shell is `internal/hostshell`** (`agent/thebot`): `bash -c` in a process group of its own, so everything a command started is killed with it. TheBot runs only in a Linux desktop; its PowerShell half went with the native Windows workers (2026-10-06).
- **A page is read with its inner frames, and five faults that hid behind that one** (`cdp._inner_frames`/`_splice_frames`/`_FOCUSED`/`_INNER_FRAMES`/`_own_text`/`_known_by_backend`, `approval.searches`/`is_refusal`, `core._keyboard_field`, `demonstration.Recorder._front`, `study._pictures`, `guidance.note_reply`/`refused`, `skill_task._gate`; `agent/tests/test_page_frames.py`, `bench/native/messaging_e2e.py`). Found in the installed Windows app on 2026-10-03: a person recorded "open linkedin and send "hello test" to ohona sahoo", taught it, asked for it with another name, and the worker clicked at guessed coordinates, typed into nothing and asked for a yes three times over without finding anyone.
  - **LinkedIn's Messaging page is a frame** (`/preload/`, same site) inside the tab's own page, and `Accessibility.getFullAXTree` stops at a frame: measured, 184 nodes outside and 1,166 inside; `observe` listed 2 elements. Now each frame this DevTools session holds (`Page.getFrameTree`; another site's frame is a target of its own and is not read) that has a size is read with `getFullAXTree {frameId}` and spliced under its frame element (node ids prefixed per frame - each tree numbers its own). Positions: a frame document's bounds are from its own origin, so the frame's content box (`DOM.getContentQuads` of its owner, CSS pixels of the page's view) is added and the document's own scroll taken off - **the snapshot's `scrollOffsetX/Y` is in the bounds' device pixels, not CSS** (measured at 125%: scrolled 60, it said 75). What is outside the frame's box is `offscreen`. Backend node ids are the page's, so click/type/focus by handle work unchanged. The field-naming scripts (`_COLUMN_NAMES`, `_GROUP_LABELS`) walk the same-site frame documents too.
  - **The keyboard is in the innermost thing that has it**: `document.activeElement` is the `<iframe>`; `_FOCUSED` goes on into `contentDocument.activeElement`. What the person typed into "Search messages" had been recorded as `type "ohona sahoo" into the screen`.
  - **A text field's suggestions are a pop-up of the browser's own**, in front when the first key comes; the recorder took any browser pop-up for a drop-down's list and did not ask the page. It asks either way now; only no field, or a `<select>`, is "a list". (Reproduced in Edge on the stand-in site, where the frame fix alone still recorded the typing with no field.)
  - **A node id means something only in the document it came from.** The person's click on LinkedIn in Google's results was recorded as `click combobox "Ask Google"` - the result link had the id that box had on the new tab page before. Elements carry the main frame's `loaderId`; `_known_by_backend` takes none from another load.
  - **A press on words in a plain block** (`<span>` holding only text): the partial accessibility tree returned the span and its ancestors, not the text inside; nothing had a name and the press became a bare point. `_own_text` reads the words off the DOM.
  - **Enter in a search box searches.** On a messaging page every Enter was "sends what was typed as a message" - so looking a person up needed a yes, and the yes sent nothing. `approval.assess` takes the field that has the keyboard (the step's element, or `context["focused"]`, which `core.act` fills from the look or from the page) and lets Enter through when it is a search field (role `searchbox`, `type=search`, or a text field whose label *starts* with search/find/filter). Keyboard unknown, or in the message box: still stopped. Send is stopped as before.
  - **A no at an approval ends the task.** Found by the bench: told "no, do not send it" at Send, the engine stopped - and the final check, seeing the message unsent, sent it back to do it all again and ask again. The watcher notes a refusal (`approval.is_refusal`: a no that asks for nothing "instead") for the task; `_gate` then reports "Stopped there, as you said" and judges nothing. Any later reply takes the refusal back.
  - **The lesson is shown every press, ringed** (`study._pictures`, `MAX_PICTURES` 14; said by the person: "some of the clicks I do you don't see where I clicked or why"). It was the screens where the window changed, five at most; the click on the first conversation of the search was in the list only as `click text "This message has been deleted."`. Now: the first screen, each press on the frame the recorder took as it was made with a red ring on the spot (its point, else the middle of its control's box), and the last screen; with more presses than pictures, presses with no named control and presses that changed the window are kept first. The prompt says the ring is what was pressed and the step list's name is only what was under the pointer.
  - **Verified:** real Chrome at 125% (boxes within 1 px of the page's own, page and frame scrolled); the person's real LinkedIn page read-only (249 elements, Search messages / Write a message… / Send, where there were 2); and `bench/native/messaging_e2e.py` on a native worker with Azure - a person records through the viewer (every step named), `/learn` (only Send needs approval), the task in plain words for another person (one approval, the site's own record has the one right message, ~60 s), a first name two people share (the first, as taught), and a no (nothing sent, not tried again). **Not done:** a frame of *another* site (payment widgets, embedded sign-ins) is still not read; nothing was sent on the real LinkedIn; a skill taught before this keeps its unnamed typing steps and its Enter marked for approval - record and teach it again. The ticket's panel opens over the top middle of the screen being recorded (it covered the page's own navigation in the bench); a person closes it by its tab.
- **On a local model a worker asks rather than claims** (TheBot `grounding.go`: `unperformedScreenNudge`, `typingFieldHint`, `unperformedScreenDoubt`). With no hosted model there is nothing to judge the screen afterwards (`verify.py`), so the commands are the evidence: a request that says to type, with no successful `gui type`/`select`/`do`, has a DONE pushed back once (with `gui observe` as the next command, and after it the fields that can be typed into), and a second DONE goes to the person as "I cannot confirm this is done" - their plain yes finishes it, anything else is what is missing. Found live on a 1.5B model: "open notepad and type hello world" ran `gui open notepad` and reported both done. A request that is only a command in backticks (``run the command: `gui open notepad` ``) is run by the terminal skill, before the screen-work rule can hand it to the operator (`namedCommandRe`), and a bare `DONE` with no marker is never salvaged as an answer: after a command that worked, what the command printed is the answer (live: `$env:COMPUTERNAME` printed the name, the model said `DONE` four times, and a failed step went to the scheduler's failure reasoning, which paged the person about `hostnamectl`); with nothing run, the person is asked in plain words, as a question of the operator's own so that reasoning never runs.
- **The Windows app runs the Linux stack in a WSL distro of its own** (`desktop/electron/main.js` `linuxReady`, `desktop/electron/wsl/setup.sh` + `dockerd.sh`, `scripts/windows/build-electron.ps1`). Decided by the person who runs this on 2026-10-06, reversing the native Windows workers of 2026-10-01 ("in the VM I can't type anything to the shell, the file explorer is shit ... just have the docker, novnc, xfce itself"); the native worker code was deleted, not kept behind a flag. Workers are the same XFCE/noVNC desktops as on Mac and Linux, and the control plane is the same compose stack (`resources/stack`, staged as on Linux). Docker needs a Linux kernel, so the app imports Alpine's minirootfs (pinned by SHA-256, shipped in `resources/wsl`) as the distro **`Decurix`** with its disk in `%LOCALAPPDATA%\Decurix\wsl`, `setup.sh` installs Docker Engine with `apk` (first start only, ~70 MB) and stages the stack into `/var/lib/decurix/stack` (copied again only when `VERSION` differs; the person's `.env` from `%APPDATA%\decurix` every start), and `dockerd.sh` is the daemon, kept in the foreground of a **detached, hidden `wsl.exe`** - WSL stops a distro when no `wsl.exe` is running in it, so that process is what keeps the desktops running after the window closes; a second `dockerd.sh` only waits on the first. **It is started through WMI** (`Win32_Process.Create` with `ShowWindow=0`, `startHiddenScript`), not spawned by the app: libuv puts every child that is not detached in a kill-on-close job (measured: a hidden non-detached `wsl.exe` died with its parent), and a detached child has no console, so `wsl.exe` makes one and Windows 11 hands it to Windows Terminal - the first build of this app opened an empty "C:Program FilesWSLwsl.exe" terminal window on every start. `conhost --headless` does not work (it exits at once). Every other `wsl.exe` call is a non-detached `windowsHide` child, whose console is created hidden. Every docker command is `wsl.exe -d Decurix -u root --cd /var/lib/decurix/stack -e env COMPOSE_PROJECT_NAME=decurix ... docker ...` (`docker()` in main.js), and `WSL_UTF8=1` so `wsl --list` is not UTF-16. **All WSL distros share one network stack**: a person's own Docker in another distro (this host's Ubuntu runs one, docker0 172.17/16) would fight a second daemon over docker0 and the `DOCKER*` iptables chains, so the app's daemon has `"bridge": "decurix0"` (10.212.0.1/24, made by `dockerd.sh`), address pools in 10.213.0.0/16 and `"iptables": false`, and `dockerd.sh` adds the one MASQUERADE rule and two FORWARD accepts for 10.212.0.0/15 itself (first in FORWARD: the other daemon sets its policy to DROP). Its images are in the classic **overlay2** store (`"features": {"containerd-snapshotter": false}`), not Docker 29's default containerd store: `desktop.BuildImages` uses the classic builder, which commits every step, and with the containerd store each commit of the 3 GB worker image took minutes (three one-file `COPY` steps, 25 min, measured on this host - the same store under this host's Ubuntu Docker is why its first builds took hours). `setup.sh` rewrites `daemon.json` every start, but a running daemon only reads it when it starts. With overlay2 a first build of the desktop image took 9-10 min here (it had taken hours). The classic builder stays: built with **BuildKit** instead (`Version: BuilderBuildKit` works from a plain tar context) the same image was no faster here - still downloading packages at 10 min, when the classic build had finished in 9-10. On top of that; the five `apt-get update` steps of `desktop.basic.Dockerfile` are one; and the app waits only for the desktop image (`--build-images -images desktop`), building the tools image (Go, Node, Rust, the coding CLIs: a desktop starts without them and the shared tools volume is filled once the image exists) after the dashboard is up (`buildToolsLater`). Verified on this host with the user's Ubuntu Docker running: containers resolve and reach the internet, `host-gateway` reaches the control plane, a port compose publishes on 127.0.0.1 inside the distro answers on Windows' 127.0.0.1 (WSL's localhost forwarding - which is how the window reaches :8080 and cloudflared.exe reaches :8090), and the other Docker keeps working. WSL missing: the app runs `wsl --install --no-distribution` elevated (one UAC prompt) and, when `wsl --version` still fails, says to restart Windows - not tested on a PC without WSL. An earlier version's Windows control plane (`resources\decurix.exe`, holding 8080) and its Ollama (`%LOCALAPPDATA%\Decurix\ollama`) are ended at each start (`stopEarlierWindowsApp`); a distro whose `VERSION` does not answer counts as stale, so whatever held 8080 is replaced by the stack. Under WSL's NAT the gated port is not on the network by itself, so the app forwards it (`desktop/electron/windows-lan.js`: one administrator prompt adds a `netsh interface portproxy` rule from this PC's address to **127.0.0.1**:port - WSL's localhost relay, which survives WSL's own address changing - and an inbound firewall rule `Decurix LAN access (<port>)`), then reports `lan_url`; a no is remembered per address in `lan-forward.json`, `DECURIX_WSL_LAN_FORWARD=0` skips it. The quick tunnel is started fresh at every start and restarted if it ends (`mobile-access.js`): a link the control plane still held from an ended tunnel used to stop a new one from starting. Some routers' DNS answer `0.0.0.0` for every `trycloudflare.com` name (this repo's host's router does): the tunnel works, the network blocks it. Its records start empty: the native control plane's database in `%APPDATA%\decurix` is not imported (its workers were not desktops). `build-electron.ps1` refuses a `#!` script under `agent/` or `desktop/electron/wsl` with CRLF endings: they run in Linux.

- **What a person answers a worker is kept, and the worker does not ask it again** (`decurix_agent/lessons.py`, `skill_task._question_gate`/`learn_answer`/`_already_told`, `messaging.set_query_gate`, `state.last_query_text`/`last_query_kind`). It goes to worker memory through `messaging.remember` (category `lesson`): on the card's learned-memory list, in `~/.decurix/memory`, and so in every engine's context on every later task.   - **Used when reading a request.** `request_reading` is shown the kept lessons too, and a value may come from one that plainly says what to use.
  - A skill's memory entry (`skill_task._remember`) now carries the lesson's summary and each question asked and answered when it was taught, word for word.

- `desktop.Manager`'s, `conversation.Store`'s, `stepimages.Store`'s, `tasks.Store`'s and `schedule.Store`'s mutexes each guard one struct's own state — hold the lock for the whole read-modify-write, not just parts of it. `querynotes`/`memory`/`claudeauth`/`suggest` have none: each of their operations is one SQL statement (`suggest`'s embedding cache write is `INSERT OR IGNORE`, so a duplicate concurrent attempt is a harmless no-op, not a race).
- **`sqlitedb.Open`'s pool holds `maxOpenConns` (8) connections, not one** — WAL journal mode lets any number of readers run alongside whichever connection is writing at a given instant, and `busy_timeout(5000)` absorbs the rare case of two connections writing at once, so the pool no longer needs to be held to one connection for that. What one connection *was* also doing for free — serialising every `Exec`/`Query` call against every other one — is not something WAL replaces: a store that reads a row and writes it back (`schedule.Store.MarkRun`/`SetEnabled` is the one example so far) now needs its own mutex for that read-modify-write to stay atomic, the same pattern `tasks`/`conversation`/`stepimages` already use for their in-memory state. `sqlitedb.OpenMemory` (tests only) stays pinned to one connection on purpose — a second connection to a `file::memory:` database is a *second, empty* database, not a shared one, so tests that want real multi-connection behavior (a concurrency regression test, say) need `sqlitedb.Open` against a temp file instead, the way `schedule`'s `TestConcurrentMarkRunAndSetEnabledDoNotLoseAnUpdate` does. **No query may run while a `*sql.Rows` is still open** remains the rule regardless of pool size — on a connection pool of 1 it silently deadlocked instead of erroring, and on a larger pool it silently burns a second connection instead (or holds back WAL's checkpoint on a long-open read) — every store reads rows to the end (and closes them) before its next statement; keep it that way.
- **Every transaction is `BEGIN IMMEDIATE`** (`_txlock=immediate` in `sqlitedb.Open`'s DSN). A deferred transaction that read and then wrote after another pooled connection had committed failed at once with SQLITE_BUSY_SNAPSHOT (517, "database is locked"), which `busy_timeout` never retries: found by `bench/screen/teach_e2e.py`, where a finished lesson's outcome was lost and its task stayed "running" for good. `TestAReadThenWriteTransactionIsNotLostToAConcurrentCommit` reproduces it. Stores open transactions only to write, so taking the write lock up front costs nothing.
- A schema change is a **new step appended** to that component's `schema` slice, never an edit to an applied one: `sqlitedb.Migrate` records how many steps each component has run and only runs the rest.
- **What the task records trust is the task ID the desktop echoes, then the worker's live execution.** `tasks.resolve` takes the reported ID only while that execution is live or ended within `lateWindow`; a stale ID (the task file still names a finished task) falls through to what is live, and a step with no live task is *dropped* rather than inventing a task — a `gui` command typed by hand is not something anyone asked for. A reported ID is checked with `tasks.ValidID` before use.
- **`tasks.Plan` mirrors the desktop's watcher, and must keep doing so.** A request sent while an intervention is open is recorded as its reply, because `watchers.command_watcher` hands any request arriving while `waiting_for_query` to `continue_after_query`. The less obvious half is `absorbQueuedReply`: a request *held behind* a running task that then pauses is consumed by the watcher as the reply too, so the queued "task" is deleted and its text becomes the intervention's reply. Change the watcher's routing and the records will quietly describe something that did not happen.
- Stopping, restarting or deleting a desktop calls `tasks.CloseOpen`: a running task becomes `abandoned`, one waiting on a human ends as `query`. Without it, the next request after a restart was routed as a reply to a pause the fresh agent had no memory of.
- Resending a failed task's exact words within `retryWindow` is **another execution of the same task** (the failure note literally says "send the request again"), so a task needing a resend is never counted autonomous.
- **Autonomy is defined once** (`tasks.AutonomyDefinition`, shown verbatim on the dashboard): only attempt ended done, no query or approval asked, not marked wrong. Approvals count as stepping in — they are the agent behaving, but a person was still paged — and the reasons table keeps them apart (`IsApprovalReason`). Task types and reasons are deterministic regexes with tests (`classify_test.go`); an on-screen action turns a task into `screen` work unless it is `consequential`.

- **The chat model is chosen for this machine, not hardcoded** (`internal/ollama` `select.go`, `autoselect.go`, `resources.go`). Unless `OLLAMA_MODEL` names a model, `EnsureReady` calls `SelectModel`: `ProbeResources` reads RAM (`/proc/meminfo` `MemAvailable`, capped by a cgroup limit; `vm_stat` on macOS; `GlobalMemoryStatusEx` on Windows), CPU busy over a 400 ms sample, and an NVIDIA GPU via `nvidia-smi` (Apple Silicon counts its unified memory as VRAM; AMD/Intel GPUs are not probed, which errs small). The budget is **(free - used by everything else) * 0.5** (`BudgetFraction()`, default `0.5`, tunable via `DECURIX_MODEL_BUDGET_FRACTION` - kept well under 100% so spinning up a model doesn't starve the desktops, the browser and the OS), applied to RAM, VRAM and free cores, minus a reserve for the embedding model. **Ollama's own loaded model is added back to "free"** (`ollamaHeld`, from `/api/ps`): otherwise a model that fit would stop fitting the moment it was loaded, and every re-check would shrink the pick. A model fits if its weights plus KV/runtime overhead (`NeedGB`; for an installed model the KV cache is exact - `kvsize.go` reads layers x KV heads x key/value width from `/api/show`, which never loads the model, once per digest, per-layer head arrays summed, times `OLLAMA_KV_CACHE_TYPE`'s element size; the old `0.06 x params` guess overstated a MoE model's cache several times) are inside the VRAM budget (GPU speed), or inside the RAM budget *and* it decodes at least `DECURIX_MODEL_MIN_TPS` on the free cores (`cores * DECURIX_MODEL_CORE_GBPS / GB read per token` - CPU decoding is memory-bound, and a mixture-of-experts model reads only its active parameters, which is why `qwen3:30b` beats a dense 14B on a big CPU-only box). Among fits the highest `Quality()` wins (parameters x a family factor; MoE = geometric mean of total and active). Those constants are estimates, loosely calibrated on this repo's measurements, not benchmarks - tune them by env var. Candidates are the installed models plus a small `catalog`; an installed model within `keepInstalledRatio` of the best is kept over a download, and an external Ollama is never pulled into unless `DECURIX_MODEL_AUTOPULL=1` (the better model is reported as `pull` instead). **The pick is sticky on purpose:** a desktop bakes `OLLAMA_MODEL` into its container at creation and Ollama holds `OLLAMA_MAX_LOADED_MODELS=1`, so a pick that followed load would leave desktops on different models evicting each other's. It is made at startup and re-made only by `ollama.Reselect`, which `createDesktopHandler` calls when **no desktop exists**; `Choose` keeps the current model unless the new one is `switchRatio` (1.25x) better. `GET /api/model` (`CurrentStatus`, 20 s cache) always shows what fits *now* next to what is in use. Not done: a running desktop never changes its model (agents read it from env); a model split across GPU and CPU is not modelled; only the machine running the control plane is measured, so with `OLLAMA_URL` on another host selection stands down (`mode: "remote"`), and on WSL with the Ollama on the Windows side it measures the WSL VM. `scripts/*/lib/ollama-setup.*` leave `OLLAMA_MODEL=auto` alone (and only pull a starter model onto a server with no chat model at all); a `.env` written before this keeps pinning its old model until it is set to `auto`.

The wrapper raises an existing window (`xdotool search --classname` - the *instance* half of WM_CLASS, which for an app window is the URL's host; `--class` matches only `Chromium-browser` and finds nothing), ignores clicks while a launch is in flight (`flock`, held until the window appears; the browser is started with `9>&-` so it never inherits the lock), and the `.desktop` carries `StartupNotify`/`StartupWMClass` for a busy cursor. `start_agent_terminal.sh` also pre-warms `chromium-browser --no-startup-window` (~170 MB idle) whenever the desktop has `*-host.desktop` launchers (window 2.6 s -> 1.1 s measured); `DECURIX_PREWARM_CHROMIUM=1`/`0` forces it either way. Like everything in `$HOME`, launchers are written when a desktop is created: an existing desktop keeps its old wrapper until recreated (the prewarm part applies on its next start).

- `memory.WorkerMemoryEntry` records are kept even if `desktop.PersistMemoryFile` (the write into the desktop's container) fails afterward — that's intentional (matches the original single-file behavior), not a bug to "fix" by rolling back the in-memory record.

- **Prompt evaluation, not generation, is what makes a desktop feel slow**, and `keep_alive` is the lever. Measured on an ordinary CPU-only laptop with `qwen2.5-coder:3b`: the agent's 545-token system prefix took **31.8 seconds** to read cold and **0.6 seconds** with the model still resident. Ollama evicts a model after 5 minutes idle and throws away the evaluated prompt prefix cached alongside it, so a task that pauses to run a command comes back to a cold model. Every caller therefore sends `keep_alive` (`ollama_client.ollama_request`, TheBot's `llm.OllamaProvider.KeepAlive`), and `ollama.Manager.preloadModel` loads the model at control-plane startup so the first human request never pays for it. The corollary: **keep the system prefix byte-identical across calls**, which is why both halves of the Ollama harness go through `ollama_client.build_system_messages` rather than assembling their own, and why `num_ctx` is a fixed 8192 everywhere — changing it makes Ollama reload the model and discard the cache.
- **Warm the Ollama the desktops actually use, at the context size they use.** `ollama.Manager.EnsureReady` used to start the bundled `decurix-ollama` container and preload the model *there* whatever `OLLAMA_URL` said, and without `num_ctx`. Measured on a 7.6 GB CPU-only host with `OLLAMA_URL` pointing at the host's Ollama: the preload held 2 GB of RAM on a server nobody talked to, the real one loaded cold in 210 s inside the first request's 300 s timeout, and even a correctly-aimed 4096-context preload would have been thrown away by the agents' first 8192 request. Same caveat as the seccomp profile and the wallpaper below: the env var is only set at container *creation*, so an already-running `decurix-ollama` needs recreating to pick it up. It only ever applies to the bundled container - an external Ollama named by `OLLAMA_URL` is not this control plane's process to configure, and needs `OLLAMA_MAX_LOADED_MODELS=2` set by hand for the same fix to apply there.

The note tells the human to send the request again, and a paused desktop routes the next request to `continue_after_query` — measured live, a new task was taken as the "reply" to a greeting that had timed out, and reported under the greeting's Task. The exception is a failure inside `continue_after_query` itself, where a resend of the reply should still carry the original task.

Nothing pulled it, and the failure was invisible in the worst way: soul kept answering questions while every write to its Data RAG, its L1 long-term memory and its negative-feedback store failed with `model "nomic-embed-text" not found`. An agent that cannot record what it learned still looks like it works — it just never improves, and repeats the same failure next time. `ollama.EnsureReady` now ensures both models (the embedding one best-effort, since the other two harnesses never embed), and `scripts/linux/lib/ollama-setup.sh` (shared by `build.sh` and `rebuild.sh`) does the same for a host or remote Ollama the control plane does not manage.
- A model that asks a query before running a single command has not tried anything, and `task_runner` pushes back exactly once (`PREMATURE_QUERY_NUDGE`). This is what "hello, whats your desktop name?" needed: it came back as a query asking the human *why they wanted to know*, blocking the desktop on a question. Two things keep the pushback honest — it fires only once, so a second HELP is always delivered, and its last paragraph explicitly invites a safety pause (payment, outgoing message, real-world consequence) to be re-sent unchanged. Verified against the real model: a bogus HELP becomes `DONE: kiolo`, while "pay the 400 dollar invoice" and "email my landlord" still escalate.
- **A reply with no marker is still an answer.** `parse_agent_response` returning `invalid` used to re-prompt with a generic restatement of the format, up to the 50-step limit, and then tell the human the agent "may be stuck in a loop". Measured live: asked how many files are in `/etc`, the model ran the right command, read the right number and replied `241` — finished at step two — then spent forty-eight more steps being lectured about markers before paging a human about a task it had already completed. Two fixes, both load-bearing: `invalid_format_nudge` quotes the model's own opening back to it (the generic version produced another bogus HELP; the quoting version produced `DONE: 241`), and after `MAX_INVALID_RESPONSES` tries `salvage_unmarked_response` delivers the text as the final answer rather than raising a false alarm.
- **A repeated command is how the Ollama loop actually runs out of steps**, and `task_runner` catches it deterministically rather than trusting the prompt to forbid it. The model writes `COMMAND:` and a *predicted* `DONE:` in the same reply; `parse_agent_response` correctly takes only the command, the prediction is dropped, and the model - which considers itself finished - sends the identical pair again. Measured on "what is the current kernel version?": `uname -r` fifty times. An identical consecutive command now gets `repeated_command_nudge` (the output it already produced, and an instruction to answer), and if it repeats again the task ends with `final_answer_from_command`. That reports **what the command actually printed, never the agent's own trailing DONE:** — on step one of that very case it predicted `5.10.124-microsoft-standard-WSL2` before running anything, and the real answer was `6.6.87.2`.
- `parse_agent_response` matches uppercase markers anywhere in the response, then falls back to a line-anchored, case-insensitive pass for `Help:`, `**DONE:**` and `HELP :` (all seen live). The two passes are not interchangeable: a lowercase `help:` mid-sentence is ordinary English, so accepting it anywhere would truncate a real DONE answer at the word "help:". Keep the loose pattern anchored and second.
- What a human reads when an engine fails must not be the engine's own words. `messaging.backend_failure_note` rewrites `context deadline exceeded` / connection refused / missing-model errors into what happened and what to do, keeping the raw text underneath — the note used to hand someone `ollama: request failed: Post "http://host.docker.internal:11434/api/chat": context deadline exceeded` as the entire explanation for why their desktop stopped. `thebot_harness._escalate` applies the same rewrite to failures TheBot words in its own voice ("could not reason about the failure (...) - stopping here").
- `thebot_harness` sends **the task and the standing context as separate fields** (`prompt` and `context` on soul's `/api/chat`), never one string. They used to be glued together, and soul classified, planned, stored in session history and answered the whole blob: "hello, whats your name?" spent 97 seconds in a planning call and came back as `NEEDS_APPROVAL: Before sending any real-world consequences...` — an answer to the safety rule — and "what is the current kernel version?" became a plan to search the web for the weather in New York. The context now only ever reaches soul's system frame; classifiers, the planner and history see the task alone. Measured before/after on `qwen2.5-coder:3b`, CPU only: the greeting went from 148 s (wrong) to 56 s (right), the kernel version from 205 s (wrong) to 45 s (`uname -r`), and creating a file in the work dir from a failed recovery that tried to `chmod /home/headless` to 18 s.
- soul is **deterministic before it is clever**: `atomizer.Triage` routes a request without a model call, and only a genuinely compound request (`looksCompound`) is sent to the planner. The removed layer asked the model "is this a task or a question?" for every request no classifier claimed — the single most expensive and least reliable call in the agent. Keep new routing rules in `triage.go`, deterministic, with a `triage_test.go` case; a chat answer that turns out to need the machine replies `NEEDS_TOOLS` and the scheduler reroutes it to the operator, so a triage miss costs one short call, not a wrong answer.
- soul keeps **one paused job per session** (`server.paused`). `thebot_harness.perform_task` sends `reply: false` (drop any paused job — this is a new request) and `continue_after_query` sends `reply: true` (resume it). A resumed approval runs the exact command it stopped before; a resumed question hands the human's words to the operator's saved transcript. Don't restate the task in a reply — the checkpoint already has it, and restating it makes the operator start over.
- The prompt frame's **volatile sections are chat-only**: live counters (`selfStats`) and the time of day go into a conversational job's frame and nothing else; every other job gets the date alone. With the counters in every frame, the job-log count — which goes up by one per job — changed the bytes right before the operator's contract and made every job re-read it cold.
- **A question for a web app is asked there, not worked out** (`ask_task.py`). Live: `chatgpt "where is addid ababa"` was triaged by TheBot as chat, rerouted to the operator, which ran `... | xargs curl -s https://www.google.com/search?q=` on the basic image (no curl), and the person was paged "Install curl using `sudo apt-get install curl`". The request already is the plan: each supported service takes the question in its URL (ChatGPT `?q=` submits it, logged out too), so the watcher opens that URL and a per-site reader polls the page until the answer stops changing. What the readers rely on was checked on the live pages in 2026-09 and is written beside each one - ChatGPT's classes are generated, but `li[data-message-role=assistant]`, `data-message-complete` and `[data-assistant-content-reference]` (source pills) are stable; Wikipedia's paragraphs moved into `<section>`s. ChatGPT marks a reply complete a moment before it marks its source pills up, so a reply can be read with "W / Wikipedia / +1" in it as words: `strip_source_pills` takes that shape out (the letter must be the source's own first letter, so an answer of "B" survives). Supported: ChatGPT, Google (AI overview + top results), DuckDuckGo, Wikipedia, YouTube. Not: Perplexity (logged out it shows a sign-in page, no answer), Bing (titles hidden behind redirects), anything that needs a sign-in. The name must lead the request (`what does google say about x` goes to the engine), another product is not a query (`google docs ...`), a job for the desktop after the answer (`... and save it to notes.txt`) goes to the engine, and a question holding a credential (`privacy.credential_in`) is never sent. A request that is only a list of quoted questions (`chatgpt "a", "b" and "c"`, `QUESTION_LIST`) is asked one question at a time, each in its own tab, with every answer in one reply; a refusal stops the rest and says which were not asked. - **What soul logs is not what the chat shows** (`thebot_harness.readable_step`). soul's job log is for debugging soul; forwarded verbatim, the card's "Working on" line and the chat's live box showed `scheduler: "chatgpt \"where is x\"" [general] -> skill=general model=qwen2.5-coder:3b`. - **An answer nothing printed is not taken** (operator `ungroundedDoneNudge`, `repeatedCommandNudge`; `task_runner.repeated_command_nudge`). Live: python3 with a missing `requests` module failed twice, the repeat nudge said "if that answers the task, reply with DONE", and the model reported a Content-Type header nothing had printed (`text/html; charset=utf-8`; the real one is `text/html`). - **A query note is shown as its task and its message** (`querynotes.QueryNote.Task/Message`, `ParseMessage`/`ParseTask` - also what `httpapi.agentReplyFromNote` uses; `/api/querynotes*` add `task`/`message`). - **An operator HELP straight after a failed command is pushed back too** (`failureQueryNudge`, at most `maxFailureNudges` = 2, the Ollama harness's rule), and it says never to ask the person to run or install something. When the failure is a program that is not there (`missingProgramHint`: `command not found`, or a launcher such as xargs/env/sh saying `No such file or directory` - `cat: notes.txt: No such file` is a missing *file*), the command's own result already says so and names what to use (python3's urllib for curl/wget). `curl` is now also in the basic image; the hint still matters for every other tool.
- **An operator HELP straight after a successful command gets one grounded push back** (`successQueryNudge`) unless it asks for something only a person can give (`humanOnlyRe`). Measured live: `ls -l /etc | wc -l` → exit 0, `118` → `HELP: It seems there was an error. Please try running the command again.`; and `uname -r` → the correct kernel version, delivered under `HELP:`. - **The operator's transcript keeps only the command, never the answer the model guessed beside it.** A 3B model writes `COMMAND: df -h DONE: 1.8T total, 20G used, 1.6T available` before anything runs; kept in history, it reads that guess back and reports it — measured, word for word, against a real `df` of 1007G/121G/835G. The same leftover guess made it call the real kernel version "not what was expected". (The Ollama harness's `task_runner` appends the raw response the same way.) Likewise `atomizer.scrubInventedContent` strips quoted content the planner wrote into a write step that follows research, unless the human typed it: the planner put `write "The newest Go version is v1.20.5"` behind a search that found 1.27, and file-write saved the guess.
- An abandoned Ollama request is **not** cancelled: when a caller times out or disappears mid-prompt, this Ollama keeps evaluating it, and the next call queues behind it with its own timeout already running — which is how one oversized prompt turned into a chain of `context deadline exceeded` failures on unrelated small requests. Prompt size is therefore a correctness issue on CPU hosts, not just speed: `THEBOT_WEB_PAGES` / `THEBOT_WEB_PAGE_CHARS` (set to 2 / 2500 by `start_agent_terminal.sh`; soul's own defaults of 3 / 6000 assume a GPU) keep a web step's synthesis prompt under the timeout — at 3 × 6000 it took more than 300 s to read and timed out.
- `thebot_harness` sends `sessionId` (the desktop ID). soul keeps real per-session history and threads it into every turn, but `session.Store`'s `Append` and `History` are both no-ops for an empty id — which is what this harness used to send, making TheBot the only harness with no memory of the request before last.
- `scripts/windows/build.ps1`/`rebuild.ps1` mirror `build.sh`/`rebuild.sh` step for step, including the Ollama-selection block, which - like its Linux counterpart - lives in a shared lib file (`lib/Ollama-Setup.ps1`, dot-sourced by both, mirroring `lib/ollama-setup.sh`) rather than being duplicated in each script. Three things in it are specific to Windows PowerShell 5.1 (the PowerShell every Windows machine has), and each one breaks the script without failing loudly:
  - The Python probes go into `decurix-desktop:basic` **on stdin, with their inputs as arguments**, never as a `-c` string, because 5.1 mangles double quotes in arguments to native programs.
  - `.env` is written as **UTF-8 without a BOM, with LF endings**. 5.1's `Set-Content`/`Out-File` add a BOM or write UTF-16, which hides the first key from `godotenv`.
  - A function's array output is unrolled, so a one-model list must be wrapped in `@()`. Otherwise `[0]` returns the name's first character.

  Each script's own `finally` tears its own stack management down only when it did *not* leave through `Exit-Build` - that covers Ctrl+C and the tunnel exiting on its own - but the two scripts' `Invoke-Cleanup` do different things on purpose: `build.ps1`'s just reports that the tunnel stopped and Decurix is still running (it never tore anything down to begin with, matching `build.sh`), while `rebuild.ps1`'s tears the whole stack down (matching `rebuild.sh`'s signal trap), since an interrupted rebuild must not leave a stack half old, half fresh. A failed build or a missing `cloudflared` leaves a running Decurix alone either way (that path always goes through `Exit-Build`).
- Windows `.ps1` twin steps with no Linux equivalent are platform fixes, not drift: `build.ps1`/`rebuild.ps1` check that Docker Desktop is actually running, and on Windows the loopback-only Ollama fix is a user environment variable plus an app restart rather than a systemd drop-in.
- The desktop agent binds `:8081` *before* waiting on its reasoning backend (`app.py` runs `harness.wait_for_backend` on a background thread). It used to call `wait_for_ollama()` inline, so an unreachable Ollama meant the port was never bound at all — and since `desktop.Manager.SendRequest` POSTs there, every human request from the chat, the Requests page and a query reply came back as an unexplained HTTP 500 while the desktop looked healthy in the dashboard. Keep the request channel independent of the model: a task that arrives with the backend down fails *inside* the harness, which reports it through `ask_for_query` as a reply the human can actually read. `wait_for_backend` also belongs to `harness.py` for the usual reason — `app.py` must not learn which engine is running.
- A request that arrives before the reasoning backend is up is **queued, never failed**. `watchers.command_watcher` leaves the file sitting in `COMMAND_DIR` while `state.backend_ready` is False and picks it up on a later pass, the same way it already defers a request that arrives mid-task; `harness.wait_for_backend` sets that flag once the engine answers. Dispatching into a backend that is still starting is what turned "Ollama is 20 seconds from ready" into a query asking a human to fix something that was about to fix itself. Every branch of `wait_for_backend` must mean *reachable*, not *launched* — `thebot` waits on both the shared Ollama and soul's own `/api/health`, because soul reports an unreachable Ollama as a reasoning failure that reads like a real one.
- The command watcher claims the task slot (`state.current_task = content`, under `state.state_lock`) *before* starting the harness thread, not inside `perform_task`. Otherwise the loop tests `current_task` again for the next queued file before the thread it just started has run a line, and dispatches a second task on top of the first — rare when requests trickled in one at a time, routine once a queued backlog can be released all at once.
- Don't hardcode a Cloudflare quick-tunnel URL as anyone's default. Quick-tunnel hostnames are regenerated on every `cloudflared` restart, so a checked-in one is dead code the day it's written — `buildDesktopEnv`'s `OLLAMA_URL` default was one, and every desktop created after that tunnel died was structurally brainless. Tunnel URLs belong in `.env` (or `internal/tunnel`, set at runtime), never in a literal.
- **`internal/lanaccess` only ever gates the second listener, never the primary one.** The primary listener (`:8080`) is what `CONTROL_PLANE_URL` points every desktop agent's callbacks at, so putting a login page in front of it would make every `POST /api/querytext`/`/api/agent/events` from inside a container fail closed the moment the control plane started, with no human anywhere to type a code. `cmd/decurix/main.go` builds two independent `*http.ServeMux`s from the one `Server` (`RegisterRoutes` called on both) precisely so a bug in the gate can never touch the primary listener's routing — the two are different `net.Listener`s on different ports, not one mux with some paths exempted. `RegisterLocalRoutes` (the code itself, and the rotate button) is the one asymmetry: registered only on the primary mux, so the code is never fetchable over the very listener it protects.
- **`lanaccess.Store`'s lockout degrades to one shared bucket for anything reverse-proxied into the gated listener**, not a per-attacker throttle: `cloudflared` (or any other reverse proxy) forwards every connection through its own local process, so every request the control plane sees through it carries the same loopback `RemoteAddr` regardless of who is actually on the other end — `recordFailure`'s per-source key can't tell a legitimate retry from an attacker in that case (a genuine direct-LAN connection, by contrast, gets AO's real per-device lockout). This is why the access code is 10 characters from a 54-character alphabet (`passwordChars`: no `0`/`O`/`1`/`I`/`l`, kept readable and typeable on a phone) rather than AO's 8: the code's own entropy is carrying weight the lockout can't, on that one path. `build.sh`/`rebuild.sh` deliberately tunnel *into* the gated listener, and only it (the `lan_tunnel_url` tunnel — see "Two listeners, one process, one set of routes" above), so this shared-bucket degradation is the normal case, not an edge case someone opted into by proxying it themselves; it is exactly the path the code's extra length was sized for. `lanaccess.RunAutoRotate`'s 48-hour automatic rotation is the other half of that same trade: entropy and a lockout that can't fully do its job are backstopped by the code simply not staying valid very long.

Also unverified: apps starting on a virtual display while the phone is locked, Doze with the screen off despite the wake lock, and banking apps (`FLAG_SECURE`) - expected to show black. iPhones cannot do any of this (no background process, no ADB).
