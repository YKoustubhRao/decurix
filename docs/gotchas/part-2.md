# Gotchas, part 2

- **Under WSL2 the local-network link is Windows' address, forwarded into WSL** (`scripts/linux/lib/lan-address.sh`, `decurix_lan_ip`, used by `build.sh` and `rebuild.sh`). In WSL's default NAT mode the address `ip route get` gives (172.x) is reachable from Windows only, so a phone handed it got nowhere. The scripts ask Windows for its own LAN address (`Get-NetIPConfiguration`, the adapter with a default gateway), and when no `netsh interface portproxy` rule already maps it on the gated port to WSL's current address, run one elevated PowerShell (`Start-Process -Verb RunAs`, the commands passed as `-EncodedCommand` UTF-16LE base64 so no quoting survives the hop) that replaces the rule and adds an inbound firewall rule `Decurix LAN access (<port>)`. One UAC prompt, then none until either address changes. Only the gated port is forwarded, never 8080. Declined or failed, the script says so and reports WSL's own address; mirrored networking (the two addresses equal) needs nothing. `DECURIX_WSL_LAN_FORWARD=0` in `.env` skips it. No `.ps1`/Mac twin: native Windows (Docker Desktop publishes on the host itself) and macOS have no WSL NAT to cross. **A quick tunnel's address is hyphenated words**: every script pattern requires `https://word(-word)+.trycloudflare.com`, and `httpapi.tunnelAddress` refuses `api.trycloudflare.com` - cloudflared names that host in the error it logs when a quick tunnel cannot be created, and a script that took it for the tunnel handed out a pairing link that answered "method not allowed".
- **"Your own link" (`internal/cftunnel`) routes only the gated listener, and only the person can set it up.** `/api/cftunnel*` are primary-only *and* `humansOnly`: the API token can create tunnels and DNS records on the person's account, and the connector token would let anything holding it run a connector that receives some of the link's visitors (and the access codes they type) - so a desktop, which can reach the primary listener, must never read either. The API token is never returned by any route; an empty token on a re-run reuses the saved one. `pointCNAME` never overwrites a DNS record it did not make (an A record, or a CNAME without its `Decurix tunnel` comment): it refuses with `ErrNameTaken`. `Disable` only stops the connector and forgets the setup; the tunnel and record stay in Cloudflare, and setting up again reuses them. The control plane runs `cloudflared` itself - the released binary needs it on PATH (the setup scripts install it) and says `missing` otherwise; the compose image does not ship it while the setup form is out of the menu, so add it to `docker/Dockerfile` when bringing that back - so the scripts' `start_lan_tunnel`/`Start-LanTunnel` skip their quick tunnel when `/api/cftunnel` says one is configured, and `GET /api/tunnel` reports the fixed link as `lan_tunnel_url` over any quick-tunnel URL a script posted. A fixed, public hostname is easier to find than a random trycloudflare one, and the gated listener's lockout is one shared bucket for all tunnel traffic (see below); the 10-character code is what holds. Put Cloudflare Access in front of the hostname for a second factor.
- **`idlepause` never guesses "idle" from task history alone.** `Checker.idleSince` takes the *latest* of the desktop's own container start time (`desktop.Desktop.StartedAt`, read off `container.Inspect`'s `State.StartedAt` in `List`/`Get`), its last task activity (`tasks.Store.LastActivity`, `MAX(updated_ns)` over that worker's tasks), and `desktop.Manager.LastViewed` (bumped by `Screenshot` and `resolveProxyTarget` — a card's thumbnail poll or an open screen tab) — never just one signal. A desktop with old task history that was just started fresh, or one with no tasks at all but someone actually looking at its screen right now, must not be stopped out from under them — idle-pause is on by default, so this is the ordinary case, not an edge case someone opted into. `idleSince` returns `ok=false` (leave it alone, never "assume idle") when `StartedAt` itself can't be parsed, which is Docker's own zero-value RFC3339 string for "never started" — a container inspect briefly failing is not evidence of anything.
- **`idlepause.Checker.Run` returning immediately when `Threshold <= 0` is load-bearing, not an optimization.** `cmd/decurix/main.go` calls `go checker.Run(ctx)` unconditionally, every startup, passing whatever `idleStopThreshold()` returns — including `0` after an explicit `DECURIX_IDLE_STOP_MINUTES=0` opt-out. The type has to be safe to start with a non-positive `Threshold` because of this, not as a defensive extra: it is the only thing that makes the opt-out actually opt out, rather than `main.go` needing its own enabled/disabled branch that could drift from `idleStopThreshold`'s own idea of "disabled".
- **`idlepause.Checker.sweep` checks up to `sweepConcurrency` (8) desktops at once, not one at a time.** A burst of desktops crossing the idle threshold in the same tick used to mean stopping them sequentially, and one `Stop` can itself take up to `DESKTOP_STOP_TIMEOUT_SECONDS` (10s default) waiting for a graceful shutdown — with many desktops idle-eligible together (the ordinary case idle-pause is *for*, at scale), a sequential sweep could take minutes and leave the rest of that tick's candidates idle-but-unstopped until the next one. Each `checkOne` only touches its own desktop's state, so nothing here needs a lock beyond the semaphore bounding how many run at once.
- **A stopped desktop no longer fails a request — `httpapi.deliverRequest` starts it and waits, up to `autoStartTimeout` (90s), before giving up.** This is what makes idle-pause's default-on behavior actually mean "works only when a task is assigned" instead of "silently breaks until a human notices and clicks Start": `desktop.Manager.SendRequest` itself stays a fast "send now, fail if not running" primitive (`ErrNotRunning`), and the wait-and-retry policy lives in `httpapi` — `sendRequestHandler` and `recordTaskHandler` are the two callers, both already about to block the human/automation on the desktop's reply anyway. The retry loop tolerates both `ErrNotRunning` (container still coming up) and `ErrAgentUnreachable` (container up, `vm_server.py` hasn't bound `:8081` yet) as "keep waiting", and returns immediately on anything else. Measured live on this repo's own dev host: a cold `ollama`-harness `basic` desktop took ~20s from stopped to accepting a request — comfortably inside the timeout, but real time a human or an API caller now waits out rather than seeing an error.
- **`desktop.Manager.SendRequest` reaches the agent by the container's address on `decurix-network`, not its name** (the same address `resolveProxyTarget` uses for the screen and recordings). The name resolves only for a control plane on that network (compose); the released binary on the host has no Docker DNS, and every chat request it sent failed as `lookup desktop_<id>: no such host`. Found by the Azure benchmark run on 2026-09-29.
- `progress.emit` is decoration and must stay that way: it never blocks, never raises into a harness, and drops lines when its bounded queue is full. A desktop reporting what it is doing must never be able to slow down or fail the task it is describing — which is also why `agentEventHandler` answers a malformed event with 200 rather than an error the agent would then have to handle.
- **Steps nobody asked for are filed under their own entry once a request follows them** (`conversation.Store.AppendUserRequest`, `thread.openedBySteps`, `UnrequestedActivity`). A step with no running turn still opens one, so a person demonstrating, or a `gui` command run by hand, stays visible. A request arriving while such a turn is open used to be treated as queued behind it, and its reply carried the demonstration's clicks as if the agent had done them. A turn opened by a request always has that request as its latest entry, so no new state is stored.
- **A turn's last step can arrive after its reply.** Steps go out on `progress`'s background queue, but the reply is POSTed directly, so TheBot's final log line ("wrote … verified on disk") reached the control plane under a millisecond *after* the answer — and `AppendStep`, seeing no running turn, opened a new one that nothing ever closed: the chat showed "Working…" forever over a finished task. Two guards: `messaging.send_query` calls `progress.flush()` (bounded) before sending, and `conversation.AppendStep` attaches a step arriving within `lateStepWindow` of an agent reply to that reply instead of reopening a turn — the second is what covers desktops built from an older image.
- `DESKTOP_ID` (what a desktop calls itself on every callback) and `Desktop.ID` (what the dashboard lists it as, derived from the container name) must produce the same string, since query notes and chat entries are keyed by it. Both now go through `sanitizeName`; they diverged for any name containing a character only `sanitizeName` rewrites (`my.box` stayed `my.box` in the env var while the desktop was listed as `my-box`), and that desktop's callbacks matched no desktop the dashboard knew. Use `desktop.SanitizeID` from outside the package.
- A dashboard card's preview is a JPEG from `/api/desktops/screenshot`, **never an embedded screen**. It used to be `<iframe src="/desktop/<id>/">` — a whole noVNC client per card, measured at 83 requests plus a WebSocket each, all against the control plane's single origin, which a browser serves over at most 6 concurrent HTTP/1.1 connections. Two desktops saturated that pool (178 requests over 7 connections, ~950ms stalls) and the VNC handshake for a screen a human had actually opened queued behind the thumbnails — 11s in one run, "Failed to connect to server" in the next. That is why "spin up two VMs and you can't work on both" was a browser-side bug with a clean server: the Go proxy served 120 concurrent requests with zero errors. `desktop.Screenshot` reads RFB directly instead (~8KB, ~80ms), and `index.html`'s `shotLoop` refreshes cards in one *sequential* sweep so the dashboard never has more than one thumbnail request in flight whatever the desktop count. Don't reintroduce a per-card iframe, and don't parallelise that sweep.
- `desktop.Screenshot` connects as a *shared* RFB client (`ClientInit` shared=1) and only ever sends a FramebufferUpdateRequest — a thumbnail must stay invisible to whoever is using the screen. It offers `Raw` as the only encoding, so the server cannot answer with a compression scheme there is no decoder for, and it reads `VNC_PW` off the container rather than the control plane's `DEFAULT_PASSWORD`, so a desktop created before that value changed still has a readable screen.
- The chat renders `content` through `textContent` only, never `innerHTML` — the text in a bubble is written by a model that can be told to emit anything. `renderContent` builds real `<pre>`/`<code>` nodes for fenced and inline spans and leaves everything else literal; keep that property when extending the formatting.
- `internal/webui/render_test.go` executes every page template. Templates are data to the Go compiler, so a typo'd action or a renamed field is invisible to `go build` and shows up as a panic or a 500 on the first request — add new pages to that test.
- `httpapi.agentProxyHandler` (`/agent/<id>/`) still proxies TheBot's own UI on port 4900, but nothing in the control plane's UI links to it any more: the chat page talks to TheBot through `decurix_agent` like every other harness, so it picks up worker memory, the safety preamble and the approval path, none of which soul's own UI goes through. Keep it as a debugging surface; don't wire it back into the UI as a second way to command a desktop.
- The base image ships `/home/headless` as `root:root` — anything that needs to write directly under it at **build time** (not runtime, where the real entrypoint/volume-mount semantics differ) needs an explicit `chown headless:headless /home/headless` first, same as the existing `RUN ... chown -R headless:headless /home/headless/.config` step. This bit the `claude` native-binary install (`~/.claude`, `~/.local`) until fixed in `docker/desktop.developer.Dockerfile`/`docker/desktop.ai.Dockerfile`.
- **Chromium in a desktop runs sandboxed**, which takes two halves that must both be present. `desktop.Manager.BeginProvisioning` gives every new desktop `internal/desktop/seccomp-desktop.json` — Docker's own default seccomp profile with `clone`/`setns`/`unshare` opened, nothing else — because Chromium's sandbox is built from user/PID/network namespaces that the stock profile forbids (the base image's answer was a hardcoded `--no-sandbox`, and the "unsupported command-line flag: --no-sandbox" bar on every window). And `agent/chromium-browser.init` probes `unshare --user --pid --net` at each browser launch and only adds `--no-sandbox` back when namespaces really are unavailable — a desktop created before the profile existed, or a daemon without seccomp (`desktopSecurityOpt` checks `SecurityOptions` and skips the profile there, since such a daemon rejects the container outright). **A desktop created before this change keeps showing the warning until it is recreated**: the seccomp profile is fixed at container creation. The warning is left visible in that fallback on purpose — the browser really is unsandboxed there.
- Desktops run with **core dumps off** (`desktopUlimits`, plus `ulimit -c 0` in `chromium-browser.init` for desktops created earlier). The `core.<pid>` files that filled a TheBot desktop's `~/Desktop` were not TheBot's: parsed out of the ELF notes, every one was a Chromium utility process (`--utility-sub-type=data_decoder` / `unzip`) dying with `*** stack smashing detected ***` in a restart loop, ~50 MB every fifteen seconds, landing in `~/Desktop` because that is where the XFCE menu starts the browser. `start_agent_terminal.sh` deletes existing ones, matching both the `core.<digits>` name and the ELF `ET_CORE` header.
- The chat renders a sent request **the moment Send is pressed** (`desktop.html`'s `pending` list), then drops that local copy as soon as a transcript snapshot contains the server's own (the first new user entry with the same text that was not in the transcript at send time). The server stays the only record — `sendRequestHandler` still appends only after the desktop accepts the request (measured at 5–12 ms) — and a failed send stays on screen with Retry and Edit.
- **The Cloudflare quick tunnel does not deliver the chat's event stream.** Measured through a `trycloudflare.com` tunnel: `/api/desktops/chat/stream` returns its headers and then *no body bytes at all* — not the snapshot the handler flushes on connect, not a request sent a second later — for as long as it was watched (40 s), while the same stream on localhost delivered the request in 70 ms. The chat used to fall back to polling only on a stream *error*, and a held stream never errors, so on a phone a sender's own request appeared only when the agent's reply finally pushed something through: the "my request only shows up with the response" bug. `connect()` now closes a stream that has not delivered its first frame within `FIRST_FRAME_MS` (4 s) and polls instead; over the tunnel a sent request shows in ~70 ms (locally rendered), the server's copy in ~2 s, and live steps from ~2 s. Anything else that relies on SSE through the tunnel needs the same fallback.
- `NEEDS_TOOLS` is taught **only to the chat skill** (`prompt.ChatRule`, appended to the frame by `GeneralSkill`), never in the shared `Persona`: with it in the persona, the operator answered "ping - just reply pong" with `HELP: NEEDS_TOOLS`, which a human received as an entire query. The operator also treats that marker as a malformed reply.
- The XFCE desktop wallpaper is set by baking `agent/decurix-desktop-wallpaper.xml` (pointing at `agent/decurix-wallpaper.svg`, copied to `/opt/decurix-wallpaper.svg`) into `/home/headless/.config/xfce4/xfconf/xfce-perchannel-xml/xfce4-desktop.xml` at image build time, in all three desktop Dockerfiles — otherwise XFCE generates its own default (the base image's stock `xfce-shapes.svg`) the first time it starts with no config present. Since `/home/headless` is the container's persistent named volume, this file only seeds *new* desktops (an empty volume on first start); it has no effect on a desktop created before an image rebuild.
- **The taskbar (`agent/decurix-panel.xml`, seeded into the `xfce4-panel` xfconf channel the same way as the wallpaper above) replaces the base image's own top-menu-bar-plus-autohide-dock layout with a single bottom bar, so a Windows user recognizes it immediately**: a Start button (`xfce4-whiskermenu-plugin`, search-as-you-type, installed alongside the theme packages) with pinned Files/Browser/Terminal launchers at the left, running windows shown icon-only and kept roughly centered by a pair of expanding separator plugins on either side of that group (imperfectly — the fixed-width tray+clock on the right isn't mirrored on the left, so the group sits a little left of true center; this is the same trade-off Windows 11 itself makes when tray content is present), and the system tray plus a stacked time/date clock (`digital-layout=0`, confirmed live against this xfce4-panel build — other values render date-only or time-only, not both) on the right. `decurix-xfwm4.xml`'s `button_layout` is set to `|HMC` to match: minimize/maximize/close grouped on the right, no window-menu button on the left. Same persistence rule as the wallpaper: only seeds *new* desktops, and an existing one keeps its old panel until recreated.
- **A launcher plugin's `.desktop` file is looked up by the panel *plugin's own ID*, never by the desktop-file's name.** `xfce4-panel` reads a pinned launcher's entry from `~/.config/xfce4/panel/launcher-<plugin-id>/<anything>.desktop` — found live by seeding a `decurix-panel.xml` whose launcher plugins referenced desktop-id filenames with no matching `launcher-<id>/` directory on disk, which silently rendered a generic fallback icon instead of erroring. `decurix-panel.xml`'s launcher plugins are hardcoded to IDs 3/4/5, so `agent/decurix-launcher-{files,browser,terminal}.desktop` must land at `launcher-3/`, `launcher-4/`, `launcher-5/` respectively (each Dockerfile's `mkdir -p`/`COPY` block) — renumbering one side without the other reproduces the same silent fallback.
- **Editing a live desktop's `xfce4-panel.xml` (or any xfconf-seeded file) by hand while `xfconfd` is already running does nothing**, and *looks* like it worked because the file on disk really does change: `xfconfd` only reads a channel's perchannel-xml file at the moment that channel is first touched by *this daemon process*, then serves everything from memory and writes back to the same file on every property change — so a `cp` over that file mid-session is invisible until `xfconfd` itself restarts. Verified live: killing only `xfce4-panel` and relaunching it kept the old panel, because the original `xfconfd` (running since container start) was still alive and still serving the old config from memory; killing `xfconfd` too (and letting the panel respawn it) picked up the new file. Also, `xfconf-query`/any manual panel restart from a `docker exec` shell must export the *session's own* `DBUS_SESSION_BUS_ADDRESS` (read off a running session process's `/proc/<pid>/environ`, e.g. `xfce4-session`) — without it, `dbus-launch` silently opens a throwaway private bus with its own empty `xfconfd`, and both reads and writes against it are talking to nothing the real session ever sees.
- **The base image sets `NO_AT_BRIDGE=1`**, which silently turns off every GTK app's AT-SPI bridge: the accessibility tree was empty until the desktop Dockerfiles set `ENV NO_AT_BRIDGE=0` (and `computer.session.ACCESSIBLE_APP_ENV` sets it for anything the layer launches). Thunar's windows belong to the XFCE session's Thunar *daemon*, so on a desktop created before that ENV change they stay invisible until the daemon is restarted — which is why `bench.py` runs `thunar --quit` before a file-manager task. Like the seccomp profile, the ENV is fixed at container creation: an existing desktop needs recreating.
- **LibreOffice misreports where it draws.** Under XFCE its AT-SPI extents for everything VCL paints (the document, table cells, toolbars, sheet tabs) are often reported too high, by an amount that depends on its state, not a constant: 27 px on one desktop; on another a freshly opened Calc was 25 px off (the menu bar's height), right again once the pointer crossed the window, and off again after a no-op window move. The frame's own extents cannot tell (it reported (0,0) with the window at (0,36)). Only the native GTK menu bar is always right, and VCL's first toolbar is drawn directly below it, so `atspi.libreoffice_offset` measures the offset every observation as how far the topmost toolbar is reported above the menu bar's bottom edge, and `_correct_libreoffice_boxes` shifts everything but the menu bar by it (none when no toolbar is shown). This is what `calc-rename-sheet` (double-click on the sheet tab) failed on. So the layer never clicks LibreOffice content by coordinates: text goes into a Writer cell or paragraph through `Atspi.Text.set_caret_offset` (`atspi.place_caret`), and a Calc cell is reached by coordinate through the Name Box shortcut (Ctrl+Shift+F5, the reference, Enter — `core._goto_sheet_cell`), because LibreOffice 24.2 does not expose the Name Box over AT-SPI at all. A Calc sheet MANAGES_DESCENDANTS with 2^31 children and is never walked; its visible used range is read cell by cell through the Table interface (`atspi._sheet_cells`). Writer's document sets the same flag with a handful of children and *is* walked — the rule is the child count, not the flag.
- **A ref means "the element at this path"**, not "the Nth element of this observation" (`elements.assign_refs`). Paths are rooted at the window title with a leading `*` stripped (an editor's unsaved-changes marker) for AT-SPI, and at the **site** (host:port), not the page title, for Chromium — so a navigation link keeps its ref on every page of a site. Renumbering per observation made "e12" point at something else after one row was inserted.
- A GTK list/tree cell's AT-SPI action is `activate` — *open the file*, not select it — so `core._perform` clicks cells, list items and icons by position instead of invoking their action. Every other widget prefers its own action over a coordinate click.
- **The browser's DevTools port (9222, `agent/chromium-browser.init`) is how pages are read and worked**, bound to 127.0.0.1 inside a container with no published ports. It is also a way for any process in that desktop to drive the logged-in browser — the same trust the agent's unrestricted shell already has, not a new one. A Chromium started *without* the port (before this change, or by hand) cannot be read; `observe` says so in a note rather than returning an empty page. Chrome accepts a DevTools websocket with no Origin header (cdp.py sends none), and since 136 refuses remote debugging on its *default* profile - which is why the launcher always passes `--user-data-dir` (see below).
- `logging_utils.log` prints to stdout, which is the *output* for `gui` (an engine reads it as the result of its action) and the *protocol channel* for the MCP server. Both call `logging_utils.log_to_file` first (`/tmp/decurix-gui.log`, `/tmp/decurix-mcp.log`). A stray `print` in the computer package breaks Claude's tools.
- The audit trail's `gui` process is short-lived, so `cli.main` calls `progress.flush()` in its `finally` — without it the action step (and its screenshots) die with the process before the background sender posts them. `progress.emit_action` drops the screenshots, never the step, when the queue is a quarter full.
- The approval gate's patterns (`approval.CONSEQUENTIAL_CONTROL`) match a control's *label*, anchored at its start ("Send newsletter", "Pay now INV-1042"), and only for activating roles. They are deliberately narrow for the reason `internal/safety` gives. The gate guards against a model's mistakes, not a hostile model: an engine with a shell could write the grant file itself, exactly as it could run xdotool directly.
- `bench.py` kills apps by **process name**, never `pkill -f <word>`: task ids like `mousepad-save-as` are in its own command line, and the first version killed itself.
- **A dispatched request file is renamed to `*.txt.done`** (`watchers._mark_handled`). `state.processed_commands` is memory and `COMMAND_DIR` is the persistent volume, so every desktop restart used to replay every request the desktop had ever received — found by the GUI benchmark, which restarts a desktop between tasks: each task queued behind replays of all earlier ones, and a spreadsheet task was answered with questions about signing in to an admin panel. A request deferred behind a running task or a backend that is not up yet keeps its `.txt` name until it is actually dispatched.
- `bench/gui/run.py` restarts a desktop after any task that did not end in a plain answer or error (`agent_is_idle`): a paused agent takes the next request as the *reply* to its query. And an approval task only passes when the gate itself fired (a step with `outcome: needs_approval`), not when the agent merely raised a query for some other reason — which leaves the invoice unpaid too.
- **A demonstration tells the person from the agent by input device, not by timing.** XInput2 raw events name their source device: a person using noVNC arrives as Xvnc's `TigerVNC pointer/keyboard`, every xdotool action as `Virtual core XTEST pointer/keyboard` (measured: devices 6/7 vs 4/5), and `demonstration.py` drops XTEST. The client must announce XInput **2.2** (`XIQueryVersion`) — only from 2.1 are raw events delivered while another client holds a grab, i.e. inside an open menu or a drag. python-xlib 0.33 parses XInput device events but not raw ones: the recorder registers a raw-event struct with `Display.ge_add_event_data` (a method of the high-level `Display`, not `display.display`) and matches `ge.GenericEventCode`, since `X.GenericEvent` does not exist there.
- **A press the recorder read late is not named from a screen that changed after it** (`demonstration.Recorder._lag`, `LATE_SECONDS`, `LATE_NOTE`; `processing.CARRIED` carries `happened`/`late`; `replay.compile_program` takes no picture for a `late` event). Found live on a 1-vCPU worker (2026-10-07): a click on the web app's Save, read ~20 s late, was named from a look taken after the save - when the same spot had become "Submit" - and a skill taught from it would have submitted the invoice. The X server's own timestamp on each raw event gives how far behind the reader is (the smallest clock gap seen counts as on time); a press read more than 0.5 s late, whose last look at the screen was taken after it, is recorded with no target and that note, and `/learn` asks about it like any position-only click. Still open: the pointer position itself is read when the event is handled (raw events carry none), so under the same lag a press can land in the recording a little off - a row's "Accepted Qty" was recorded as "Rate" and a click as a drag in that run; the lesson's Q&A is where a person corrects such steps.
- **A pause that ends on the screen it began on records no private step** (`demonstration.UNCHANGED_SCREEN`, `Recorder._resumed`). The toolbar pauses while a Reason is written, and every resume used to write a `manual` event - so a taught application task ended with "29. a private step done by hand", which `/learn` kept even after the person said it was only the note. A real private step (a sign-in) changes the screen and is still recorded.
- **Xvnc changes the keymap while someone types.** It maps the keysyms a VNC client sends onto keycodes on the fly and types a capital by toggling Caps Lock around it, announcing both with `MappingNotify`. The recorder refreshes its keymap on that event, names keys from its own `KEY_NAMES` table (python-xlib's `keysym_to_string` returns None for Shift_L, Caps_Lock and every other named key), and reads the Lock state back from the server whenever a key goes down with nothing held. Measured before each fix: "Human Co" recorded as four runs split by `keycode_66`, then as "hUMAN cO" when an earlier session had left Caps Lock on.
- **A typing run keeps its field until something moves focus** (`demonstration._focus_after`), and text typed into a field that cannot be told is withheld whenever a secret field is on screen. Both close a leak found live: an unrecognised key split a password's typing in two, the second half had no element, and it was stored as plain text.
- **A demonstration's "what changed" is discarded when the person's next input landed before the screen was read** (`change_missing`). Observing takes a second or two and people do not wait: a sign-in click's "Welcome back" was recorded as what the typing before it did, and a replay would have waited for it after the wrong step.
- A replay is **refused (409) while the desktop has a task running, queued or waiting** (`tasks.Store.Busy`), rather than routed: sent to a paused agent the watcher takes it as the reply, and queued behind a running task it is absorbed as the reply if that task pauses. A replay's parameters travel only in the request body to the desktop and live in `replay_task`'s memory until it runs — the chat, the task record and the command file see `/replay <id> [from=N]`, never a value.
- The agent's HTTP server is a `ThreadingHTTPServer`: exporting a recording streams a zip for as long as it takes, and a single-threaded server would hold every chat request behind it.
- **Everything the agent keeps for itself lives under `~/.decurix`**: `config`'s command/querytext/final/memory dirs, the computer layer's `computer/` and `recordings/` (an `audit/` from before recordings is imported into them once at startup by `recording.import_legacy_audit`, with its typed secrets withheld), and TheBot's `WORKSPACE_ROOT` (`ai/`). `~/work` is the only directory it adds to the top of the home, because that is where tasks run and what a human browses. `start_agent_terminal.sh` moves an older volume's `~/command`, `~/helptext`, `~/final`, `~/memory`, `~/audit` (and `~/ai`, on a TheBot desktop only) into place before the agent or soul starts, never overwriting an entry already there - a second step then renames a `~/.decurix/helptext` it finds (freshly moved, or already there) to `~/.decurix/querytext`. A container keeps the image it was created from, so a desktop created before the move still runs an agent that reads `~/memory` — which is why `desktop.Manager.PersistMemoryFile` writes there while it is that desktop's only memory directory.
- **A ticket is opened the same way any request is, but Record/Stop/Continue/Reason/End are not command files.** `record_task.py` keeps the open ticket as its own module-private state (`_ticket`, the way `replay_task.py` keeps `_held`) rather than in `state.py`, because nothing outside the module reads it directly — the GUI toolbar's begin/pause/resume/end calls go straight into `record_task.begin()` etc. over HTTP, bypassing the command directory and the watcher entirely, since they only ever act on whatever ticket is already open. `tasks.Store.Busy` is still what keeps a second ticket (or a replay) from being opened while one is: `perform()` occupies the task slot for the ticket's entire lifetime, exactly like an agent's task would.
- **`httpapi.callAgent`'s payload parameter is `any`, and a nil `map[string]string` boxed into it is not the untyped `nil` the function tests against** — Go's classic typed-nil-in-an-interface trap. `ticketActionHandler` hit this for `begin`/`resume`/`end` (no fields to send): a `var payload map[string]string` left nil and passed straight through would satisfy `payload != nil` anyway, and `json.Marshal` would send the literal `null` as the body — which the agent's `_body()` rejects (`json.loads("null")` isn't a dict) as 400 rather than sending no body. Pass the bare `nil` literal itself for a call with no fields, not a nil-valued typed variable.
- **The ticket toolbar's own poll must not rebuild the panel when nothing changed.** It reads GET `/api/desktops/ticket` every 2.5s the way `desktop.html`'s chat polls the transcript, but unlike the chat's whole-snapshot renders, rebuilding this panel on every tick would wipe out a task name being typed into the `+` input mid-keystroke (new `<input>`, empty value) even though the ticket state hadn't actually changed. `refresh()` compares the fetched ticket against the last one (`JSON.stringify`) and skips the render entirely when they're equal; a create-ticket **failure** (busy desktop, dropped request) also preserves what was typed, via a `draftTask` variable read back into whatever `<input>` gets rebuilt next, so a rejected submission doesn't make someone retype it.
- **End does not wait for `record_task.perform()`'s own thread to clear the ticket, so its HTTP response can still show the ticket "open" for an instant.** `end()` sets `demonstration.stop()` (if capturing had started) and signals `_ended`, then returns immediately — `perform()`'s background thread wakes and clears `_ticket` a moment later, off this request's critical path. Trusting that response's `ticket` field for the toolbar's post-End render would flash the ticket panel once more before the next poll corrected it; the toolbar's `act("end", ...)` special-cases the answer instead — captures `session_id` for the download link if the response carried one, sets its own `ticket = null` unconditionally, and renders the "recording saved" view right away.
- **The dashboard card has no Record button of its own** — `index.html`'s `.dcard-actions` only opens the chat and the screen (plus restart/stop/delete); *making* a recording lives solely in the ticket toolbar inside the screen itself. Don't re-add a card-level Record: the toolbar is the one thing that already knows whether a ticket is open, recording, or paused, and a second, unsynced entry point would just be another place for that state to go stale. What the card *does* have is a **Recordings dropdown** (running desktops only, `data-rec-list`): the finished demonstrations, oldest first, each with Replay / Learn / Download, read from `GET /api/desktops/recordings` when the list is opened and calling the same `/api/desktops/recordings/{replay,learn,export}` the recordings page does. Replay there sends no parameters, so a recording that typed a secret halts and asks; the full page (`/recordings/<id>`) is where values are given.
- **"Your task is done" is announced on every page** (`theme.html`'s `announce`). A finished task leaves no query note, so `queryTextHandler` also records it in an in-memory feed (`httpapi/finished.go`, last 50, `GET /api/tasks/finished?after=<seq>`; a first call without `after` returns only the latest seq, so a page never replays old news). Notes and finished tasks are told the same way: a toast when the page is in front (not on that desktop's own chat, which shows the reply), a system notification when the bell is on, otherwise a dot in the tab's title until it is looked at. Notes are titled by kind ("finished", "could not finish", "needs your approval", "needs you").
- **A query note is resolved by answering it, and resolving keeps it.** `querynotes.Store` marks a note resolved (`resolved_ns`, `resolution` `answered`/`manual`) instead of deleting it; `List` returns only open notes, `ListResolved` the history behind the Queries tab's Resolved section (`GET /api/querynotes/resolved`). `queryTextHandler` stores the outcome kind on each note, and `recordDelivered` - which every door (chat, requests page, a query's own reply box, a schedule) passes through - calls `ResolveAnswered(desktop)` when the request routed as `tasks.RouteReply`. Only notes of kind `query`/`approval` are resolved that way: a finished task's report is not answered by a reply and stays open until someone resolves it. A note from before `kind` existed has none, so it is never auto-resolved. The Queries page polls (4 s) to drop cards answered elsewhere.
- **The "Recording saved" view of the ticket toolbar offers Replay, Learn and Download**, the same calls the recordings page makes (`/api/desktops/recordings/{replay,learn,export}`). Replay and Learn are refused (409) while a task is open, and End answers before the ticket's own task has finished closing, so `startFromRecording` retries a 409 a few times before showing the reason. Neither is given values: a recording that typed a secret halts and asks.
- **A saved skill is written into the desktop's learned memory.** `skill_task._learn_reply` calls `messaging.remember` on a `save` decision, which POSTs `/api/desktops/memory` (category `skill`): the entry shows in the card's learned-memory list and is written back into `~/.decurix/memory`, so every harness reads that the skill exists and how to run it. A draft, a discard or an unclear answer records nothing. Best-effort - a failed post never fails the lesson. Corrections a later run learns are not recorded there, only the skill file keeps them.
- **A request that is a recorded task done again is done the way the person did it: mimic first, intelligence only for the difference** (`computer/mimic.py`, `skill_task.mimics`/`perform_mimic`, dispatched by `watchers.command_watcher` before the harness, no backend needed). The desktop's model is small, so what a person recorded is the plan. The request is compared word by word (`difflib`) with the task every finished demonstration was recorded for (its `task`, else its title) and every ready skill's `goal`. Every ticket word that is not filler, not something the person typed or clicked, and not a value (a number, a quoted phrase, a capitalised name) is the task's shape and must be there unchanged - so `bing X` after a ticket for `google X` is another task, and nothing reads meaning into "google". What differs is put where the recording has it literally: into what was typed, a clicked control's name (its recorded path dropped), a page opened. Window titles and expected results take a changed typed value *whole* (`step_spans`/`value_spans`): the lone word "koustubh" must not rename the window "Koustubh - Chrome" (a browser profile) the steps were recorded in. Only a value the recording typed in another form ("5 March" typed as `05/03/2026`) asks the model one fixed question (`adapt_values`: recorded task, what was typed, new task -> what to type), and the person when there is no model; a model that would type everything unchanged means it is another task, as does a difference with nothing typed to adapt, and a second job in the request (`SECOND_JOB`: "... and email it") - those go to the engine. A recording nobody taught is built into a skill for that run only (`learning.build`, `one_off`: never saved, no experience recorded); a taught skill is preferred over its own recording and its saved steps are never rewritten - substitutions go into the run's expanded copy. The same request as recorded replays as recorded.
- **A skill has a name a person can give it, and its goal survives a rename.** `/learn <ids> name="Search Google"` (quotes allowed; `skill_task.learn_request` and `httpapi.learnContent` build the same string) makes the skill's `title` that name and its file name a free slug of it (`skills.unique_name`: naming a skill after one that exists never overwrites it). The goal (what `mimic.plan` matches against) is the recording's `task`: `recording.update` keeps the first title as `task` the first time a recording is renamed, so a friendly name does not lose the words typed for the ticket. The name box is on the card's Recordings list (the title, edited in place), the ticket toolbar's "Recording saved" view, and the recordings page's Teach form.
- **A replay puts the screen back to the size its point clicks were recorded at** (`replay._fit_screen` -> `screen.set_size`, xrandr `--newmode/--addmode/--mode`, as noVNC's remote resize does). A screen's size follows whoever viewed it last: a demo recorded at 1527x727 met 1280x720 after a restart and halted at its first click, although the same size lays the window out pixel for pixel. Only when every point step shares one recorded size. `screen.grab`/`size` read the live geometry every time: the old per-process cache kept capturing the size the agent started at after noVNC resized the screen.
- **A point click whose picture fails because this run typed something else is matched by kind** (`visual.make_kin`/`find_kin`, `replay._find`/`_kin`/`_first_change`). Recorded as a search for `koustubh is great`, the first result's title "Kaustubha" was clicked at 352,544; searched for `who is rama`, the first result is "Rama", 58 px higher, and the look correctly finds nothing. A *kin* describes what kind of thing was clicked: a line of text in a coloured ink (a link), its height, the column it starts at, and which of those it was counting from the top; the replay clicks the same-numbered one now (measured on the real frames: (353, 487), on "Rama"). Only when **all** hold: the look is `missing` (never `ambiguous`), an earlier step of this run typed something other than what was recorded (so the picture was expected to change), the step is not `consequential`, and two consecutive looks at the screen agree on the spot (a page still loading is not clicked). Ink is judged by hue, chroma and brightness, not RGB distance: anti-aliasing keeps a thin letter's hue, and dark teal text on a pale highlight (Google's AI overview) is close to a link's blue in RGB. Black or grey text is never described ("the third black line" means nothing). The kin is read from the step's recording frame at run time (`step["session"]` + `event`), so skills taught before this get it too, while their recording is on disk. The run reports it ("clicking the 1st line of text in its colour and size in that column"). Not handled: an ad or another result type pushed in above the first result is what gets clicked, since it is the first of that kind.
- **A "kin" must look like a line of text** (`visual._looks_like_text`: at least `KIN_MIN_ASPECT` times as wide as tall, and on a plain ground above and below that is not the ink). Found live on a skill that searched in a host Chrome: for another search, a 5-px sliver of a portrait's blue backdrop at the results' column was taken for "the first link" and clicked. Now the run finds no kin there and goes on to the engine or the person, never the picture.
- **The first `/learn` question also invites an explanation in the person's own words** (`learning._answer_goal`). The whole reply is kept as `skill["explanation"]`; each sentence naming a step ("step 6 clicks the first search result") goes on that step as `intent` (shown in the overview as "you said: ..."), and the rest is `done_when`. `Ladder(explanation=)` puts both into the engine's grounding prompt, and a stuck step's question repeats the step's `intent`. It is one question, not a new one, so every scripted lesson in the tests is unchanged.
- **A desktop icon is opened by its launcher, not by its picture** (`computer/launchers.py`, `replay._open_desktop_icon`). Found live on a skill that searched Google in a copied host Chrome: the recorded picture of the icon was mostly xfdesktop's hover tooltip, and at replay time the icon was drawn selected, so step 2 never matched - and `skip` then stopped step 3 because the window it opened was not there. A click or double click recorded on the bare desktop (no window in front, no element) whose expected result is a window W is done by the one `.desktop` launcher (in `~/Desktop` or `~/.local/share/applications`) whose Name is W with its "(Host)"-style tag dropped - never a guess between two - or by raising W when it is open already. A step recorded *in* W while W is not in front raises it or opens it the same way, once, before halting (`_find`). A drag on the bare desktop of at most `DESKTOP_NUDGE_PIXELS` (40) only nudged an icon (XFCE keeps them on a grid): the replay does nothing for it and `/learn` leaves it out (`learning._tidy`, after the burst folding, which still takes a nudge inside a burst of presses). **An app found open, or a kept host app its launcher reconnects to, is in whatever state it was left in**, not the fresh one the recording's next steps were made in: when a later step in that window cannot find its target before any step there has worked, the run's result carries `reopen` and the question offers `restart` (`skill_task.RESTART_RE`): close W with `_NET_CLOSE_WINDOW` (`screen.close_window`, what its close button does - never a kill), wait for it to go, and run again from the step that opens it. Only on a person's word: whatever is open in W goes with it. **A point click after the run typed something else, whose picture and "kin" both miss, asks the person to click it and reply `done`** (`after_change` on the result): measured on a real Google page whose first result was below a large AI overview, scrolling and taking the first thing that looked alike matched a link inside the overview first, so the replay does not scroll-and-guess.
- **A browser window is opened by the browser's own icon, whatever it is called** (`launchers._opens_the_browser`): since the desktops run Chrome the icon is "Google Chrome" while a page's window keeps its canonical "... - Chromium" title, so no name matched and a taught search's first step (double-clicking that icon) fell back to its picture and halted. A launcher whose command is the browser (and not a web app's `--app` window) now opens a browser-titled window; a host app's launcher named for the window still wins. `bench/screen/teach_e2e.py` checks both halves: with the icon covered by the open browser the run uses it, and with the icon gone and the browser closed it stops and asks (20/20).
- **Workflows are similar, not the same: a skill run leaves out steps that dealt with something this run never meets** (`computer/detour.py`, `escalation.Ladder.detour`, `replay._recover`). Found live: a person recorded a Google search, Google showed a CAPTCHA, and they clicked "I'm not a robot", three picture tiles and Verify before the result; replayed with another search Google showed none, and the run halted at "I'm not a robot". When a step's target is not found (a `_Halt` with `missing`), the live screen is compared with the recording's screens *before* that step and before each of the next `MAX_AHEAD` (8) in the same phase - only while the steps between are `skippable` (click/key/scroll/drag, never consequential, typed, by hand, `open` or `manual`). If a later step's screen is clearly closer than this step's own, the steps between are left out and the run goes on there. The comparison is **by where content is, not by pixels**: 16 px cells with edges, overlap with one cell of slack, minus cells busy in every frame (a pixel diff ranked the mostly-white CAPTCHA page *closer* to a white results page, 0.85 vs 0.77; by content 0.43 vs 0.69), and, when OCR is available, the words on each screen minus those typed into the task and those every screen shares; the text may only lower the margin. A margin of `SURE_MARGIN` (0.18) is taken alone; `MIN_MARGIN` (0.08) and up is put to the desktop's engine with the three screens' text (`DETOUR_SYSTEM`), which can also veto a sure one. Measured on the real frames (fixture `agent/tests/fixtures/detour/captcha-search.json`, cells and OCR lines only - the frames themselves are 3 MB and the CAPTCHA page printed the user's IP address, stripped): step 5 -> step 10, margin 0.22 with text, 0.34 by layout alone; the CAPTCHA on screen, a half-solved grid and a results page at the results step all leave everything alone. Only a run with a ladder (`/skill`, mimic) does this - `/replay` still halts as recorded - and a run that left steps out ends `completed_unverified`, never `verified`. Not learned into the skill: each run decides afresh.
- **A point click whose picture and kin both miss can be placed by the engine reading the screen** (`computer/ocr.py`, `Ladder.ground_point`). The recording's frame is OCR'd for the line under the click (and the lines around it); the live screen for its lines; the engine is asked which line plays the same part now (`POINT_SYSTEM`, "the same kind of thing in the same role, not the same words") or 0, and a choice under `GROUND_CONFIDENCE` places nothing. Never for a strict step (approval-gated, optional). **OCR needs `tesseract-ocr`**, now in all three desktop images; without it (a desktop from an older image) both OCR rungs are skipped and detours fall back to layout alone. Tesseract reads Chromium's blue link titles on white as noise at 1x; `ocr._pgm` thresholds to black-on-white (luma < 170) and scales 2x first - measured, every result title read, ~1.3 s per frame on a 6-core host.
- **`click anyway` lets a person release a point click whose picture did not match**, for that run only (`skill_task.ANYWAY_RE`, `_unanchor`; the expanded program's copy of the step loses its `look`, the saved skill keeps it). An open drop-down, a focus ring or a hover state is enough to fail `visual.find`, and a person looking at the screen can say the spot is right; before this the only answers were retry/skip/stop/`use "control"`, none of which could click it.
- **A `NEEDS_APPROVAL:` the model wrote in its own answer is a pause in Decurix only** (`thebot_harness._written_pause`). soul finished that job as `answered` and holds no checkpoint, so the reply sent with `reply: true` resumed nothing and was run as a request of its own: `google "sanmayee is great"` -> "NEEDS_APPROVAL: I want to Google..." -> "proceed" -> "I can't assist with that request". Now the original task is sent again (`reply: false`) with the question and the answer in its `context` (never glued onto the prompt); a pause soul itself holds (`outcome: needs_approval`) is still resumed in soul.
- **A lesson's last question asks for the skill's name** (`learning._confirm`, `learning.rename`). Any reply but a whole-reply yes/no (`KEEP_NAME`/`THROW_AWAY`, anchored: "Save invoice" and "Delete old files" are names) becomes the title, and its free slug the file name; `skill_task._learn_reply` then deletes the draft file kept under the old name. A name given at `/learn ... name="..."` is offered back instead ("I will save it as ..."). The goal (what `mimic.plan` matches) never changes. A plain agent question is chat kind `query` ("Needs your answer"), no longer shown as "Needs your approval" - only `kind: approval` is.
- **The screen is the control plane's page, not noVNC's** (`httpapi/screen.go`, `web/templates/screen.html`). `/desktop/<id>/` renders the viewer itself (for a stopped desktop too, `desktop.Manager.ScreenAccess` reads name + `VNC_PW` off the container); only the WebSocket (`/desktop/<id>/websockify`) and noVNC's own `vnc.html` are still proxied. Why: noVNC's page stopped on its "Credentials" prompt on a black page (the old autoconnect helper looked for `noVNC_password_dlg`, which noVNC 1.6 renamed to `noVNC_credentials_*`), and it loaded 81 files / 763 KB per desktop from websockify's Python server on 1 vCPU. The viewer is two requests (page + the cached bundle), live ~0.3 s after load on a warm desktop, and owns every state as one calm screen: connecting, waking a paused desktop, starting a stopped one when opened, and after a drop waiting up to 20 s for a desktop that comes back on its own (an X session ending restarts the container) before offering Start - it never starts a desktop someone stopped under an open screen. The session bar (name + status dot, the recording ticket toolbar mounted inside it, chat, clipboard, keys, full screen with `navigator.keyboard.lock`) hides itself unless the pointer is at the top edge, a pop-over or the ticket panel is open, or someone is typing in it. Clipboard: a copy in the desktop goes straight to this computer's clipboard on a secure page; Ctrl/Cmd+V hands the desktop this computer's clipboard first (`clipboardPasteFrom`, then the keystroke). Touch: a keyboard button above the taskbar (bottom-left is its Start button) feeds a hidden textarea's `beforeinput` into keysyms. The page holds the VNC password in its script, so it is `no-store` / `no-referrer`; the proxy already hands the raw RFB stream to whoever can load it, so this gives nothing new. `bench/screen/e2e.py` checks all of it against a real desktop (open, bar, clipboard both ways, typing, restart/paused/stopped recovery, phone); `bench/screen/teach_e2e.py` is the record -> `/learn` -> run flow through the viewer.
- **An open screen keeps its desktop awake** (`Server.keepScreenViewed`): `MarkViewed` every `screenViewedEvery` (5 s) for as long as the WebSocket lives. It was touched only when the WebSocket connected, so idle-pause - including the fast pause 15 s after a task ends - froze desktops under a person watching them. The proxy's own auto-unpause now invalidates the cached `List`, or the dashboard and viewer kept saying "paused" about a desktop in use.
- **A restart the control plane did not ask for is reported by the agent that comes back** (`task_context.mark_active`/`take_interrupted`, `watchers._report_interrupted`). A desktop whose X session ends restarts its container on its own (exit 0, `unless-stopped`); the task it was on stayed "running" for good ("Working..." over nothing). The started-and-unfinished task is kept in `~/.decurix/active-task.json` (not `/tmp`, which a restart empties) and reported as an `error` with `interrupted: true`; `queryTextHandler` records it only while `tasks.Store.IsOpen` says the task is still open, so a restart through the API (which already closed it) gets no second note. A request saved while the agent is waiting on a question gets `-reply` in its file stem (`messaging.REPLY_MARK`); one that finds no question waiting (the agent restarted in between) is answered with a note instead of being run as a new request - "keep" used to go to TheBot as a chat message. `ask_for_query` sets `waiting_for_query` before posting the question, not after, so a reply that beats `send_query` back is still a reply.
- **The command watcher cannot die and cannot hang silently.** One pass is `watchers._pass()`; the loop catches `BaseException` (logging can itself fail). The approval store's `flock` waits at most `approval.LOCK_TIMEOUT_SECONDS` (10) and raises `TimeoutError`, which every caller already handles as an `OSError`. `watchers.watchdog` logs every thread's stack and a chat step when a pass has not started in `STALL_SECONDS` (45): a reply once sat unhandled for four minutes with nothing in the log, and the process was gone (container restart) before it could be inspected.
- **End records everything done before it** (`demonstration.py`). The recorder grabbed a full-screen frame on its input thread for every keystroke; on 1 vCPU typing a phrase put it 10-20 s behind, and End (SIGTERM) stopped reading at once - " breeding season" and the Enter after it were lost. Now only the first key of a burst (`KEY_BURST_SECONDS`) captures a frame, SIGTERM sets `stop_requested` and the reader drains what is already on its X connection (bounded by `DRAIN_SECONDS`, even under continuous input) before `stopping`, and `_process` empties the queue before its last flush.
- **`/learn` tidies a demonstration before asking about it** (`learning._tidy`; the recording itself is untouched, `/replay` still does what was recorded). A burst of presses on one spot within `REPEAT_SECONDS` that contains a double-click - clicks, a press that barely moved (a ≤`REPEAT_PIXELS` drag, even one that nudged a desktop icon), more clicks while a slow app starts - becomes that double-click, expecting what the last press produced: replayed as recorded it opened the app three times. Two consecutive typing runs into the same field within `SPLIT_TYPING_SECONDS` become one value (never a secret). The first question says what was tidied. Every click recorded only as a position is then **one grouped question** (`coordinates:s1+s2+...`): `keep`, `manual`, or exceptions like `manual 1, skip 5` / `skip 2 and 4` / `manual 1-2` (`_coordinate_choices`; a number outside the question or a conflict is asked again, twice unclear is `manual` for all). Answers are still stored per step (`coordinates:<id>`), so a lesson drafted under the old one-at-a-time questions resumes and asks only about the rest; a single remaining step is asked the old way. A step a person chose to do by hand reads "you do this by hand: ..." (`step["by_hand"]`), not "a private step". Verified end to end: record a search through the viewer clicking the icon impatiently, `/learn` (every answer back in ~1 s), run the skill with a new value (Chromium shows the new search), and with the browser already covering the icon the run stops rather than clicking blind and `skip` finishes it.
- The base image's `~/Desktop/README` (link to its `readme.md`) and `versionsticker.desktop` are removed by `start_agent_terminal.sh` on every start - only those exact two.
- **A card's pill is a traffic light**: green running and free, yellow (`--busy`) working / recording / needs you / provisioning, red crashed. Crashed is `desktop.Desktop.Crash` (`crashReason`): state `dead`/`restarting`, or exited with a code other than 0/143, or 137 with `OOMKilled` - 0, 143 and a plain 137 are how `Stop` (SIGTERM, then SIGKILL after its timeout) ends one. `Status` stays `stopped` so nothing reading it changes meaning. `/api/desktops/activity` carries `status`/`crash` from the cached `List`, so a card turns red or green without a reload.
- **A desktop's card says what it is doing** (`GET /api/desktops/activity?ids=a,b`, `httpapi/activity.go`; `index.html`'s `pollActivity`, 2.5 s, one request for every card): the request its running turn was opened for and the latest step, read off the chat snapshot so the card can never disagree with the chat; a `/record` turn is a ticket ("Recording: <task>"). The pill reads needs you > recording > working > running, and a finished task's report left open in the rail (`kind` done/error) no longer hides that the desktop is busy again. A ticket also narrates itself in the chat: Record, Stop, Continue and End each emit a step (`record_task`), where it used to say "Ticket open" and then nothing until the first click.
- **A card rendered while its desktop was idle-paused follows the desktop waking up.** idle-pause pauses a desktop seconds after a task ends, and a request wakes it, but the dashboard's pills and "Idle (Paused)" overlay are server-rendered: found end to end, a card read "Paused" through a whole task. `paintPills` treats live activity as proof the desktop is running (working/recording, overlay hidden) and goes back to "paused" when the turn ends.
- **A result check follows a changing value into window titles too** (`learning.CHECK_TEXT`, `replay.unmet`, `skills.expand`). A browser search comes back as a window titled "<what was typed> - Google Search - Chromium"; `_follow_param` only rewrote element names, so a taught search halted at its last step, after the search had worked, waiting for the demonstration's title. `window`/`active_window` checks now hold `{typed_text}` like element checks do. A skill taught before this keeps its literal title check until it is taught again.
- **The demonstration recorder reads the screen once per run of actions, not twice** (`demonstration._flush`, `_look`): it called `core.observe()` and then `core.observe(frame=settled)` and kept only the second. Measured on a 1-vCPU desktop: a click took 10.3 s to reach the chat, the typing after it waited behind that (~15 s), and Stop took 15-20 s to finish; now ~3 s per click and Stop is immediate. What remains is the settle wait (up to `core.SETTLE_SECONDS`) while a page loads: typing followed by Enter on Google reached the chat ~12 s after Enter end to end.
- **A result check that echoes a changing value follows it** (`learning._follow_param`, `replay.fill_name`). What a demonstration typed comes back in what the screen then says ("Saved Initech"); baked in as recorded, every run with another value halted asking whether the result was fine. When a person says a typed value *changes*, any element check whose name contains the demonstration's example becomes `Saved {customer_name}` and `replay.unmet` fills it from the run's values. A placeholder with no value stays literal so it fails rather than passes on something never seen, and `skills.expand` renames it per item for a list parameter, the way it already renames a value check. A value said to stay the same leaves the check alone.
- **A demonstration's typing replaces the field on replay only if the field was empty, and the recorder must not misread its own typing as content.** `demonstration._entry` sets `append` from the element's value in the last settled look at the screen - which is normally taken *after* the typing, so a field that had been empty read as holding exactly what was typed and was recorded `append: true`; every later run then added to whatever the field held (`InitechUmbrella Corp`). A value equal to the typed text now counts as empty-before; a value holding more than the typed text is still an append. Found live, not in the unit tests: the fake recorder never took its look after the typing.
- **A finished recording is a `quiet` callback, not a Query rail note.** `record_task._report` calls `write_final_reply(..., quiet=True)` on success: no file in `querytext/` (its watcher would send it as a note) and `quiet: true` on `POST /api/querytext`, which `queryTextHandler` honours by skipping `QueryNotes.Add` while still closing the task and answering in the chat. Failures (`did not finish`, `nothing in it`, `nothing was recorded`) are still ordinary notes — something went wrong and a person should see it.
- **The ticket toolbar's tab is a drag handle, not just a click target.** Pointer-down on `#decurix-ticket-tab` starts tracking; past `DRAG_THRESHOLD` (6px) it "pins" the toolbar (`decurix-pinned` class, cancelling the default centered `transform`) to an explicit `left`/`top` clamped to the viewport, so it can be moved off whatever it's covering on the desktop underneath. A drag's terminal `pointerup` still fires a `click` on the tab — the same handler that opens/closes the panel — so the click listener checks the `dragged` flag first and swallows that one click rather than also toggling the panel.
- **Every rewrite in the proxy's `ModifyResponse` chain writes UTF-8, but the proxied container's own `Content-Type` never says so.** `rewriteDecurixBranding` (always first) now sets `Content-Type: text/html; charset=utf-8` explicitly. It has to be there and not later in the chain: `injectTicketToolbar` splices its own copy in right before `</body>`, far past a browser's ~1024-byte `<meta charset>` sniffing window, so by the time that text exists in the document the browser has already committed to whatever encoding it guessed for the whole thing. Without the header, a guess other than UTF-8 turns every non-ASCII byte added anywhere in the chain to mojibake — this is what an em dash in the toolbar's own copy needs the header for, not anything wrong with how that string is written in Go.
- **A note written while paused stays paused; whether to continue afterward is the toolbar's call, not `demonstration.note`'s.** `note()` no longer refuses a call while paused (that used to be its only guard on `_running()`'s state) — it writes the note into whatever pause it finds, active or not, and always (re-)pauses after with its own summary as the reason. The toolbar's Reason button pauses *before* opening its text box (not after submitting, like Stop), and only follows a successful submit with an explicit `resume` when its own click is what caused that pause (`reasonAutoPaused`, reset on every path that leaves the box) — never when Reason was opened on top of a pause already in effect, since that pause may be covering exactly what the note is warning about, and auto-continuing would hand it straight back to the recording.
- **Triggers are one page (`/triggers`, `web/templates/triggers.html`), not one page per kind.** A trigger is anything that sends a request without a person pressing Send: a repeating schedule, a one-time run, an email rule - its "New trigger" form is a segmented picker whose JS `kinds` table has one entry per kind (label + `create`), so a new kind is one radio and one entry. It lists schedules, email triggers, mailboxes and the jobs email started; the keep-awake panel sits on top because every kind needs the machine awake. The requests page's compose form offers the same three (repeat / once / "Run when an email arrives"); the list of existing triggers is on the Triggers page only. What both pages share - the email-rule fields and `window.Triggers` (mailbox loading, rule create/test, the list rows) - is `web/templates/triggerparts.html`, parsed only for those two pages (`webui.templatePaths(page, triggerParts)`).
- **A schedule (`internal/schedule`) is a fourth door onto `submitLocked`, set up from the requests page or the Triggers page, never from the chat.** Creating one never sends the request immediately — its first run is the next time the cron expression matches (or, for a one-time run, the future time it was given), same as cron itself never fires the instant a job is added. `Runner.fire` appends `\n\nTIME:{<RFC3339 UTC>}` to the request text on every trigger and always advances the schedule afterward, whether or not the submit itself succeeded — a desktop that is unreachable this minute must not turn every following tick into a retry of that same stale run, and a control-plane outage across several missed occurrences produces one catch-up run on the next tick, not a replayed backlog. Cron fields are matched in UTC regardless of the host's own timezone, and `cron.go` is a small hand-written parser (no external dependency) rather than a library, matching this repo's `modernc.org/sqlite`-over-cgo preference for a static, dependency-light binary. A schedule whose expression can no longer match anything (day 31 in a month field restricted to February, say) disables itself on the next `MarkRun` instead of being checked forever.
- **A one-time schedule (`Schedule.RunOnce`, created by `Store.CreateOnce` with a future run time instead of a cron expression, `cron_expr` left `""`) fires exactly once and then disables itself** — `MarkRun` special-cases `RunOnce` to skip the cron-based "next occurrence" computation entirely (there is no cron expression to recompute from) rather than trying to `Parse("")` and erroring. `createScheduleHandler` (`internal/httpapi/schedules.go`) accepts either `cron` or `run_at` (RFC3339) on the same `/api/schedules/create` endpoint, never both — the requests page's "Repeat on a schedule" and "Run once at a future time" checkboxes are mutually exclusive for the same reason. Re-enabling (`SetEnabled(id, true)`) a paused `RunOnce` schedule that has *not* fired yet keeps its original run time rather than recomputing one (there is nothing to recompute from), which means a run time that passed while paused fires as an immediate catch-up on the next tick, same as a cron schedule that missed occurrences during an outage; re-enabling one that *has* already fired errors, since firing is `RunOnce`'s terminal state and there is no second occurrence to resume into.
- **No automated sender reaches a busy desktop, and none can race a person** (`httpapi/sendlock.go`). A request reaching an agent that waits on a question is taken as the *answer* (`tasks.Plan`, `watchers.command_watcher`): an email's "yes, pay it" must never become a person's approval, nor a schedule's run land as someone's reply. `Server.Submit`/`SubmitTracked` - the doors schedules, DAG nodes, email triggers and `/api/channels/inbound` use - are `submitWhenFree`: under the desktop's **send lock** they check `tasks.Store.Busy` and send, or refuse with a `*DesktopBusyError`, which callers outside httpapi recognise by its `DesktopBusy()` method (they cannot import httpapi) and treat as "try again later": a schedule is held (`Schedule.Waiting`, shown on the Requests page) without advancing, a DAG node is released, an email job goes back to pending with the reason. Every person-initiated send takes the same lock (`submitRequestWithFiles`, and the replay / `/skill`/`/learn` / ticket handlers around their own Busy check), so a check-then-send is atomic against all of them. A person may still send to a busy desktop - that *is* how they reply. Verified live: a second invoice email arriving while the agent waited on a question was held ("Waiting: the agent is waiting for your reply"), and went out as its own task 10 s after the first finished.
- **A mailbox is read by UID, which is what makes sleep safe.** Connecting records UIDVALIDITY and UIDNEXT, so mail already there never fires; each poll reads UIDs above `last_uid` (at most `maxPerPoll`), and `RecordPoll` saves the new position *and* the jobs in one transaction - a crash, a dropped connection mid-poll or a laptop sleeping mid-poll neither loses an email nor queues it twice (`TestAFailedPollNeitherLosesNorRepeatsAnEmail`). A connection is opened per poll, never kept: a socket does not survive a sleep. `Runner.noticeSleep` compares *wall-clock* gaps between ticks (`Round(0)`; the monotonic clock stops while asleep) and polls every mailbox at once on waking. A new UIDVALIDITY rebaselines rather than firing on the whole folder.
- **A From line proves nothing; `verifySender` reads the provider's own verdict.** Only the *topmost* `Authentication-Results` counts (a sender can write any such header into its own email; the provider's is added above it), and for Gmail only one whose authserv-id is `mx.google.com`; it must show `dmarc=pass header.from=<domain>` or `dkim=pass header.i/d=<domain>` for the From domain. `VerifiedOnly` (default on in the page) records an unverified match as `skipped`, and "Send anyway" retries it. Email sent to yourself is usually not verified. Verified live through Dovecot: a spoofed "Acme CEO" invoice (`dmarc=fail`) was skipped while a genuine one ran.
- **The Triggers page (`/triggers`, and `/email`, which now redirects to it) and `/api/mail*` are refused to the desktops** (`httpapi/humansonly.go`, 403). An agent - or a prompt injected into one - must not read someone's inbox headers or add a rule. A container is recognised by address: inside a Docker network desktops use (`desktop.Manager.ContainerNetworks`, cached a minute) and not its gateway - a browser reaches the control plane from loopback (binary on the host) or from the gateway (compose's published port). Verified live under compose: from `desktop_mailbot`, `/email`, `/api/mail` and `rules/create` answer 403 while its own callbacks work, and the host's browser gets 200. Not covered: the released binary on Docker Desktop (macOS/Windows), where a container's call to `host.docker.internal` arrives on loopback like the browser's. `/api/keep-awake` stays open (the host script needs it; it reveals nothing).
- **An email-triggered request writes the email out as plain delimited text and says the task again after it** (`mailtrigger.Render`, `emailStart`/`emailEnd`). Measured on the desktops' own model (qwen2.5-coder:3b, Ollama harness, a real desktop, real email via Dovecot): an `EMAIL:{...}` block like a schedule's `TIME:{...}` was read as a shell variable - `grep ... <<< "$EMAIL"`, against a variable that does not exist, in 3 of 6 runs. The text is marked as the sender's (information, not instructions), `---` in it is broken up so it cannot fake the end marker, and the request after the email keeps a sender's "ignore all previous instructions" from being the last thing the model reads. A request starting with `/` is sent as written.
- **The Ollama loop no longer reports work it never did** (`task_runner.UNRUN_COMMAND_NUDGE`, `UNGROUNDED_DONE_NUDGE`, `TASK_WANTS_CHANGE_RE`, `WRITES_RE`). Found by the email tests on a real desktop: the model replied `HELP: ... COMMAND: echo INV-7001 >> ~/work/invoices.txt DONE: ...`; the parser rightly took the HELP, the plain pushback then got `DONE: The invoice number is INV-7001.`, and the task was recorded done with nothing written (3 of 3). Now a HELP carrying a command is answered by naming that command as not run (the model must send it itself, so every command check still applies; the guessed DONE beside it is not kept), and a DONE is pushed back once when the model proposed a command it never ran, or when the task asks for a change (append/write/save/create/delete/...) and no *successful command that can change something* (`WRITES_RE`: a redirect into a file, `tee`/`cp`/`mv`/`rm`/`mkdir`/`sed -i`, a script) has run - "extracted the number, then said DONE" was the next failure measured. A question is never pushed back, and a second DONE is taken. **Commands deliberately stay in `/bin/sh` (dash)**: running them in bash so the model's `<<<` works made 8-email runs worse (2 and 3 of 8 against 6 of 8) - see the note above `commands.run_command`.
- **In a task that says to append, the Ollama loop never runs a command that would overwrite a non-empty file** (`task_runner.overwrite_target`, `OVERWRITE_NUDGE`). Measured live: asked to append an invoice number, the model wrote `echo "INV-9802" > ~/work/invoices.txt` and the line the previous email's task had appended was gone - the run itself looked fine; the loss showed a task later. Such a command is refused before it runs and the model told to use `>>`; after `MAX_OVERWRITE_NUDGES` (2) the person is asked. It recognises a plain `> file` onto an existing non-empty file only (not `/dev/*`, not `2>`), in both `perform_task` and `continue_after_query`: a net for one measured mistake, not a sandbox.
- **Mailbox passwords are encrypted at rest** (`mailtrigger/secret.go`: AES-256-GCM, key in `DECURIX_DATA_DIR/mail.key`, 0600, created with `O_EXCL`). It keeps the password out of a copied `decurix.db`, not away from someone who can read the whole data directory. A plaintext password (from before the key) is sealed at startup; a key that no longer opens one makes the mailbox "Password needed" rather than failing.
- **Email jobs are sent at most once, and retried only when nothing was sent.** A job is claimed (`pending` -> `sending`, a compare-and-swap) before it is sent, so two dispatchers - the tick and a "Check now" - cannot both send it (`TestTwoDispatchersNeverSendTheSameEmailTwice`). A failed send is retried after 1, 5 and 15 minutes, then failed; a busy refusal is not an attempt. A job left `sending` by a control plane that stopped is marked failed with "check the desktop's chat" (`Store.RecoverInterrupted`), never resent on its own: its task may already have run, and may have consequences.
- **A mailbox whose password is refused is not polled again until a person gives a new one** (`Account.NeedsPassword`, `Runner.due`): repeating a refused login is how an account gets locked. "Check now" still tries once. A mailbox that keeps failing otherwise (network down) is polled at doubling intervals up to 15 minutes. A poll works through up to 500 new emails in batches of 50; a mailbox or rule deleted while a poll runs leaves no jobs behind (`RecordPoll`).
- **Keep-awake is held only while it is wanted, and only stops *idle* sleep.** Lid close, Sleep from the menu and a flat battery still sleep the machine - no application can veto them - and the page says so. It is wanted while a mailbox is polled, an email job waits to be sent, a schedule or DAG cron is pending, or a desktop has a task running or queued (`tasks.Store.Working`) - not for a task waiting on a person, which can wait for days. The host scripts ask with `?holder=script`, which is how the page knows whether anything is actually holding the machine in a container deployment (`State.Script`; it says "Nothing is keeping this computer awake" otherwise). Verified live on this repo's WSL host: `powercfg /requests` lists a SYSTEM request from `powershell.exe` while held and none after release, for the Go helper, `lib/keep-awake.sh` (also against the real compose deployment) and `Keep-Awake.ps1`. A `docker pause` of the control plane for 2m36s stood in for a sleep: on thawing it logged the gap, polled at once, and the email delivered meanwhile was read within a second and ran. Every child of the WSL loop gets `3>&-`: a `sleep` that inherited the helper's pipe kept the request alive 30 s after the loop was killed. The host is on S3 standby, where a SYSTEM request fully blocks idle sleep; on Modern Standby (S0ix) laptops Windows may still drop to standby once the screen is off - not verified.
- **Windows apps run on the host and show in the VM** (`internal/winhost`, `httpapi/hostgui.go`, `desktop/hostapps.go`'s `hostGUILauncher`). Copying a Windows app to a VM writes a launcher that opens `/host-gui/view` in the VM's own Chromium (`--app=`), not a `host-run` that would open the app on the person's own screen. The app itself is started by `bridge.ps1` on a **private Win32 desktop** (`CreateDesktop` + `CreateProcess` with `lpDesktop`): it renders normally but is never on the visible desktop - `FindWindow` from the interactive desktop finds nothing, and a count of the app's windows on it stays where it was (checked for Character Map, Paint, Chrome, Bruno, VS Code). What the viewer shows is **every visible top-level window of the app composited in z-order** (`Native.Compose`: menus, drop-downs, tooltips and dialogs are separate top-level windows, so a single-window capture made them invisible and unclickable), each captured with `PrintWindow(PW_RENDERFULLCONTENT)` and cropped to `DWMWA_EXTENDED_FRAME_BOUNDS` (Windows' invisible resize border captures black; a popup's shadow margin does too, so near-black is drawn transparent over the window beneath); a click is hit-tested against the topmost window at that point. Input is **window messages, always posted** (`WM_LBUTTONDOWN/UP`, `WM_CHAR`, `WM_KEYDOWN` to the innermost child under the point, keyboard to `GetGUIThreadInfo`'s focus window of the topmost window) - never `SendInput`, which only reaches the visible desktop, and never `SendMessage`, which does not return until the app has handled the message: a click that opens a modal dialog runs a nested message loop and froze the whole session.
- **Modifier keys need the input queue's key-state table, not just messages.** `GetKeyState` (how an app learns Ctrl/Shift/Alt is held) reflects hardware input only, so a posted `WM_KEYDOWN` carries no modifiers and Ctrl+S or Shift+click do nothing. `WithModifiers` runs the event on a helper thread that has called `SetThreadDesktop(private desktop)` and `AttachThreadInput` to the app's thread, sets the shared key-state with `SetKeyboardState`, posts the messages, and holds ~80-150 ms so the app dequeues them under that state (a toolkit that handles shortcuts in its message loop, like WinForms, only sees posted messages). Verified by the test app's own `KeyDown`/`MouseDown` handlers reporting `ctrl`/`shift`. The viewer sends the browser's `keyCode` (it is the Windows virtual-key code) with `mods` (`c`/`s`/`a`) for named keys and any Ctrl/Alt shortcut, and the text a key produces (`type`) otherwise - AltGr arrives as Ctrl+Alt and is treated as text.
- **The clipboard is the person's own** (it belongs to the window station, which the private desktop shares). So *paste* (the viewer's `paste` event) is typed into the app line by line (`Session.Paste`) and never touches the host clipboard, and *copy* (Ctrl+C/X in the viewer, `Session.Copy`, only vk 67/88) presses the key in the app and reads the host clipboard only if `GetClipboardSequenceNumber` changed, then puts back what was there when it was plain text or empty. An app's own Copy menu item is not noticed. The VM's clipboard is set with `execCommand('copy')` on a hidden textarea, because `navigator.clipboard` needs a secure origin and the viewer is plain http.
- **What can and cannot be hidden.** A packaged app is either a full-trust desktop program that ships in a package (Notepad, Paint, Terminal: `EntryPoint="Windows.FullTrustApplication"` plus an execution alias) - `Resolve-Packaged` finds the alias and runs it like any program - or a **true UWP app (Calculator, Camera), which Windows only activates on the visible desktop and which cannot be hidden**; that is refused with an explanation rather than leaking a window. `shell:AppsFolder\{known-folder GUID}\x.exe` resolves to its real path, and a classic app listed as `shell:AppsFolder\<AppUserModelID>` (Chrome, Brave, Discord) is found through its Start menu shortcut by the name `Get-StartApps` gives it. A Chromium browser or Electron app (recognised by `icudtl.dat` beside the executable or one folder down, plus a name list) would hand a second launch to the copy already running - on the person's own desktop - so it gets a **persistent private profile** (`%LOCALAPPDATA%\Decurix\hidden-profiles\<desktop>-<app>`): a sign-in made inside the hidden app survives, and the person's own profile (locked by the running copy) is never what is shown. Browsers also get `--no-first-run --no-default-browser-check`: on a private desktop nobody can answer a modal first-run or "make me your default" dialog, and a modal dialog swallows the keyboard for the whole window (which read as "typing does not work" until the composited frame showed the dialog). A `.lnk` is resolved to its target first. Not supported, and why: **audio** (the desktop containers have no sound device and noVNC carries none, so there is nowhere in a VM to play it), file drag-and-drop, an app that ignores synthetic window messages, and Notepad-style apps show whatever state they restore (Windows 11 Notepad reopens its saved tabs).
- **The helper launches the app with a clean environment** (`CleanEnvironment`): `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS` are stripped. A helper started from inside an Electron program (or VS Code's extension host, whose `ELECTRON_RUN_AS_NODE=1` reaches Windows through WSL interop) otherwise hands it to the app, and an Electron app started that way runs as plain Node, rejects its own `--user-data-dir` and exits with code 9 - which looked exactly like "VS Code cannot run on a private desktop" until the environment was checked. The working directory defaults to the app's own folder for the same family of reasons (a `\\wsl.localhost\` UNC cwd breaks Electron apps).
- **Access to the host-gui API is by signed launch token, and never through a tunnel** (`winhost.Token`, `httpapi.hostGUIAuthorised`, `hostGUIDirectOnly`). The API lets a caller see and drive a program on the host, and it is on the unauthenticated primary listener, so a session id (`<desktop>-<app>`, guessable) is not enough: each launcher carries `token=` = HMAC-SHA256 over the session id, the program and its arguments, keyed by a secret in `DECURIX_DATA_DIR/hostgui.key` (0600, so launchers survive restarts). `start` validates the token against exactly what it launches (a launcher edited to run something else has no valid token), remembers it for that session, and every later request (frame, stream, input, stop) must present it. Requests carrying `Cf-Connecting-Ip`/`Cf-Ray`/`X-Forwarded-*`/`Forwarded`/`X-Real-Ip` are refused: the viewer runs in a window of the VM and reaches the control plane directly, never through the tunnel. `desktop.Manager.HostGUISecret` and `httpapi.Server.HostGUISecret` are both set by `main` from `winhost.LoadSecret`. Launchers written before tokens existed stop working; copy the apps again.
- - **"Is this Windows" (`desktop.IsWSLOrWindows`) never rests on a `/mnt/c` folder existing.** `docker-compose.yaml` always creates that mount, and the Linux scripts mount the host's own `/` there, so on a Mac or an ordinary Linux machine it is an empty folder or a Linux root, and the check used to say Windows: the control plane then ran the Windows Start Menu query (whose last resort starts a container) and tried to warm a helper it can never have. The kernel (`/proc/version`, `WSLENV`) decides, or a drive that really holds a `Windows` folder (`hasWindowsInstall`). `queryWindowsStartApps` returns nothing at all off Windows.
- **Native Windows has no bash and no POSIX modes.** `createHostCmd` runs a signed command as the program itself (no `bash -c`, which on a WSL install would run it inside Linux), and `/api/host-bridge/open` uses `rundll32 url.dll,FileProtocolHandler` so no shell parses the link's `&`. `hostbridge open` waits `hostOpenWait` for the opener to fail and reports it (`startAndWatch`); it used to answer success for a control plane in a container with no `xdg-open`, which is the ordinary Mac/Linux compose case: opening a link on the host from a desktop is honestly unavailable there. `hostgui.key`'s 0600 does nothing on Windows; its folder's per-user ACL is what protects it.
- **Bridge gateways are bound on Linux only** (`cmd/decurix/main.go`). On Docker Desktop (macOS, Windows) the bridge gateway addresses exist only inside its VM, so binding them fails, and `host.docker.internal` already reaches a loopback listener.
- **`scripts/mac/lib/host-mounts.sh` points compose's host mounts at real folders.** Compose defaults `DECURIX_HOST_HOME`/`DECURIX_HOST_MNT_C` to `/home` and `/mnt/c`, which a Mac does not have and Docker Desktop for Mac does not share; the Mac scripts export the user's home and an empty folder. It has no `.ps1` twin: `scripts/windows/` leaves the defaults, which Docker Desktop for Windows resolves inside its own WSL VM - not checked on a real Docker Desktop for Windows.
- Tests that stand bash in for the Windows helper, or run the bash launchers a VM would run, skip on Windows (`requireBash`); the native-Windows behavior has its own tests in `internal/httpapi/hostgui_windows_test.go`, built only for Windows.
**Apps can be copied into a desktop that already exists**: `POST /api/desktops/host-apps/copy` (`id`, `host_apps` comma-separated IDs from `/api/host-apps/detect`) runs the same `MigrateHostApps` creation does - to add apps later, and to overwrite launchers an older build wrote. There is no dashboard control for it yet; the dashboard's app picker lives in the create dialog.
- **The copy-apps picker lists only what a VM can really show, and says how** (`HostAppItem.Mode`, `desktop.vetHostApps`). A listed entry is one of: `web` (a service whose web version opens in the VM's own Chromium - the description says you sign in there), `host_gui` (a Windows program the host has *confirmed* it can run hidden), `data` (credentials/settings copied as files) or `helper` (the host-run bridge). Everything else is left out rather than offered with a caveat: Linux and macOS apps (their only launcher was `host-run`, which opens on the host's own screen, and the DISPLAY-tunnelling that would draw it in the VM was never verified), the chrome/edge/firefox/vscode/youtube defs (same launcher, plus profiles the VM has no app to use - Windows browsers encrypt cookies with DPAPI), and audio/video apps (`needsSound`: the VMs have no sound device). `host_gui` is decided by the bridge itself: `winhost.Check` sends `check <target> <args>`, which runs the very `Resolve-Launch` a real `launch` runs but starts nothing, so the list and a launch cannot disagree. It refuses what is known to fail or to leak a window onto the visible desktop: true UWP apps, shell-only targets, folders, non-programs (`.msc`, `.cpl`), WSLg shortcuts (the "(Ubuntu)" entries - Windows shows those itself), programs whose manifest asks for administrator rights (the prompt cannot be answered on a hidden desktop) and shell/script-host stubs (`control.exe`, `cscript.exe`...). Measured on a real host: 110 of 174 Start-menu apps refused. **"Confirmed" means the host can start it, not that its window is proven to render** - that would need launching every app, and a scan must not start Outlook. Verdicts are cached per target until a forced rescan (a full check took ~8-25 s), and `MigrateHostApps` only honours IDs the current scan offered. Without a checker (`desktop.SetHostAppChecker`, installed by `httpapi.NewServer`), or when the helper fails, no Windows program is offered: an app that could not be asked about is not one that can be promised.
- **A copied app that only opens a local web page opens that page in the VM's own browser** (`winhost.Manager.LocalPage`, `desktop.localPageLauncher`, `vmPageURL`). The bridge already recognised such a launcher (a small program whose text holds `--app=http://localhost:PORT`, e.g. the the web app launcher) and ran its browser on the hidden desktop - where the worker got a picture: no fields, coordinate-only demonstrations, a password field not known to be one. `check` now reports the launcher (a seventh field; `launchr` carries it too, so a fast launch still starts the server), and the VM launcher tries the page at `host.docker.internal:PORT` first, in an app window of the VM's Chrome; when nothing answers it asks `/api/host-gui/start` for the app (whose launcher starts the server) and waits; only a page the VM still cannot reach is shown through the viewer. The picker says "A web app: opens in the VM's browser". Works when the server listens beyond the host's loopback (a WSL container, as the web app is); a Windows process bound to 127.0.0.1 only falls back to the viewer.
- **A host app's controls are real elements in the VM, read from Windows' accessibility tree, with a vision model as the fallback** (`bridge.ps1`'s `Tree`/`ReadControls`, `winhost.Controls`, `httpapi/hostcontrols.go`, `hostgui.html`'s `#ax`). The viewer was a canvas, so to a worker every Windows program was a picture. The helper's `tree` walks the app's visible windows with UI Automation on a thread attached to the private desktop (it works there: Character Map, Excel, a hidden Edge measured) in one cached request (~0.5 s), maps each control into the picture's pixels by the rule `Compose` cuts the picture by (`Geometry`, worked out afresh: with nobody watching nothing is composed), and answers at once with the last read while the next runs beside the input, saying whether that read began after the latest input (`fresh`). Chromium (browsers, Electron) is started with `--force-renderer-accessibility`, or its page is four title-bar buttons. A browser page's root Document says it is read-only and is left out; a RichEdit field is a Document that says nothing and is a field (Character Map's "Search for"). **When an app reports no usable control** (`Controls.Actionable`: not text, images or the title bar's buttons) and a hosted brain reads pictures, `sessionControls` has it list the controls of the current picture (`visionSystem`, at most every `visionEvery` and only for a changed picture; boxes checked and cut to the picture, a password field's value dropped, no `focused`), and the viewer says "Controls read from the picture by the vision model". Verified live in a worker through a dev control plane: Character Map driven by name (a checkbox, a field typed into, a button), and an owner-drawn WinForms form with no accessibility at all filled and saved through the vision read. Not done: Excel cells are `gridcell`s to click, not fields to type into; a vision read costs a model call per changed picture while a viewer is open.
