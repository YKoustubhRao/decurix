# Computer use: one action layer, every engine

Every desktop can see and act on its own screen through `decurix_agent/computer`. The layer lives in the desktop, below the engines, so no engine that acts through it skips the approval gate or the audit trail. Input sent to the screen some other way (a program the worker runs) does not pass the gate: see [gate-boundary.md](gate-boundary.md), "What this does not cover". The three calls:

```
observe()  screenshot (python3-xlib) + windows + elements: AT-SPI for GTK/XFCE/LibreOffice,
           the Chrome DevTools Protocol for Chromium (its AX tree + one DOMSnapshot for boxes)
act()      observe -> resolve the target (ref | role+name | path | x,y) -> approval.check
           -> do it (CDP input / AT-SPI action or caret / xdotool) -> wait for the screen to
           settle -> observe -> compare -> audit.record
verify()   observe again, compare with the last observation, optionally check text/element
```

How the engine reaches it:

- The **MCP server** (`computer/mcp_server.py`) that gave Claude Code these as tools went with the claude harness (removed 2026-11-07).
- **TheBot** uses the `gui` shell command through its operator's `COMMAND:` loop and, on a local brain, reads the element list **as text only**. A 3B model on a CPU cannot read pixels; `elements.render` is budgeted to `DECURIX_GUI_TEXT_CHARS` (3500 local) because the operator shows a local model at most 4000 characters of any command's output. TheBot's `atomizer.Triage` routes screen work (`wantsScreen`: a surface *and* an action) to the operator, ahead of the web skill that would otherwise fetch any URL itself.

`gui` exit codes are a contract harnesses read: 0 done, 1 could not, **3 NEEDS_APPROVAL (nothing happened)**, 4 verify failed.

Approval travels this way: `approval.check` stops a click on a Send/Pay/Buy/Publish-like control (or Enter in a messaging page), records a *pending* approval and returns NEEDS_APPROVAL. The harness pauses deterministically — `operator.screenApprovalReason` → `NeedsApproval` checkpoint. The human's reply reaches `watchers.command_watcher`, which calls `approval.resolve_reply` **before** the harness sees it. On a desktop with a gate (`approval.remote()`), the pending action, the grants and the reading live in the gate process, and `resolve_reply` only asks the gate what it did with the signed copy of that reply ([gate-boundary.md](gate-boundary.md)); the rules below are what the gate applies. The reply is read **once** (`approval.reading`) as `yes` / `if` (yes only once something holds) / `no` / `unclear` (a question back, something else): code settles only a reply that plainly says yes or no (every word a plain yes, or a plain no); any other reply, in the person's own words, slang or language, is the model's reading; with no model it is `unclear`, and the action waits to be asked again, never guessed. A reply settles the pending action only when the question it answered put that action to the person (`approval.asked_about`: the gate's own line for it, as `request_text` words it); a reply to another question - an older card, a question of the engine's own - settles nothing and withdraws the pending action, so its repeat is asked in the gate's words. Only `yes` becomes a one-shot grant fingerprinted to that action: its kind, control, window, the page's address and the filled fields beside it (`_what_it_acts_on`) - the same Send in another chat, or the same form with another amount, is another action. The model's readings are cached by (action, reply), never by the reply alone. A grant lasts at most 15 minutes (`GRANT_SECONDS`). On a desktop with no gate only, the person's latest reply to a question of the engine's own (`note_reply`) is the yes of the next gated action when that question named the control by its whole label (`names_control`) and the model, reading the reply against that question and that exact action, says yes (`reading(..., plain=False)`: code never settles this one, and with no model the gate asks); a shared word is not enough (review 2026-11-02). In the gate, a reply is only ever the yes of the request it answered, worded by the gate. TheBot's written pause gets no waiver either: a yes to it is that one action's, and every other action is still asked. The reading is kept (`last_reading`) and sent to soul with the reply (`approvalReading` → `scheduler.Request.Reading` → `RunContext.HumanReading`): soul acts on it rather than on its own word list (`safety.IsApproval` stands in only when none came), and tells the model what the reply decided (`notApprovedNote`: a condition to meet first, a question to answer with HELP:, or a no). Every other host path that acts on an approval reply (`long_task`, `skill_task`, `replay_task`, `lessons`) uses the same reading (`says_yes`). The repeated action consumes the grant. A new task calls `approval.reset()`. A reply to a question with set answers - "reply `retry`, `skip` or `stop`", "reply `done` if it is done", a step left to do by hand, the held catastrophic command - goes through the same rule in `approval.read_choice(reply, question, choices, plain)`: code decides only a reply that is, whole, one of a choice's plain phrases; any other reply is read once by the model, which returns the choice and the rest of their words as the instruction - kept, never dropped (a replay that cannot follow it hands the run to the model with them); with no model it is `unclear`. No word list anchored at a reply's first word decides anything (audit, 2026-10-24).

Besides Send/Pay/Buy/Publish, the gate asks before the step that leads straight into a committing act ("proceed / continue / go to checkout / payment / file / submit") and before deleting a named thing ("Delete user", "Delete permanently"); a bare "Delete" or "Submit" is left to the dialog that confirms it (`confirms_permanently`) and to the pre-save checks below. **What a press does is one decision, `approval.press_effect`** ("asks" / "commits" / nothing), used by the gate, the pre-save checks (`commits`) and healing alike. A label is read as words (`label_words`: symbols, emoji and arrows dropped, `&`/`+`/`/` read as "and") and its consequential phrases are matched at *every* word (`consequential`; review 2026-11-02, second round: "Confirm & Pay", "🔒 Pay", "Securely pay", "Continue to payment", "Authorize", "Pay now →" all passed a first-word match). A word that is only read there is not a commit (`_only_reads`): a read or navigation word before it ("View post", "Track transfer"), nothing but nouns of looking after it ("Payment history", "Pay slip", "Transfer history"), or a creation word before a kind of record ("New Purchase Invoice"); words that destroy or end something are never read so ("Delete history" asks). Anything else holding such a word asks: unsure is asked.

**Which presses ask, since D-04 (review 2026-11-03, later the same day).** On a button, a committing word anywhere in the label asks. The vocabularies that read a label as a name (`_READ_AFTER`, `_ATTRIBUTES`, `_ALSO_NOUNS`, `_OF_WORDS`, `_READ_BEFORE`, `_CREATE_BEFORE`, `_NAMED_AFTER`) now apply only to controls that go somewhere: a link, a tab, an item of a navigation menu (`approval.goes_somewhere`, from role and container). Structure still exempts arranging ("Send to back"), a form's own part ("Delete row"), `DOCUMENT_NAME` and options. So a button labelled like "Stock Transfer" now asks, and ERP screens ask more often; the examples of names in the next paragraph hold only for links, tabs and menu items.

**What asks, what only names (review 2026-11-03).** A committing word is a noun, not an act, after a preposition ("Get Items From Purchase Order"), before only attribute nouns ("Post Date", "Buy Price"), as a kind of record after a word that is not a joiner or adverb ("Stock Transfer"), and when a create word opens a new record ("Make Purchase Receipt"); "Delete row" and its kin remove a part of the form being filled and are the form's own Save's to commit. "File GSTR-1", "Approve", "E-sign", "Sign" (not "Sign in"), "Release funds", "Submit order", "Cash out" and the plain send/pay/buy verbs of a few other languages ask. **Return or Space on a focused button, and a click at a point that resolved to no element, are presses for the gate** (`core._pressed_by_key`, `core._unresolved_press`: the page's own answer at the point, else the text under it; a spot nothing names is asked; plain page is not). **Keys that move the keyboard and then press, in one call** (`gui key Tab Return`, `shift+Tab space`, `Down Enter` in a list, `Escape Return`, a chord like `Tab+Return`) are asked whenever the screen holds a control a press would commit, a dialog that cannot be taken back, or a chat (`approval.press_after_focus_move`, `_holds_consequential`; `core.act` hands the gate the screen's controls as `context["controls"]`, and a caller that gives none is taken to hold one). Where Tab lands is not predicted (tab order, scripts, focus traps): pressed alone after the moving keys, the Return is judged against the control that then has the keyboard. Keys that stay in a text field (letters, Backspace, the caret keys, ctrl+a/c/v/x/z) are not a move, and Return is not one in a field of lines. **Money moved, a trade, a release, a sign-off (recheck 2026-11-03):** "Bank Transfer" (a noun of money before transfer: `_MONEY_NOUNS`), "Disburse", "Sell", "Liquidate", "Refund", "Release", "Execute trade", "Place trade", "Sign off" ask; "Stock Transfer", "New Bank Transfer", "Bank Transfer details", "Release notes", "Sell price", "Sign off date" do not. A replay saves with no ask when its values are the request's, its sources' or the person's demonstration (`core.TAUGHT_VALUES`); a value in no source is refused.

**A yes is bound to every field the press sends** (`approval.check(..., sends=)`, `sent_digest`, `core._what_it_sends`): each filled field of the window, a checked box among them, and the fields of the `<form>` a click or an Enter submits, hashed into the grant's fingerprint; a secret field counts as filled, never by its value. The person is shown every filled field up to 3000 characters (`_what_it_acts_on`). Review 2026-11-02: the fingerprint held the first three fields shown, so an amount in the fourth could change under a yes. **Enter that submits a form is a press on its submit control** (`core._enter_submits`): Enter in a page's single-line field whose `<form>` has a submit control, or a typed new line there, is put to the gate as a click on that control (`approval.check(..., require=)`), whatever the form's size - Enter in a one-field form whose button says "Pay now" is asked for; a search form's is not.

**A password goes unasked only to a site the request names** (`approval.site_known`). On a gated desktop the gate answers from its own signed copy of the request, for the action's task only ([gate-boundary.md](gate-boundary.md), "What the control plane tells the gate"), never from the task file in `/tmp` or the skills and recordings, which the worker's user can write. A desktop with no gate also counts what a person taught or recorded on it. A host is named by itself or by a domain it is under, on label boundaries. A site that is only an address (an IP literal) is one endpoint, its scheme, address and port (a default port when none is written), and is named only when the text writes a URL with exactly that endpoint (`http://192.168.1.20:8080/login`). An address mentioned as data ("the server 10.0.0.5") names no site, and a password into another port of the same address asks. Before 2026-11-04 an address could never be named, so every password typed into one was asked.

**A script a worker wrote for itself** (`playbooks.py`) runs with no approval - in its proof and in `tool_task` - so it runs unattended only shut off (`script_sandbox.py`): inside a network namespace of its own (bubblewrap's `--unshare-all` where it works, else `unshare --user --map-root-user --net --ipc --pid --fork --kill-child`, so nothing the script started outlives it; the desktop's seccomp profile allows the namespaces and denies `mount`, so in practice it is `unshare`), with an environment built from nothing (no `DISPLAY`, bus, agent token, proxy or control-plane address; HOME, `DECURIX_DIR` and TMPDIR in a scratch folder), in a scratch copy of the work folder; what it writes there is copied back into the work folder only (regular files, never through a link, never outside it), and what it drafts with `office email` is drafted for real afterwards by the agent. Whether a namespace holds is probed (a child must fail to reach a port the agent listens on). Where none holds, no learned script is written (`_distil` spends no model call) and none runs unattended: `tool_task` hands the request to the engine and says why. Review 2026-11-02: the static reading (`playbooks._sound`/`ungated_effect`) alone was walked past with `/usr/bin/curl`, `"cu" + "rl"`, aliased imports, subprocess lists; it stays as an early refusal (now also of a program by its path and of anything naming `~/.decurix`, the display, the agent's token or its ports), never as the boundary. **Not a full boundary:** with `unshare` alone the script still sees the filesystem as the worker's user does - the network and the display's environment are gone, but a write by absolute path into `~/.decurix`, or X11 spoken by hand over `/tmp/.X11-unix`, is stopped only by the early refusal. The real fix is a separate Linux user for what runs unattended, as the gate already has.

Soul's own questions are read the same way (`replies.go`, `replyAccepts`): where a value comes from, whether a web page may be trusted, whether work looked at is done. A plain yes or no is settled in code; any other reply is the model's reading on a hosted brain (accepts / corrects / points / refuses / asks); only "accepts" vouches. A reply that does not vouch for the values it was asked about is never their source by naming them back.

Every action — done, failed, or paused — is recorded twice: as an event of the task's recording on the desktop's persistent volume (see [recordings.md](recordings.md)), and as a chat step via `progress.emit_action` → `POST /api/agent/events` with `action` + half-size `before_png`/`after_png` → `conversation.AppendActionStep` + `stepimages.Store`. The chat renders those steps with Before/After thumbnails. Both copies go through `privacy.py` first.

**Secrets withholding fails closed (2026-11-02).** `privacy.withhold_known` (and `withhold_spoken_secrets`, `credential_in`, `known_secret_in`) never let a text through because something went wrong: an error, or a secrets file that is there but cannot be read, gives `privacy.HELD_BACK` ("[held back: this text could not be checked for secrets]") in place of the whole text; a secret that could not be written to the secrets file is still withheld in that process. Every sender does the same when privacy itself cannot be loaded: the chat/task-record note and its fallback (`messaging.send_query`), memory (`messaging.remember`), each progress line and each step's `action` (`progress._post`), a handoff, an Outbox draft (refused instead). Besides the request's own secrets (hashes) and named credentials, secrets are withheld by shape (`GENERIC_SECRETS`): a password/passcode/secret/token/api-key label with `:`/`=` and a value (`DB_PASSWORD=`, `client_secret:`), "the password is X" when X has a digit or a mark, an OTP/verification code or CVV with its digits, a bearer/basic token, a private-key block, a password in a URL's authority and a secret-named URL parameter, and a long high-entropy token next to key/secret/token words, "Password X" with no colon when X has a digit or a mark, a card number (Luhn-valid and written in fours or named as a card's, never after "A/c", "Order", "Ref", "Total"...), and a PIN (`PIN_VALUE`, digits only). A value runs to a space or a quote ("password: Abc;123xyz" goes whole). Never a figure, a date, a GSTIN, a PAN, an invoice or account number, a postal PIN code, or a usage line's "tokens: 12,345". **PINs (2026-11-03):** a card's, ATM's, UPI, login or bank PIN, an M-PIN/T-PIN, and 4-5 digits after a bare "PIN" are secrets, remembered from a request and withheld everywhere. Six digits (first 1-9) after a bare "PIN" may be a postal code: beside a place's name or an address's words ("Bengaluru PIN 560001", "Udupi, PIN: 576104") they are kept; beside a sign-in's words ("user ram, PIN: 482193", "my PIN is") they are a secret; with neither they are withheld where written and never remembered, so a postal code never hides a matching total elsewhere. "PIN code"/"Pincode" is always an address, and a word ("Pin: Mumbai 400001") is never a PIN. The control plane's copy (`internal/withhold`) follows the same rules, and `withhold.Reply` withholds a bare answer ("552901") to a question that asked for a secret. A web `lookup` is a third party: a question holding an identifier (GSTIN, PAN, IFSC, account, Aadhaar, record number), an amount, a company's name or a party the worker keeps facts about is refused - only the generic question goes.

**Rows into a spreadsheet, verbatim text, windows from before (2026-10-19).**
- `gui type CELLREF "a\tb\nc\td"` - text with Tabs or new lines aimed at a sheet's cell (or typed with no target while the active window's sheet has the focused cell) is a block: `core._type_sheet_block` enters it row by row (the Name Box to each row's first cell, Tab between cells, Enter), and `_read_back_block` reads every cell back through `atspi.sheet_cell_text`. A cell that does not show what was typed (AutoInput's completion, a number read as a date) or a formula showing an error (`#NAME?`, `Err:502`) is listed and the command exits 4. Anywhere else a Tab is still refused (one field per typing: a Tab carries the rest into the next form field). A host app in a viewer is not covered.
- `gui type [TARGET] -` reads the text verbatim from stdin (a heredoc), for quotes the shell would otherwise eat (`"=IF(D2=""x"",1,0)"` is bash concatenation).
- `core._task_windows` records the windows open at a task's first look. The engine's `gui type`/`gui key` with no target is refused while the window in front is one of those that the task has not worked in (`_adopt_front`: an action by ref or point, `gui open`, `gui front`). Replays and a person's actions are not asked. Leftover documents are not closed.
- Why an action is slow: each `gui` command is a new process that looks twice (AT-SPI walk of the app plus up to 60x26 sheet cells read one D-Bus call at a time, `WALK_SECONDS` 6 each), waits for the screen to settle (up to 4 s), saves screenshots and posts an audit and chat step - 10-20 s on the 8 GB host. Bulk entry is one command for that reason; the per-action cost itself is unchanged.
- In a host-app viewer (real Excel), a block typed with no target goes where the app's cursor is - each cell's text, Tab, Enter after each row - and is read back from the viewer's cell list (`_type_relayed_block`, `_read_back_relayed`); the host clipboard is never used. Keys with no target and no window in front are refused (`_nothing_in_front`: Alt+F4 there asks to log out). Not verified live.
- `gui type D1 ...`: an A1-style coordinate is a cell target (refs are `e12`). In a sheet read over AT-SPI it is made from a listed cell (`_sheet_cell_named`); in a host-app viewer the cursor is put there by the viewer's Name Box and Enter (`_goto_relayed_cell`), and the read-back is anchored at it.

## The gui daemon (L1, 2026-11-07)

A `gui` command used to start Python and import the screen stack every time (p50 2.3 s; docs/lightweight.md). Now `agent/gui` runs a thin client (`computer/gui_client.py`, `python3 -I -S`, interpreter modules only) that hands the command to one **gui daemon** per desktop (`computer/daemon.py`), in the worker's user, which lives while it is used.

- **Its lifetime (2026-11-07).** Nothing starts it at boot. A command that finds no daemon starts one (`gui_client.start_daemon`) and runs in its own process as before, never waiting for it: `python3 -m decurix_agent.computer.daemon` with that command's environment (the `PYTHONPATH` `gui` set; the daemon drops secret-looking variables at once, as before), in `/`, stdin `/dev/null`, its own lines to the startup log (`/tmp/decurix-startup.log`, only when it is a regular file of the user's; `DECURIX_GUI_DAEMON_LOG`), detached: a second fork and its own session (soul's KillTree of the command's group does not reach it), none of the command's descriptors (the caller's pipes end with the command). It exits after `DECURIX_GUI_DAEMON_IDLE_MINUTES` (10; 0 never) with no command - counted from the last command's end, never while one runs - and takes its socket with it, so an idle desktop carries none (about 30 MB). One per user: before it imports anything it takes the folder's lock (`daemon.claim`, `daemon.lock`, flock), and a client starts none while the lock is held; two commands that both found none start one daemon, the second exits at once (exit 3). A stale daemon (its code changed) exits after its last command and the next command starts one on the new code. Started by an engine's command it runs at that command's niceness (10); a command asking a higher priority is refused (code 6) and runs in its own process, since a process can raise its niceness but never lower it. `DECURIX_GUI_DAEMON_AUTOSTART=0` starts none (the daemon tests run their own); `DECURIX_GUI_DAEMON=require` starts one and waits up to 60 s for it to serve (the latency bench). Broker mode is unchanged: the screen broker is not started on demand, takes no lock and never exits for idleness, and `gui` there never starts a daemon.

- **What it is.** A fork server on `/tmp/decurix-gui-<uid>/gui.sock` (folder mode 700, the user's own; the client checks owner and mode before trusting it, and the daemon checks the peer's uid). It has imported what `gui` imports, the Xlib modules and the AT-SPI typelib (no connection made; if an import starts a thread it starts again without gi). The client passes its stdin, stdout, stderr and working folder as descriptors, with argv, its whole environment, umask and niceness; the daemon forks, and the child takes all of that on (dup2, fchdir, `os.environb`, fresh stdio with a new process's buffering) and runs `python3 -m decurix_agent.computer` in itself. The exit code, or the signal that ended the child, is the client's; output goes straight to the caller's pipes.
- **What it keeps.** Imports only. Nothing one command does reaches the next: each is a fresh fork of a process that has only imported. Connections (DevTools, the accessibility bus, X) are opened by each child as before, never shared. Commands run side by side as separate processes always could (up to 8; one more runs in-process). Module-level settings read at import: the daemon finds them in the imported sources (`daemon.import_time_reads`), and a command whose value differs gets the agent's modules imported again in its child. `DECURIX_GUI_TEXT_CHARS`, which TheBot sets per command, is now read per command (`cli.text_budget`). A command whose interpreter settings differ (`PYTHON*`, `LANG`, `LC_*`, `HOME`) is refused and runs in-process; a module file changed on disk (a dev loop's `docker cp`) refuses everything and the daemon exits when its last command ends; the next command starts one on the new code.
- **The fallback.** No daemon, a folder that is not the user's own, no answer within 2 s, a refusal, or a daemon gone before the command started: the client execs `python3 -m decurix_agent.computer` exactly as `gui` did. The client commits only after the daemon's accept (`A`, then its `G`), so a command is never run twice; once the child said it started (`S`), a daemon that vanished without an exit code is reported as "what it did was not seen", exit 1, never run again. A stdin that is a terminal (a person typing `gui type -`) always runs in-process: a forked child is not in the terminal's foreground group. `DECURIX_GUI_DAEMON=off` forces in-process; `=require` exits 125 instead of falling back (the latency bench, `bench/resources/gui_latency.py`).
- **It holds no yes.** The daemon makes no decision: a consequential action asks the gate over the gate's own socket from the command's child, as a `gui` process does, and nothing of a grant lives in the daemon (it never calls the gate). It holds nothing secret: secret-looking variables (`*_TOKEN`, `*_KEY`, passwords) are dropped from its own environment by starting it again without them, a command's environment is that command's child's only, and it logs only its own events (to the startup log), never arguments, environment or output. It writes nothing else: the socket and its folder in `/tmp`.
- **Killing.** A client killed by its caller (soul's KillTree) closes its socket; the daemon kills the child's process group at once, as the group kill would have. Ctrl-C at the client is passed on as SIGINT to the child's group.
- **Broker mode** (`DECURIX_SCREEN_USER=1`, off by default): the same daemon serves as the screen broker in the screen user's uid, on `/run/decurix-screen/gui.sock`, for the worker's uid only, and `gui` never falls back in-process. What it takes of a caller, how screenshots reach the caller, the DevTools relay and the launch helper: gate-boundary.md, "Next: the input broker".
- Started without `-I`, as `gui` itself runs, so what it imported is what a `gui` process would have (user site-packages included); a `decurix_agent` folder in the caller's working folder no longer shadows the installed one, since the daemon imported before any command.

## Waits: an almost empty page, and downloads (2026-11-07)

Measured live: `gui observe` on a small page took 3.7 s, 3.0 s of it one fixed pause; `gui click` 2.4 s, 1.0 s of it the download check.

- **An almost empty page** (fewer than `EMPTY_PAGE_ELEMENTS` = 6 browser elements) is looked at again before it is reported, because a page that draws itself after it "loaded" was reported as empty and the engine reloaded a record it had just saved (`cli.settled_look`). With the browser able to say how the page is (`cdp.drawing_state`: `document.readyState`, `data-decurix-busy` or any `aria-busy`, and how long ago its last fetched resource arrived), it is looked at every 0.4 s within the old budget (5 x 3 s) and reported as soon as it is decidedly drawn: it grew past 6 elements; or it held the same shape (role and name of each element) for `EMPTY_PAGE_STEADY` = 1.2 s while the page is complete, not busy, fetched nothing within those 1.2 s and shows no progress bar; or it held its shape for 3 s whatever the browser says (the old rule). An empty page never settles by holding still. When the browser cannot be asked at all, the look is exactly the old one (a 3 s pause, two looks with the same shape). What the window cannot see: a request still on its way with nothing on the page saying so; past 1.2 s of such silence the page is taken as drawn (the old rule took it so past 3 s).
- **Downloads** (`core._may_download`, `_downloads_note`). Only the browser downloads: a click, double-click or key whose target is not in it - by the element's source and application, the topmost window under a point, or the window in front for keys; unknown counts as the browser - takes no snapshot of the download folder and waits for nothing. In the browser, "nothing new within a second means nothing downloaded" counts its second from the action, so it runs while the screen settles and is looked at; an action that showed no visible result at all (the click whose answer may still be coming from a slow server) gets its second after the look, as before. A file the browser has begun (`.crdownload`, `.part`) is still waited for up to 6 s, and a held "Unconfirmed" download is still said.

## App guides: shipped and learned

`app_skills/<name>/SKILL.md` ships guides to well-known apps (front matter `applies-to` names the app; a task that names it, or `gui open`s it, gets the guide; `gui guide NAME` prints one). A desktop also learns guides to apps nobody wrote one for: the engine works the app out (the screen, `lookup "APP how to ..."` on the web) and, once its work there is right, writes what it found with `gui guide --learn NAME --applies-to "words" --description "..."`, the guide on stdin. `app_skills.learn` holds it under `~/.decurix/app_skills/.pending/<task>/<stage>/`; `app_skills.promote` makes it a guide only when the work it came from is checked done: the stage of a planned run that wrote it (`long_task` when that stage completes), or the whole task (`skill_task._playbook` on a DONE verdict; `long_task.final_report` when every stage passed). Pending guides of tasks that never ended done are dropped after 7 days. A guide is refused when it holds a credential, an e-mail address or a run of 8+ digits (it is how the app works, never a value), and a learned guide never replaces a shipped one (the same name is kept as `<name>-notes`, shown beside it). A learned guide is rendered as "learned on this desktop ... where the screen differs, the screen is right"; re-learning keeps the previous version as `SKILL.prev.md`.

## Enter in a web form

`gui type REF "...\n"` and `gui key enter` hold the Enter back when it would submit a form that still has empty fields (an `<input>`, not a search box, in a `<form>` with a submit control): the text is typed, nothing is submitted, and the operator is told to move on with Tab or a click and to press the form's own submit button when everything is filled (`cdp.ENTER_SUBMITS`). An Enter that would submit a form is also a press on its submit control for the approval gate, whatever the form's size (`core._enter_submits`, above).

## Number fields and saving a form

A number field (`<input type=number>`) is set as a whole value and read back. A click on its up/down arrows, Up/Down while it has the keyboard, and the wheel over it would step its value: the first two press nothing, the wheel scrolls the page from beside it. Before a form with three or more filled fields is sent by a click on its submit control, `gui click` lists what it holds and presses nothing; `gui click REF --checked` sends it when nothing changed since the list.

The pre-save checks (a record entered twice, a placeholder, an invented or unsourced value, the declared record's ledger, and that listing) run for every action an engine takes that commits what a form or page holds, whichever way it is pressed (`core._commit_check`, review 2026-11-02): a click or double-click - by ref, name, `--see` or the act tool (its `checked: true` is `--checked`) - on a `<form>`'s submit control or on any control whose label says it saves, submits, posts, files, sends, pays or deletes (`approval.commits`), a CDP element or an AT-SPI one; a control with no `<form>` (an application drawn with divs, a desktop dialog) is checked against the filled fields of its window, secrets and file names left out. Enter in a form's single-line field that would submit it (and `gui type REF "...
"`, with the typed text counted) is checked too, and a full form is never sent by an Enter: its submit control lists it. Ctrl+S on a web page runs the checks without the listing. A right-click commits nothing. The listing's confirmation is noted per task (`core._form_check_file`, the task's id in the note's name and in the note): a form listed in one task is never sent by a `--checked` click in the next.

**Whose values the form check judges (2026-11-04).** The unsourced check (`core._unsourced_fields`) judges only the values this task's tools typed or chose exactly (`core._entered_fields`, from `evidence.entered`). The filler check (`filler.invented`) judges every field except a value the application itself showed in that field before the worker put anything there (`core._not_the_apps`, compared by `values.same_value`, so a reformatted or re-cased value does not dodge it). What the application filled in itself is never judged as invented. A recording that cannot be read makes the check not made.

**Replays go through the same checks and the gate (review 2026-11-02, second round).** Every step of a replay - `/replay`, a taught skill's run, `gui do` - is acted with `check_form="replay"`: what never goes (a record entered twice, a placeholder, a value the declared record does not hold) halts it; a value no source of today's request holds and the demonstration did not give is refused (as for an engine); a full form of sourced values saves with no listing and no ask (review 2026-11-03: asking at every save trained approval without reading) - the approval gate still asks at pay/send/file/sign. A step counts as verified only when its result was not already on the screen before it acted (`replay._shown_by_step`, against `core.act`'s `before`; a value it was to leave in a field counts). A run that did not see every result (`completed_unverified`) is not done for an engine: `gui replay`/`gui do` exit 4 with "NOT CHECKED", the MCP run tools return an error, and `skills.note_run` counts only a verified run. A step whose action happened before something went wrong (`ActedError`: typed text that did not hold, a connection that broke; a pressed cell whose field never appeared) is never healed, retried or resumed as if it had not: one that commits is `reconciliation_required`, any other halts there with the step counted as run. A `gui do` that stopped part way notes where (`skill_engine._note_stopped`, per task): the next run of that skill for the request carries on from the stop or is refused - never from step 1 again - and one whose step may have taken effect is not run up to that step at all. A tab that crashed mid-action (`BrokenPipeError`, any `OSError` from its connection) is a failed action, audited like any other, and `gui` exits 1 (it exited 0 with no audit step). A committing or gated AT-SPI control that is no longer the widget looked at (`atspi.resolve` checks its role, own name and process) is not clicked where it was drawn.

A ref no longer on the screen is re-bound to a control drawn anew only within the same window and document - the same role and name, the same group and title, the same page address - and only when one element fits (`core._gone` keeps where each gone ref was, `elements._same_named`); otherwise the engine is told to observe again.

## The record ledger: declare, check, read back

A record the work enters (an entry, a voucher, a party, an order) is declared before it is typed: `gui record KEY --from FILE [--scope "entity or period"] --fields -` with a JSON object of the form's own field labels to the document's values on stdin (`computer/records.py`). Every value must stand in the source document - as a number in any formatting, a date in any format, or its words - or on a screen the task read, in the request or in the person's words; one that stands nowhere refuses the whole declaration with the field named. Before the form is saved (`_form_check`), its fields are matched to the declared ones by label words and compared by meaning: a field holding another value stops the click ("No. holds '1' where the record says '1188'"); a declared field the form does not name, or a filled field the record does not cover, is said beside the listing; when at least half the declared values match and none differs, the save goes through on one click with no listing. The scope's words must show in the window title or the page at the save, or the click is stopped once. After a save the page is read back and each declared value marked seen or absent; `gui records` lists the ledger, the reviewer is shown it as a table (soul `record_ledger.go`, with "declared and never saved" and "saved but not shown" as points of its own), and the final judge sees it among what was observed. Parties are resolved by identifier before a record names them: `gui select REF "name" --id IDENTIFIER` (`computer/resolve.py`).

What the final check holds against the saved records is one function, `ledger_checks.findings`, called on every route that can report a task done: the general gate, a taught skill's read-back (`_succeed`), a planned run's final report (and, advisory, after each stage), a replay. It finds a field the task set on a saved form that no declaration covers; more new records saved than declared ones ("a record was made that no declaration covers"); one record saved twice, by the number in its own number field, with or without a declaration (`core.saved_twice`); an entry picked from an application's list into a form the task saved that nothing given backs (`records.picks`, `records.pick_backed`); and each JUDGEMENTS item the report marks `| not backed`. A pick is backed in one of these ways:
- an identifier match: the action's record says `resolved_by: "identifier"`. The summary's words never count;
- words that pick the option out among the entries the list offered (`records.option_backed`). Every word of the option that no other entry has must be given: a figure only with its sign, a single letter only next to another of the option's words. These words may come from the request, from the organisation's knowledge, or from the person's word as the control plane recorded it (`person_record.py`): their replies in the task, confirmed by judgement id and text hash, and their judgements on the skill being run;
- a request's file that states the option for that field: beside the field's label, or in its table column (`records.option_beside_label`);
- a person's kept answer about that field in that application. It is a control-plane learned row (`field_answer`), checked against the text of the judgement it came from, and is kept only at a final report (`ledger_checks.keep_answers`).

Nothing the worker's own user can write backs a pick: not `<task>.said`, not the skill file, and not a local answers file. With no control-plane read, the person's word backs nothing (H-PY-18). A list's filter, pager or sort order is no pick: only the selects into a form whose save was answered count. A declaration may add fields to a record the task saved already (read back off the page looked at last), which lets the undeclared ones go.

## Workbook updates: what the tool refuses and says

`office update` on a workbook (`tools/office.py update_workbook`) decides in code what a model would otherwise get wrong one run in ten (all found live 2026-10-26): an edit that would empty a cell holding text (a label, a heading, a name) is refused with the cells named unless the spec says `"clear_text": true`, since a block made like the earlier ones keeps their labels; a `copy_rows` whose range stops short of its block (the next row has two or more cells filled, or a figure or formula) is refused naming that row, unless `"partial_block": true`; a date cell (its own format, or the filled cell's above when new) takes a year-first text date and writes the date itself, and refuses a bare number (a serial worked out in the head); and the update's result names every filled cell it wrote over (`replaced 2 filled cell(s): SALES!D25 453 -> 452, ...`), which the soul reads to forget a value written over (`noteReplaced`), so the document whose figures are gone is a coverage gap again.

A code of digits declared for a record is the document's only whole: `3306` for a bill written `VAI-3306` is refused naming the whole token (`records.written_whole`), because the pre-save check would otherwise be walked around by declaring the record again with the part. The other way round too: an identifier (a value with a digit in it) stands in a text only as a whole token (`records.stands_in`) - `INV-1234` is not seen in `INV-12345`. Which declared record a form is, is found by its key standing in the form's values, or by the key's number (`B9` → `9`) in the record's own number field - the one declared field holding the key or its number, found on the form by its label (`records._key_number_on_form`); the same digits in any other field (`Qty 9`) bind nothing, and a record with no such field, or two, is not bound by its number.

## Filling a Word document

`office update DOC.docx SPEC` with `{"replace": {"{{FULL_NAME}}": "Ananya Deshpande", ...}, "output_path": "letter.docx"}` fills a document or template in one command - body, tables, text boxes, headers and footers, also where Word split a placeholder across runs, keeping the formatting - and lists any placeholder still left. A filled document that still holds a placeholder fails the final check. It is never done by clicking Find & Replace on the screen.

**Reading an approval with no model (F-02).** `approval.reading` decides in code only a reply that is, whole, a plain yes or a plain no.
