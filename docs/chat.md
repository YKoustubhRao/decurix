# One chat, every harness

`/view/<id>` (the dashboard's **Chat** button) renders `web/templates/desktop.html`, which is the chat and nothing else — no embedded screen, identical for all three harnesses. On a running desktop it has **Clear chat**, a paperclip (or drop/paste) for files, and a **This is a secret** toggle. Files go to the desktop's `~/work/inbox/<id>/` before the request is handed over and are named in the request under "Files attached to this request, saved on this desktop:" (at most 10 files, 25 MB each, 64 MB in all; `httpapi/attachments.go`). A desktop that is not running has no dead end there: a paused one's page offers **Wake** and a stopped (or crashed) one's **Start**, the card's own routes (`/api/desktops/unpause`, `/api/desktops/start`), and the chat loads once it runs; the page polls `/api/desktops/status`, so a desktop woken or started elsewhere opens its chat without a click. One still being made says so and offers nothing. (The page reads the desktop through `Manager.Get`, which takes Docker's `Running` flag, true for a paused container too, so a paused desktop usually shows its chat at once, and a request sent there wakes it.)

A desktop's screen is a separate page, `/desktop/<id>/`, opened in its own tab from the dashboard's open-in-a-new-tab button. It is the control plane's own page (`screen.html`, `screenViewerHandler` in `screen.go`) with its own copy of noVNC's core (`/static/novnc/rfb-1.6.0.js`), not noVNC's page proxied from the desktop. So it opens even when the desktop is paused or stopped, and wakes or starts it. Only its WebSocket (`/desktop/<id>/websockify`) goes to the desktop. The ticket toolbar ([recordings.md](recordings.md)) and the resource-alert popup are spliced into it as server-owned markup. It reads `resize=scale` and `view_only=1` from its URL and has its own touch keyboard. noVNC's own page is still reachable at `/desktop/<id>/vnc.html`; there `rewriteDesktopHTML` swaps noVNC's branding for Decurix's, splices in the same toolbar, and adds the touch keyboard and pinch-zoom (`mobileViewerEnhancements`) only when the URL carries `?ui=touch`. The dashboard and the recordings page still put `?ui=touch` on the screen URL; `screen.html` ignores it.

Nothing in the chat page branches on which engine is running, because every harness is addressed and reports back the same way:

```
human types in the chat
  → POST /api/desktops/send        → tasks.Plan (new task / reply / retry → a task ID)
                                   → httpapi.deliverRequest (a gated desktop's gate is told first)
                                     → desktop.Manager.SendRequest(RequestBody{content, task_id,
                                       secret, execution_id, ...}) → :8081
                                     → COMMAND_DIR/<stem>[-reply].<task id>.txt → watchers.py
                                     → task_context.start(id) → harness.py → engine
                                   → recordDelivered: tasks.CommitReply + conversation.AppendUserRequest
                                     (a reply also resolves its note: querynotes.ResolveAnswered)

the agent works
  → progress.emit(line) / emit_action(line, action, before, after)
      → POST /api/agent/events {task_id} → conversation.AppendTaskStep
                                         → tasks.AddStep (the record)
                                         → stepimages (an action's before/after screenshots,
                                           served at /api/desktops/step-image?id=)

the agent finishes, or needs a human
  → messaging.write_final_reply / ask_for_query(kind) → POST /api/querytext
        {task_id, kind: final|error|query|approval, checked, engine, model,
         input_tokens, output_tokens, cached_input_tokens, cost_usd, secret, gate}
      → tasks.RecordOutcomeExec (done/error closes the execution; query/approval opens
                                 an intervention the next human request replies to)
      → querynotes.Add          (not for done: the Queries page keeps questions,
                                 approvals and failures, the whole formatted note)
      → conversation.AppendAgentReply (the chat shows only the agent's own words;
                                 AppendAgentNote for a still_working receipt)

the human judges the answer
  → POST /api/tasks/verdict (chat's Correct/Wrong, or the task page) → tasks.SetVerdict
                                                                    → conversation.SetVerdict
```

A verdict is a person's: it is stored with who gave it, and one with no person behind it (a desktop's own call) gets 403. Tapping the verdict already given takes it back. Step screenshots live in the control plane's SQLite (`internal/stepimages`, JPEG, 1 GB in all, oldest dropped first); the full-size frames stay in the desktop's recordings.

**Reading a task back.** Every dashboard card has a task dropdown (the desktop's newest 50 tasks, newest first, polled with the rest of the card from `GET /api/desktops/overview` every few seconds, so a task just sent appears without a reload) and a **Trace** button opening `/tasks/<id>/trace`: the full record in the site chrome - the request, each attempt with its engine, model, timing, tokens and cost, and every step in order with its timestamp and kind (command, output, screen, note), the questions asked and the answers given, and the final report. Long steps fold to their first line. `/tasks/<id>/trace.txt` is the same as plain text (`webui.TraceText`), behind the page's **Copy as text**, **Download .txt** and **Plain text** buttons, so a run can be shared as one file. When run records are kept, an ended attempt also has **Download the run record** (`/api/runs/<id>/bundle`, [trajectory.md](trajectory.md)). Both routes read the task store only and are served on both listeners, like `/tasks/<id>`. What they show is what the control plane recorded: a step's text is cut at `maxStepTextBytes` (2 KB) when it arrives at `/api/agent/events`, so a command's long output is in the trace only as far as the agent reported it.

The chat page holds no transcript of its own: it renders whatever snapshot the control plane last sent over `GET /api/desktops/chat/stream` (SSE, whole snapshots rather than deltas, so a reconnect is self-healing), falling back to polling `GET /api/desktops/chat`. The thread lives in memory and is written through to SQLite; it keeps the newest 200 entries and 400 live steps (`conversation` `maxEntries`/`maxSteps`), since the task records are the durable history. That is what makes one desktop's conversation the same on a laptop, on a phone through the tunnel, and in a second window — and why a desktop's agent is genuinely *central* to it, rather than one chat box per browser.

Replying to a blocked agent is just sending it another request: `watchers.command_watcher` routes a request arriving while `state.waiting_for_query` is set to `continue_after_query` instead of starting a new task. So the chat, the Queries page's reply box (`/dashboard`; the Desktops page's "Needs you" rail links each note's **Reply**, beside **Resolve**, to that note's card there: `/dashboard?note=<id>#req-<id>`, which scrolls to it, lights it and puts the cursor in its reply box, or says it was answered or resolved already) and the Requests page are three doors into one conversation. **A reply names the question it answers:** `messaging.save_request` marks a request as the reply only when its `task_id` is the waiting task's (the control plane sends the paused task's ID, after checking the note is the desktop's newest open one); a request with no ID or another task's is no answer, and `watchers.answer_waiting` refuses to settle a question - an approval above all - from a file not marked as its reply. Such a message is never dropped in silence (a long request may have read it as the answer): the person is told it was not taken as the answer, and the open question is put to them again in its own words, so their answer comes back as its reply (`watchers._not_the_reply`). And `:8081` itself serves only the control plane: every route but `GET /health` needs `Authorization: Bearer <token>` (`DECURIX_AGENT_TOKEN`), and a desktop created without a token refuses them all with 401 "recreate it" (fails closed). Any request a browser made (an `Origin` or `Sec-Fetch-*` header, a DNS-name Host) or a write whose body is not JSON is refused before the token is checked (`http_api.refusal`). The worker's own programs cannot read the token either: it is in none of their environments, and the agent and soul that hold it are non-dumpable ([gate-boundary.md](gate-boundary.md), "The agent token's two holders").

While a long request runs as a planned run ([long-requests.md](long-requests.md)), every message that arrives - a reply or a new request - is read by `long_task.take_message` first: an approval's yes or no still goes straight to the gate, an answer resumes only the stage that asked, a change to the task is receipted and folded in, and an unrelated request waits for the run as before.

## Outcomes, secrets and approvals (review 2026-11-03)

**One outcome model.** Every page shows a task's outcome from one function, `tasks.DisplayOutcome(status, checked)`: `done_checked` ("Done"), `done_unchecked` ("Done, not checked", amber), `needs_you`, `failed`, `stopped`, `running` and `queued`. A nil `checked` (the desktop said nothing) is not checked. A status this build does not know is shown as it is, never as a success. The finished feed says "finished its task, not checked" for an unchecked done (`tasks.FinishedPhrase`). The task CSV has a new last column, `outcome`.

**An outcome names the task it ends.** A report for a task that is not open on that desktop (it ended, or is not its) gets **409** from `/api/querytext` and is shown nowhere. The agent's resend loop treats any 4xx as refused and lets the kept outcome go; a 5xx is tried again. Only a report with no task ID uses the "oldest live execution" fallback. A late step stays on its own task inside the 10 s window, then is dropped.

**How the agent reports.**
- A stop is reported `kind="error"`, `checked=False`, with text starting "Stopped, as you said". It is never `kind="final"`, which the control plane records as completed. This holds for replay stops, TheBot's needs-input after a stop, a task called off at its question (`watchers._called_off`) and `skill_task`'s stops.
- When the final gate itself raises, the report goes out `checked=False` with "Not checked - the final check itself failed ..." as its first line (`messaging.write_final_reply`).
- `/workflow list` is `gated=True` (not checked).

**Putting a file back.** When the final check finds that a run changed a file the person gave it and the original copy was kept, the report's line for that file ends with "to put the original back, send `/restore <id>`" (the file name too when several are offered). `/restore <id> [file ...]` is a chat command (`skill_task.parse_restore`): it reads the offer by its id, never the words of a message, writes the kept copy back, and reports it done only when the restored bytes' SHA-256 equals the kept copy's. The worker's version is kept beside it as `(changed by worker)`. A file the person changed after the run is not overwritten without a yes to its own question ([learning-and-verification.md](learning-and-verification.md)).

**Secrets rest on data, not a word list.** A query sent with `secret: true` has its reply kept as `[secret withheld]` in the task store, the chat, the send response and the concierge; the reply still reaches the desktop as typed. The agent sets the flag only from structure: a replay stopped on a step the recorder kept private, a taught run asking for a parameter the skill marks secret, or a secret-field target (`messaging.send_query`/`ask_for_query` `secret=`). It then remembers the reply as a secret and never keeps it as a lesson. A person's "This is a secret" toggle (desktop chat, Queries page reply box) does the same. `withhold.Text` is a fail-safe backstop only, and may grow only where withholding too much is harmless. Model API keys and Cloudflare tokens are never stored unsealed: without the key file, saving refuses with a reason.

**What the desktop keeps of a secret (C14, phase 2).** The control plane decides once, before delivery, whether the records keep a message withheld (`tasks.StoredForm`), and tells the desktop `secret: true` exactly then. On the desktop, the command file's handled copy (`.done`), the task file's `.request` copy and `active-task.json` hold the withheld form; a message marked secret is withheld whole. A job handed to soul carries the task's secret values as `secrets`, data beside the prompt and never in it, and soul withholds them from what it writes. The approval gate gets its own signed copy of the values ([gate-boundary.md](gate-boundary.md)).

**Approvals in the chat.** The desktop chat's `seen_at` is frozen at the first keystroke of a draft (`draftSeen` in `desktop.html`), so a "yes" typed while a newer question arrives does not answer it. Approve and Deny buttons, bound to the note id, appear under the newest approval only, and only when it is the desktop's newest open question and its approval gate worded it (the gate's words are shown first, then the worker's). A typed yes is still taken under `draftSeen`'s rule. The concierge shows Approve/Deny only when the newest open question is a gate-worded approval (`/api/concierge/answer` with `note_id`); otherwise it says "Answer on its card". A bare ok, sure, go or yes never answers an approval in the concierge. The skills page's Workflows section has no approve control: a stage's go-ahead is the approval question in chat, which the gate decides, and the proposed-stage box says "It asks in chat before it starts this stage. Reply there." (owner decision O-6 kept the typed yes, with these limits).
