# Learning with the brain; never an unseen success

Three rules, from the person running this: while a worker is learning its range of tasks it leans on the brain, and less once a task runs smoothly; a lesson must be strong enough that a recording plus a good Q&A lets it do real, varied workflows; and it may ask, or say it failed, but must **never** report success for a task that failed.

- **Maturity (`experience.note_verdict` / `clean_streak` / `stage`).** Every run of a skill records how it ended: `mode` (model or replay), `ok`, `checked_by` (screen, model, person) and `helped` (a person stepped in, the model took over a replay, or the check sent the model back once). A skill is `apprentice` until `TRUST_AFTER` runs in a row succeeded, were checked, and needed no help (`DECURIX_SKILL_TRUST_RUNS`, default 3; `0` trusts from the start - replay-only benches), then `trusted`. One failure or rescue and it is learning again. A person's answer is help, except a reply that approves the plan of the work exactly as it was put (`skill_task._plan_approved_as_is`, read by `approval.read_choice`): every run puts its plan first, and counting a routine yes as help kept every skill an apprentice for good (2026-10-31). A reply that adds anything to the plan is help. `skills.summary`'s `health` carries `stage` / `clean_runs`.
- **Learning = the engine does it, guided by the skill** (`skill_task._by_model`, when `_engine_can_drive`: TheBot on a hosted brain, or the Office engine). The request goes to the engine as `Do the task you were taught, "<title>" (skill <name>) with ...` (a mimicked request goes as the person typed it), and `guidance.py` puts `_procedure` into its model's context: what the task is, the person's words and every Q&A answer, rules, corrections from earlier runs, this run's values with what each means, the steps, and how to work - `gui skill NAME --look N` (the screen step N was done on, the pressed spot ringed in red, left as the command's picture so a vision brain sees it), `gui do NAME --from N` for stretches that match, one item at a time for a list, and never DONE for what the screen does not show. TheBot's triage sends that request to the operator (`taughtTaskRe`: found live, it was a "question" for the tool-less chat skill, which answered as if it had done the task). **Trusted = replay**, and a replay that gets stuck is handed to the model before a person (`_execute` -> `_by_model(from_step=...)`, once per run; a step that ran but whose result did not show is marked so the model never repeats it blindly).
- **No unseen success (`verify.py`, `skill_task._finish` / `_gate` / `check_unchecked`, `messaging.set_final_gate`).** A replay whose every step's result showed is a success by the screen (in apprentice stage, with a model, it is also judged). Anything else - `completed_unverified` from `/skill`, mimic or `/replay`, any "done" an engine reports for a taught task, and any engine task that acted on the screen (`_did_screen_work`: its task recording has an action) - is judged: the model sees the screen now, the demonstration's final screen, the criteria, and `evidence.observed()` (the task's recorded actions and what tools read off the screen - `gui ask` notes its answers - because the final screen shows only the end of a list). Only `done` with confidence >= 0.8 is done; `not_done` sends the model back once with what the check saw; anything else asks the person ("I cannot confirm this is done ... reply `done`, `retry`, or say what is wrong"). Their words are kept as a `correction` every later run reads. Without a model the person is asked. Pure chat and shell answers are not gated. `write_final_reply(..., checked=True)` marks a report that went through the gate; a gate that throws still sends the report, marked "Not checked". Found live: after a person's "yes", the engine's first attempt reported both questions answered without asking either - the check (`not_done`, 0.99) sent it back, and the second attempt was verified.
- **The lesson (`study.py`).** With a hosted model, `/learn` first studies the demonstration: steps with windows, typed values and expected results, the person's notes, and up to `MAX_PICTURES` screens (the start, each change of window, the end). It writes an `understanding` (summary, step purposes, what each input is and whether it varies, done_when, incidental steps, rules) and up to `MAX_QUESTIONS` questions it could not work out (decisions, repetition, preconditions, consequential steps). The goal question shows the understanding and asks for corrections; the model's questions come next, one at a time (`study:<id>`, before the rule-based ones); each answer is folded in by `absorb`, which may ask one follow-up (at most `MAX_FOLLOW_UPS` per lesson) and drops waiting questions the answers already settle (`settled`). The value question says what the model thinks each value is, and the last question shows the whole procedure; a reply of more than `MAX_NAME_WORDS` words there is a correction, not a name. Only a bare `stop`/`cancel` abandons a lesson ("stop and tell me" is an answer). The person's answers are kept word for word in `dialogue` and read by every later run - the model's rule list is its own merged rewording. Verified live on the ChatGPT recording: it understood the task from the screens alone, took "a list, one by one, wait for each answer, report them all", dropped a question already answered only after this fix, and later runs asked each question separately and were checked done.
- **Not done / not verified.** The Office engine gets the guidance text but `gui skill --look`'s picture only reaches a TheBot operator (its shell tool attaches none); `bench/learn_documents` passes end to end on Azure with the model driving new skills (2026-09-30, after the grounding, spelling, report and list fixes; a `gui skill` run line now shows a list as `ITEM 1; ITEM 2; ...` and the operator contract says a list takes every item in one run - an engine read a two-line PO and entered the first line, twice); `bench/backoffice` was not re-run; `bench/screen/teach_e2e.py` needs a desktop with no hosted brain or `DECURIX_SKILL_TRUST_RUNS=0`, and was not re-run. The approval gate stops ChatGPT's "Send message" like any Send: a skill that sends prompts through a chat UI asks for a yes per prompt; `gui ask` (a URL, no Send) does not.
- **Formulas without stored results (2026-10-19).** Before the final gate reads what a task wrote, `produced.store_results` stores LibreOffice's results in each workbook (.xlsx/.xlsm) whose formulas have none (`office.calculate_workbook`, the same `_store_results` `office create/update` use; formulas, charts and styles kept). One that still has none is `not_done` with no model asked (`skill_task._gate`, `tool_task`). `office.formulas_without_results` reads this from the sheet XML: an empty-text result (`t="str"`, empty `<v>`) is a result. `office read` names the fault ("Formulas without stored results ... office calculate FILE") instead of only showing values it calculated on a copy - found live, a script-written workbook passed its read-back that way with every price blank in the file.
- **Typed totals and the saved file (2026-10-19).** A workbook's Total row of typed numbers that equal the sums above them is `not_done` in code when the request asked for formulas (`produced.formulas_asked`), and only noted in the report otherwise (`produced.typed_totals`). When the request names files and the task saved them, `verify.judge(deliverables=...)` is told those saved files decide that part: an unsaved change still on the screen, or a mistake the action log shows and the file no longer has, is a note, not `not_done`.
- **Facts of the saved file before any model (2026-10-19).** `_gate` checks in code: a requested file that is nowhere (`missing_requested`), a picture's size against its source and the size asked (`image_findings`), a .docx's page breaks and typed `\f` (`document_findings`, `office.docx_structure`). A request that names files is always gated (the early return no longer skips it). A file on the person's computer that cannot be read is asked about (`unread_host`), never passed. The judge treats a report whose own evidence contradicts the request as not_done.
- The code-decided checks of the files a task made are one function, `produced.file_facts`, read by the final gate (`skill_task._gate`), a planned stage's check (`long_task.code_problems`) and a proven tool's (`tool_task`); add a new fact there, not in one route.
- **What the file holds, row by row (2026-10-19).** `produced.file_facts` also decides from the saved workbook: a column filled down a table that stops short of it or a Total that sums less (`gaps`), typed numbers among a column's formulas when formulas were asked for and a Total split over two rows when a Total row was asked for (`layout`). The judge is shown the last four rows of every workbook cell by cell. A worker's own sum agreeing with what it typed proves nothing about the rows it never typed.

- **Readiness before permission.** [Readiness](readiness.md) adds owner-reviewed offline artifact evaluations, independent saved-file evidence and scoped grants in the control plane. A skill's `trusted` experience remains execution economy; it cannot enable a responsibility. Practice is excluded from production autonomy.
- **Formatting is read back, and a highlight that is nowhere is not done (2026-10-20).** `office read` of a workbook says per sheet: the filter range, each conditional-format rule (range, rule, the fill or font it applies, colour named with its hex), the rows each fill colour is on (runs: `red FF0000 fill on rows 2, 5, 9-11`) and each column's number format (`office.sheet_formatting`). When the request asks for rows or cells to be filled or highlighted (`produced.HIGHLIGHT_ASKED`) and no workbook the task made has any conditional format or any fill below its first row, the final check (`skill_task._gate`) and a planned stage's checks say not done with no model asked (`produced.missing_highlight`). Whether the right rows carry it is left to the check that reads the file: no condition is evaluated in code.
- **A figure given as a source's own must be the source's (2026-10-20).** A result line "Closing balance per bank statement" ("Opening balance per X", "Balance as per X", "Total per X") is compared in code with what X states (`sources.py`, a `FileFacts.source_mismatch` of `produced.file_facts`, so the final gate and a planned stage both get it): only when the label names exactly one of the request's input files (its name's words and the words the request puts beside it) and that file plainly states the figure (its Balance column's last line, a row labelled Closing/Opening balance or Total). A difference is not done with no model asked. For balance work the judge is also shown what each input states (`sources.evidence`), and its rules say a figure "per" a source that contradicts it is not done. The operator's rules say to compare a figure the work arrives at with an input that states it before reporting.

## The person's files stay as they were

On a desktop with a shared folder, `source_guard.take` notes and copies the folder's files when a task starts. At the final gate (and a planned stage's check, and a script tool's), a file the request gives (attached, named, or in a folder it names: `source_guard.given`) that was there before and changed without the request asking for it is put back from its copy and the result is "not done", saying "The task changed your file X, which should have stayed as it was; I put the original back". Such a file is a source, never checked as an output (`is_source`). Any other file of the shared folder is the person's own business (they, or another worker, may change it meanwhile): never judged, never put back (2026-10-21).
- **The judge sees the whole task, and looks closer when it needs to (2026-10-21).** `verify.judge` keeps up to `MAX_TASK_CHARS` (20,000) of the task it is given - a planned stage's check puts the person's binding answers, the system's read-back, the code checks' evidence and the other stages' context after the instruction, and the old 1,500-character cut dropped them. A judge that is unsure only because a part of a file was not shown names up to `MAX_LOOK` words to find (`"look"`); the caller's `look_up` (`produced.lines_with`: each file's first lines and every line holding a term) is shown and the judge decides once more - once only.
