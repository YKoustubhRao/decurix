# Learning with the brain; never an unseen success

Three rules, from the person running this: while a worker is learning its range of tasks it leans on the brain, and less once a task runs smoothly; a lesson must be strong enough that a recording plus a good Q&A lets it do real, varied workflows; and it may ask, or say it failed, but must **never** report success for a task that failed.

- **Maturity (`experience.note_verdict` / `clean_streak` / `stage`).** Every run of a skill records how it ended: `mode` (model or replay), `ok`, `checked_by` (screen, model, person) and `helped` (a person stepped in, the model took over a replay, or the check sent the model back once). A skill is `apprentice` until `TRUST_AFTER` runs in a row succeeded, passed a check independent of the worker, and needed no help (`DECURIX_SKILL_TRUST_RUNS`, default 3; `0` trusts from the start - replay-only benches), then `trusted`. Which checks count is in "Trust rests on independent checks" below. One failure or rescue and it is learning again. A person's answer is help, except a reply that approves the plan of the work exactly as it was put (`skill_task._plan_approved_as_is`, read by `approval.read_choice`): every run puts its plan first, and counting a routine yes as help kept every skill an apprentice for good (2026-10-31). A reply that adds anything to the plan is help. `skills.summary`'s `health` carries `stage` / `clean_runs`.
- **Learning = the engine does it, guided by the skill** (`skill_task._by_model`, when `_engine_can_drive`: TheBot on a hosted brain, or the Office engine). The request goes to the engine as `Do the task you were taught, "<title>" (skill <name>) with ...` (a mimicked request goes as the person typed it), and `guidance.py` puts `_procedure` into its model's context: what the task is, the person's words and every Q&A answer, rules, corrections from earlier runs, this run's values with what each means, the steps, and how to work - `gui skill NAME --look N` (the screen step N was done on, the pressed spot ringed in red, left as the command's picture so a vision brain sees it), `gui do NAME --from N` for stretches that match, one item at a time for a list, and never DONE for what the screen does not show. TheBot's triage sends that request to the operator (`taughtTaskRe`: found live, it was a "question" for the tool-less chat skill, which answered as if it had done the task). **Trusted = replay**, and a replay that gets stuck is handed to the model before a person (`_execute` -> `_by_model(from_step=...)`, once per run; a step that ran but whose result did not show is marked so the model never repeats it blindly). A trusted skill stays the model's when its rules ask for a check before starting (`_asks_for_a_check_first`) or once a replay of it ran to the end and could not be confirmed (`_supervise` marks it `supervised`): a task whose rules ask for more than its steps does not get cheaper by dropping the part that keeps them.
- **No unseen success (`verify.py`, `skill_task._finish` / `_gate` / `check_unchecked`, `messaging.set_final_gate`).** A replay whose every step's result showed is a success by the screen (in apprentice stage, with a model, it is also judged). Anything else - `completed_unverified` from `/skill`, mimic or `/replay`, any "done" an engine reports for a taught task, and any engine task that acted on the screen (`_did_screen_work`: its task recording has an action) - is judged: the model sees the screen now, the demonstration's final screen, the criteria, and `evidence.observed()` (the task's recorded actions and what tools read off the screen - `gui ask` notes its answers - because the final screen shows only the end of a list). Only `done` with confidence >= 0.8 is done; `not_done` sends the model back once with what the check saw; anything else asks the person ("I cannot confirm this is done ... reply `done`, `retry`, or say what is wrong"). Their words are kept as a `correction` every later run reads. Without a model the code-decided checks still run (sums, files, recipients, the person's changed files reported) and what needs a judgement is "not checked": screen work asks the person, file work goes out headed "Not checked - ..." and recorded `checked=False`. One function maps every check's result to the report, `verify.outcome(verdict, problems, not_made, error)`: only a confident `done` with no problem, no check left unmade (`FileFacts.could_not`: a blocking check that raised) and no error is done; a refusal at an approval is not done and not checked; it fails closed (review 2026-11-02). Pure chat and shell answers are not gated. `write_final_reply(..., checked=True)` marks a report that went through the gate; a gate that throws still sends the report, marked "Not checked". Found live: after a person's "yes", the engine's first attempt reported both questions answered without asking either - the check (`not_done`, 0.99) sent it back, and the second attempt was verified.
- **Every route goes through `verify.outcome` (review 2026-11-03).** A shell-only task whose commands could have changed something (`playbooks.changed_things`) is gated like file work; a taught run's own files are read back by `produced.file_facts` before `_succeed` reports `checked=True` (a fault is not done, a check not made is "Not checked", `gated`); an error, a stop or a given-up report that no check judged is `checked=False, gated=True`; a long run's fallback line carries the head's word on checking. A learned tool's emails are read dry, checked, and drafted for real once (`tool_task._draft_once`).
- **The lesson (`study.py`).** With a hosted model, `/learn` first studies the demonstration: steps with windows, typed values and expected results, the person's notes, the guides to the apps it worked in (`app_skills.context`), and up to `MAX_PICTURES` (14) screens (the screen of each press with the pressed spot ringed in red, then the end). It may ask to look something about the app up on the web (`tools.lookup`, at most `MAX_RESEARCH`, never with data in the query) and folds what it finds in. It writes an `understanding` (summary, step purposes, what each input is and whether it varies, done_when, incidental steps, rules, the workflow brief) and up to `MAX_QUESTIONS` (8) questions it could not work out (decisions, repetition, preconditions, consequential steps). The goal question shows the understanding and asks for corrections; the model's questions come next, one at a time (`study:<id>`, before the rule-based ones); each answer is folded in by `absorb`, which may ask one follow-up (at most `MAX_FOLLOW_UPS`, 4, per lesson) and may point a position-only click at the control the answer names (`_aim_spots`), and drops waiting questions the answers already settle (`settled`). The value question says what the model thinks each value is, and the last question shows the whole procedure; a reply of more than `MAX_NAME_WORDS` words there is a correction, not a name. Only a bare `stop`/`cancel` abandons a lesson ("stop and tell me" is an answer). The person's answers are kept word for word in `dialogue` and read by every later run - the model's rule list is its own merged rewording. Verified live on the ChatGPT recording: it understood the task from the screens alone, took "a list, one by one, wait for each answer, report them all", dropped a question already answered only after this fix, and later runs asked each question separately and were checked done.
- **Not done / not verified.** The Office engine gets the guidance text but `gui skill --look`'s picture only reaches a TheBot operator (its shell tool attaches none); `bench/learn_documents` passes end to end on Azure with the model driving new skills (2026-09-30, after the grounding, spelling, report and list fixes; a `gui skill` run line now shows a list as `ITEM 1; ITEM 2; ...` and the operator contract says a list takes every item in one run - an engine read a two-line PO and entered the first line, twice); `bench/backoffice` was not re-run; `bench/screen/teach_e2e.py` needs a desktop with no hosted brain or `DECURIX_SKILL_TRUST_RUNS=0`, and was not re-run. The approval gate stops ChatGPT's "Send message" like any Send: a skill that sends prompts through a chat UI asks for a yes per prompt; `gui ask` (a URL, no Send) does not.
- **Formulas without stored results (2026-10-19).** Before the final gate reads what a task wrote, `produced.store_results` stores LibreOffice's results in each workbook (.xlsx/.xlsm) whose formulas have none (`office.calculate_workbook`, the same `_store_results` `office create/update` use; formulas, charts and styles kept). One that still has none is `not_done` with no model asked (`final_gate._gate`, `tool_task`). `office.formulas_without_results` reads this from the sheet XML: an empty-text result (`t="str"`, empty `<v>`) is a result. `office read` names the fault ("Formulas without stored results ... office calculate FILE") instead of only showing values it calculated on a copy - found live, a script-written workbook passed its read-back that way with every price blank in the file.
- **Typed totals and the saved file (2026-10-19).** A workbook's Total row of typed numbers that equal the sums above them is evidence for the judge when the request asked for formulas (`produced.formulas_asked`, `FileFacts.typed_totals`), and only noted in the report otherwise (`totals_note`: "they will not follow the rows if a row changes"). Neither fails the work by itself (harness audit, 2026-10-21). When the request names files and the task saved them, `verify.judge(deliverables=...)` is told those saved files decide that part: an unsaved change still on the screen, or a mistake the action log shows and the file no longer has, is a note, not `not_done`.
- **Facts of the saved file before any model (2026-10-19).** `_gate` checks in code: a requested file that is nowhere (`missing_requested` for a planned stage's own outputs, which blocks; `missing_named` for a name read from the request's words, which is evidence), a picture's size against its source and the size asked (`image_findings`, evidence), a .docx's page breaks (`page_break_findings`, evidence) and typed `\f` or a template placeholder a source held left in it (`document_findings`, `office.docx_structure`, blocking). A request that names files is always gated (the early return no longer skips it). A file on the person's computer that cannot be read is asked about (`unread_host`), never passed. The judge treats a report whose own evidence contradicts the request as not_done.
- The code-decided checks of the files a task made are one function, `produced.file_facts`, read by the final gate (`final_gate._gate`), a planned stage's check (`long_task.code_problems`) and a proven tool's (`tool_task`); add a new fact there, not in one route.
- **What the file holds, row by row (2026-10-19).** `produced.file_facts` also reads the saved workbook: a formula whose stored result is an error (#REF!, #VALUE!, #DIV/0!) blocks (`gaps`); a column filled down a table that stops short of it or a Total that sums less (`gap_notes`: an intentional blank looks the same), and typed numbers among a column's formulas when formulas were asked for or a Total split over two rows when a Total row was asked for (`layout`), are evidence for the judge. The judge is shown the last four rows of every workbook cell by cell. A worker's own sum agreeing with what it typed proves nothing about the rows it never typed.

- **Readiness before permission.** [Readiness](readiness.md) adds owner-reviewed offline artifact evaluations, independent saved-file evidence and scoped grants in the control plane. A skill's `trusted` experience remains execution economy; it cannot enable a responsibility. Practice is excluded from production autonomy.
- **Formatting is read back, and a highlight that is nowhere is not done (2026-10-20).** `office read` of a workbook says per sheet: the filter range, each conditional-format rule (range, rule, the fill or font it applies, colour named with its hex), the rows each fill colour is on (runs: `red FF0000 fill on rows 2, 5, 9-11`) and each column's number format (`office.sheet_formatting`). When the request asks for rows or cells to be filled or highlighted (`produced.HIGHLIGHT_ASKED`) and no workbook the task made has any conditional format or any fill below its first row, the final check (`final_gate._gate`) and a planned stage's checks put that to the judge as a note (`produced.missing_highlight`); it no longer fails the work by itself. Whether the right rows carry it is left to the check that reads the file: no condition is evaluated in code.
- **A figure given as a source's own must be the source's (2026-10-20).** A result line "Closing balance per bank statement" ("Opening balance per X", "Balance as per X", "Total per X") is compared in code with what X states (`sources.py`, a `FileFacts.source_mismatch` of `produced.file_facts`, so the final gate and a planned stage both get it): only when the label names exactly one of the request's input files (its name's words and the words the request puts beside it) and that file plainly states the figure (its Balance column's last line, a row labelled Closing/Opening balance or Total). A difference is evidence for the judge, not a verdict (E-13: which line states a balance, and its sign, are a book's conventions); a figure compared and held is what the `code` basis of trust rests on (below). For balance work the judge is also shown what each input states (`sources.evidence`), and its rules say a figure "per" a source that contradicts it is not done. The operator's rules say to compare a figure the work arrives at with an input that states it before reporting.

## The person's files stay as they were

On a desktop with a shared folder, `source_guard.take` notes and copies the folder's files when a task starts. At the final gate (and a planned stage's check, and a script tool's), a file the request gives (attached, named, or in a folder it names: `source_guard.given`) that was there before and changed is reported as a fact, not a verdict (since 2026-11-03, E-12): `source_guard.changed_sources` gives each such file with a short diff and whether the original is kept, and the judge and the person both see it. Nothing is put back inside the check, and the old verb rule that did (`check_and_restore`) is gone (2026-11-07). A file is put back (`restore_sources`) on one of two structured words only:
- **The judge's verdict.** Its JSON may carry `"put_back": [file]` for a changed given file the request did not ask to change (`verify._parse`, at most `MAX_PUT_BACK`). `skill_task._settle_sources` puts back only the names that point at a file the guard saw change (`source_guard.named_in`: the folder path, the person's path, or a name only one changed file has); any other name puts nothing back. The report then says "Put back your file ...".
- **The person's reply to the offer.** At the final gate `source_guard.offer` notes each changed file whose original is kept, with its sha256 at the run's end, under one id per task (`snapshots/<task>/offer.json`). The report's line for the file says first "to put the original back, send `/restore <id>`" (with the file's name when several are offered). `/restore <id> [file ...]` is a `skill_task` command (`parse_restore`, `_restore_request`): it names that offer by its id, and no words of a message are read for it. A file that holds anything else now than at the run's end, because the person or another program changed it since, is not put back: the person is asked once, and only a yes (`approval.reading`) puts it back; a no stops with nothing written.

Every restore keeps the version there now beside the original (`<name> (changed by worker)<ext>`) and is checked in code: done only when the restored bytes hash to the kept copy (`restore_sources`). The report gives the hash, and a mismatch is not done. A file put back is taken out of the offer (`withdraw`), so a second reply never writes over the kept version. The offer is made on the final gate's route only: a planned stage's check and a script tool's still say where the original is kept and "ask me to copy it back". The old verb list (`may_change`) is evidence only. Such a file is a source, never checked as an output (`is_source`). Any other file of the shared folder is the person's own business (they, or another worker, may change it meanwhile): never judged, never put back (2026-10-21).
- **The judge sees the whole task, and looks closer when it needs to (2026-10-21).** `verify.judge` keeps up to `MAX_TASK_CHARS` (20,000) of the task it is given - a planned stage's check puts the person's binding answers, the system's read-back, the code checks' evidence and the other stages' context after the instruction, and the old 1,500-character cut dropped them. A judge that is unsure only because a part of a file was not shown names up to `MAX_LOOK` words to find (`"look"`); the caller's `look_up` (`produced.lines_with`: each file's first lines and every line holding a term) is shown and the judge decides once more - once only. Wired for the planned stage's check, the final gate and the tool route. Found live: series 16 H1 stage 1 passed "checked in code only" because the CL-4142 row it needed was not in the sample.
## Since the review of 2026-11-03

**One definition of what blocks.** `produced.FileFacts.BLOCKING` / `blocking()` / `not_made()` hold for every route: the final gate, a taught run's read-back, a desktop tool's run and a long request's stage. `not_made()` is `could_not` plus Office files that could not be opened (`unchecked`). A check that raises is NOT_MADE (`stage_checks._checked`; [long-requests.md](long-requests.md)).

**In `final_gate._gate`, "not checked" ranks below every definite finding**, so it never hides one. A check not made, or a host file not read, is "not checked", said once.

**An engine answer with no screen work and no file** has the sums it writes out, and any program-printed numbers, checked in code. When the tools read anything (observed evidence, files read, commands), it is judged with that evidence. Otherwise it goes out with the first line `UNCHECKED_ANSWER` ("Not checked: nothing I did or read can confirm this ..."), `checked=False`.

**A stop is never kind "final".** `skill_task._stopped` sends kind "error", not checked, starting "Stopped, as you said". Every route does the same (`replay_task`, the watchers, `thebot_harness`).

**What else blocks, and what is evidence.**
- A missing file blocks only when a planned stage's own outputs name it. A file name read from the request's words is evidence (`FileFacts.missing_named`).
- A placeholder blocks only when a document the task filled held it (E-10, E-11).
- A source figure the result does not hold is evidence (`source_mismatch` is in `notes()`), and no sign or line-order convention decides (E-13).
- Indian digit grouping (1,00,000) and ₹ are notation; `verify.false_sums` reads them, and also a sum that ends a sentence with a full stop.
- A range of numbered things and how many it holds ("Rows 2 - 10 = 9.") is no sum: `values.range_count` decides it by structure (two whole numbers, ascending, a word right before them in the same clause, and the right side the range's count, both ends counted). A reversed difference ("Balance 200 - 350 = 150") is not that count and stays a wrong sum. The call from `verify.false_sums` is owed (verify.py belongs to another change).
- Payee checks decide by where each bank identifier comes from, never by header words (F-01; [long-requests.md](long-requests.md), "Where money goes, since F-01"). A token of IBAN shape whose check digits hold but whose country's IBAN length is not known (`payees._is_iban` answers None) is reported "IBAN NOT CHECKED" among the unchecked payments: never passed as fine, never ignored, never refused.
- A unit on one side only ("18%" against the "18" a field holds) is one figure when the field's label states the unit (`values.field_units`), or when the person said that field takes it. The save then asks one numbered question of its own, alone, in place of the engine's next one (`unit_answers.py`, the same way as a date's order). What backs the answer is the person's reply as the control plane recorded it, never the agent's note: on this task, their judgement whose question holds the sentence "Reply 1 if the field "Rate" on <host><form> takes its figures in %"; on a later task, a learned `field_unit` row derived from it. The control plane keeps that row only when the reply is the row's option and the sentence stands in the question asked (`checkFieldUnit`). A "2" makes the figures differ. A control plane that cannot be read backs nothing, and the same question is not put again in that task.
- A figure declared bare keeps the unit its backing writes it with (owner decision, 2026-11-08; `records._source_units`, `values.units_beside`). Found live: a note said "18%", `gui record` took the Rate as "18", the save compared 18 with the unit-less field's 18 and the unit question never came. What backs it: the record's source for a value kept `from source`, and what was given (`given_text`: the request, its files, the person's answers) for one kept `from seen` - never the application's pages. Where every place it writes the figure carries one unit, the intent becomes the figure as written there ("18%"), so the save against a field whose label states no unit asks the person; a label that states it ("Rate (%)") settles it as before. Where it writes the figure with a unit and also bare, the declaration is refused once with both forms shown; with two units and never bare, every time. Kept, not refused, for the one-unit case: a refusal once could be answered by declaring the bare figure again, which passes a wrong value silently. A unit is a percent sign anywhere, or one word only where figure and word make a whole value (a table's cell, a label's value to the end of its line): "Qty 18 Nos" in running text stays bare. A currency is not kept: `values` matches a currency against a bare figure by design.
- One comparator for figures and dates (2026-11-08, review round 2): a kept cell (`stage_checks.same_cell`), a fact (`provenance.fact_value`, `same_figure`) and a working row's arithmetic (`stage_facts`) read dates by `values.parse_date` under the request's order (13/04/2026 under MM/DD is decided by nothing) and compare numbers by `values.within_precision`, a tolerance only where a figure written rounded stands for the precise one; a computed value claims no precision of its own (`values.same_figure(..., a_computed=True)`).
- A figure declared with its unit ("5%", "5 kg") stands in a source that writes that figure with that same unit (`records.stands_in` by `values.units_beside`), however short: a one-digit percent was refused as unsourced every time (2026-11-08).
- A record's number, reference or id given as words is not backed by standing in the document (2026-11-08, learn-v1 bill 4; `records.wordy_identifiers`). The supplier's copy printed "Invoice number: as per covering letter"; the worker declared those words as the bill's number and `declare` took them as `from source`, because they stand in the document beside the field's label. A field whose label names a number, reference or id (`label_words`: "No.", "#", "Ref" are these) holds a code, and a value of two or more words with no digit is words, not a code: the document there says where the code is. Such a value is refused at `gui record`, at the save (`core._form_check`, "Not pressed", a replay's press too), and at the final check (`ledger_checks.findings`, kind `identifier_as_words`, for a record saved with or without a declaration), each telling the worker to ask the person for that field by name. Only the people's own words back words there (`records._free_text`: the request, the person's confirmed answers, what they taught, the organisation's knowledge) - never the request's files. The finding never quotes the command (it may carry a credential). The approval rule itself is unchanged.
- A save check never judges a value it read in part (2026-11-08, learn-v1 bill 1; `cdp.FORM_VALUE_CHARS`, `cdp.cut_value`, `records._read_in_part`). A declared value over `records.MAX_VALUE` is refused, never kept cut.
- A choice left unset that the record does not declare is a point at the save (2026-11-08, learn-v1; `records.undeclared_unset`, `records.unset_choice_line`). `cdp.FORM_FIELDS` skips empty fields, so a select left at its empty first option never reached presave and the record that left it out was saved. The readers now report such choices by structure (no option selected, the selected option's value empty, an ARIA combobox with no value; never the option's words, never a "required" mark), and one the record does not declare by label is a point naming the field: declare it from a source, or ask the person. ADVISORY (`records.UNSET_CHOICE_BLOCKS = False`): it informs without blocking - in the save's own output after the read-back line, and in `gui records`, which the reviewer reads - until it passes the replay gate and a clean live round.

**TheBot's operator.**
- A DONE given again after every command failed is put to the person as "Not checked". The only exception is a DONE that quotes a failed command's output (a mechanical check). This holds on local and hosted brains.
- Triage: anything that is not conversation goes to the operator, including questions about the person's own data. The tool-less chat skill keeps only greetings and talk about TheBot or the user.
- A decomposed recovery is verified only when every step verified. A retry of another kind, or one whose result is a model's own words, is reported as "tried instead" and is not verified.
- An unread reply to a vouch or source question vouches for nothing. The question tells the person that a plain "yes" settles it.
- An unverified handoff result fails closed when no review weighed the report.
- Values count as "only the work's own code printed" only when the file was written from the command's own text and then run as the program.

**Recall is not a filter.** Raw nomic-embed-text cosine, as soul calls it (with no query or document prefix), does not separate relevant from unrelated facts: measured on 2026-11-03, relevant facts scored 0.44-0.69 and unrelated ones 0.28-0.56. No fixed floor works, so frames say "may be relevant" instead.

## Trust rests on independent checks (W0.5, phase 2)

A skill's streak (`experience.clean_streak`) counts a run only when it succeeded, needed no person, and a check
independent of the worker passed: a comparison that could have failed and did not. For files (`code`,
`FileFacts.compared_clean`), that means at least one figure a made workbook presents as a source's own ("Total as
per bills", "Closing balance per bank statement") was compared with what that source states (`sources.mismatches`,
counted in `FileFacts.source_compared`), none of them differed, every figure the request states is held, and nothing
blocks. Files that only opened are no check. The request's own figures, and an input's facts merely found in the
output, are evidence and never the basis: a file that restates the request holds them all, and so do a copy of the
input, a partial copy, a failure note quoting one figure and a file with one figure wrong (review rounds 3 and 4).
A total that code recomputed from source data would also count, but no check computes one yet. So `code` is a
transcription check: it says a figure the output gives as a source's own was compared with that source, digit for
digit, and held. It does not say the work was checked. A workbook that says "nothing entered" and restates the
source's own total earns it (review round 5, N3). A figure given as one input's own of a kind that input does not
state, such as a "closing balance per bills" where the bills state none, compares with nothing and withholds the
basis. Every record it declared read back
from the application with its values shown, and no save outside the declared records and no other ledger finding
(`ledger`, `records.all_read_back` and `ledger_checks.findings`), or a person (`person`). The screen
(every step's result appeared) and the model's judgement are kept on the verdict as `basis` and never advance the
streak: a replay can show each step's result and still have entered the wrong thing. Verdicts written before `basis`
existed count for nothing, so every skill earned its trust again. A trusted replay is still judged on a deterministic
share of task ids, 1 in `DECURIX_SPOT_JUDGE_EVERY` (default 5; 0 never, 1 always), through the same judge
(`py.judge.spot`); a spot "not done" records a failure and the skill is learning again. Every outcome carries a
structured verdict (`verdict.py`, decurix.verdict/v1): `checked` is always `verdict == "done"`, a stop is `stopped`
(`messaging.write_stopped`, never done), and a report whose path gave no verdict of its own gets a `legacy` one with no
basis. Two paths still do: `tool_task.perform` and `workflow_task._report` (`test_verdict.LEGACY`, a list that may
only shrink).

## A date the save cannot read either way (review rounds 2-4)

When a save cannot compare a date because its day and month could be either way and no order is known for that side,
the save waits, and the person is asked the date question with both readings. It goes out as a query of its own in
the engine's next turn (`messaging.ask_for_query`) and takes the place of whatever the engine asked then. That
includes an approval question and a question raised for a secret: these are replaced too, not added to and not
asked alongside. The engine is told its question was not put to the person and asks it again. A replaced approval's
held action is withdrawn, because the date reply is no yes. Only the reply to the date query, with the whole text "1"
or "2" and a judgement, sets that side's order. A task that ends with the question open is unchecked, and its report
says the question.

## What labels a run is kept until exported (W0.8, phase 2)

Retention is by label, not age (`retention.py`). A run is labelled when its final report goes out or a person replies
on it (`~/.decurix/runs/<task>/LABELLED`); until the control plane has pulled its bundle and written `EXPORTED`, the
2-day note prune and the recordings' disk budget skip it. `LABELLED` holds the execution id and the label's
sequence number, one line each, rewritten at every label. `EXPORTED` holds the execution id, the manifest SHA, then
`LABELLED` as that pull read it. An export covers the run only while that copy equals `LABELLED` now; no clock is
compared, because the control plane's tar copy rounds file times to the second. An `EXPORTED` written before it
carried that copy falls back to the execution id and a 2-second tolerance on times. Over budget with only such runs
left, nothing is deleted
and the log says so (at most hourly). The run's manifest (`run.json`) names the agent's code and soul by hash and lists
the parts that exist.
