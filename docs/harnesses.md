# The agent harness: TheBot and its brains

**Every desktop runs TheBot; what it chooses is its brain** (`Desktop.Brain`, `desktop-brain` label, `DECURIX_BRAIN` env; `httpapi.desktopBrain` refuses any other harness with 400, and a hosted brain nobody set up). `ollama` (default) is the shared local model as before. `claude` / `azure` / `openai` (any OpenAI-compatible server the control plane was given: OpenAI itself, OpenRouter, a Brainiac box on the own network; `llm.ProviderOpenAI`, 2026-11-01) point soul's OpenAI-compatible provider at the control plane (`LLM_PROVIDER=openai`, `OPENAI_BASE_URL=<control plane>/api/llm/<brain>`, a placeholder key) with `EMBED_PROVIDER=ollama` (embeddings stay local and best-effort), `DECURIX_LLM=<brain>` so `harness.ask_model` asks the same hosted model (and never falls back to loading the local one), and `thebot_harness.wait_for_backend` waits for soul only. A hosted desktop also gets `DECURIX_BRAIN_MODEL`, `OPENAI_MODEL=default` and bigger web-research budgets (`THEBOT_WEB_PAGES=3`, `THEBOT_WEB_PAGE_CHARS=6000`; a local brain keeps 2 and 2500 from `start_agent_terminal.sh`).

**TheBot adapts to its brain (`agent/thebot/internal/llm/caps.go`, `llm.Capabilities` on `RunContext.Brain`).** New engine work goes into TheBot, keyed on what the model can do rather than on which provider it is:
- **Vision.** A hosted brain's is decided by the control plane when its key is saved (`llm.Hub.Test`: Claude's current models all read images; an Azure or OpenAI-compatible deployment is sent a one-pixel PNG and a refusal means text only), stored with the settings and baked into the desktop as `DECURIX_BRAIN_VISION`. The Ollama brain gets no such variable: soul asks Ollama `/api/show` (`capabilities` has `vision`, `model_info.*.context_length`) in the background until it answers - `/api/show` reads the manifest and never loads the model, which matters on this repo's memory-starved host. Never probe the shared Ollama with a chat.
- **What vision changes in the operator** (`skills/operator.go`). The contract gains `visionRule`. `gui` is run with `DECURIX_GUI_SCREENSHOT`, so every screen command leaves a PNG of the screen as it ended up (`cli.save_screenshot`, whole for a hosted brain, half size for a local one: `DECURIX_GUI_SCREENSHOT_SCALE`). A whole-size picture carries a ruler (`DECURIX_GUI_RULER=1`), so a position read off it is right after the provider shrinks it. The PNG is attached to that command's result. A local brain keeps only the newest screenshot; a hosted one keeps older ones until its next maintenance pass (below), so its transcript is only appended to. `office read` is run with `DECURIX_OFFICE_IMAGES=attach`, so a scan's `[page image: ...]` pages are attached too. Up to `maxDocumentPictures` (6) pages are kept, *separately* from screenshots, so the screen never pushes the invoice out of view. A text-only brain gets `DECURIX_OFFICE_IMAGES=ocr` instead: tesseract's reading of each page, flagged as OCR. Dropping an old picture rewrites an earlier message, which costs a local vision model its Ollama prompt cache; that trade is accepted only for vision brains.
- **Budgets.** A hosted brain gets 16000 characters of command output (4000 local), 12000 of `gui` element list (`DECURIX_GUI_TEXT_CHARS`, 3500 local) and 80 operator turns a budget (16 local; 40 ran out live on a three-line order). They are fixed on the goal's `operatorState` when it starts, so a paused goal resumes with the same ones.
- **Benchmarks run on a brain with `--brain azure|claude|ollama`** (`bench/brain.py`: the environment `buildDesktopEnv` gives a desktop with that brain; model calls go through this tree's control plane on 127.0.0.1:8080, which must have the brain set up; the skills bench's fake control plane forwards `/api/llm/*` there). Without the flag, `bench/recordings` and `bench/skills` start their desktop on the old model-free settings, as before. Verified on Azure (gpt-5.4, vision) on 2026-09-29: recordings, skills and learn_documents (including path A, where TheBot found the taught skill with `gui skill`, read the PO with `office read` and ran `gui do` with list values) all pass. For benches that `docker exec` into a desktop, run the control plane with `DECURIX_IDLE_STOP_MINUTES=0`: idle-pause pauses a desktop seconds after a task and `docker exec` refuses a paused container.
- **TheBot's back-office tools, as shell commands** (`tools/office.py`'s `main`, taught in the operator's contract):
  - `office update BOOK.xlsx -` takes a JSON spec on stdin: `edits` plus `replace_refs`. It edits the sheet XML in place, so charts survive; never rewrite a workbook with openpyxl.
  - `office create BOOK.xlsx -` makes a new workbook.
  - `office email --to --cc --subject --attach` takes the body on stdin and drafts into the Outbox through `tools/outbox.py`. A draft is never sent: only a person's Send on the Triggers page sends it. Its subject and body pass through the secret withholding first, and an attachment must be a file of the work (`~/work`, the shared folder, `~/Downloads`; never under a hidden folder or `~/.decurix`: `privacy.file_may_leave`).
  - TheBot's command safety does not stop `office email`; it stops only real senders (`sendmail`, `mutt`, ...).
  - Triage sends an email-to-prepare to the operator (`wantsEmailDraft`: draft/prepare/compose an email, reply, reminder, letter or message; the Outbox; or "write an email" with an address or an attachment). Left to the chat skill, it answered with the email's text and put nothing in the Outbox. "Help me write an email asking my boss for Friday off" names no address and stays conversation.
- `llm.Message.Images` carries pictures (PNG, JPEG, GIF or WebP, told apart by their first bytes: `llm.ImageType`), and each provider sends them in its own shape: OpenAI `image_url` parts (and so, through the control plane's proxy, Claude image blocks), Anthropic `image` blocks, Ollama `images`. Bytes that are not a picture are never sent as one (a provider refuses the whole call): OpenAI and Anthropic get a note in their place that says to read the file as text, and Ollama simply leaves them out. `Message` is no longer comparable with `==`, so tests use `reflect.DeepEqual`.

**The legacy harnesses were removed on 2026-11-07 (O-4):** `ollama` (`task_runner.py`), `azure` (the Office (GPT) engine) and `claude` (Claude Code, with its guard hook, the computer MCP server, the shared login `internal/claudeauth` and the CLI in the tools image). A desktop created with one keeps its stored `harness` and runs TheBot (`config.CREATED_HARNESS` is what it was made with; `harness.py` logs one line saying so). `harness.py` exports `perform_task`, `continue_after_query`, `wait_for_backend`, `ask_model` and `cancel_running`, and stays the only file that may branch on the engine:

- **`thebot`** (the only harness; the API picks it when none is given and refuses any other): TheBot's `soul` binary, built from `agent/thebot/` (its own Go module) in the `thebot-builder` stage of `docker/desktop.basic.Dockerfile` into `/opt/soul` (one image; `developer` and `ai` are tags of it), and started by `start_agent_terminal.sh` as a daemon on port 4900 when `AGENT_HARNESS=thebot`. That script maps the desktop's `OLLAMA_URL`/`OLLAMA_MODEL` to soul's `OLLAMA_HOST`/`CHAT_MODEL` and sets `THEBOT_STANDALONE=0`, so soul needs no env var of its own. The control plane always passes `OLLAMA_MODEL` (`internal/ollama.Model`, `devstral-small-2:24b`, unless `.env` names another); the fallbacks for a desktop or soul started without one are the same model in all three places (soul's `CHAT_MODEL` default in `internal/config`, `start_agent_terminal.sh`, the Python agent's `config.OLLAMA_MODEL`), and soul's config test locks it. A hosted operator job notes the SHA-256 of the rules text it was given (`rulesFor`) beside its trace (`trace.Rules`, `~/.decurix/ai/traces/<task>.rules`), which the run's manifest carries as `rules_sha` ([trajectory.md](trajectory.md)). A failure note names the hosted brain by its own name (`thebot_harness._brain_name`: Claude, Azure OpenAI or an OpenAI-compatible model), never the unused local model. Inside soul a job goes: **recall** (L1 facts) → one shared **system frame** (`internal/prompt`: persona + host context, byte-identical for every model call in the job so Ollama's prompt cache carries across them) → **triage** (`internal/atomizer/triage.go`, deterministic: `chat` / one `skill` / `operate` / `plan`) → a tagged step **graph** from the planner only for `plan` (`[do] [shell] [web] [read] [browser] [download] [write] [code] [docs] [answer]`, with `(after N)` dependencies) → the **scheduler** (`internal/scheduler`) runs ready steps in parallel (`THEBOT_MAX_PARALLEL_STEPS`, 3) under a process-wide model-concurrency limit (`llm.Limited`: `MODEL_CONCURRENCY`, else `OLLAMA_NUM_PARALLEL` (1) on Ollama and 4 hosted), bounds a job at `THEBOT_JOB_TIMEOUT_SECONDS` (7200), recovers a failed step (retry / decompose / ask), replans the rest once if it still fails, and **pauses** with a `Checkpoint` when a step needs approval or an answer → one **synthesised reply** for multi-step jobs. `operate` is the **operator** skill (`internal/skills/operator.go`): a Go `COMMAND:`/`DONE:`/`HELP:` loop carrying the measured lessons of the removed Ollama harness, which is what lets TheBot answer "what's the kernel version?" by running `uname -r` instead of planning a web search. Consequential commands and requests are stopped by `internal/safety` before they run, whatever the model decided.
  - **What soul reports as done (2026-11-02): fail closed.** A step's `Verified` is a success the step saw, nothing less. The browser skill verifies only a run the extension finished with an answer; an error, captcha, stall, timeout or answerless "done" is a failure marked `fatal` (not retried), with the log of what it saw. The terminal skill never verifies a nonzero exit (an empty stderr included; marked `fatal` so recovery does not swap in an unrelated command that exits 0), with one exception decided by the program the command line ran last (the first word of its last stage, `negativeAnswer`), never by output text: exit 1 from `grep`/`egrep`/`fgrep`/`zgrep`/`rg` ("no match"), `diff`/`cmp` ("the inputs differ") or `test`/`[`/`[[` ("the test is false") is that program's answer, reported as `answered` (`Meta["answered"]`, "Exit code: 1 - answered: no match"), not as the work succeeding and not as fatal. `grep x f && echo found` still fails. A command that exited 0 while a backgrounded child still held its pipes (`exec.ErrWaitDelay`) is a success everywhere a shell runs (`hostshell.Exited`: the terminal skill, the operator's shell, the coding harness). The coding skill verifies only `BuildReport.Succeeded()`: tests pass, the project builds, and a smoke start (when one ran) started. file-write keeps a Markdown/text file's fenced blocks whole (only a reply that is one fenced block is unwrapped; several blocks for one code file are not guessed at), takes no version number for a file name ("Go 1.27"), and verifies by reading the file back. download (and every page fetch: `internal/websearch`, the coding harness's research) goes through `internal/netguard`: it resolves each host and dials only public addresses - not loopback (soul 4900, the agent API, Chrome 9222), RFC 1918 (host.docker.internal, decurix:8080), link-local (169.254.169.254), unique-local, CGNAT 100.64/10, unspecified or reserved - checked on the address actually dialled (no DNS rebinding), on every redirect, with no proxy. A URL is taken only from the request, the person's reply, or a page a verified step fetched (`givenURL`, `PriorSourceURLs`), never from a model's prose. download checks each file's bytes against its kind (a login page under `invoice.pdf` is not saved), verifies only when every file found was saved, and bounds every read (`maxPageBytes`, `maxFileBytes`). A chat reply, a web skill's summary and a RAG answer are marked `MetaModelReply`: later steps see them labelled as a model's own words (`PriorFindings`), and the operator never notes them as seen (`PriorSourcedFindings`), so a web page's text cannot become a traced source for what the shell loop types. In the operator, a stalled loop (a command repeated past its nudge, unmarked replies, a bare DONE) puts what it has to the person as "Not checked", never as a verified result. The commit gate's verifier and case matrix answer an error, a 429, an unreadable or cut-off answer with a "Not checked" point (`notChecked`, never advisory), not a pass. The providers mark a cut-off answer (`llm.Result.Truncated`: OpenAI `finish_reason` length, Anthropic `stop_reason` max_tokens, an Ollama stream that ends without `done` - which is also an error, retried); the operator asks again for a cut-off reply instead of acting on it, and the chat, web, file-write, reviewer and verifier calls never take one as complete. `canonicalNumber` strips only a currency's mark, so "INV 5000" is an identifier, not 5000. `saysWhyLeftOut` needs a stated reason (because, a duplicate, another client's, another period's), not a bare "no"/"not". `safety.IsApproval` is false for a reply with a question or a condition in it ("ok, what will this send?", "yes if the total matches").
  - **A fix a web page or a model proposed is a proposal (2026-11-02).** In the coding harness (`coding/diagnose.go`) a `FIX_COMMAND` from web research or a model's reply (`Diagnosis.IsProposal`; the built-in table's fixes are not) runs only with the person's yes to that exact command: the build stops (`BuildReport.NeedsApproval`), the coding skill pauses with `NeedsApproval` and a `codingCheckpoint`, and on the re-run the same failure gets the command they saw, once (the scheduler's single-use grant); a no declines it for that run. A researched fix is written to L1 only after it ran with approval and the check that had failed then passed (`settleLearning`).
  - **What L1 keeps.** `memory.L1.Store` refuses a secret-shaped fact (`memory.LooksSecret`: a password, PIN, OTP or code given after its name, a token or key by its shape, credentials in a link, a long mixed random string), whoever asks; `feedback.RecordNegative` does the same. A judged fact (`ConsiderExchange`) is stored only if every value-shaped token in it (a number, an identifier, an email) is in what the person said: a value the answer carried from a client's documents has no scope in L1 and would be recalled into every later task.
  - **A yes is one action's, once.** The scheduler hands the person's yes to the paused step only, as a single-use grant (`singleUse`): used up by the first `IsApproved` of that exact action, withdrawn when that run ends (`runStep` clears `rc.Approved` before any retry, reroute or decomposed recovery), never written into a `Checkpoint`. A retry after a failure, a second identical command, or a resumed job asks again. No request approves itself: soul's `/api/chat` has no `approved` field and `scheduler.Request` no `Approved`, so the check on a consequential request's own words is asked every time (`thebot_harness` sends no `"approved"`). On a desktop with an approval gate (`cmd/soul/gate.go`: `/run/decurix-gate` exists, or `DECURIX_GATE_REQUIRED=1`, which the control plane sets on every desktop) soul believes no reading of a reply sent in the request (`approvalReading`): a paused approval becomes the gate's own request (`gateAsk`), and the job resumes on the gate's settlement of that one request (`gateSettled`, waited for up to 45 s). Anything else resumes it as "unclear", never as a yes. A gate that refuses to ask (the question cannot be shown without the task's secrets) is a no to that one action; after `maxGateRefusals` (3) in a row the job stops.
  - **Who may call soul (`cmd/soul/guard.go`).** Soul listens on every interface of the desktop container, so other containers on the Docker network reach port 4900 too. Before any route: a write that is not `Content-Type: application/json` is refused (415: a page in the worker's Chrome can POST text/plain with no preflight), and so is a request whose `Origin` is not the Host it was sent to, or whose `Sec-Fetch-Site` is another site (403). Every `/api/` route but `/api/health` needs `Authorization: Bearer <DECURIX_AGENT_TOKEN>` (`config.AgentToken`), compared in constant time (401). Without a token soul fails closed: those routes are refused (401, "created without an agent token: recreate it") until the desktop is recreated with one; it no longer serves an open API. The control plane's `/agent/<id>/` proxy sends that header (`desktop.AuthorizeAgentRequest`), as does `thebot_harness` (`config.agent_auth_headers`). The SOUL_HOST default stays `0.0.0.0`. One exception: `/api/llm/call` also takes soul's call key (below, "One path for the worker's calls"), which opens that route and no other.
  - **Commands in their own process group.** `hostshell.CommandContext` starts the shell as a group leader and, when its context ends, kills the whole group (`cmd.Cancel` → `KillTree`, `WaitDelay` 2 s): killing only bash left a build's compiler holding the pipes, and the terminal skill and the coding harness's builds hung past every timeout. `hostshell_windows.go` exists only so the module compiles and its tests run on a Windows development host (bash from Git).
  - **What `thebot_harness` sends soul.** One `POST /api/chat` per job: `prompt` (the request, never glued to anything), `context` (soul folds it into the system frame: the desktop's identity, worker memory, up to 8 taught skills in name order so the frame does not change per request, the organisation's knowledge for this worker and task (`org_context`: org, role, worker and task lines, read once per task so every job of the task sends the same bytes, secrets withheld, at most 6000 characters, not repeated when a taught task's guidance carries them; docs/skillhub.md), guides for the apps the task names, a taught task's guidance, and, for a hosted brain only, a playbook and a learned method, then the plan the person already answered and `SAFETY_PREAMBLE`), `workdir`, `sessionId` (one per desktop; a workflow stage's attempt gets its own, so earlier stages' conversation is not re-sent), `reply`, `approvalReading`, `planAgreed`, `earlierSaid`, `taskId` and `secrets`. Soul takes at most 1000 secret values of at most 64 KB each (`withheld.MaxValues`, `MaxValueLen`) and refuses more with 400; the harness does not send such a task at all (`_secrets_too_big`), since a value soul cannot take would be kept unwithheld. The job is followed over soul's SSE stream (`/api/jobs/<id>/stream`), with polling as the fallback; each log line is put into a person's words (`readable_step`) or left out. The harness waits `THEBOT_JOB_TIMEOUT_SECONDS` + 300 s, then cancels the job. A job's `usage` (prompt, response and cached tokens) goes to `usage.add`.
- TheBot's `SAFETY_PREAMBLE` (`thebot_harness.py`) instructs the agent to stop and request human approval — via the `ask_for_query` → querytext path — before payments, sending messages on the human's behalf (WhatsApp/email/SMS), or any action with real-world consequences it isn't fully confident about, signalled with a `NEEDS_APPROVAL:` prefix on its final answer. It also says a request already decides what it asks for (no "shall I?"), and that on the screen the `gui` command's gate, not the model, decides which click needs a yes.

**Which app a request asks to work in (`atomizer.WorkApps`, 2026-10-19).** Triage and the operator's `behindTheApp` share one reading: "use/using/with APP", "open it in APP", "in APP (the app on your desktop)" name where to work; "in/into/on APP" followed by a file of that app's kind (", orders.xlsx", "(orders.xlsx)") or by "format/file" names the file's format, and the file is made with `office`. The operator is also told once, when under 40% of its goal's time is left (`timeNoteFor`), how its screen actions went and to finish, save and check (or ask) before the job limit; a `gui type` with shell-doubled quotes is sent back to use stdin (`quotesNudge`), and the grounding check reads a heredoc's body and traces a formula's quoted words like typed text (`formulaLiterals`).

**Long goals and what a result rests on (2026-10-22, hosted brains only).** A goal's context is managed in `skills/context.go`: once the re-sent transcript passes `contextBudgetChars`, or a turn budget is spent by a window that made progress (up to `maxContinuations` more budgets), the older part is replaced by one progress message (the model's own NOTES, the harness's `Ledger` of what every command did, every word the person said in the goal) between the untouched prefix and the newest messages; the "few turns left, finish" note comes only when no budget follows. What a compaction keeps is bounded in characters (`keepRecentChars`, `ledgerShownChars`), and another is not tried until the transcript has regrown (`compactRegrowth`). A ledger line whose output it shortens names a file holding the whole output (`keepOutput`), so a step can be read again even when its screen has since changed. Between compactions a hosted goal's transcript is only appended to: stale screen listings, screenshots older than the newest and older command outputs (masked to their start and a file holding the whole: `maskOldOutputs`) wait for one maintenance pass (`maintain`, when `maintenanceDue`), because on GPT-6-class deployments any rewrite of the transcript's tail threw the prompt cache away - measured 2026-11-01 on three office workflows, the cached share went from 27-35% to 54-70%, same checks, about 40-60% less input billed at the full rate. A pass is due only when it takes off at least 40% of a transcript of at least 40,000 characters (`maintainShare`, `maintainMinChars`). Every call carries a `prompt_cache_key` per goal and call kind (`llm.cacheKey`: a hash of the first message and the first user message), dropped for good if a provider refuses it. A local model keeps the per-turn digests. `skills/judgements.go` asks, before a DONE and before an action the approval gate stopped (each kind with its own cap of rounds), for the JUDGEMENTS the result rests on, each with its backing quoted; code only finds where each quote stands (whole words, or only its words near each other) in what the goal was shown, and the approval shows the list ("What this rests on"). `skills/reviewer.go` is the one place judgement is made about the result: an independent model call (tried twice) is shown facts that code gathers with no verdict of its own (the request; every reply of the person with what it answered, kept apart from the transcript so compaction never loses it; the worker's memory and lessons; every command with what it printed; documents saved and offered on screen; web pages looked up; the passage around each cited quote; points an earlier review raised; the report and its calls) and names what is not done, not taken in, not established or contradicted, each with how it is settled (recheck, lookup, person). Per round that goes back once to the operator; what is still open goes to the person as one question, numbered through and told as what each point is (up to `maxReviewQuestions` a goal); past that it is carried with the report or the approval ("Still open after an independent review"), never dropped - and a review that could not be made says so. The question asked is given back with the answer. A gate stopping a command while points are being settled carries them to the approval. The harness does not add pattern- or threshold-based nudges for judgement; code blocks only on what it decides for certain (a broken file, a secret, the approval gate). A web page is a source only once the person vouches for it; a link the person gives is a source at once. `office update` takes `insert_rows` (references move with the rows) and `copy_rows` (the next period's block made from the last one as a copy and paste: references move, the period's name is replaced in labels, typed figures and labels carrying a date or a reference are left to fill, nothing is written over a filled cell, formulas reading another sheet are named to check), and `office read` maps a sheet that repeats one layout and tags each row with its block (`sheet_blocks`) - a long one shows its newest blocks whole.

The operator's guards read a command line as the shell runs it (`shellSegments`): each gui command of a chain on its own, a here-document as its command's stdin. `quotesNudge` sends back any gui type whose quoting the shell would change (a quote opening or closing mid-word, a formula with odd quotes or unmatched brackets); the contract says every formula goes on stdin (`gui type CELL - <<'EOF'`).

**Since the review of 2026-11-03.**
- **Soul runs as part of Decurix by default.** Acquired skills (`.skills/`), the coding harness and remembered build fixes are on only with `THEBOT_STANDALONE=1` (owner decision O-8). Inside Decurix a build request goes to the operator, with no coding harness and no 32768 `num_ctx`.
- **A remembered "yes" is never a yes**, standalone either: a fix approved before is asked about again, with "a record on this machine says this command was approved for it on <date>" in the question: the record is an L1 row the worker's own user can write, so it is reported as a record, never as the person's yes.
- **The operator's own plan keeps its "with your OK first".** A plan put to the person (`plan.go`, docs/learning-loop.md B) lists its commits with the control each is made with; from then on every gui command of the goal carries `DECURIX_PLAN_ASK_FIRST`, and `core.act` holds such a press for the approval gate (`_plan_hold`), so the person's yes comes through the gate's usual path and the press runs on resume (`approvedRun`, counted in `CommitsRun`). A no leaves it unpressed and the report is sent back (`commitsIssue`) unless it says why.
- **A later job of a task keeps what the person said.** `"earlierSaid"` in the `/api/chat` body is the person's replies on the task so far, each with the question it answered, as the control plane confirms them (`thebot_harness._earlier_said`, from `person_record.answers`; at most 20, each cut to 4000 characters). Soul seeds a new goal with them (`skills.RunContext.EarlierSaid`, `seedEarlierSaid`): they are in its review's "what the person said" section, and the reply's words (never the question's) are a source a typed value may come from. Found live (2026-11-08, learn-v1 bill 2): the final check sent the bill back, the new job started a goal of its own, and its review, shown none of the person's replies, called the cost centre they gave backed by nothing.
- **A plan is agreed by a typed flag.** `"planAgreed": true` in the `/api/chat` body is how the host says a request is a stage of an agreed plan; `thebot_harness._run_thebot` sends it in every body, from structure only ([long-requests.md](long-requests.md)). Soul no longer reads the plan-agreed marker from the request text. The learned-method marker counts only in the system frame.
- **Commands the model runs start without** `DECURIX_AGENT_TOKEN`, `*_TOKEN` and `*_API_KEY` (`hostshell.ChildEnv`). `OPENAI_API_KEY` and `OLLAMA_API_KEY` stay, because the gui tool reads them. A model's own push or upload that relied on an inherited token now fails, on purpose.
- **`/api/health` on an Anthropic brain** asks `GET /v1/models/{model}`, never a chat call.
- **Bounds.** A 4 MB chat body cap, at most 500 sessions (least recently used evicted), paused jobs bounded, and no error text sent to clients.
- **The local transcript stays inside `num_ctx`** (8192, with 1024 kept for the answer). Over it, old command outputs are masked (the prefix never is, the newest two messages stay whole); still over, the goal ends as not checked, because Ollama would otherwise drop the oldest messages after the system one, the contract and the task first. The token estimate is `max(3 bytes per token, the highest measured tokens per byte) x bytes`, plus per-message template tokens, calibrated from Ollama's `prompt_eval_count`; the highest rate is used because a call served partly from the prompt cache reports fewer tokens. The prompt prefix stays byte-identical (a test pins it).
- **Stores.** Soul's SQLite stores migrate by appended steps (`internal/migrate`). A store written by a newer soul is skipped for that run (`storesOff` in `/api/health`), and soul still starts.
- **Downloads never overwrite** an existing file.
- **The same save refusal on an unchanged form ends in a question** (2026-11-08, learn-v1 bill 1; `skills/save_refusal.go`). The save check refused "Save bill" with the same "Not pressed: ... Notes holds ..." seven times and more while the form did not change; the worker declared again, typed again, tried curl and the browser's dev tools, and spent its budget. The operator now counts the refusal from the tool's own output: a gui command that acts on the screen, exit code 1, and the line `gui: Not pressed: ...` (not "Not pressed yet", a listing to confirm). The refusal quotes what each field it judges holds and what the record says, so the same refusal (element refs and spacing aside) means those fields and the record did not change; commands between do not reset the count, another refusal does. At the third (`maxSameSaveRefusals`) the loop ends with a question to the person that quotes the refusal and names the field, and the goal is kept for their answer.

**What soul tags and records (phase 2, 2026-11-04).**
- **Every model call names a purpose** (`llm.Options.Purpose`, constants in `agent/thebot/internal/llm/purpose.go`;
  `purpose_test.go` fails on a call site without one, and a call that has none goes out as `untagged`). It leaves soul
  as `X-Decurix-Purpose`, with `X-Decurix-Task` (from `/api/chat`'s `taskId`), `X-Decurix-Turn` (`<job>:<n>`, one per
  operator turn, counted across the whole job: `llm.NextTurn`) and `X-Decurix-Caller: soul`. These are headers only:
  the body, and so the prompt prefix, is byte-identical whatever the tags (`TestTagsNeverChangeTheRequestBody`).
- **Commands the operator runs** get `DECURIX_TASK_ID` and `DECURIX_TURN_ID`.
- **Soul's own trace** of each task goes to `~/.decurix/ai/traces/<task>.jsonl` (`internal/trace`), withheld by
  `memory.RedactSecrets` first; the control plane pulls it with the run's bundle ([trajectory.md](trajectory.md)).
  A trace is at most 32 MB a task (`trace.MaxBytes`), then one `{"kind":"truncated"}` line and no more. Nothing
  prunes the folder on the desktop yet.
- **One path for hosted calls.** Inside Decurix (`THEBOT_STANDALONE` not `1`), `LLM_PROVIDER=anthropic` is refused at
  start, and `LLM_PROVIDER=openai` must point at the control plane's proxy (`<CONTROL_PLANE_URL>/api/llm/...`, same
  scheme and host, parsed): a hosted model is reached only where the call recorder sees it (`config.Validate`).
- **One path for the worker's calls (plan rule 3, phase 1, 2026-11-08).** The Python agent's own model calls
  (`llm_client.chat`/`ask_once` on a hosted brain, `ollama_client.ask_once` on the local one: the final check, a
  taught skill's values, the grounder, the escalation ladder; every `py.*` purpose) go through soul's
  `POST /api/llm/call` (`cmd/soul/llmcall.go`, `agent/decurix_agent/soul_call.py`): OpenAI-shaped messages (text and
  `data:` pictures; text between two pictures labels the one after it), `max_tokens`, `temperature`,
  `response_format` (`llm.Options.ResponseFormat`: OpenAI's as it is, Ollama's `format`), `stop`, `timeout_ms`, the
  task's secret values, and the brain the caller expects (`hosted`/`local`; another is refused). Soul makes it through
  its own provider chain - concurrency limit, metering, trace line, the proxy's tag headers (task, and the turn and
  job from the asking command's `DECURIX_TURN_ID`), prompt-cache key - with the caller's purpose verbatim
  (`llm.AgentPurpose`: only `py.*`/`legacy.*`, never one of soul's own), and answers `{text, truncated, usage}`. A
  provider's failure comes back with its own status and `"where":"provider"` (so `llm_client` maps a 429, a 5xx, a
  400 as before; soul's own retries count against `llm_client`'s budget); soul's own refusal says `"where":"soul"`,
  and the caller goes straight to the proxy (or Ollama) as before - as it does when soul is not running, has no such
  route (an older image) or the process has no token or key, logged once per process. Bounds: 24 MB a call (the
  proxy's own), 256 messages, 64000 tokens, 15 minutes (240 s by default). Not a job: soul adds the call to no job's
  usage, and Python counts it once (`usage.add`). Signatures and return shapes of the Python functions are unchanged.
  **Who may ask:** the agent shows the agent token; a command soul runs (the worker's `gui`) never has it
  (`hostshell.ChildEnv`), so soul writes a random **call key** at start to `~/.decurix/soul-call.key` (0600; beside
  its workspace, `SOUL_CALL_KEY_FILE`), which opens `/api/llm/call` and nothing else (`guard.go`). It is not a
  boundary - the same user can read it - and it opens only model calls, which any process on the desktop can already
  make at the proxy; it is a file, not an environment variable, so `env` never prints it into a transcript. **The
  approval gate never asks soul** (`soul_call.in_gate`: `approval.IN_GATE` or `DECURIX_CALLER=gate`): it is another
  user's process and must not depend on, or believe an answer from, a process of the worker's user, so
  `py.approval.read`/`py.approval.choice` in the gate go straight to the proxy as `caller: gate`.
- **Decisions in soul (plan rule 3, phase 2), first `py.judge`, behind `DECURIX_SOUL_JUDGE=1` (off by default).**
  The final check's prompt and its reading of the answer live in `internal/judge` (`System`, `Messages`, `Decide`);
  `POST /api/llm/judge` (`cmd/soul/judge.go`) takes a call's fields with `evidence` (as `verify.judge_evidence` makes
  it: data only, pictures as `data:` URLs), and for a second look `look` and `closer`, in place of messages; makes the
  call as `/api/llm/call` does (`makeCall`); and answers with `decision` - the verdict, or `{error, cut_off}` for an
  answer it could not read, which `verify.judge` maps to unsure as it maps its own. Only `py.judge` and `py.judge.*`
  purposes, the agent token only (the call key opens `/api/llm/call` alone). Python calls it through
  `llm_client.chat_decided` (retries and the cut-off retry as `chat`) and takes today's path - its own prompt and
  `_parse` through `/api/llm/call` - when soul cannot (down, a 404 from an older image: not asked again that process,
  a refusal). Until the switch defaults on, both copies exist and one recorded corpus holds them byte for byte
  (`internal/judge/testdata/parity.json`; `agent/tests/test_judge_parity.py --write` regenerates it after a deliberate
  change to both). The gate is untouched.
  **Second, the escalation ladder's four questions (`py.escalation.ground`, `.judge`, `.detour`, `.point`), behind
  `DECURIX_SOUL_ESCALATION=1` (off by default; read once per skill run, `skill_task._ladder`).** Their system texts,
  prompts and readings live in `internal/escalation` (`Prepare`, `Question.Messages`, `Question.Decide`); Python's
  `escalation.Ladder` builds each question's evidence as data (`_ground_evidence` and the evidence of the other three:
  the ranked candidates, the screen as `elements.render` writes it, the OCR lines of the recording's frames and of the
  screen now) and keeps the tools and what it does with a decision (the trail, asking a person, leaving steps out).
  `POST /api/llm/escalation` (`cmd/soul/escalation.go`) takes a call's fields with `evidence` in place of messages, the
  question named by the purpose; refuses evidence with a field it does not know; makes the call as `/api/llm/call`
  does, on the call's brain; and answers with `decision`: `{choice, confidence, verdict: chosen|doubt|none}` for
  ground and point, `{achieved, confidence}` for judge, `{verdict: skip|keep|unsure, confidence, reason}` for detour.
  `escalation.from_soul` checks it (a choice outside the list, or a verdict its confidence does not carry, is an
  engine that could not be asked - fail closed). The chain is `harness.ask_model`'s (`harness.ask_decided`: the hosted
  model through `llm_client.ask_decided`, a local one through `ollama_client.ask_decided` with its own options), and
  wherever soul cannot make the call the question is today's. In broker mode the screen side's ladder sends the
  evidence with its ask and the agent answers with soul's decision beside the text (`screen_call._answer`). The reading
  follows Python exactly - `json.loads` with NaN and Infinity, `int()` and `float()` of Unicode digits, their
  OverflowError (`internal/pyread`, shared with `internal/judge`); `internal/escalation/testdata/parity.json` and
  `agent/tests/test_escalation_parity.py --write` hold the two copies to one corpus.
