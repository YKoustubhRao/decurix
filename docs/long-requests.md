# Long requests: a durable plan without a spec

One chat request used to be one soul job, killed at `THEBOT_JOB_TIMEOUT_SECONDS` (25 min). A request that holds several deliverables now becomes a **planned run** of the existing workflow runner (`workflow_runner.py`, spec `planned: true`), each stage its own job. Module: `agent/decurix_agent/long_task.py`; hooks in `workflow_task.py` (prompt, stage gate, conclusion), `watchers.py` (route, mid-run messages, restart), `messaging.py` (`ask_for_query` hook, `post_question`, `reply_on_task`), `harness.cancel_running`.

**When.** `long_task.looks_long` is code only: kinds of deliverable named (workbook, register, reconciliation, ageing, deck, memo, report, email, document, plan, records in an app), +1 for a list of 3+ items; 4+, or 3+ with 5+ attached files or a long text. Only then one model call drafts the plan; `{"long": false}` or one stage runs the request the ordinary way. **Off by default** until run live: on with `DECURIX_LONG_REQUESTS=1`, or on a running desktop (whose environment is fixed) with a file `~/.decurix/long-requests` reading `on`; the environment wins when set. Off, the watcher behaves exactly as before. Short requests: no change, no model call.

**Plan -> spec** (`spec_from_plan`). Stages: instruction (with the request's rules), inputs (attached files only), outputs relative to the work folder (`work_dir` = `config.WORK_DIR`), `must_contain` words, drafts count (`format: drafts`, `min_count`; only a count the request states or an exceptionless rule yields - drafts "where needed" have none, and every input email must be drafted for or named in the report with why not, `reply_coverage`; a stage's drafts are all its attempts'), `depends_on` (earlier stages only). A stage with no file or draft writes a CSV log. All stages `retry_safe`, 2 attempts.

**Runner for planned runs.** Optional `work_dir`; a stage can be `parked` (question) and the run `awaiting_answer`; `claim` skips parked stages and anything whose `depends_on` is not complete; a stage that fails for good is `failed` while independent stages go on; a completed stage's file changed by a later stage is re-checked, reopened only if it fails its checks; `reopen`, `annotate`. Sequential (non-planned) runs behave as before.

**A stage.** `stage_prompt`: the stage, what it hands in, the ledger (stages done and their files, "Carry forward:" facts, the person's answers, amendments), re-check/retry/answer/interrupted notes, the request without its attachment block, and only the stage's inputs as attachments (soul's grounding then asks it to read just those). `stage_finished`: the final gate's own code checks (`produced.store_results`, `typed_totals` when formulas were asked, `verify.false_sums`, `program_numbers`), the runner's artifact checks, then `verify.judge` on the stage's files and drafts. `not_done` -> one more attempt told why; `cannot` -> parked as a question; anything else that is not a confident `done` (unsure, an outage, no model, a blocking code check that raised - `checks_not_made`) -> completed NOT checked (`verify.outcome`, the one decision): later stages go on, and the final report opens "Made, but not everything is checked: ...", lists each such stage under Needs you and is recorded `checked=False` - never "Done - every stage was made and checked" (review 2026-11-02). Figures the cross-check could not settle make the run not checked the same way.

**Check maturity: code blocks only on domain-free invariants (harness audit, 2026-10-21; [harness-audit.md](harness-audit.md)).** Every check in `stage_code_findings` has a name and an entry in `long_task.CHECK_MATURITY`. BLOCKING is only for: the person's files and changes (`removed_residue`, `removed_still_there`, `app_emptied`, source_guard), provenance (`filler_values`: a value typed into a form, `draft_facts`: a fact a draft states - each held by no source and no recorded work, `provenance.py`), own arithmetic (`working`: a cell its own formula contradicts; `false_sums` in the report and drafts), seen in the system (`system_entry`), and `file_facts`' invariants (unstored formulas, a Total row short of its column, a named file not made, placeholders, accounts and recipients on no record, a figure a source contradicts). Everything else is ADVISORY: it never fails a stage, it goes to the stage's judge as evidence (`_judge(evidence=...)`: "What code checks noticed ... not a verdict") and to the person under "Please check" in the final report. LOUD advisories (`LOUD`: `repeated_rows`, a figure that includes rows an input repeats exactly) come first under "Needs you" and in the report's first line ("Done - but N figures include rows the input repeats"); no report wording switches them off. Business rules (holds, refunds, rates, first come, backorders) are never code: they are the request's and the operator's taskRules. A check not listed is advisory. The replay gate runs every check, advisory ones included.

**What blocks, exactly (independent review, 2026-10-21).** Code blocks only on what it decides mechanically and with certainty; a check that guesses is evidence. Provenance (`provenance.Sources.unsourced`) blocks only an amount, an identifier (compared on its digits: spaces, dashes and a country prefix do not count) or an address that no source holds and no ONE arithmetic step explains (a sum, difference, product, quotient or percentage of a figure the text itself states, "12,000 with 18% GST is 14,160", a month's share of a year); dates and letter-and-digit tokens (FY27, 2FA, Q3, SO-5199) are evidence (`doubtful`), and a value only the work's own files explain is said so to the judge (`own_work_only`). A given file the request asks to update, fill or edit - anywhere in it, its attachment block, "it" or "the attached form" included (`source_guard.may_change`) - may change; any other change to a given file is put back with the worker's version kept beside it as "<name> (changed by worker)<ext>", and the stable finding names both. `file_facts` blocks a formula showing an error (#REF!, #DIV/0! - `office.formula_errors`), never a column that stops short or a Total short of its table (`gap_notes`: an intentional blank looks the same). An Office file that does not open blocks (`office.open_status`); a password-protected, Strict Open XML or template file is "not checked", never broken; the run-wide re-check flags only a file that opened when handed in and no longer opens (`produced.no_longer_open`). Figures that include an input's repeated rows are LOUD only when the table has an identifier or a date column, or the repeat is a block copied in order (`table_quality` "loud"); otherwise a quiet line. A long table reaches the judge as its header, the rows the findings name, its totals and an even sample (`produced.sample_table`). `agent/tests/test_correct_work_never_refused.py` holds realistic correct outputs no benchmark saw (a trip total, a due date, FY27 and a phone with its country code, repeated stock rows and intentional blanks, a form the request said to fill, a protected workbook, a title before a name, a removal reversed) that no check may block, and wrong ones that must: every new check passes it.

**The replay gate: every code check passes it before it ships.** All of a stage's code checks live in one function, `long_task.stage_code_findings` (stage_finished calls it; add a new check there by name, never beside it). `agent/tests/test_replay_gate.py` rebuilds saved live runs that were right or nearly right (`replay/<run>/` in the live-run fixtures folder - `DECURIX_TEST_FIXTURES`, by default `decurix-tests/fixtures` outside the repo, never committed: the request, the work folder, the Outbox drafts, the stages as the report gave them, `expected.json`) as planned runs and runs every stage through `stage_code_problems`, then the cross-check's code part (`code_disagreements`, and `model_disagreements` on the places the live model pointed at). A finding outside the run's `expected.json` "allowed" (the known-wrong items of a nearly right run; empty for a right one) fails it. A new check that flags correct work fails here, not on the next live round. Tests that need a live-run fixture skip (naming the missing path) when the folder lacks it (`agent/tests/fixture_paths.py`). A run is added with `decurix-tests/wide/process/build_replay.py`; it stores each PDF's poppler `pdftotext -layout` text (pdf_text/), which the gate reads on every host. The app a request binds to each deliverable (`stage_app`) is checked across the six live requests in `live_requests.json` among the live-run fixtures outside the repository (`DECURIX_TEST_FIXTURES`, default decurix-tests/fixtures; the tests skip without it), shared with the soul's corpus tests (WorkApps, AppsFor, Triage, the named-app nudges).

**Messages mid-run** (`take_message`, off the watcher thread, serialized). `stop` in code. An approval's yes/no goes straight to the gate (`watchers.answer_waiting`), unread. Otherwise one model call: answer(s) to named open questions, amendment (with stages it affects), both, status, unrelated, or **unclear** - then nothing is applied and one confirming question is asked; the reply is read together with the earlier message. An answer unparks only its stage (or, for the question the whole run waits on, goes to the engine as the answer alone, any change beside it). An amendment: ledger, an immediate one-line receipt ("Noted: ... re-checking X, Y"), completed stages it affects plus their dependents reopened, the running stage re-checked when it ends; while a question is pending it is asked again. Unrelated requests stay queued for after the run.

**Questions** (`take_question`). A stage's `query` always parks the stage (posted at once when another stage can run; when only parked stages are left the run asks once with all of them). Asking uses no attempt. The answer re-runs the stage with it leading the prompt ("The person decided: ..."), and any check note from before the question is dropped (round 5: an answer fed into the paused job, behind a stale "not accepted" note, was not applied). Approvals pause the whole run exactly as before. A stage that fails its checks on its last attempt is not the end of the run: it parks with what the check found and "try again (with guidance) / skip it / stop"; independent stages go on. "skip it" leaves it out (reported, with what depended on it).

**A stage's question, in order** (`take_question`; one reading since the harness audit, 2026-10-21). (1) "I ran out of steps/time" is no question: the stage carries on (`_carry_on`, `MAX_CONTINUATIONS`). (2) What only the person can give (`person_keeps`: a password or credentials, a captcha or code, their approval asked for) goes to the person, never to a model or back to the stage. (3) Figures the question gives that do not add up (`verify.false_sums`, code) send it back to recheck. (4) ONE main-brain reading, `route_question` (`ROUTE_SYSTEM`), with the request, its systems and its input files' columns as evidence: PERSON, OWN_TOOLS (its app, screen or means - asked again after that recovery, it goes to the person said as what failed), OWN_READING (re-read the source), SOURCE (leave to use a system or file the request gives), IN_INPUTS (a column of an input table), SETTLED (a sentence of the request answers it), UNCHECKED (something it can check first). Code checks only that a pointer is the request's own sentence, system, file or column word for word - else the person; a decision stage's question is the person's unless it is about its own tools; no model, the person. Each send-back once per stage, at most `MAX_SEND_BACKS` (2) in all (ledger `bounces`). The six phrase lists this replaced (`ABOUT_OWN_TOOLS`, `OWN_MECHANICS`, `PERSON_ONLY`, `OTHER_MEANS`, `source_asked_for`, `request_settles`) kept missing the next wording and fought each other. Then the person: the stage parks; the same question again after an answer parks as "stuck" with what was taken and the ways on. An approval (not a decision stage's) goes to the gate unchanged. After the person: the classifier says when a reply hands the decision back (`hands_back`): `handed_back` answers with what the question proposed, but a decision stage's (or a for-approval stage's) question stays the person's, kept pending; a stuck or stopped stage's reply is try again / skip / stop (`stuck_replies`); then `rescope_after_answer` and `binding_text`. Whether a change keeps what is done is the classifier's reading of the person's own words (`keeps_done`; not known, it is a change - fails safe), and whether a decision stage only lists things for approval is the planner's (`for_approval`; not said, the person is asked). Every live wording is in `stage_questions.json` in the live-run fixtures folder (`DECURIX_TEST_FIXTURES`), run through the whole pipeline by `test_stage_question_corpus.py`: add each new one there.

**Code checks come from the request.** A plan's `must_contain` word is kept only when the request quotes it; a per-item output (one invoice per order) is a pattern (`invoice_*.pdf`, `min_count`), never a placeholder name. The planner gives a decision the request says to ask about its own early stage, so work that does not need it goes on. Each attempt's tokens (and output tokens) are in the ledger; a re-run is given its previous attempt's report so it starts from its own files.

**Cross-check, report, cost.** When nothing more can start: figures under the same label in 2+ outputs (code) and figures the model points to that code finds verbatim are compared at their written precision, as the same kind of fact (a date as a date, an amount in any currency form or declared unit, a percentage on one scale, a sign given by -/+/brackets/words; a name or a code is never a figure - every case in `cross_check_cases.json` in the live-run fixtures folder); the odd one out's stage (majority, else the downstream one) is reopened, at most 2 rounds; the rest go under "Please check" - a cross-check disagreement never makes the headline "Not everything is done" (series 15 H2, 2026-10-21). A disagreement is a different magnitude in the same unit only: no word near a figure decides its sign (the sign-word lists are gone), equal magnitudes written with opposite signs (a recon's -3,926 shortage, a journal's 3,926 debit) are a quiet line, and figures written in other units ("12 BOX", "144 PCS") are not compared. The final report (checked): Done (files, how checked), Not done (each failed stage with attempts and reason, each skipped stage naming what it needed), changes the person made and where applied, answers used, Assumed, cross-check, Needs you (questions, drafts to send, disagreements), and one cost line (minutes, tokens: overhead + per stage; per-stage seconds/tokens kept in `<run>/ledger.json`).

**Restart.** `watchers._report_interrupted` -> `resume_interrupted`: the run bound to the interrupted task carries on once the backend is up (an interrupted stage is told to check what is in place first), or waits again for the open question.

## Decisions the person makes

A stage the planner marks `"decision": true` is the person's: it works out what needs deciding, saves the working file and asks with HELP (a parked question). It never drafts an email for it (`spec_from_plan` sets its drafts to 0; any stage gets drafts only when `asks_for_drafts(request)`), and it is accepted only once the person decided (`decision_problem`). A message read as that decision (`d:<stage id>` in the classifier, or an answer whose words are the decision's rather than the open question's, `_about`) is kept as the stage's decision (`take_decision`): a parked stage runs again with it, a finished one is re-checked; the question it was not the answer to stays open. A stage that asks the same question again after an answer (`same_question`) parks with what was taken and why it did not settle it, and try again / skip it / stop. A draft addressed to one party of the inputs that names another with figures is a code-decided failure (`produced.draft_disclosures`).

**What the person's words decide is the model's reading (independent review and series 15 H1, 2026-10-21).** The classifier reads, for an amendment, `removed` (whole records), `removed_lines` (a line of a record: never the record) and `restored`; for each answer, `excluded`, `restored`, `names` (what it decides about), `undecided` (items the question lists that it does not decide) and, for a finding question, `keep`. Code keeps only names and references the person's message or the question writes, and enforces them: `stage_facts.removed_records`, `excluded_names`, `binding_text` (the whole question, the reading first, "correctly missing" only for what is listed), `_recheck_after_decision`. An answer that leaves listed items undecided gets one follow-up naming only those (`_rest_to_ask`); "use your judgement" to it makes the worker decide each and list it under 'Assumed:' with its money effect, and the final report lists it under "Needs you" (`assumed_for_person`). A blocking finding that comes back on a retry with the worker's "Kept ...: <reason>" line goes to the person as a "finding" question with the model's view as evidence; only their "keep it" clears it (`overrides`). The planner also declares each stage's `enters` (the system it enters records in, or null - the verb test is only a fallback, advisory) and the plan's `payment_details_from_messages` (then a payment to details from a message, for a payee no record has, is put to the person as an approval: `payee_approval`).

**Decisions and stop (round 5, 2026-10-20).** The planner puts every stage whose content can change with a decision after the decision stage and copies the request's rules into each stage word for word. It also declares, for each decision stage, `affects` (the ids of the stages whose work depends on which items its answer lets through) and `for_approval`; a stage it names in `affects` that runs before the decision is marked `before_decision` and redone from the sources after the answer. No word list reads a stage's text for this (the verb lists `computes`/`_DECIDES_WHICH` are gone since the harness audit, 2026-10-21): with `affects` missing, nothing is redone and the decision stage asks. An answer's restatement of a stage (`rescope_after_answer`) is taken only when it adds no word beyond the stage's own title and text, the question and the answer (`restatement_adds`, a few words for in/out aside); otherwise the stage keeps its text and the answer still binds its check. As a safety net, when a question is answered, every stage that finished while it was open and is built on it (depends on the asking stage, reads its file, or its outputs name what was decided) is reopened with the decision leading (`_recheck_after_decision`). A stop is acknowledged at once; the report follows when the running stage's engine ends, at the latest `STOP_GRACE_SECONDS` (30) after the stop, and only once; a report that cannot be put together still says it stopped. A task's final report the control plane could not be told is kept in `~/.decurix/unsent/` and sent again every 30 s (`messaging.resend_unsent`).

**A request of its own mid-run (2026-10-20).** A message that brings its own files or is the request in hand sent again (`new_request_reason`, code), or that the model reads as a new piece of work of its own (`classify` kind "new_request"; a long reply of many points to an open question is still its answer - length and deliverable-word counts were dropped on 2026-10-22), is never read as an answer or a change: it is held (`~/.decurix/held-requests/`) and the person is asked once, as a question, whether to finish the run first, drop it for this, or read it as their answer (`pending_request`). Every question goes as kind query, also on a message's own task. Records the ledger makes from the person's words (answers, decisions, changes, facts) and what the message classifier is shown pass through the secret withholding (`privacy.withhold_known`); the request itself stays as written. A stage's instruction also carries, word for word, the request's sentence for each file it hands in that the request names (`deliverable_words`): those words decide its scope.

**Ordering rules, retries, room (2026-10-20).** The stage that reads the sources records, per line, every attribute a later rule orders by; a stage whose instruction holds an ordering rule is told to apply it with one script on that attribute and show the order served (`ordering_rule`). A retry prompt says the stage is NOT finished and to do all that is left. A stage whose job ran out of steps or of time mid-way carries on with no attempt used (`MAX_CONTINUATIONS` 3) before the person is asked: per-record work on the screen (entering orders one by one) that needs more than one job's room finishes that way, whatever the number of records - the planner cannot know it before the sources are read.

**Delegated answers, own-tooling questions (2026-10-20; read by the model since 2026-10-21).** "Use your judgement", "your call", "fine" and the like answer every open question with what it proposed (`handed_back`, on the classifier's `hands_back`); a question about the worker's own reading of a source goes back to the stage once (`route_question`: OWN_READING); questions to the person name things, never ids (`no_internal_ids`).

**Where money goes (2026-10-20).** The operator's taskRules say, once, that payee details come only from the records the request gives and that a message asking to change them is reported, never applied (no keyword list picks stages, and the stage prompt no longer repeats it, since 2026-10-21). Every produced payment table is checked in code against the input records (`payees.mismatches`, via `produced.file_facts`, so the stage check, the final gate and the tool route all see it); a payment to an account not on record fails the stage and heads the final report with `WARNING -`, and suspicious messages are warned about there too. A payee is on record only when a record's cell is its whole name, word for word, legal form, "M/s" and "&"/"and" aside (`payees.names_payee`: "Ram" is not "Ramesh Traders" nor "Sita Ram Traders", "ABC Pvt Ltd" is not "ABC Traders"; 2026-11-03), and an account or IFSC only exactly. With no master to check against, the payments are `PAYEES NOT CHECKED` (`payees.unchecked`): the final check is left unmade, so the result is not checked, never passed (2026-11-02). Only a payment file counts (`payees.payment_table`): a bank-details column (IFSC/IBAN/SWIFT/UPI, or an account its label or a bank column makes a bank's, never a ledger's "GL Account"/"Account Head") and a column of money paid out ("Amount Payable", "Net Pay"; not "Total Sales" or "Taxable Value") (2026-11-03).

**The report reaches the person (2026-10-20).** The run's message is at most 6,000 characters (warnings first, one line a stage, not done, needs you, cost) and names the full report, saved in the work folder's `decurix-reports/`; any note too long for the control plane is cut where a sentence ends with its whole text saved there, and a refused outcome or question is sent again short (`messaging.send_query`). Each stage's attempt has its own soul conversation (`thebot_harness._session_id`); its prompt carries the ledger. A decided decision stage, and a stage handing in files other stages make, are not failed for leaving them unchanged.

**Records entered in an application (2026-10-20).** An answer part-way through a stage never narrows it: the re-run is told it is not finished and to do all that is left. Entry work is checked from the application (each saved record read back and compared line by line); "every/each" against an earlier stage's table is counted in code (`coverage_problems`, evidence for the judge since 2026-10-21); a wrong record the application cannot correct ("WRONG IN THE APPLICATION:") fails the stage and heads the report.

**Accounts and addresses come from the records (2026-10-20).** Money and drafting stages build accounts and recipients by a lookup from the master, never typed; a draft to an address in no input is not done (`payees.unknown_recipients`), like a payment to an account on no record.

**A change sent after the work was reported (2026-10-21).** `long_task.final_report` keeps the reported run (`~/.decurix/last-reported-run.json`: request, report, outputs). A short message with no files of its own, within `FOLLOW_UP_HOURS` (8) of that report and headed for the general handlers (`watchers._follow_up_or`), is read against it by the model (`follow_up`, `FOLLOW_UP_SYSTEM`: change / question / new). A change becomes a request of its own - the original request, what was reported, the files it made, and the person's words, told to redo only what the change affects in the same files and drafts - planned and checked like any other (`_perform_long`). A question or anything new is handled as it always was; a stopped run is not kept. Found live: series 16 H1, Admin's tie-up hotel limit arrived after the audit was reported and was answered "Got it".

**Earlier findings and a later change (2026-10-21).** Each fact a stage records keeps how many of the person's changes it began with (`seen`); in a later stage's ledger text a fact older than a change made since is listed apart, "found BEFORE a change the person made since (re-check each ... the change wins)", never under "use it; do not work it out again" (`_ledger_text`). Found live: series 15 H3, the fee letters kept billing a pupil the person had taken out.

**A refused stage asks the person to settle the points in dispute (2026-10-21).** The owner's yardstick: a weak brain plus the person's answers must reach what a strong brain reaches alone - intelligence shows as fewer questions, never worse results. So a stage its check keeps refusing no longer asks only "try again / skip it / stop": one reading (`dispute_points`, `DISPUTE_SYSTEM`) turns the finding and the worker's report into at most six points - what the work says, what the check says, the source line - and `stuck_question` asks the person which is right ("1: the work is right"). A reply that says what is right (`settles_something`: more than the go-on words) binds the check like any answer (`binding_text`); "try again" alone still does not. With no points, or no model, the finding is given as before.
