# Skills: learning a task from demonstrations

Modelled on Orby's public description of its Large Action Model — "observe, learn and automate": watch a person do the work (screen, page, actions), generalise it into a workflow, show it to that person to approve, run it. Orby's internals are proprietary (only the loop, a planner/grounder split and "SAIL" interface learning are public), so this is that loop on Decurix's existing parts, not a port of their code. **The rule-based lesson needs no model**, in the spirit of soul's "deterministic before clever": what can be worked out from recordings is, and what cannot is asked. With a hosted model, `study.py` studies the demonstration first and asks its own questions (below, and [learning-and-verification.md](learning-and-verification.md)).

```
person records (a ticket, or several)        the recordings the desktop already makes
  → /learn <recording> [<recording> ...]     learning.build: compile each, align them, generalise
      → one question at a time (ask_for_query) goal / study / start / loop / variable(s) /
                                               optional / coordinates / unsupported / approval / confirm
      → yes  → ~/.decurix/skills/<name>.json  (status "ready"; a draft is saved after every answer)
  → /skill <name> [param=value ...]          trusted: skills.program → replay.run, no model
                                             apprentice (with a hosted model): the engine, guided by the skill
      → asks: a missing value, a screen that is not where the task began, a step that is stuck
      → a correction that then worked is written back into the skill
```

- **Generalising (`learning.build`).** Several demonstrations are aligned step by step (`difflib` over each step's kind and target, never its typed text). What differs between them is the task's shape: text typed differently is a variable that changes every run (no question needed), a step only some demonstrations have is asked about as optional, and a step's expected result shrinks to the checks *every* demonstration agrees on. One demonstration can only ever be one instance, so its typed text is asked about. A person's `note` (the ticket toolbar's Reason) rides along and is shown back in the first question.
- **Questions are derived from the skill's own state, with stable IDs** (`goal`, `study:<id>`, `start`, `loop:<loop id>`, `variable:<step id>`, `optional:<step id>`, `coordinates:<step id>`, `unsupported:<step id>`, `approval`, `confirm`). Several undecided typed values are asked in one question (`variables:<id>+<id>...`), and so are all position-only clicks (`coordinates:<id>+<id>...`); the answer is still kept per step, so a half-answered lesson asks only the rest. A reply to a coordinates question that names a control ("the Save button") points that step at it (`learning._target_named`). A step has an `id` that never changes and an `n` that does (a skipped step renumbers the rest, `skills.renumber`) — a question and its saved answer name the *id*. That is what lets an interrupted lesson be resumed by `/learn` on the same recordings (`skills.draft_for`) and ask only what is left.
- **An unclear answer is never guessed.** `learning.answer` asks again once, then takes `CAUTIOUS[kind]` and says so: typed text *changes* (asked for each run), an uncertain step is *always* required (halts rather than skips), a coordinate click goes to *manual*, a loop stays *fixed*, the start question takes *yes*, the approval question takes *ask*, an unconfirmed skill stays a *draft*. Nothing runs until a person has said yes to the whole skill (`status: "ready"`).
- **Whether a run may start on its own is the teacher's choice** (the `approval` question, `skill["approval"]`). `ask` makes every run from step 1 pause first ("You taught me to check with you before I start ...", reply yes or no); `go` starts at once. A skill taught before this question existed has no answer and runs as it always did. The one place this is decided is `skill_task._start_pause`, called before every way a run from step 1 begins: the replay, the model doing the task while it learns, and the model gathering its documents. Before 2026-11-07 the last two started without the pause. It is about starting the task, never about its steps: the per-action approval gate applies either way, so a "go" skill's gated Send or Pay still stops for its own yes. The engine is told nothing of the choice. `state.request_preapproved`, which once told soul to skip its own check of the request's wording, was removed: soul has no such check now and takes no approval from a request body.
- **A secret is never a parameter.** A typed step whose value the recording withheld becomes a `manual` step (the run stops with `needs_human` and a person types it on the screen) — a skill must not need a password in the chat, the command file or the task record, the same rule `/replay` keeps.
- **The approval gate is not the skill's to switch off.** A step gated when it was recorded is `consequential` and stops for approval every run; the confirm question *tells* the person this, it does not ask. `skill_task` runs everything through `replay.run` → `core.act`, so `approval.check` and the audit trail apply exactly as they do to an engine.
- **Optional steps step over one thing only** (`replay._Halt.missing`): a target that is not on the screen. A target that is *ambiguous* (two candidates), an action that fails, or an expected result that never appears still halts an optional step — the run never guesses between candidates.
- **Running asks instead of failing.** Before the first step: any value the skill learned changes every run and was not given (`/skill x name="Acme"`, or just the value when one is missing), and — if a person said to — that the screen looks like where the recording began (`learning.start_checks`, using `replay.unmet`). When replay halts, `skill_task` asks: `retry` / `skip` / `stop` / `use "<control>"` for a step that did not run, `continue` / `stop` for one that *did* run but whose result never showed (never a retry — that could act twice, the same reasoning as `reconciliation_required`, which is final and never asks). Two replies it cannot read in a row end the run rather than guess, and `MAX_STUCK_ASKS` bounds the questions per run.
- **What a person answers is learned only if it worked.** `use "Save as"` re-targets that step (`_retarget`: same role, new name, the recorded path dropped) on the run's in-memory copy, and `_succeed` writes it into the skill (and bumps `version`, appends to `learned`) only when the run then ended `verified` / `completed_unverified`. A `skip` is this-run-only and changes nothing on disk. Carrying on past the last step (skipped, or done by hand) finishes the task as such, not as a halt at a step that does not exist.
- **Loops** (`learning._find_loops`): a block of 2-60 steps repeated with *different text typed each time* (and every step seen in every demonstration, no manual or `open` step in it) is a candidate, asked about as `loop:<id>`. Since 2026-11-01 the repetitions need not be back to back: up to 60 steps may come between two (`between`: the person opening the next document to read it, making a record it needed) - dropped from the steps on `each`, kept in words on the loop (`between_summaries`) for the model to read when such a case comes up; and what every gap ends with the same way, typed the same (bringing up a fresh form), is the block's first steps, the first repetition being that much shorter (it reached the form another way; a key press counts as the same press whatever had focus). A demonstration of five bills (292 steps, 6-37 steps between bills) is one block of 42. `each` keeps one whole repetition and makes what it types a **list parameter** (`param["list"]`, `examples` holds what the demonstration typed), the extra repetitions' steps dropped; `fixed` (also the cautious default, and a no-op) leaves every step and asks about each typed field as usual. The typed fields of an undecided loop are *not* asked about individually — the loop answer decides what they are. At run time `skills.expand` writes the block out once per item, naming each typed field `<param>__<n>` (and renaming the recorded value check to follow it), keeping every step's `id`; a list is items separated by `;` or a new line, all lists the same length (`skills.list_problem`, asked again whole rather than guessed at), at most `MAX_LOOP_ITEMS`. The run's step numbers are the *expanded* program's, which is why `skill_task._retarget` maps a step number back to the skill's own step by `id`: a correction made in item 2 holds for every item.
- **A task done once per document, whose documents are not in hand** (`skill_task` "The per-document part", 2026-11-01): a run whose list values the request's own files cannot give goes gather -> fill -> replay. Gather: the engine does the steps before the block for this request (`_by_model(phase="gather")`: save every document where the person's steps put theirs, enter nothing, report each file's path); its report comes back through the final gate (`_gate`, guidance mode `phase`) to `_after_phase`. Fill: the documents that appeared since the gather began (`_new_documents`, by modification time under the home folder) are read in one model call for the lists (`binding.fill_lists`, one item per document; a document the person's rules leave out is named under `left_out` as `skip` with its rule, and one that is to be entered but does not fit the taught shape - another number of tax rows, another kind of tax, a value it cannot read - as `by_hand`; a list whose items do not count one per entered document is dropped rather than typed misaligned). The per-item block is the loop that repeats the most steps (`_item_loop`; a navigation repeat before it is not the task's shape), the replay starts at that block's first step id in the expanded program, and a value whose example is an address (a page, a folder) is never asked of the documents (`_needed`). After the replay, the `by_hand` documents go to the model (`_by_model(phase="rest")`: only those, each once, the entered ones named as done), and the replay's result and the model's report are judged as one (`_after_phase(REST_PHASE)` -> `_finish`); an unconfirmed gathered run asks the person rather than giving the model a third pass over work already entered. The rest phase is told the phases in order and what each did (`_rest_how`: the gather's "enter nothing" was that phase's rule, the replay's records are right and stay, every source was read before any record) - found live (2026-11-02) that without it the model called the replay's vouchers a breach of "the settled collection-only restriction" and asked whether to undo them. The files the gather saved are a fact code decides (`_documents_note`: each one's presence and size, which were left out and which entered by hand) and go to the final check and into the report; before that, three months of four ended with the check asking the person because nothing of the gather phase had reached it but the worker's word. Then, while the skill is still an apprentice, the plan is put to the person once (`_plan_text`: the documents, what was left out, each item's values; a plain yes starts it, anything else hands the rest to the model with the person's words); a trusted skill starts at once. Replay: `_execute` from the block's first step (`run["start"] = _loop_start`), `skills.expand` writing the block out per item; a halt hands the rest to the model from that step as any replay's does, and `_finish` judges the result. A gather that saved nothing, or documents that do not give every list, leave the whole task to the model as before (`gathered: "failed"`). Why: the model, told the replay was "the quickest way", worked every item by hand (3-8M tokens a month, the fourth month no cheaper than the first) - docs/token-economy.md.
- **Resuming needs only what is still to run** (`skills.needed_from`): `gui do NAME --from 4` does not ask again for a value only step 2 typed, the way `replay.run` already skips parameters before its start step — except with a loop, whose steps are numbered again per item, where everything is needed.
- **An engine cannot answer a question, so `skill_engine.run` refuses instead**: a missing value, unusable lists, a draft, another run of the same skill still going (its run lock), a request for another app or site than the one the skill works in (`skill_engine.other_system`: one hosted-model call, skipped when the task was handed over as this very skill), or a screen that is not where the task began (only when a person said to check) return `halted_before_effect` with what to do, and nothing happens. It never rewrites a skill — a correction is a person's, made in the chat — and only counts a successful run (`skills.note_run`). `gui do`'s hint for carrying on is `gui do NAME --from N`, not `gui replay` (`cli._print_replay(result, command=...)`). The three engines are told skills exist in their own prompts (`ollama_client.SYSTEM_PROMPT`, `operator.go`'s prompt, `claude_harness.SCREEN_SYSTEM_PROMPT`).
- **The control plane teaches and runs through the same door as a replay** (`httpapi/skills.go`'s `sendTaught`): refused with 409 while the desktop's agent has a task running or paused (a lesson or a skill run sent to a paused agent would be taken as the reply), otherwise Plan → the desktop's `POST /recordings/<id>/learn` or `POST /skills/<name>/run` → Commit. Unlike a replay's, a skill's parameters *are* in the request the chat shows (`/skill add-a-customer customer_name="Acme"`), because a skill has no secret parameter — a secret is a step a person does by hand. A value that is secret by its form is still held back from the gate's copy and the recorder (`withParamSecrets`, a second wall). `skillContent` (Go) and `skill_task.request_text` (Python) build the same string and are each tested against the same expected value; change one and the other's test says so. A value holding both kinds of quote cannot be written into a request and is refused (400), not bent.
- **A `/learn` conversation is a task that is not an attempt**: `tasks.Classify` types it `teaching` and `tasks.Report` skips it like a demonstration, because every question it asks is the point and not a person stepping in. A `/skill` run is `screen` and *is* counted: a skill that had to ask something is, correctly, not autonomous.
- **Verified live, not just in tests** (`bench/skills/e2e.py`): a real `decurix-desktop:basic` container running this tree's agent, a mock control plane on the host catching its questions, and real Chromium on a local form. The agent records two demonstrations of a task through `gui`; `/learn` on both asks two questions (when it is finished, and whether to save — it learned from the two demonstrations that the name changes, and dropped the "Saved <name>" check that differed between them); `/skill` asks for the value and the page really shows it; after the form's button is renamed the skill stops and asks, `use "Save changes"` finishes the run, and the correction is in the saved skill. Run it after touching the agent side; it needs Docker and a built image and takes about two minutes.
- **Values come from the run's documents when a hosted model is there** (`decurix_agent/binding.py`). A `/skill` request's first line is the command; lines after it are the run's context (an email trigger's rendered email and its attachment paths - `mailtrigger.RenderWithFiles` appends them to `/skill` rules only, every other slash command is still sent as written). Values the command does not give are read from that context and the files it names (`office.read_document`; scans as pictures) by one `llm_client.chat` call that is given each parameter's name, the field it is typed into and the demonstration's value **as an example of which thing to read, never as the answer**; each filled value carries where it was read, and the run's report lists them ("Values read from the documents"). What the documents do not show is asked for exactly as before - or, for a run the model does while still learning the task, left for it to read from its sources itself: such a run is handed **only values the request and its documents hold** (as written, or the same amount; table rows only when some of their values are held), because a value handed on reads as the person's and the final check holds the work to it (`binding.fill(strict=True)`, 2026-10-24); a replay still gets a value worked out or guessed, marked "not written so ... check it"; values still go through the constraint and list checks, and consequential steps still stop for approval. No model (`DECURIX_LLM` unset): nothing changes. Pulling a value out of a chat *sentence* is still not done.
- **A task the model does while still learning it is not stopped by a value its documents do not have** (`skill_task._prepare`). One demonstration fixes the task's shape to what it showed: an application bill taught from two lines made `item_2`/`typed_text_4` required, and the next bill had one line - the run asked for the second item before doing anything, and "there is no second line" could not answer that question (found live, 2026-10-07). When the run would go to the model (`_learning_by_model`) and the documents have been read (`run["filled"]`), what they did not give is left to the model, which reads them and the lesson itself. Lists that do not line up and values a field refuses are still asked for; a replay (a trusted skill, no model) still asks for every value.
- **A lesson settles the rules of the work, not only its clicks** (`study.BRIEF_TOPICS`, 2026-10-27). The study fills a workflow brief, one entry per topic every run of a kind of work turns on: where the work comes from and how to find all of it; what to do with a revised, cancelled, repeated or someone else's document; where files are kept and how they are named; how an existing record is found and when a new one is made; where each value comes from and how a document becomes records; what to check before entering; what needs the person's OK and what is never done; the proof of done and what the report says; what to do when a value cannot be read or found. Each entry is `seen` (with where the recording shows it), `assumed` or `unknown`. The read-back question shows them numbered with where each came from ("seen: step 4" / "my guess, please confirm"); a plain yes confirms the guesses (`study.confirm`), a correction is folded in (`study.absorb`); every `unknown` topic no question of the model's covers gets its own question, asked first (`_brief_questions`), and the model is told to ask about every doubt the recording left (a step with no visible reason, a value not found in the documents). The brief becomes `[topic] rule` lines in `understanding.rules`, which every run follows and its final check is held to (`skill_task._taught`). Found live: each topic was a failure a run met with no rule for it. A study that gives no brief at all keeps the old lesson.
## Since the review of 2026-11-03

- **Teaching answers (D-21, D-22).** A reply is decided in code only when it is, whole, a plain phrase of one choice (`learning.PLAIN`). Otherwise it is read by `approval.read_choice`, and with no model it is asked again. At the last question a name is put back to the person ("I will save it as ...") and only a plain yes saves.
- **A skill runs only by its exact name, slug or title.** Words only suggest one (D-16).
- **Procedures with no model.** With no model, nothing is kept as a standing procedure, and a later request gets one only when it names it whole. Two shared words are not a match (E-28).
- **Playbooks.** A playbook's shape and name are read from the request with its secrets withheld, and `playbooks.save` scrubs the book. A script holding a secret or a credential is not kept. `playbooks.find` is a word pre-filter only; a tool runs with no engine only on `tool_task.read_args`' fits reading.
- **Learned scripts run in the sandbox** with a pid namespace too, so nothing a script starts outlives it ([gate-boundary.md](gate-boundary.md)).
