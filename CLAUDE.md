# Decurix

Decurix is a control plane for spinning up disposable "desktop" VMs (Docker containers running a full XFCE desktop over VNC) and driving them with an autonomous AI agent. A Go server manages desktops via the Docker API; each desktop container runs a Python agent that watches for tasks, executes shell commands to get them done, and raises a query with a human through the control plane when it's stuck.

## Architecture

```
cmd/decurix/main.go — entrypoint: loads .env, builds the Docker client, wires
                       the packages below, registers routes, ListenAndServe(:8080)
                       plus a second, access-code-gated ListenAndServe (:8090 by
                       default - see "Two listeners, one process, one set of
                       routes" below); --version, and --build-images/--rebuild
                       which build the
                       desktop images from the embedded context and exit;
                       --cli, which skips all of the above and hands off to
                       cli.go instead (see "The --cli terminal client" below)
cli.go             — runCLI: an interactive REPL that is the same binary's
                       --cli mode, a text alternative to the dashboard/chat
                       page for a control plane already running somewhere -
                       reached purely over internal/httpapi's existing JSON
                       API (GET/POST /api/desktops*, /api/querynotes), so it
                       needs no Docker client and no database of its own
embed.go           — package decurix at the MODULE ROOT: //go:embed of
                       docker/desktop.*.Dockerfile + agent/ → DesktopBuildContext.
                       It has to live at the root because go:embed cannot reach
                       above its own directory and the context spans two dirs.

internal/desktop   — owns the Docker client; desktop image build
                      (images.go: MissingImages/BuildImages, tars
                      decurix.DesktopBuildContext to the daemon); container CRUD
                      (Create/Start/Stop/Restart/Delete/List), image/network
                      ensure, SendRequest (POST to a desktop's :8081),
                      List/desktopFromContainer: one ContainerInspect per
                      desktop, fanned out up to listInspectConcurrency (8) at
                      once rather than one at a time — List is what the
                      dashboard, the JSON API and internal/idlepause's sweep
                      all call, so its cost has to stay roughly flat as the
                      desktop count grows, not linear in wall-clock time,
                      LastViewed (screenshot.go/proxy.go touch it on every
                      thumbnail fetch and every proxied screen request — the
                      "someone has this open" signal internal/idlepause reads,
                      cleaned up in Delete alongside the shots cache),
                      ProxyTarget (resolves the VNC reverse-proxy address),
                      AgentRequest (recordings.go: one call to a desktop's :8081 API,
                      how recordings are read off the desktop rather than copied),
                      PersistMemoryFile (docker-exec write into a desktop),
                      claudelogin.go: the interactive half of the shared Claude
                      Code login (StartClaudeLogin/SubmitClaudeLoginCode/
                      CancelClaudeLogin, driving `claude auth login` in a
                      throwaway container so the dashboard's popup can hand a
                      human its sign-in URL and feed back the verification
                      code) and PersistClaudeCredentials (PersistMemoryFile's
                      write-into-a-desktop pattern, seeding a new claude-harness
                      desktop with the session internal/claudeauth stored),
                      Screenshot (screenshot.go: a minimal RFB client that reads
                      a desktop's framebuffer straight off Xvnc:5901 and returns
                      a cached JPEG thumbnail — what the dashboard cards show),
                      sandbox.go (the seccomp profile + core-dump ulimit every new
                      desktop is created with — what lets Chromium run sandboxed;
                      the profile itself is seccomp-desktop.json, go:embed'ed)
internal/ollama    — DesktopURL/DesktopModel (the Ollama every desktop is given) and
                      preloading the model there at startup, plus WarmAsync (debounced
                      background warm-up called when a desktop starts, a chat opens or a
                      request is sent - see the memory-starved-host gotcha at the end); also the lifecycle of the
                      bundled "decurix-ollama" container, used only when OLLAMA_URL names it
                      select.go/autoselect.go/resources.go (+ mem_<os>.go): the model
                      chooser - probes RAM/CPU/GPU and picks the smartest chat model that
                      fits 50% of what is free (see "The chat model is chosen for this
                      machine" below); served at GET /api/model (httpapi/model.go) and
                      shown as the chip at the top left of every page (theme.html's
                      "topbar")
internal/sqlitedb  — opens the one embedded SQLite database (modernc.org/sqlite, pure Go,
                      so releases stay CGO_ENABLED=0) at DECURIX_DATA_DIR/decurix.db, and
                      Migrate(db, component, steps): each store below owns its own tables
                      and appends schema steps, never edits an applied one
internal/querynotes — queries submitted by agents (SQLite). A note is resolved, never deleted: List is the open
                      ones (the rail, the badge, the Queries tab), ListResolved the history
internal/memory    — worker-memory entries (SQLite); deleted with the desktop they were learned on (DeleteForDesktop)
internal/conversation — per-desktop chat transcript: the requests and replies a human and a
                      desktop's agent exchanged (each tagged with its task ID and the
                      human's verdict), plus the live steps of the turn running right
                      now. Served from memory, written through to SQLite, loaded back
                      per thread on first use. What makes a desktop's chat the same on
                      every device
internal/stepimages — byte-bounded SQLite store of the before/after screenshots attached
                      to on-screen action steps (PNG in, JPEG out), served at
                      /api/desktops/step-image; the desktop keeps the full-size originals
internal/tasks     — the task records: Task → Execution → Steps → Interventions →
                      Outcome, per Worker (a desktop ID, kept after its container is
                      deleted). store.go routes a human request (Plan/Commit: new task,
                      reply to an open intervention, or retry of a failed task), attributes
                      steps and outcomes (by echoed task ID, else the worker's live
                      execution), verdicts, CloseOpen on stop/restart/delete. classify.go:
                      deterministic task type and intervention reason ("/learn" is type
                      `teaching`, kept out of autonomy like a demonstration; "/skill" is
                      `screen`). report.go: autonomy by engine/worker/type and the
                      reasons people stepped in
internal/winhost   — runs a Windows app on a PRIVATE WIN32 DESKTOP of the host, so it has no
                      window on the person's own screen, and lets the control plane see
                      and drive it: bridge.ps1 (embedded; the Windows half) is spoken to
                      over the stdin/stdout of the process that runs it - no listener, so
                      nothing but the Manager that started it can reach the app. Manager/
                      Session: one session per id plus ONE WARM SPARE helper (a launch
                      finds a helper already running, and one is started for the next);
                      the helper pushes pictures (Watch/Viewer: a whole picture first, then
                      only the rectangle that changed), Do/Mouse/Wheel/Type/Key, Copy/Paste,
                      Check (which programs can run hidden, from the same helper), Stop/StopAll;
                      token.go signs and checks the launch tokens (LoadSecret keeps the key in the data dir). Takes its host
                      command as a Starter, so it depends on nothing internal and is tested
                      against a bash fake speaking the same line protocol
internal/tunnel    — in-memory store of the addresses scripts/linux/build.sh
                      (or rebuild.sh, or their Windows twins) discovers and
                      reports via POST /api/tunnel: a Cloudflare quick tunnel
                      URL for the gated listener below (LANTunnelURL) and this
                      machine's own LAN address for it (LANURL), surfaced in
                      the dashboard's Mobile menu; Get/AdminURL (the primary
                      listener's) are legacy - no current script reports them
internal/idlepause — Checker.Run: a ticker that stops a desktop once it has sat
                      idle (tasks.Store.Busy empty, and past Threshold since the
                      later of its container's own start time, its last task
                      activity, and desktop.Manager.LastViewed) - on by default
                      at 5 minutes (cmd/decurix.defaultIdleStopMinutes),
                      DECURIX_IDLE_STOP_MINUTES=0 opts out, and it never does
                      more than the same Stop a human's own button does
internal/lanaccess — Store: the rotating access code gating the second,
                      LAN-facing listener main.go starts alongside the
                      primary one (see "Two listeners, one process, one set of
                      routes" below) - Middleware shows an "enter the code"
                      page to anything without a valid session cookie, Rotate
                      replaces the code and drops every session it granted,
                      RunAutoRotate calls Rotate on its own every
                      AutoRotateInterval (48h) so a leaked code doesn't stay
                      valid indefinitely - always started (see idlepause's
                      "always started" precedent), same non-positive-disables
                      contract. Depends on nothing internal by design, same
                      tier as tunnel/sqlitedb: it must never be able to
                      reach, and must never be reached by, the primary
                      listener's own routing
internal/devices   — the phones/laptops paired with the gated listener ("Remember this
                      device" on the access-code page): a long-lived token per device,
                      stored as a SHA-256 only, surviving code rotation until revoked from
                      the Mobile menu (/api/lan-access/devices*, primary listener only).
                      Implements lanaccess.DeviceRegistry, so lanaccess stays dependency-free
internal/llm       — the hosted models a desktop's brain can be: Claude (claude.go: the
                      OpenAI chat shape translated to the Messages API through the official
                      Go SDK - system/tool calls/tool results/images, turns merged to
                      alternate, temperature dropped and forced tool_choice made "auto"
                      because the current models refuse both) and Azure AI Foundry (Client,
                      api-key added). Hub holds both, set up by a PERSON in the create
                      dialog (never .env) and saved in SQLite with the key sealed (llm.key);
                      Save runs Test first, so a key the provider refuses is never kept, and
                      an empty key on a save keeps the saved one. Served on the primary
                      listener only: /api/llm/<provider>/{chat,v1/chat/completions,v1/models}
                      for the desktops (/api/llm/chat is Azure, for older desktops),
                      /api/llm/settings{,/forget} humansOnly. Resolve allows only
                      "default"/"fast". /api/llm (both listeners) is the status, never a key.
                      Depends on sqlitedb and sealed
internal/outbox    — emails agents drafted (the azure harness's draft_email, POST /api/outbox
                      from a desktop), waiting for a person: the Triggers page's Outbox lists
                      them with their attachments, and only a person's Send (humansOnly)
                      hands one to mailtrigger.Store.SendMail. Claim (draft -> sending) makes
                      a double click send once; a send interrupted by a restart is marked
                      failed, never resent on its own. Depends on nothing internal but sqlitedb
internal/sealed    — AES-256-GCM for the few secrets kept in SQLite, key in a file of its
                      own in the data dir (mailtrigger's mail.key, cftunnel's cloudflare.key)
internal/cftunnel  — "Your own link": a named Cloudflare Tunnel giving the gated listener a
                      fixed https://<name>.<domain> instead of a quick tunnel's changing URL.
                      Configure does the Cloudflare side once through the API (zone, a
                      remotely-managed tunnel, ingress to 127.0.0.1:<gated port> only + a
                      404 catch-all, a proxied CNAME); Run keeps `cloudflared tunnel run` as
                      a supervised child (token in TUNNEL_TOKEN, never argv). Several
                      connectors can run one tunnel - Cloudflare picks any that is up - which
                      is what a multi-device setup will build on
internal/wsconn    — the one WebSocket implementation (RFC 6455, hand-written, no library):
                      Upgrade (server side: the host-app viewer, the phone link, the phone-app
                      viewer) and Dial (client side: the phone agent dialling out)
internal/phonehost — the control plane's end of a phone link: Hub.Serve runs one linked
                      phone's WebSocket; Apps asks it for its installed apps (cached 2 min),
                      Open starts an app on a new virtual display of the phone and returns a
                      Session (video frames out, Input in). Depends on nothing internal but wsconn
internal/phoneagent — the phone's end, run by `decurix --phone` in Termux on an Android phone:
                      pairs with a pairing link (Pair, like the "Pair this device" form), dials
                      /api/phones/connect with its device cookie, and drives the phone through
                      local ADB and scrcpy's own server (pinned v4.1, downloaded once and checked
                      against the release's SHA-256): list_apps for the app list, and per opened
                      app one server with new_display=WxH/dpi plus a START_APP control message.
                      Depends on nothing internal but wsconn and phonehost (the protocol)
internal/claudeauth — the one shared Claude Code login every claude-harness
                      desktop is seeded from (in place of an ANTHROPIC_API_KEY):
                      a single-row SQLite table holding the raw
                      ~/.claude/.credentials.json content plus the account's
                      email, so it survives a control-plane restart, build.sh
                      leaves it alone, and rebuild.sh wipes it for free as part
                      of wiping decurix-data — no script changes needed for
                      either half of that
internal/schedule  — recurring or one-time-future requests set up from the
                      requests page (not the chat): Store persists each one
                      (desktop, request text, either a standard 5-field cron
                      expression or a single future run time (RunOnce), next/
                      last run) in SQLite; cron.go is a small pure-Go
                      parser/matcher (no external dependency, matching the
                      sqlitedb/modernc.org choice to stay CGO_ENABLED=0) with
                      the standard day-of-month/day-of-week OR rule, run in
                      UTC. Runner ticks (20s default) and fires a schedule
                      through the Submitter interface once its next-run time
                      has arrived, appending "\n\nTIME:{<RFC3339>}" to the
                      request text so the agent knows when that run
                      triggered; a recurring schedule always advances to its
                      next occurrence after firing (success or not), so a
                      control-plane outage causes one catch-up run on
                      restart, never a backlog - a RunOnce schedule instead
                      disables itself after its one firing, the same
                      terminal state a cron schedule reaches when it runs out
                      of matches. Depends on nothing internal but sqlitedb
internal/mailtrigger — email triggers (set up on the Triggers page, /triggers, or from the
                      requests page's compose form; /email redirects there): a mailbox
                      connection (Account: IMAP over TLS, an app password
                      encrypted in SQLite - secret.go - and never serialised)
                      is polled every DECURIX_MAIL_POLL_SECONDS (60); each
                      email above the last UID read is matched against that
                      mailbox's rules (a case-insensitive regex on the sender
                      and/or subject) and a match queues a Job (the rule's
                      request + the email, Render) that goes out through
                      SubmitTracked - the automated door, which sends only to
                      a free desktop. store.go (mailboxes, RecordPoll),
                      rules.go, jobs.go (claim -> send -> sent/retry/failed),
                      runner.go (poll, match, dispatch, sleep detection),
                      imap.go (a hand-written read-only client: EXAMINE,
                      BODY.PEEK - never marks anything read), message.go
                      (headers/MIME to text; the provider's own DMARC/DKIM
                      verdict for Rule.VerifiedOnly). Depends on nothing
                      internal but sqlitedb (Submitter is a narrowed
                      interface over *httpapi.Server)
internal/keepawake — keeps the machine from idle-sleeping while something
                      needs it awake (Keeper.Wanted: a watched mailbox, a
                      waiting schedule or DAG cron) and releases it the moment
                      nothing does: SetThreadExecutionState on Windows (a
                      locked OS thread), a powershell.exe helper fed on/off over
                      stdin under WSL, systemd-inhibit on Linux, caffeinate on
                      macOS. Inside a container it does nothing and
                      GET /api/keep-awake tells the host script instead
                      (scripts/*/lib/keep-awake.sh, Keep-Awake.ps1). Depends on
                      nothing internal
internal/suggest   — picks a desktop for a request before it is sent, for the
                      requests page's compose form: the one most recently
                      actually in use, or - when some desktop's own worker
                      memory (internal/memory) closely matches the typed
                      request - that desktop instead. Mirrors idlepause's
                      narrow-interface pattern (DesktopLister/ActivityStore,
                      plus a MemoryLister over memory.Store) so it needs no
                      changes to desktop/tasks/memory themselves. Embeds text
                      through the shared Ollama (ollama.Embed, EmbedModel)
                      and ranks by cosine similarity; a memory entry's
                      embedding is cached in its own SQLite table
                      (suggestion_embeddings) the first time it's compared
                      against, so a suggest call after that only ever pays
                      for one embedding round trip - the typed text's own.
                      Every failure path (no Ollama, no embedding model,
                      nothing in memory yet) just falls back to recency and
                      never blocks or fails sending a request - the same
                      best-effort posture ollama.Manager.preloadModel already
                      takes. Depends on desktop (narrow interface), tasks
                      (narrow interface), memory (narrow interface), ollama,
                      sqlitedb
internal/httpapi   — the only package touching net/http; all HTTP handlers,
                      composes desktop+querynotes+memory+conversation+stepimages+tasks+
                      tunnel+claudeauth+lanaccess+schedule+suggest+webui. schedules.go: the
                      requests page's recurring-request CRUD (/api/schedules,
                      .../create, .../delete, .../toggle) and Server.Submit, which
                      implements schedule.Submitter by calling the same submitRequest
                      every human-typed request already goes through - a schedule's
                      fired request is a fourth door onto Plan/deliver/Commit, after
                      the chat, the requests page and a query reply. lanaccess.go: the two routes
                      RegisterLocalRoutes registers only on the primary listener -
                      the current LAN/tunnel access code and the button that rotates
                      it - never served back over the listener that code itself
                      gates. claudeauth.go: the dashboard's Claude
                      login popup (/api/claude-auth/status + login/start + login/code
                      + login/cancel), backed by desktop.Manager's claudelogin.go and
                      saved through claudeauth.Store. hostgui.go: the host-gui API
                      (/api/host-gui/start|ws|stop and the /host-gui/view page; the ws route uses
                      internal/wsconn, hand-written RFC 6455 - no library, to keep the binary static):
                      a copied Windows app's launcher in a VM opens that page in the VM's own
                      browser, which shows the app and sends the person's mouse and keyboard
                      back - see "Windows apps run on the host and show in the VM" below.
                      recordings.go (incl. the import of a recording made elsewhere): the recordings page and the
                      /api/desktops/recordings* + /api/desktops/demonstration proxy, replay
                      as a task (Busy check, Plan/Commit, parameters never recorded), and the
                      ticket API (/api/desktops/record opens one, /api/desktops/ticket* drives
                      it - the GUI screen's own toolbar). proxy.go: desktopProxyHandler's
                      injectTicketToolbar splices that toolbar into every load of the screen.
                      activity.go: GET /api/desktops/activity, what each dashboard card
                      says its desktop is doing (read off the chat snapshot).
                      skills.go: the skills page and its API (/skills/<id>, /api/desktops/skills*,
                      /api/desktops/recordings/learn) - list/show/delete proxied to the desktop's
                      :8081, and "teach" and "run" as tasks (Busy check, Plan, the desktop's own
                      endpoint, Commit) exactly like a replay, with skillContent/learnContent
                      building the "/skill ..." and "/learn ..." request the chat shows
internal/webui     — html/template rendering (PageData, dashboard/requests/desktop-view
                      pages); parses out of web.TemplatesFS, never off disk.
                      render_test.go executes every page, so a broken template fails
                      the test run instead of the first request that reaches it
web/embed.go       — //go:embed templates/*.html → web.TemplatesFS and favicon.svg →
                      web.FaviconSVG; what makes the compiled binary standalone
                      (package web has no internal deps)
web/novnc/         — rfb.js: noVNC 1.6.0's core bundled into one ES module (MPL 2.0, see
                      its README for the rebuild command), embedded as web.NoVNC and served
                      once, cached for good, at /static/novnc/rfb-1.6.0.js - what the screen
                      viewer (templates/screen.html) runs
web/favicon.svg    — the brand mark (theme.html's #i-blossom on a filled tile), served
                      at /favicon.svg by httpapi.faviconHandler and linked from the
                      shared "theme" head partial, so it shows in the browser tab
web/templates/     — theme.html (shared design tokens + icon sprite + top bar +
                      chrome JS, pulled in by every page via {{template "theme"}} /
                      "sprite" / "topbar" / "chrome-js"; parsed alongside each page
                      by webui.templatePaths), dashboard.html, index.html,
                      requests.html, desktop.html (the per-desktop chat behind the
                      dashboard's Chat button — one chat for every harness, and
                      nothing else on the page; the screen opens in its own tab),
                      screen.html (a desktop's screen, /desktop/<id>/: see "The screen is
                      the control plane's page" below),
                      hostgui.html (the viewer for one app running on a private host
                      desktop: a canvas drawn from patches pushed over one WebSocket, which
                      also carries the input back), tasks.html (the autonomy dashboard, /tasks), task.html (one
                      task record with its steps, screenshots, interventions, verdict)
                      recordings.html (/recordings/<id>: record a demonstration,
                      browse recordings step by step, replay, export, and Teach - which
                      starts a lesson from it and any other demonstrations picked) and
                      skills.html (/skills/<id>: what the desktop was taught - run one
                      with its values, see its steps, delete it, finish an unfinished lesson)

  │    Google Chrome stable behind /usr/bin/chromium-browser (see "The browser is Google Chrome" below)
  ├─ XDG autostart (agent/decurix-agent.desktop) → agent/start_agent_terminal.sh
  │    → /opt/vm_server.py (detached background process, no visible terminal); it
  │    also reinstalls agent/chromium-browser.init as ~/.chromium-browser.init (the
  │    browser's launch flags) and clears core dumps Chromium left behind
  └─ decurix_agent/ (Python package, imported by vm_server.py; :8081 inside the container)
        ├─ config.py       — env vars (incl. AGENT_HARNESS), /home/headless/.decurix/
        │                     {command,querytext,final,memory} dirs and /home/headless/work
        ├─ state.py        — shared mutable state (current_task, waiting_for_query, ...) as
        │                     plain module attributes; every other module does
        │                     `from decurix_agent import state` and reads/writes
        │                     state.current_task etc. (module singleton = shared globals)
        ├─ identity.py     — get_identity_context(engine): who this desktop is (name, ID,
        │                     user, work dir), as facts for the system prompt. Shared by all
        │                     three harnesses - without it "what's your desktop name?" was
        │                     unanswerable and came back as a query
        ├─ memory_context.py — get_memory_context: reads ~/.decurix/memory/*.txt; shared
        │                     by all three harnesses below
        ├─ messaging.py    — save_request (intake), send_query/ask_for_query/write_final_reply
        │                     and backend_failure_note (turns a raw engine error into a note
        │                     that says what to do about it)
        │                     (POSTs to control plane /api/querytext, with kind+reply so the
        │                     chat needn't re-parse the note) — shared by all three harnesses
        ├─ readiness.py    — wait_for_http_ok(url, label): the one "is it up yet" probe,
        │                     shared by every harness that has a backend to wait for. Never
        │                     raises and never gives up - "not up yet" is a state to sit in
        ├─ task_context.py — the control plane's task ID for the request being worked on:
        │                     carried in the command file's name (<stem>.t<16 hex>.txt), set
        │                     by watchers.py, and written to /tmp/decurix-current-task so the
        │                     `gui` command and the MCP server (other processes) report it too
        ├─ usage.py        — per-task model/tokens/cost totals each harness adds to, sent by
        │                     messaging.send_query with every reply
        ├─ progress.py     — emit(): POSTs one live activity line to the control plane's
        │                     /api/agent/events, on a single background sender thread with a
        │                     bounded queue. Best-effort and harness-agnostic: this is what
        │                     makes the chat's step-by-step view identical for all three
        ├─ harness.py      — the ONLY place that branches on AGENT_HARNESS; re-exports
        │                     perform_task/continue_after_query from whichever harness below
        │                     is active, with identical signatures, plus wait_for_backend()
        │                     which blocks until that harness's engine is reachable and then
        │                     sets state.backend_ready - the flag watchers.py gates on
        ├─ ollama_client.py + parser.py + commands.py + task_runner.py
        │                   — the "ollama" harness: hand-rolled COMMAND:/DONE:/HELP: loop
        │                     driving a local Ollama model
        ├─ claude_harness.py
        │                   — the "claude" harness: shells out to the `claude` CLI in
        │                     non-interactive mode per task; Claude Code runs its own
        │                     agentic loop internally, so this just streams its events to
        │                     progress.emit and maps the final "result" event to
        │                     write_final_reply/ask_for_query, and tracks a session_id
        │                     (module-private state) to --resume across
        │                     ask_for_query ⇄ human-response round trips
        ├─ azure_harness.py + llm_client.py
        │                   — the "azure" harness ("Office (GPT)" in the create dialog): a
        │                     tool-calling loop on the hosted model, reached through the
        │                     control plane (llm_client -> /api/llm/chat). Tools: shell (the
        │                     dangerous ones wait for a yes), the MCP server's own screen /
        │                     recording / skill tools (so the approval gate and the audit trail
        │                     apply as for Claude), tools/office.py (read_document, read/create/
        │                     update_workbook, combine_pdf), draft_email (to the Outbox - it can
        │                     never send), ask_human, finish. A pause keeps the conversation in
        │                     module state; continue_after_query answers the paused tool call.
        │                     llm_client also answers every harness's ask_model when DECURIX_LLM=1
        ├─ study.py        — /learn with a hosted model: the model studies the demonstration (steps, notes,
        │                     key screens) into an `understanding`, asks only what it could not work out, one
        │                     at a time, folds each answer in (see "A worker learns with the brain" below)
        ├─ verify.py       — the check before any success is reported: the model judges the screen now,
        │                     the demonstration's end screen and what the tools observed; done / not_done /
        │                     unsure, and only a confident done is done
        ├─ guidance.py     — a taught task handed to the engine: what its model is told, and what the final
        │                     gate checks the engine's "done" against
        ├─ binding.py      — a taught skill's values read from the run's documents by the hosted model
        │                     (each parameter's recorded value is the example of what to read); used by
        │                     skill_task when a /skill run was not given them - see "Values come from the
        │                     run's documents" below
        ├─ tools/office.py — documents for back-office work, also the `office` shell command: PDFs
        │                     (pdftotext; a scan is shown as page pictures), images, workbooks
        │                     (openpyxl), Word, .eml. update_workbook edits the sheet XML in place
        │                     (openpyxl drops charts): cells, plus replace_refs to extend what
        │                     charts/tables/names read; fullCalcOnLoad, calcChain dropped
        ├─ thebot_harness.py
        │                   — the "thebot" harness: TheBot's `soul` binary (agent/thebot/,
        │                     its own Go module, built into all three images and started as a
        │                     daemon by start_agent_terminal.sh) is a persistent HTTP server
        │                     with its own atomizer/scheduler/skills loop. This submits the
        │                     task, the standing context (identity + worker memory + approval
```

Control plane → desktop communication happens over the Docker bridge network `decurix-network` (container name `desktop_<id>`, not published ports). Desktop → control plane communication uses `CONTROL_PLANE_URL` (`http://decurix:8080` over `decurix-network` when the control plane runs from `docker-compose.yaml`, which sets `DECURIX_CONTROL_PLANE_URL`; `http://host.docker.internal:8080` for the released binary on the host, see `desktop.controlPlaneURL`) — always the primary listener below, never the gated one, since an agent's own callbacks must never depend on a human having typed an access code anywhere.

**Two listeners, one process, one set of routes.** `cmd/decurix/main.go` builds two `*http.ServeMux`s from the same `Server` and calls `RegisterRoutes` on both, so they serve identical behavior; only `RegisterLocalRoutes` (the LAN access code + rotate button, see `internal/httpapi`'s `lanaccess.go` above) is added to one of them. The primary listener (`:8080`) has no login, and what it serves is host-level power: it creates desktops (Docker socket) and `/api/host-bridge/*` runs commands on the host. So it is **never exposed beyond this machine and its own desktops**, by four independent layers: (1) `docker-compose.yaml` publishes it on `${DECURIX_ADMIN_BIND:-127.0.0.1}` only, so the LAN cannot reach it; desktops call back over `decurix-network` instead of through the published port (`DECURIX_CONTROL_PLANE_URL=http://decurix:8080`); (2) no script tunnels it - `scripts/*/build.sh`/`rebuild.sh` open exactly one Cloudflare quick tunnel, to the gated listener (`lan_tunnel_url`), and their foreground loop only keeps the script alive; (3) `httpapi.RefuseForwarded` wraps it and answers 403 to any request carrying `Cf-Connecting-Ip`/`Cf-Ray`/`X-Forwarded-*`/`Forwarded`/`X-Real-Ip`, so a stale script or a hand-run `cloudflared` pointed at `127.0.0.1:8080` gets nothing (a safety net, not the boundary - headers are a deny-list); (4) `RegisterLocalRoutes` puts everything that runs or shows something on the host (`/api/host-bridge/{exec,open,clip}`, `/api/host-gui/*`, `/host-gui/view`) and the access code itself on the primary mux only, so the gated listener - reachable by anyone holding the code - has no route to host code execution (`TestHostRoutesAreOnlyOnThePrimaryListener` pins the split; a test that needs those routes must call `RegisterLocalRoutes` too). The second listener (`:8090` by default, `DECURIX_LAN_PORT`) is wrapped in `internal/lanaccess.Store.Middleware` and gives out a rotating access code (shown in the dashboard's Mobile menu) before granting a session cookie - published on all interfaces, reachable on the local network as `lan_url` and off it through its own tunnel; see the lockout note on `lanaccess.Store.recordFailure` below for what changes once real tunnel traffic reaches it. **Consequence:** a desktop created before this change has `CONTROL_PLANE_URL=http://host.docker.internal:8080` baked in, and on a native-Linux host that address (the docker0 gateway) no longer reaches a port published on loopback - recreate such desktops. **The host bridge only runs what a launcher was signed for.** Anything running in a desktop (an agent that browses the web and runs shell commands) can reach the primary listener over `decurix-network`, so `/api/host-bridge/exec` requires `desktop` + `token`, where `token` is `winhost.ExecToken` (HMAC over the desktop ID, program and the JSON-encoded arguments, keyed by the same `hostgui.key` as launch tokens; `ValidExecToken` in `hostBridgeExecHandler`). A launcher gets its token from `hostFallback` when the app is copied; the arguments must match exactly, so a launcher's own `"$@"` is no longer passed on. `host-run` has three modes only - `open <http(s) link>`, `clip`, `signed <token> <cmd> args` - and the generic `host-run <anything>`, `win-run`/`mac-run` and the reverse-SSH fallbacks (an unsigned path around the check) are gone. `/api/host-bridge/open` accepts only `safeOpenURL` links (the target is spliced into a shell line, and Go's `%q` is not shell quoting: `https://x/$(id)` used to execute), `/clip` is capped at 64 KB. A desktop can still ask for exactly the commands its launchers carry, and set the host clipboard; it cannot run anything else. Launchers written before this stop working (403, and `host-run` says to copy the app again: `POST /api/desktops/host-apps/copy`). **Still true:** the control plane holds the Docker socket, which is root on the host - it is what creates desktops and, on a WSL host, runs the privileged `nsenter` hop behind a signed Windows command. Removing it means a narrower Docker access path (a rootless/remote daemon or a proxy that filters `--privileged`, host mounts and `pid=host`), not a network fix. `desktop.Manager.StaleControlPlane` logs, once at startup, the desktops still carrying the old callback URL. The released binary binds the primary listener to loopback plus the Docker bridge gateways (`primaryListenAddrs`, `Manager.GatewayIPs`: `decurix-network`'s and `bridge`'s IPv4 gateway - what `host.docker.internal` resolves to on Linux), so desktops still call back through `host.docker.internal` and the LAN cannot reach it (checked live: `127.0.0.1` and a container answer, the LAN address refuses). Inside a container it binds every interface, since compose decides what is published. `DECURIX_ADMIN_ADDR` (comma-separated `host:port`) overrides it. A gateway address that cannot be bound (Docker Desktop, where `host.docker.internal` reaches host loopback anyway) is skipped with a warning.

The scripts also discover this machine's own LAN-facing IP (`ip route get 1.1.1.1`'s `src` field on Linux/macOS — asks the kernel which address it would use, no packet actually sent; a UDP `Connect` to a public IP on Windows, the same trick) and `POST /api/tunnel` `lan_url` (the gated port) built from it — stored on the same `tunnel.Store` as the gated tunnel's `lan_tunnel_url` and shown together in the Mobile menu (tunnel link first since it works off-network), so a phone on the same network can skip the tunnel round-trip entirely. They no longer report `admin_url` (the primary listener is not reachable from the LAN) or `url` (nothing tunnels it); `tunnelHandler` and the store still accept both, only so an older script's report does not error, and the Mobile menu shows them under a clearly-labelled unauthenticated heading if one arrives. `httpapi.tunnelHandler`'s POST only ever sets the fields present in that call's body, since the LAN report (once, right after startup) and each tunnel-URL report (once per line the `cloudflared` process prints) are separate calls that must never blank out each other's fields.

Go package dependency direction (no cycles): `httpapi` → `llm`, `outbox`, `desktop`, `querynotes`, `memory`, `conversation`, `stepimages`, `tasks`, `tunnel`, `claudeauth`, `lanaccess`, `schedule`, `mailtrigger`, `keepawake`, `suggest`, `webui`, `winhost`; `webui` → `desktop`, `querynotes`, `memory`, `tasks`, `web`; `desktop` → `ollama` (only for `ollama.DesktopURL`/`DesktopModel`, the Ollama a new desktop is given), `winhost` (only `winhost.Token`, to sign a launcher's token), `decurix` (the root package, for the embedded build context); `idlepause` → `desktop` (only for the `desktop.Desktop` struct and the `DesktopLister` interface `*desktop.Manager` satisfies) via a narrow interface, so it can be tested with a fake instead of a real Docker client; `schedule` has no internal dependency of its own - its `Runner` reaches `httpapi` only through the `Submitter` interface `*httpapi.Server` satisfies (`Submit`), the same narrowing `idlepause` uses for `desktop`; `suggest` → `memory`, `ollama` (only for `ollama.Embed`), `desktop` (only for the `desktop.Desktop` struct and its own `DesktopLister`, the same narrowing `idlepause` uses), `tasks` (only for its own `ActivityStore`, narrowing `tasks.Store.LastActivity`), `sqlitedb`; `querynotes`, `memory`, `conversation`, `stepimages`, `tasks`, `claudeauth`, `schedule`, `suggest`, `devices`, `outbox` → `sqlitedb` only; `mailtrigger`, `cftunnel`, `llm` → `sqlitedb`, `sealed`; `phonehost` → `wsconn`; `phoneagent` → `wsconn`, `phonehost`; `ollama`, `sqlitedb`, `sealed`, `wsconn`, `tunnel`, `lanaccess`, `winhost`, `keepawake`, `web`, `decurix` depend on nothing internal. Note that `desktop` does *not* depend on `claudeauth`: `httpapi.createDesktopHandler` reads the stored session and hands `Create` its raw credentials JSON as a plain string, and `claudelogin.go`'s login flow hands the same shape back to `httpapi` to save — `desktop` only ever sees bytes, never the store.

### Three agent harnesses

**New desktops all run TheBot; what they choose is its brain** (`Desktop.Brain`, `desktop-brain` label, `DECURIX_BRAIN` env; `httpapi.desktopBrain` refuses any other harness with 400, and a hosted brain nobody set up). `ollama` (default) is the shared local model as before. `claude` / `azure` point soul's OpenAI-compatible provider at the control plane (`LLM_PROVIDER=openai`, `OPENAI_BASE_URL=<control plane>/api/llm/<brain>`, a placeholder key) with `EMBED_PROVIDER=ollama` (embeddings stay local and best-effort), `DECURIX_LLM=<brain>` so `harness.ask_model` asks the same hosted model (and never falls back to loading the local one), and `thebot_harness.wait_for_backend` waits for soul only. The ollama/claude/azure harnesses below remain for desktops created before this, and `bench/gui/run.py --engine ollama|claude` no longer creates such desktops. The shared Claude Code login (`claudeauth`) is no longer offered in the dashboard.

**TheBot adapts to its brain (`agent/thebot/internal/llm/caps.go`, `llm.Capabilities` on `RunContext.Brain`).** New engine work goes into TheBot, keyed on what the model can do rather than on which provider it is:
- **Vision.** A hosted brain's is decided by the control plane when its key is saved (`llm.Hub.Test`: Claude's current models all read images; an Azure deployment is sent a one-pixel PNG and a refusal means text only), stored with the settings and baked into the desktop as `DECURIX_BRAIN_VISION`. The Ollama brain gets no such variable: soul asks Ollama `/api/show` (`capabilities` has `vision`, `model_info.*.context_length`) in the background until it answers - `/api/show` reads the manifest and never loads the model, which matters on this repo's memory-starved host. Never probe the shared Ollama with a chat.
- **What vision changes in the operator** (`skills/operator.go`). The contract gains `visionRule`. `gui` is run with `DECURIX_GUI_SCREENSHOT`, so every screen command leaves a PNG of the screen as it ended up (`cli.save_screenshot`, whole for a hosted brain, half size for a local one). The PNG is attached to that command's result, and only the newest screenshot is kept. `office read` is run with `DECURIX_OFFICE_IMAGES=attach`, so a scan's `[page image: ...]` pages are attached too. Up to `maxDocumentPictures` (6) pages are kept, *separately* from screenshots, so the screen never pushes the invoice out of view. A text-only brain gets `DECURIX_OFFICE_IMAGES=ocr` instead: tesseract's reading of each page, flagged as OCR. Dropping an old picture rewrites an earlier message, which costs a local vision model its Ollama prompt cache; that trade is accepted only for vision brains.
- **Budgets.** A hosted brain gets 16000 characters of command output (4000 local), 12000 of `gui` element list (`DECURIX_GUI_TEXT_CHARS`, 3500 local) and 40 operator turns (16 local). They are fixed on the goal's `operatorState` when it starts, so a paused goal resumes with the same ones.
- **Benchmarks run on a brain with `--brain azure|claude|ollama`** (`bench/brain.py`: the environment `buildDesktopEnv` gives a desktop with that brain; model calls go through this tree's control plane on 127.0.0.1:8080, which must have the brain set up; the skills bench's fake control plane forwards `/api/llm/*` there). Without the flag, `bench/recordings` and `bench/skills` start their desktop on the old model-free settings, as before. Verified on Azure (gpt-5.4, vision) on 2026-09-29: recordings, skills and learn_documents (including path A, where TheBot found the taught skill with `gui skill`, read the PO with `office read` and ran `gui do` with list values) all pass. For benches that `docker exec` into a desktop, run the control plane with `DECURIX_IDLE_STOP_MINUTES=0`: idle-pause pauses a desktop seconds after a task and `docker exec` refuses a paused container.
- **TheBot has the Office (GPT) engine's two back-office tools, as shell commands** (`tools/office.py`'s `main`, taught in the operator's contract):
  - `office update BOOK.xlsx -` takes a JSON spec on stdin: `edits` plus `replace_refs`. It edits the sheet XML in place, so charts survive; never rewrite a workbook with openpyxl.
  - `office create BOOK.xlsx -` makes a new workbook.
  - `office email --to --cc --subject --attach` takes the body on stdin and drafts into the Outbox through `tools/outbox.py`. The Office (GPT) harness's `draft_email` now calls the same module. A draft is never sent: only a person's Send on the Triggers page sends it.
  - TheBot's command safety does not stop `office email`; it stops only real senders (`sendmail`, `mutt`, ...).
  - Triage sends an email-to-prepare to the operator (`wantsEmailDraft`: draft/prepare/compose an email, reply, reminder, letter or message; the Outbox; or "write an email" with an address or an attachment). Left to the chat skill, it answered with the email's text and put nothing in the Outbox. "Help me write an email asking my boss for Friday off" names no address and stays conversation.
- `llm.Message.Images` carries PNGs, and each provider sends them in its own shape: OpenAI `image_url` parts (and so, through the control plane's proxy, Claude image blocks), Anthropic `image` blocks, Ollama `images`. `Message` is no longer comparable with `==`, so tests use `reflect.DeepEqual`.

Each desktop picked a harness at creation time (`Desktop.Harness`, `desktop-harness` container label, `AGENT_HARNESS` env var passed into the container — see `internal/httpapi/desktops.go`'s `createDesktopHandler` and `internal/desktop/docker.go`'s `buildDesktopEnv`). All three reach the exact same command/querytext/memory/progress contract through `harness.py`'s dispatch:

- **`ollama`**: the hand-rolled `COMMAND:`/`DONE:`/`HELP:` loop in `task_runner.py`, driving an Ollama model.
- **`claude`**: requires the developer or ai profile (`claude` binary isn't installed in basic) and a shared Claude Code login completed once through the dashboard's popup (see `internal/claudeauth` and `internal/desktop/claudelogin.go` above) rather than an `ANTHROPIC_API_KEY` in `.env` — `httpapi.createDesktopHandler` reads the stored session and `desktop.Manager.Create` seeds it into the new container's `~/.claude/.credentials.json` (`PersistClaudeCredentials`) only when the harness is `claude` and someone has logged in. Runs `claude -p "<task>" --output-format stream-json --verbose --dangerously-skip-permissions --append-system-prompt "<memory + safety rules>"`, optionally `--resume <session_id>` to continue after a human responds. No `--bare`: that flag forces API-key-only auth ("OAuth and keychain are never read" — confirmed against the CLI's own `--help`), which is exactly what this harness now needs to *not* do; the trade-off is that `--bare`'s other isolation (hooks, LSP, plugin sync, attribution, auto-memory, CLAUDE.md auto-discovery) is back on too, same as running `claude` anywhere else — none of it matters inside a desktop's empty `~/work`. `--dangerously-skip-permissions` is intentional and matches the Ollama harness's existing unrestricted shell access (`commands.run_command`) — not a new risk category, just the same one applied to a second engine. `stream-json` (which *requires* `--verbose`) is what lets the turn be watched as it happens; its final `result` event carries the same fields the one-shot `json` format returned, so only `_run_claude` knows the difference.
- **`thebot`** (default: the create dialog lists TheBot, Claude, Ollama in that order, and the API picks it when no harness is given): TheBot's `soul` binary, built from `agent/thebot/` (its own Go module) into all three images and started as a daemon on port 4900 when `AGENT_HARNESS=thebot`. Reuses the same `OLLAMA_URL`/`OLLAMA_MODEL` every desktop already gets, so it needs no env var of its own. Inside soul a job goes: **recall** (L1 facts) → one shared **system frame** (`internal/prompt`: persona + host context, byte-identical for every model call in the job so Ollama's prompt cache carries across them) → **triage** (`internal/atomizer/triage.go`, deterministic: `chat` / one `skill` / `operate` / `plan`) → a tagged step **graph** from the planner only for `plan` (`[do] [shell] [web] [read] [download] [write] [code] [docs] [answer]`, with `(after N)` dependencies) → the **scheduler** (`internal/scheduler`) runs ready steps in parallel under a process-wide model-concurrency limit (`llm.Limited`), recovers a failed step (retry / decompose / ask), replans the rest once if it still fails, and **pauses** with a `Checkpoint` when a step needs approval or an answer → one **synthesised reply** for multi-step jobs. `operate` is the **operator** skill (`internal/skills/operator.go`): a Go `COMMAND:`/`DONE:`/`HELP:` loop carrying the Ollama harness's measured lessons, which is what lets TheBot answer "what's the kernel version?" by running `uname -r` instead of planning a web search. Consequential commands and requests are stopped by `internal/safety` before they run, whatever the model decided.
- All three system prompts (`SYSTEM_PROMPT` in `ollama_client.py`, `SAFETY_SYSTEM_PROMPT` in `claude_harness.py`, `SAFETY_PREAMBLE` in `thebot_harness.py`) instruct the agent to stop and request human approval — via the same `HELP`/`ask_for_query` → querytext path — before payments, sending messages on the human's behalf (WhatsApp/email/SMS), or any action with real-world consequences it isn't fully confident about. Claude and TheBot signal it with a `NEEDS_APPROVAL:` prefix on their final answer; the Ollama loop uses its `HELP:` control signal.

### One chat, every harness

`/view/<id>` (the dashboard's **Chat** button) renders `web/templates/desktop.html`, which is the chat and nothing else — no embedded screen, identical for all three harnesses. A desktop's screen is a separate thing, opened in its own tab from the dashboard's open-in-a-new-tab button (the only emitter of `?ui=touch`; see the `injectMobileEnhancements` note below - the ticket toolbar described next is unconditional, like the branding rewrite, since noVNC's page loads for no other reason). Nothing in the chat page branches on which engine is running, because every harness is addressed and reports back the same way:

```
human types in the chat
  → POST /api/desktops/send        → tasks.Plan (new task / reply / retry → a task ID)
                                   → httpapi.deliverRequest → desktop.Manager.SendRequest(content, task_id) → :8081
                                     → COMMAND_DIR/<stem>.t<id>.txt → watchers.py
                                     → task_context.start(id) → harness.py → engine
                                   → tasks.Commit + conversation.AppendUserRequest

the agent works
  → progress.emit(line) → POST /api/agent/events {task_id} → conversation.AppendStep
                                                           → tasks.AddStep (the record)

the agent finishes, or needs a human
  → messaging.write_final_reply / ask_for_query(kind) → POST /api/querytext
        {task_id, kind: final|error|query|approval, engine, model, tokens, cost_usd}
      → querynotes.Add          (the Query rail keeps the whole formatted note)
      → tasks.RecordOutcome     (done/error closes the execution; query/approval opens
                                 an intervention the next human request replies to)
      → conversation.AppendAgentReply (the chat shows only the agent's own words)

the human judges the answer
  → POST /api/tasks/verdict (chat's Correct/Wrong, or the task page) → tasks.SetVerdict
                                                                    → conversation.SetVerdict
```

The chat page holds no transcript of its own: it renders whatever snapshot the control plane last sent over `GET /api/desktops/chat/stream` (SSE, whole snapshots rather than deltas, so a reconnect is self-healing), falling back to polling `GET /api/desktops/chat`. That is what makes one desktop's conversation the same on a laptop, on a phone through the tunnel, and in a second window — and why a desktop's agent is genuinely *central* to it, rather than one chat box per browser.

Replying to a blocked agent is just sending it another request: `watchers.command_watcher` routes any request arriving while `state.waiting_for_query` is set to `continue_after_query` instead of starting a new task. So the chat, the Query rail's reply box and the Requests page are three doors into one conversation.

### Computer use: one action layer, every engine

Every desktop can see and act on its own screen through `decurix_agent/computer`. The layer lives in the desktop, below the engines, so the approval gate and the audit trail cannot be skipped by any of them:

```
observe()  screenshot (python3-xlib) + windows + elements: AT-SPI for GTK/XFCE/LibreOffice,
           the Chrome DevTools Protocol for Chromium (its AX tree + one DOMSnapshot for boxes)
act()      observe -> resolve the target (ref | role+name | path | x,y) -> approval.check
           -> do it (CDP input / AT-SPI action or caret / xdotool) -> wait for the screen to
           settle -> observe -> compare -> audit.record
verify()   observe again, compare with the last observation, optionally check text/element
```

How each engine reaches it:

- **Claude** gets them as MCP tools (`mcp__computer__observe/act/verify/open`) via `claude_harness.MCP_CONFIG` (verified: the stream's init event lists the server `connected` with all four tools). Every result carries the screenshot, because Claude can read one.
- **Ollama** and **TheBot** use the `gui` shell command through their existing `COMMAND:` loops (no contract change) and read the element list **as text only**. A 3B model on a CPU cannot read pixels; `elements.render` is budgeted to `DECURIX_GUI_TEXT_CHARS` (3500) because `task_runner` shows a model at most 4000 characters of any command's output. TheBot's `atomizer.Triage` routes screen work (`wantsScreen`: a surface *and* an action) to the operator, ahead of the web skill that would otherwise fetch any URL itself.

`gui` exit codes are a contract harnesses read: 0 done, 1 could not, **3 NEEDS_APPROVAL (nothing happened)**, 4 verify failed.

Approval travels the same way for all three: `approval.check` stops a click on a Send/Pay/Buy/Publish-like control (or Enter in a messaging page), records a *pending* approval and returns NEEDS_APPROVAL. The harness pauses deterministically — `task_runner.pause_for_screen_approval` on exit 3, `operator.screenApprovalReason` → `NeedsApproval` checkpoint, `claude_harness._handle_result` if a pending approval exists whatever Claude wrote. The human's reply reaches `watchers.command_watcher`, which calls `approval.resolve_reply` **before** the harness sees it: a yes (`is_approval`, the same regexes as soul's `safety.IsApproval`) becomes a one-shot grant fingerprinted to that action; anything else drops it. The repeated action consumes the grant. A new task calls `approval.reset()`.

Every action — done, failed, or paused — is recorded twice: as an event of the task's recording on the desktop's persistent volume (see "Recordings" below), and as a chat step via `progress.emit_action` → `POST /api/agent/events` with `action` + half-size `before_png`/`after_png` → `conversation.AppendActionStep` + `stepimages.Store`. The chat renders those steps with Before/After thumbnails. Both copies go through `privacy.py` first.

### Recordings: demonstrations, the audit trail, and replay

Built on OpenAdapt's design (openadapt-capture's recorder and secret exclusion, openadapt-flow's recording layout, volatility classifier, resolution ladder and run outcomes), on Decurix's own action layer. One format holds everything done on a desktop's screen, whoever did it:

```
~/.decurix/recordings/<session>/          task-<task id> | adhoc-YYYYMMDD | demo-<when>-<rand>
  meta.json      kind, title, task_id, started/ended, screen, actors, counts, status (demos)
  events.jsonl   one action per line: i, t (seconds on the session clock), actor (agent|human),
                 kind, element (role/name/path, no backend handle), text or withheld{},
                 before/after frame names, change (sentence) + expect (the same as data)
  frames/        PNGs named by a hash of their pixels - an "after" that is the next "before"
                 is stored once
```

- **Agent actions** get there through `audit.record` (from `core.act` / `open_target`), under the session of `task_context.current()`; the task's request titles it (`task_context.current_request`, beside the task ID file).
- **A person's demonstration** is `demonstration.py`, a process of its own started by `POST /demonstration/start` on the agent: XInput2 raw events → `processing.merge` (openadapt-capture's click/double-click/drag/scroll/shortcut rules, plus one `type` per run of characters with BackSpace applied) → the element under each action from the last observation of a settled screen → `recording.append` with `actor: "human"`. **Pause** drops all input and frames for a private step (a sign-in) and records a `manual` step on resume, which a replay hands back to a person.
- **Replay** is `replay.compile_program` + `replay.run`: typed text becomes parameters (secret ones have no default and must be given), each step's target is found again by path then role+name (never guessed: none or two halts), coordinates only for a step recorded without an element on the same screen size and window, and each step waits for what it left on screen when recorded (a URL shape with id-like segments as `*`, a window, a dialog/heading/alert, a field holding the typed text), with volatile text never checked. Outcomes, never a success it did not see: `verified`, `completed_unverified`, `halted_before_effect`, `halted`, `reconciliation_required` (a consequential step ran and its result never appeared — never retried), `needs_approval`, `needs_human`. Every replayed step goes through `core.act`, so the approval gate and the recording apply (`replay_of` on each event).
- **A ticket: a person doing a task, recorded from the GUI screen itself.** The screen's own top-of-page toolbar (`proxy.go`'s `injectTicketToolbar`, spliced into every load of noVNC's `vnc.html` the way `rewriteDecurixBranding` is) is a `+` that opens a ticket and, once one is open, Record/Stop/Continue/Reason/End. `+` sends the typed task as `/record <task>` through `POST /api/desktops/record` — refused while the agent is busy, like a replay — and it is otherwise an ordinary request (Plan/Commit, in the transcript, doesn't wait for the backend, neither does `/replay`). The watcher dispatches it to `record_task.perform`, never the engine. **Opening a ticket does not itself start capturing** — Record does, so a person can create the ticket, walk over to the screen, open the app they'll use, and start only when actually ready. From there Stop is `demonstration.pause` (a private step, e.g. signing in) and Continue is `resume`; Reason (`record_task.note` → `demonstration.note`) appends a person's own written explanation of what they are doing to the recording — its own event kind, `note`, never compiled into a replay step (`replay.compile_program` skips it outright, not merely leaves it out of `REPLAYABLE`, so it can never reach a replay's "cannot note" halt) and, like a typed field, withheld rather than kept if the text itself looks like a credential. **The toolbar pauses before Reason opens its text box, not after submitting it** — clicking Reason calls the same `pause` action Stop does (so nothing on screen is kept while the explanation is composed, not just while it's read back), and submitting calls `note`, which — whether it finds recording already paused (this pause, or an earlier Stop) or not — always writes the note and then (re-)pauses, `demonstration.note` calling `pause()` itself with the note's own (privacy-safe) summary as the reason, refreshing it if one was already set. `note` no longer refuses a paused call — that used to be its only guard; now, whichever pause it lands in, it just rewrites the reason and stays paused. Whether the toolbar then continues automatically is its own call, not `note`'s: the toolbar tracks whether *its own* Reason click is what paused things (`reasonAutoPaused`) and only follows a successful submit with an explicit `resume` when it was — a pause already in effect before Reason was opened (Stop, pausing for something the note is *about*) is left exactly as the person set it, since auto-continuing could hand the very moment the note was warning about straight back to the recording. End (`record_task.end`) stops capturing if it had started and finishes the ticket's task, which is what makes the recording's export downloadable — the toolbar offers that link the moment End answers. Every one of Record/Stop/Continue/Reason/End is a direct call to `/api/desktops/ticket/action` (`ticketActionHandler`), not a command file: they only ever act on whatever ticket `record_task.py`'s own state already has open, so they don't go through the watcher. `GET /api/desktops/ticket` (`ticketStatusHandler`) is what the toolbar polls (every open tab, and any Record/Stop click, keep this and the recordings page's own view in sync) — deliberately separate from the recordings page's own ad-hoc "Record a demonstration" (`POST /demonstration/start`, no ticket, no task), so the two can never fight over the same session. Its task type is `demonstration` (`tasks.IsRecordCommand`), which an on-screen step never turns into `screen` and `tasks.Report` leaves out of autonomy — no engine attempted it.
- It is reachable three ways: the recordings page's Replay button (control plane → `POST /recordings/<id>/replay` → a `/replay <id>` command file → `replay_task.perform`, a task with engine `replay`), typing `/replay <id>` into the chat, and by an engine: `gui recordings [words]` / `gui recording <id>` / `gui replay <id> [--param n=v] [--from N]`, or the MCP tools `recordings` / `replay`. `gui replay` exit codes follow the gui contract (3 on approval, 4 on reconciliation_required).
- **Privacy is applied at the source** (`privacy.py`): a value typed into a password field (AT-SPI `password text`, `input[type=password]`, a secret `autocomplete`, a field labelled for a secret) or text shaped like a credential (API keys, tokens, private keys, Luhn-valid card numbers) is withheld with a reason, never rewritten; secret fields' boxes are painted over in saved frames; URLs lose userinfo and secret-named parameter values; a value over 512 characters is omitted, not cut. The engine is handed `[text withheld: password field]` too.
- The control plane never copies recordings: `desktop.Manager.AgentRequest` proxies `/api/desktops/recordings*` and `/api/desktops/demonstration` to the desktop's `:8081` (the page is `/recordings/<id>`, linked from each dashboard card and from a task that acted on screen). Recordings of tasks and hand-run actions are pruned oldest first past `DECURIX_RECORDINGS_MB` (default 1024); demonstrations are never pruned.
- **A recording says how far it can be trusted before anything runs (`computer/lint.py`)**, from openadapt-flow's lint/certify and AgentRR's "check functions": a pure read of the compiled program (no screen, no model) that grades it `ready` / `rehearse` (run it once, watching) / `risky` from its worst finding - `risk`: a step with nothing to find its target by, a click on a bare coordinate, an approval-gated step that leaves nothing to check; `warn`: a target named for the moment it was recorded ("Invoice INV-1043"), under 60% of steps checked; `info`: secrets it must be given, steps for a person, anchored clicks. It is advice: nothing here stops a replay, and a replay that meets what a finding warned of halts exactly as before. `GET /recordings/<id>` returns it as `lint`, `replay.render_text` puts a `Readiness:` line in front of an engine choosing whether to replay, and the recordings page shows it above the steps. `replay.NEEDS_TARGET` is the one list of steps that must have a control or a position, shared with lint.
- **A click on a coordinate keeps a picture of what was around it (`computer/visual.py`)**, openadapt-flow's "template" rung, so a replay no longer clicks blind. `compile_program` crops a `LOOK_WIDTH` x `LOOK_HEIGHT` (144 x 48 px) window around the click out of the event's saved `before` frame into `step["look"]` (a base64 PNG *inside the step*, not a frame name: a skill outlives the recordings it came from) - only for a click with no element (a canvas, a custom-drawn control; text in the accessibility tree is an element and uses structure), and only when the picture is *recognisable*: enough blocks with structure (`MIN_CELLS`) **and** distinct from itself (`_distinct`: slid 8/16/24 px it never looks the same - two border lines have structure and identify nothing, they are under every row of a menu). `look["partial"]` says the structure runs off the window's left/right edge (a label longer than the window); lint reports it. `replay.resolve` then checks the live frame: at the recorded spot one comparison (a few ms), else a search within `SEARCH` (96 px) - `found` (click follows it, and the run says it moved), `missing` (halts, "does not click there"), `ambiguous` (two places, halts, "does not guess which"), `unverifiable` (no look, or a screen of another size: the step runs as before).
  **What is compared is structure, not tone**, and every choice below was made on real Chromium pixels, not drawings (see "Tuning it" below). Both sides become a gradient map (after a 2x2 blur, so a half-pixel resample still matches), judged in 8x8 blocks taken every 4 px. A mean brightness difference - the first version - scored `Cancel` against `Save` in the same style at 7-11 of a limit of 14 and made a hover highlight (the whole button a shade darker) *miss*: the words are a small share of the pixels and a shade is all of them. A shade changes no edge; a different word breaks every block it touches. Blocks **overlap** and **include the right/bottom edge strips**: tiled blocks split a glyph-sized change across neighbours (none reaches the threshold), and a window that is not a whole number of blocks wide left its last columns uncompared, where a label's last letter lived - both found by test on real frames, both fixed.
  **Two limits, not one:** `MAX_MISMATCH` (0.02, the share of blocks that may differ) *at the recorded spot*, `MAX_MISMATCH_MOVED` (0.009; was 0.01 on Chromium 112 - re-tuned on a corpus built in Chrome 154, where the one-digit neighbour row scores 0.012 instead of 0.018) anywhere else. The further from where it was recorded, the less a near-match proves: on real pixels the row above `Invoice 1042 Paid` is `Invoice 1041 Paid` - one digit, 0.018 of the blocks - and was found for it. The accepted matches scored at most 0.006 when relocated, so 0.01 is the middle of the gap. The coarse search pools the gradient's *energy* into 4x4 cells at two phases per axis (`PHASES`); an earlier version took the gradient of a block-averaged image and scored a control 2 px off its grid worse than places that were nothing like it. It only nominates places; each is aligned at full size and judged block by block, and **ambiguity is decided on the refined score of each distinct place, never the coarse one**.
  **What it will not do, on purpose:** it halts (asks a person, the same path an element that is gone takes) when the screen is in another *state* than when recorded - a focus ring, a hover underline, a neighbouring control that changed inside the window, a half-pixel resample of thin text. A false halt is put to a person; a click on the wrong thing is not undone, so the tuning is *asymmetric*. And it cannot tell apart controls that differ only beyond its window (a 13 px checkbox whose label runs on for 120 px): those are marked as such in the corpus, and lint's `partial_anchor` says so. No numpy or PIL in a desktop image, so `visual.py` has its own PNG codec (the recorder writes filter-0 PNGs; the reader undoes all five filters for frames from elsewhere).
  **Tuning it** (`bench/recordings/`): `corpus.py` runs *inside* a desktop and builds real frames of eight kinds of control (button, link, checkbox, icon, input, menu item, tab, and table-cell text, which has no element) - each recorded, then seen again as what should still be it (again, hover, moved four ways *by its measured position*, other surroundings, half-pixel resample, focused, dark theme) and as what must not be taken for it (similar decoys in its place, gone, a different page). `tune.py <corpus dir>` judges `visual.find` against it on any machine (`--set NAME=VALUE` overrides a constant, `--verbose` lists every answer) and reports the two error classes separately: **UNSAFE** (found what is not there / clicked elsewhere; any is a failure) and **over-cautious** (halted on what was there; budget 10%). Current: 123 frames, **0 unsafe, 6 of 74 over-cautious (8%)**, nearest decoy 0.018, median 250 ms and worst ~520 ms on the search path (healthy path ~4 ms; measured on a 6-core host - a 1-vCPU desktop is slower, and a halt costs `DECURIX_REPLAY_FIND_SECONDS` of polling). Run both after touching `visual.py`; the corpus is regenerated, not committed (`docker exec -u headless -e PYTHONPATH=/opt <desktop> python3 corpus.py /tmp/corpus`, then `docker cp` it out).
- **A value is checked against what its field takes, before the first step (`computer/constraints.py`)**, AgentRR's parameter constraints. One example proves nothing about a type ("Customer" typed `1042` once is not a number field), so a constraint is *enforced* only when the field itself says so: a `spinbutton`, or a label that names the kind of thing ("Work email") *and* an example that is one. One of the two alone is kept as a `hint` and never refuses anything. Only kinds that are the same everywhere are enforced (email, web address, number); dates and phone numbers are hints. `compile_program` and `learning._generalise` record `param["constraint"]` (`skills._program` carries it, `expand` copies it); `replay.run` returns `halted_before_effect` for a given value that breaks one (a default recorded by the person is not judged), and `skill_task._prepare` asks for it again saying why - and ends the run after a second wrong answer, as it already does for lists.
- **A recording made elsewhere can be imported (`computer/ingest.py`, `POST /recordings/import`, `POST /api/desktops/recordings/import`, the page's Import button)**: a Chrome DevTools Recorder / Puppeteer Replay JSON export (the format Puppeteer Replay, Playwright's importers and Browser Use's Workflow Use read) becomes a finished demonstration with no frames, so everything downstream - compile, replay, `/learn`, lint, export - works unchanged. `aria/Sign in[role="button"]` becomes a role and a name; a selector that only says `text/...` becomes a **label-only target** (`target` with a `name` and no `role`), which `replay.resolve` matches among `ACTIVATING_ROLES` only - a heading reading the same is *not* a candidate, a hard filter (the first version fell back to it, found by test) - and never guesses between two. A step it can only locate by CSS/XPath is kept with **no target**, so the replay halts there ("nothing to find this step's target by") and lint says so; `replay._run_step` now refuses a click/select/drag with neither a target nor a position *before* acting (it used to depend on `core.act` erroring). `assertedEvents` and `waitForElement` become the step's expected result; hover, scroll, script waits and custom steps are returned as `skipped` with a reason and shown on the page. **The recorder writes what was typed into a password field into its JSON verbatim, so every value goes through `privacy.withhold_text`** (a field labelled "Password" is judged as the text field it is even with no role), URLs through `privacy.reduce_url`; a test asserts the secret never reaches disk. Not done: OpenAdapt captures (their `recording.db` schema was not verified) and Playwright codegen (it emits code, not data).
- **What other open-source agents did can be imported too (`computer/ingest_agents.py`)**: BrowserGym / AgentLab trajectories (`{"goal", "steps": [{"action", "axtree_txt" | "axtree_object" | "obs"}], "final"}` or a bare list - AgentLab's own pickles are not unpickled, a JSON step list is the adapter) and OpenHands event streams (a JSON *list* of `{"action", "args"}` / `{"observation", "extras"}`; `POST /recordings/import` accepts an object or a list). Both name a control by a `bid`, which means nothing outside BrowserGym; it is tied back to a role and name through the tree of the observation the action was chosen from, and a step whose tree is missing is kept with **no target and an `imported.why`**, never guessed at. Action strings are read with `ast`, never evaluated (a trajectory is data from elsewhere; a test feeds it `__import__('os').system(...)`). `click/dblclick/fill/select_option/press/keyboard_*/goto/go_back/scroll/mouse_click` become steps; `focus/check/uncheck` become clicks and say so; `hover`, drags, tabs, uploads, modifier-clicks are `skipped` with a reason; `noop/send_msg_to_user` are ignored. Every step is an **agent's** (`actor: "agent"`), the AgentRR "large model records, small model replays" case.
  **What real trees taught** (BrowserGym 0.14.3 on MiniWoB++; fixtures in `agent/tests/fixtures/agents/` are real, not hand-written): (1) BrowserGym's tree grammar (`browsergym/utils/obs.py`) puts `value='v'` after the name with a *space* and every other property after a comma - the first parser took properties to start at a comma and silently lost every filled-in field and every dropdown; it is now written from the formatter's source. (2) A great many controls have **no name** (`textbox ''` twice in a login form), which role+name cannot tell apart and a replay must not guess between, so a target carries **`nth`** (its place among controls with the same role and name, from 1, in tree order) and the event a **`hint`** (the label beside it, "Username"), which names the parameter and is what tells the privacy layer "Password" is a secret. `replay.resolve` honours `nth` (a rule of the target, not a guess of the replay's; out of range is "not on the screen"; lint's `positional_target` warns it is only as good as the page's order), and a name-less target with no `nth` is still "does not guess". A hint is only taken from an earlier *sibling* label - the first version took the previous field's value (`••••`) as the Login button's hint. (3) A password is a plain `textbox` to the accessibility tree; nothing marks it protected. The signals are the label and - once typed into - **the tree reporting its value as bullets**, on the node's own `value` key (not among its `properties`, which the OpenHands path missed until a cross-format test disagreed). (4) OpenHands **deletes `axtree_object` when it saves a trajectory** (`DELETE_FROM_TRAJECTORY_EXTRAS`), and a saved browse observation's `content` is page *text*, so bids in a stripped trajectory cannot be resolved: the import warns, lint grades it risky, and the replay stops.
  **An unidentified control stops the run before anything acts.** A `type` step with no target means "type into whatever has focus" (`keyboard_type`, a person typing), and a `fill('19', ...)` whose control could not be identified used to become exactly that - found by the live run, whose summary check (reward only) passed while the outcome column said `halted`, not `halted_before_effect`: the stripped trajectories typed into an unfocused page before their first click stopped them. `imported.why` now compiles to `step["unresolved"]`, `_run_step` halts on it for *every* kind, lint says `unidentified_control`, and the Chrome importer sets it for a field it can only name by a CSS selector. **A credential written into a task's own words is a leak too:** MiniWoB's goal reads `the password "Ttlh"`, and it was being kept as the recording's title (shown on the page, in exports). `privacy.withhold_spoken_secrets` redacts `password/pin/token/secret/... "value"` in every imported title.
- **A program as subtasks, and a skill as a SKILL.md** (from UI-Mate and Understudy, both deterministic - no model, so they read the same every time). `workflow.py` is UI-Mate's *demonstration workflow*: a phase (a run of steps in one window or site, `replay._phases`) is a subtask; its completion criterion is the last thing its steps expected (`replay.mine_checks`); its steps are advisory descriptions with **no coordinates**, and a point is described as "the control shown in the recording"; the live screen is authoritative (the contract text says so), the current part is shown in full and the others as goals, and **a part that contains an approval-gated step says so before it is reached** (found by a test: only the current part's steps were listed, so a boundary was invisible until arrival). What it lacks against UI-Mate is the intent sentence its vision model writes - a subtask's goal is the place and what was done. `replay.render_text` gives an engine a `Parts:` line; `GET /recordings/<id>/workflow` gives data and text. `skillmd.py` is Understudy's three layers - **Intent** (done when, inputs, what only a person does, the procedure, what needs approval), **Routes** (preferred: `gui do NAME --param ...`; fallback: follow the procedure with `gui`; observed: browser vs GUI steps) and **GUI replay hints** (how each step is found again - role and name, `nth`, or a picture, never coordinates) - in the **Agent Skills** format, so a task taught here can be handed to any agent that reads skills. `GET /skills/<name>/skill.md`, `/api/desktops/skills/export`, a "SKILL.md" button on the skills page. Checked against the **official reference validator** (`skills-ref`, `pip install skills-ref`): it reads the file, and `test_workflow.py` runs it when installed. It found one wart: the spec's `metadata` is a map of strings, and a nested block was stringified into a Python repr - so the keys are flat (`decurix-version: "2"`). Front matter never carries `<`/`>` (the spec warns they can inject into the loader's prompt).
- **Verified live** (a real `decurix-desktop:basic`: Xvnc, XFCE, Chromium, Python 3.12), not only in tests. `bench/recordings/e2e.py` (about three minutes; `--keep` leaves the desktop): a click on a `<canvas>` list is recorded as a bare position with a look; replayed unchanged it clicks the row; with the whole list moved it *follows*; **with the rows reordered it clicks `Invoice 1042` where it now is and not `1041` where the click was recorded**; a different row in the slot, the row removed and an empty page all click nothing and say why; a Chrome Recorder export is imported, replayed on real Chromium (both typed fields checked to hold what was typed) and a bad email is refused before anything is typed. `bench/skills/e2e.py` (teach, run, heal, ask, remember) passes with these changes; **it was stale before them** - identical failure on a pristine `HEAD`, because the healing ladder now repairs a plain rename ("Save" -> "Save changes") without asking - so it now asserts the heal, then asks about a rename nothing recognises ("Go"). The recordings page (readiness panel, findings, the Import button, imported steps reading `click textbox "Customer name"` like recorded ones) was opened in a desktop's own Chromium against the real control plane and looked at. **Other agents' work, replayed** (`bench/agents/`, needs BrowserGym in a Python 3.12 venv - `uv venv --python 3.12`, `uv pip install browsergym-miniwob`, `playwright install chromium`, and the `miniwob` wheel's html): `gen_trajectories.py` has real BrowserGym solve MiniWoB++ tasks (9 solvers, 3 seeds; 24 of 24 solved by BrowserGym itself; `click-link` is skipped because that task's "link" is `StaticText` with no bid, unsolvable by bid for any agent) and keeps them as a BrowserGym trajectory, as the OpenHands event stream, and as OpenHands' *saved* form (trees stripped). `e2e.py` puts each task page in a real desktop's Chromium in **the same instance** BrowserGym solved (`Math.seedrandom(<the seed BrowserGym drew>)`), imports, replays with `gui replay`, and reads the page's own `WOB_RAW_REWARD_GLOBAL`: **BrowserGym format 24 of 24, OpenHands with trees 24 of 24** (the same rewards BrowserGym scored; nameless login fields by `nth`, passwords supplied at replay, dropdowns, checkboxes, focus), **OpenHands stripped 0 of 24 and all 24 `halted_before_effect`** (nothing acted), and `--negative` replays the password tasks with a wrong password and the pages score **-1** - the harness can fail (the replay itself says only `completed_unverified`: it cannot see a wrong password, the benchmark can). Not verified: replay across *different* instances of a task (raw replay types what was recorded - that is what `/learn` is for), tasks needing several pages or timing, and a real OpenHands run (its event *shapes* are from the `openhands-ai` 0.37 serialiser source, not from a live agent). Not built: OpenAdapt captures (schema unverified), open-record-replay's `events.jsonl` (only its event *types* are public, not their fields), UI-Mate's re-planning (it is a trained model; only the workflow view is here) and Understudy's route rewriting (direct tool > CLI > browser > GUI needs a model). Also not verified: a 1-vCPU desktop's timing of a `find` (the harness ran on a 6-core host), and toolkits other than Chromium - the corpus is Chromium pixels only, so GTK/LibreOffice controls (which the layer already treats specially: LibreOffice misreports where it draws) have not been measured.

### Skills: learning a task from demonstrations, asking what is unclear, then doing it

Modelled on Orby's public description of its Large Action Model — "observe, learn and automate": watch a person do the work (screen, page, actions), generalise it into a workflow, show it to that person to approve, run it. Orby's internals are proprietary (only the loop, a planner/grounder split and "SAIL" interface learning are public), so this is that loop on Decurix's existing parts, not a port of their code. **No model is involved**, in the spirit of soul's "deterministic before clever": what can be worked out from recordings is, and what cannot is asked.

```
person records (a ticket, or several)        the recordings the desktop already makes
  → /learn <recording> [<recording> ...]     learning.build: compile each, align them, generalise
      → one question at a time (ask_for_query) goal / start / variable / optional /
                                               coordinates / unsupported / confirm
      → yes  → ~/.decurix/skills/<name>.json  (status "ready"; a draft is saved after every answer)
  → /skill <name> [param=value ...]          skills.program → replay.run, no model
      → asks: a missing value, a screen that is not where the task began, a step that is stuck
      → a correction that then worked is written back into the skill
```

- **Generalising (`learning.build`).** Several demonstrations are aligned step by step (`difflib` over each step's kind and target, never its typed text). What differs between them is the task's shape: text typed differently is a variable that changes every run (no question needed), a step only some demonstrations have is asked about as optional, and a step's expected result shrinks to the checks *every* demonstration agrees on. One demonstration can only ever be one instance, so its typed text is asked about. A person's `note` (the ticket toolbar's Reason) rides along and is shown back in the first question.
- **Questions are derived from the skill's own state, with stable IDs** (`goal`, `start`, `loop:<loop id>`, `variable:<step id>`, `optional:<step id>`, `coordinates:<step id>`, `unsupported:<step id>`, `confirm`). A step has an `id` that never changes and an `n` that does (a skipped step renumbers the rest, `skills.renumber`) — a question and its saved answer name the *id*. That is what lets an interrupted lesson be resumed by `/learn` on the same recordings (`skills.draft_for`) and ask only what is left.
- **An unclear answer is never guessed.** `learning.answer` asks again once, then takes `CAUTIOUS[kind]` and says so: typed text *changes* (asked for each run), an uncertain step is *always* required (halts rather than skips), a coordinate click goes to *manual*, an unconfirmed skill stays a *draft*. Nothing runs until a person has said yes to the whole skill (`status: "ready"`).
- **A secret is never a parameter.** A typed step whose value the recording withheld becomes a `manual` step (the run stops with `needs_human` and a person types it on the screen) — a skill must not need a password in the chat, the command file or the task record, the same rule `/replay` keeps.
- **The approval gate is not the skill's to switch off.** A step gated when it was recorded is `consequential` and stops for approval every run; the confirm question *tells* the person this, it does not ask. `skill_task` runs everything through `replay.run` → `core.act`, so `approval.check` and the audit trail apply exactly as they do to an engine.
- **Optional steps step over one thing only** (`replay._Halt.missing`): a target that is not on the screen. A target that is *ambiguous* (two candidates), an action that fails, or an expected result that never appears still halts an optional step — the run never guesses between candidates.
- **Running asks instead of failing.** Before the first step: any value the skill learned changes every run and was not given (`/skill x name="Acme"`, or just the value when one is missing), and — if a person said to — that the screen looks like where the recording began (`learning.start_checks`, using `replay.unmet`). When replay halts, `skill_task` asks: `retry` / `skip` / `stop` / `use "<control>"` for a step that did not run, `continue` / `stop` for one that *did* run but whose result never showed (never a retry — that could act twice, the same reasoning as `reconciliation_required`, which is final and never asks). Two replies it cannot read in a row end the run rather than guess, and `MAX_STUCK_ASKS` bounds the questions per run.
- **What a person answers is learned only if it worked.** `use "Save as"` re-targets that step (`_retarget`: same role, new name, the recorded path dropped) on the run's in-memory copy, and `_finish` writes it into the skill (and bumps `version`, appends to `learned`) only when the run then ended `verified` / `completed_unverified`. A `skip` is this-run-only and changes nothing on disk. Carrying on past the last step (skipped, or done by hand) finishes the task as such, not as a halt at a step that does not exist.
- **Loops** (`learning._find_loops`): a block of 2-12 steps repeated back to back with *different text typed each time* (and every step seen in every demonstration, no manual or `open` step in it) is a candidate, asked about as `loop:<id>`. `each` keeps one repetition and makes what it types a **list parameter** (`param["list"]`, `examples` holds what the demonstration typed), the extra repetitions' steps dropped; `fixed` (also the cautious default, and a no-op) leaves every step and asks about each typed field as usual. The typed fields of an undecided loop are *not* asked about individually — the loop answer decides what they are. At run time `skills.expand` writes the block out once per item, naming each typed field `<param>__<n>` (and renaming the recorded value check to follow it), keeping every step's `id`; a list is items separated by `;` or a new line, all lists the same length (`skills.list_problem`, asked again whole rather than guessed at), at most `MAX_LOOP_ITEMS`. The run's step numbers are the *expanded* program's, which is why `skill_task._retarget` maps a step number back to the skill's own step by `id`: a correction made in item 2 holds for every item.
- **Resuming needs only what is still to run** (`skills.needed_from`): `gui do NAME --from 4` does not ask again for a value only step 2 typed, the way `replay.run` already skips parameters before its start step — except with a loop, whose steps are numbered again per item, where everything is needed.
- **An engine cannot answer a question, so `skill_engine.run` refuses instead**: a missing value, unusable lists, a draft, or a screen that is not where the task began (only when a person said to check) return `halted_before_effect` with what to do, and nothing happens. It never rewrites a skill — a correction is a person's, made in the chat — and only counts a successful run (`skills.note_run`). `gui do`'s hint for carrying on is `gui do NAME --from N`, not `gui replay` (`cli._print_replay(result, command=...)`). The three engines are told skills exist in their own prompts (`ollama_client.SYSTEM_PROMPT`, `operator.go`'s prompt, `claude_harness.SCREEN_SYSTEM_PROMPT`).
- **The control plane teaches and runs through the same door as a replay** (`httpapi/skills.go`'s `sendTaught`): refused with 409 while the desktop's agent has a task running or paused (a lesson or a skill run sent to a paused agent would be taken as the reply), otherwise Plan → the desktop's `POST /recordings/<id>/learn` or `POST /skills/<name>/run` → Commit. Unlike a replay's, a skill's parameters *are* in the request the chat shows (`/skill add-a-customer customer_name="Acme"`), because a skill has no secret parameter — a secret is a step a person does by hand. `skillContent` (Go) and `skill_task.request_text` (Python) build the same string and are each tested against the same expected value; change one and the other's test says so. A value holding both kinds of quote cannot be written into a request and is refused (400), not bent.
- **A `/learn` conversation is a task that is not an attempt**: `tasks.Classify` types it `teaching` and `tasks.Report` skips it like a demonstration, because every question it asks is the point and not a person stepping in. A `/skill` run is `screen` and *is* counted: a skill that had to ask something is, correctly, not autonomous.
- **Verified live, not just in tests** (`bench/skills/e2e.py`): a real `decurix-desktop:basic` container running this tree's agent, a mock control plane on the host catching its questions, and real Chromium on a local form. The agent records two demonstrations of a task through `gui`; `/learn` on both asks two questions (when it is finished, and whether to save — it learned from the two demonstrations that the name changes, and dropped the "Saved <name>" check that differed between them); `/skill` asks for the value and the page really shows it; after the form's button is renamed the skill stops and asks, `use "Save changes"` finishes the run, and the correction is in the saved skill. Run it after touching the agent side; it needs Docker and a built image and takes about two minutes.
- **Values come from the run's documents when a hosted model is there** (`decurix_agent/binding.py`). A `/skill` request's first line is the command; lines after it are the run's context (an email trigger's rendered email and its attachment paths - `mailtrigger.RenderWithFiles` appends them to `/skill` rules only, every other slash command is still sent as written). Values the command does not give are read from that context and the files it names (`office.read_document`; scans as pictures) by one `llm_client.chat` call that is given each parameter's name, the field it is typed into and the demonstration's value **as an example of which thing to read, never as the answer**; each filled value carries where it was read, and the run's report lists them ("Values read from the documents"). What the documents do not show is asked for exactly as before; values still go through the constraint and list checks, and consequential steps still stop for approval. No model (`DECURIX_LLM` unset): nothing changes. Pulling a value out of a chat *sentence* is still not done.
- **A task the model does while still learning it is not stopped by a value its documents do not have** (`skill_task._prepare`). One demonstration fixes the task's shape to what it showed: an application bill taught from two lines made `item_2`/`typed_text_4` required, and the next bill had one line - the run asked for the second item before doing anything, and "there is no second line" could not answer that question (found live, 2026-10-07). When the run would go to the model (`_learning_by_model`) and the documents have been read (`run["filled"]`), what they did not give is left to the model, which reads them and the lesson itself. Lists that do not line up and values a field refuses are still asked for; a replay (a trusted skill, no model) still asks for every value.

### A worker learns with the brain, then runs on its own - and never reports an unseen success

Three rules, from the person running this: while a worker is learning its range of tasks it leans on the brain, and less once a task runs smoothly; a lesson must be strong enough that a recording plus a good Q&A lets it do real, varied workflows; and it may ask, or say it failed, but must **never** report success for a task that failed.

- **Maturity (`experience.note_verdict` / `clean_streak` / `stage`).** Every run of a skill records how it ended: `mode` (model or replay), `ok`, `checked_by` (screen, model, person) and `helped` (a person stepped in, the model took over a replay, or the check sent the model back once). A skill is `apprentice` until `TRUST_AFTER` runs in a row succeeded, were checked, and needed no help (`DECURIX_SKILL_TRUST_RUNS`, default 3; `0` trusts from the start - replay-only benches), then `trusted`. One failure or rescue and it is learning again. `skills.summary`'s `health` carries `stage` / `clean_runs`.
- **Learning = the engine does it, guided by the skill** (`skill_task._by_model`, when `_engine_can_drive`: TheBot on a hosted brain, or the Office engine). The request goes to the engine as `Do the task you were taught, "<title>" (skill <name>) with ...` (a mimicked request goes as the person typed it), and `guidance.py` puts `_procedure` into its model's context: what the task is, the person's words and every Q&A answer, rules, corrections from earlier runs, this run's values with what each means, the steps, and how to work - `gui skill NAME --look N` (the screen step N was done on, the pressed spot ringed in red, left as the command's picture so a vision brain sees it), `gui do NAME --from N` for stretches that match, one item at a time for a list, and never DONE for what the screen does not show. TheBot's triage sends that request to the operator (`taughtTaskRe`: found live, it was a "question" for the tool-less chat skill, which answered as if it had done the task). **Trusted = replay**, and a replay that gets stuck is handed to the model before a person (`_execute` -> `_by_model(from_step=...)`, once per run; a step that ran but whose result did not show is marked so the model never repeats it blindly).
- **No unseen success (`verify.py`, `skill_task._finish` / `_gate` / `check_unchecked`, `messaging.set_final_gate`).** A replay whose every step's result showed is a success by the screen (in apprentice stage, with a model, it is also judged). Anything else - `completed_unverified` from `/skill`, mimic or `/replay`, any "done" an engine reports for a taught task, and any engine task that acted on the screen (`_did_screen_work`: its task recording has an action) - is judged: the model sees the screen now, the demonstration's final screen, the criteria, and `evidence.observed()` (the task's recorded actions and what tools read off the screen - `gui ask` notes its answers - because the final screen shows only the end of a list). Only `done` with confidence >= 0.8 is done; `not_done` sends the model back once with what the check saw; anything else asks the person ("I cannot confirm this is done ... reply `done`, `retry`, or say what is wrong"). Their words are kept as a `correction` every later run reads. Without a model the person is asked. Pure chat and shell answers are not gated. `write_final_reply(..., checked=True)` marks a report that went through the gate; a gate that throws still sends the report, marked "Not checked". Found live: after a person's "yes", the engine's first attempt reported both questions answered without asking either - the check (`not_done`, 0.99) sent it back, and the second attempt was verified.
- **The lesson (`study.py`).** With a hosted model, `/learn` first studies the demonstration: steps with windows, typed values and expected results, the person's notes, and up to `MAX_PICTURES` screens (the start, each change of window, the end). It writes an `understanding` (summary, step purposes, what each input is and whether it varies, done_when, incidental steps, rules) and up to `MAX_QUESTIONS` questions it could not work out (decisions, repetition, preconditions, consequential steps). The goal question shows the understanding and asks for corrections; the model's questions come next, one at a time (`study:<id>`, before the rule-based ones); each answer is folded in by `absorb`, which may ask one follow-up (at most `MAX_FOLLOW_UPS` per lesson) and drops waiting questions the answers already settle (`settled`). The value question says what the model thinks each value is, and the last question shows the whole procedure; a reply of more than `MAX_NAME_WORDS` words there is a correction, not a name. Only a bare `stop`/`cancel` abandons a lesson ("stop and tell me" is an answer). The person's answers are kept word for word in `dialogue` and read by every later run - the model's rule list is its own merged rewording. Verified live on the ChatGPT recording: it understood the task from the screens alone, took "a list, one by one, wait for each answer, report them all", dropped a question already answered only after this fix, and later runs asked each question separately and were checked done.
- **Not done / not verified.** The Office engine gets the guidance text but `gui skill --look`'s picture only reaches a TheBot operator (its shell tool attaches none); `bench/learn_documents` passes end to end on Azure with the model driving new skills (2026-09-30, after the grounding, spelling, report and list fixes; a `gui skill` run line now shows a list as `ITEM 1; ITEM 2; ...` and the operator contract says a list takes every item in one run - an engine read a two-line PO and entered the first line, twice); `bench/backoffice` was not re-run; `bench/screen/teach_e2e.py` needs a desktop with no hosted brain or `DECURIX_SKILL_TRUST_RUNS=0`, and was not re-run. The approval gate stops ChatGPT's "Send message" like any Send: a skill that sends prompts through a chat UI asks for a yes per prompt; `gui ask` (a URL, no Send) does not.

### Skills that heal, escalate and learn

Exact replay halts the moment a control is not where it was recorded. A skill run (`/skill`, skill_task) now has a ladder in front of that halt, and a memory behind it - Orby's planner/grounder split and "observe, learn, automate" loop on the parts above. Opt-in per `replay.run(..., ladder=)`: `/replay` and a bare `replay.run` still halt exactly as before, so a recording replays *as recorded* and only a taught skill adapts.

```
step's target not found as recorded
  1. heal    healing.rank/decide  score each candidate on name, container, neighbours, position, role;
                                  take one only if it clears ACCEPT *and* leads the runner-up by MARGIN
  2. ground  escalation.Ladder    ask this desktop's own engine (harness.ask_model) to choose among
                                  the numbered candidates, or say 0
  3. ask     skill_task           the candidates numbered, what was tried, "reply 1"; one word answers it
```

- **A guess never passes for a match.** Confident needs the score, the label similarity and the lead to each clear a bar. A containing label scores 0.75 on purpose ("Delete" vs "Delete all" are different actions), so a name alone never suffices; position, container and neighbours have to agree. Letter-overlap only counts for near-typos (ratio >= 0.8) - `save` vs `archive` reaches 0.6 otherwise, found by a test that "healed" it.
- **A step that could do harm is strict** (`healing.strict`: approval-gated, or optional): needs 0.85 with a label of 0.85+, so a synonym rename can never heal it, and it **never reaches the engine**. The approval gate in `core.act` is not on the ladder and nothing here can grant one; a yes is still one action's. `_approval_text` only tells the person more (what the step does, what it would type, what it led to when recorded, whether the control was found by a repair).
- **The engine is a grounder, not an agent.** `harness.ask_model(system, prompt)` is one question, no history, no tools (`claude -p --tools ""`, or Ollama `/api/chat`; TheBot has no single-question endpoint so it asks the Ollama it already uses) - and `harness.py` is still the only file that branches on the engine. It picks from the list the screen actually has; a choice outside it, prose instead of JSON, confidence under 0.75, a timeout or no engine at all is "not sure" and drops to the person. `DECURIX_ESCALATION_MODEL_CALLS` (default 3 per run, 0 disables) bounds it - on a CPU host an abandoned request keeps evaluating (see the Ollama gotcha), so a run must not fire an unbounded chain. It is only offered while `state.backend_ready`. The two system prompts are constants so Ollama's prefix cache carries.
- **A result that is not there exactly can be *judged*.** `Ladder.judge` asks the engine whether the screen shows the step did its job (needs 0.85). That is a judgement, not a check: such a step counts as unverified, so the run ends `completed_unverified` and says "took the screen's word for step N" - `replay.py` still never reports a success it did not see. Never for a `consequential` step, whose missing result stays `reconciliation_required`.
- **Learning (`experience.commit`) keeps a lesson only if the run then succeeded** - the rule `_retarget` already had, made general. A repair the screen confirmed (the step's expected result appeared) becomes an `alternates` entry at once; one nothing confirmed must repeat `PROMOTE_AFTER` (2) times; a control a person picked is kept by `_retarget`, which now files the old name as an alternate too. `locate` (box + neighbours) is refreshed only from a step found as recorded or a repair the screen confirmed. A run that stopped or failed records history *on a fresh copy read from disk* (`skill_task._settle`) - the run's own copy holds corrections not yet shown to work.
- **A skill reports its own wear.** `experience.health`: a step that needed a repair or a person in 3 of its last 5 runs is *fragile*; `_finish` appends "record it again and `/learn` it", and `skills.summary` carries `health`.
- **Ingestion keeps what healing needs.** `compile_program` adds `step["locate"]` (the recorded box and screen size, beside the target so nothing comparing targets changes) and `phase`/`phase_label` (a change of window starts a phase), which a question shows as "Part 2 of 3: Customers". The container names come from the target's own path.
- **An engine running `gui do` gets healing only** (`skill_engine.run`, no model, no person) and keeps nothing: a skill is rewritten by a person's correction or by a `skill_task` run, never by an engine's.
- **Not built, on purpose: a standing approval** ("always allow this"). It would be the skill switching off the gate, which the section above forbids; the richer approval text is the safe half of it. **Not verified live:** the engine calls (`ask_once` for Claude in particular) and the ladder against a real desktop - the unit tests script the engine and the screen, `bench/skills/e2e.py` has not been extended to a renamed control. Do that before relying on the model rungs.

The benchmark is `bench/gui/`: 20 tasks (12 in a web admin panel, 5 in LibreOffice, 3 in GTK apps, 3 of them approval checks), fixtures and outcome checks that run inside a desktop (`fixtures/bench.py`), and `run.py`, which drives each engine through the control plane's chat API on a fresh desktop and reports success rate per engine. `--engine oracle --container <desktop>` runs each task's scripted `gui` solution with no model — the proof that a task is solvable and its check is right. Results go to `bench/gui/results/` (gitignored).

### The `--cli` terminal client

`decurix --cli` (`cmd/decurix/cli.go`) is a text alternative to the dashboard/chat page: an interactive REPL (`list`/`create`/`start`/`stop`/`restart`/`delete`/`chat`/`queries`) that talks to a control plane already running somewhere, purely over `internal/httpapi`'s existing JSON endpoints — no Docker client, no database, nothing the server-mode branch of `main()` sets up. `main()` checks `-cli` immediately after `-version` and before any of that setup, same posture as `-build-images` short-circuiting startup. `chat <id>` polls `GET /api/desktops/chat` (the same snapshot the chat page's polling fallback uses) once a second, tracking how many `Thread.Entries`/`Thread.Steps` it has already printed so a repeated poll only shows what's new, and returns to the prompt once the turn stops `Running` with at least one new entry; Ctrl+C during that wait returns to the prompt without cancelling the task (it keeps running on the desktop) by trapping `os.Interrupt` only for the duration of that wait, never at the top-level prompt.

`build.sh --cli` / `rebuild.ps1 -Cli` (etc.) run their normal flow through "Decurix is running", then run `docker compose exec desktop-manager ./decurix --cli` instead of opening the Cloudflare tunnel — the same binary the container already runs, reached at its own `127.0.0.1:8080` (also `--cli`'s default `-url`, which is why it works unchanged if someone runs the released binary directly against the compose-published port instead). Both scripts clear their INT/TERM trap right before that hand-off: `build.sh`'s otherwise prints a "tunnel stopped" message that would not make sense here, and `rebuild.sh`'s otherwise tears the whole stack back down on Ctrl+C — correct for an interrupted *rebuild*, wrong once the rebuild has already finished and someone is just leaving the CLI.

### Distributable builds

`scripts/release/release.sh` / `release.ps1` cross-compile `cmd/decurix` for linux, windows and darwin × amd64/arm64 with `CGO_ENABLED=0 -trimpath -ldflags "-s -w -X main.version=<version>"`, writing to `dist/`: a bare binary per target, a per-target archive (`.zip` for windows, `.tar.gz` otherwise), and `SHA256SUMS`. Version defaults to `git describe --tags --always --dirty`, and `main.version` backs `decurix --version`.

The binary is fully self-contained: static (`CGO_ENABLED=0`, no libc — which is why the SQLite driver is modernc.org/sqlite, not mattn/go-sqlite3), web templates from `web/embed.go`, desktop build context from `embed.go`, and `.env` optional. The one file it *writes* is `decurix.db` in `sqlitedb.DataDir()` (`DECURIX_DATA_DIR`, else `os.UserConfigDir()/decurix`; the Docker image sets `/data`, which `docker-compose.yaml` mounts as the `decurix-data` volume). So an archive carries **nothing the binary depends on** — a generated `README.txt`, an `.env.example`, and `decurix-android-arm64`, the phone build a phone downloads from the control plane when it sets up its link (optional: without it `/phone/link` says the helper is missing and everything else works). `stageBundle`/`Copy-Bundle` branch on `goos` purely to write that README with one OS's commands (`./decurix` vs `.\decurix.exe`).

Keep it that way: any new runtime file dependency must be `go:embed`ed, not added to the bundle. If you ever have to put a real dependency in the archive, the "single executable is the whole product" claim in README.md needs to change with it.

## Conventions / gotchas

- `CODE_MAP.md` is auto-generated (ctags + LLM summaries) — don't hand-edit it; it's regenerated from source after edits.
- Go doc comments: every exported/significant func gets a one-line `// FuncName does X` summary directly above it — keep following that pattern for new functions.
- The agent's output must start with exactly one of `COMMAND:` / `DONE:` / `HELP:` (see `ollama_client.SYSTEM_PROMPT`) — `parser.parse_agent_response` searches for whichever marker appears first, so don't change that contract without updating both sides.
- The desktop agent (`vm_server.py`) is launched as a detached background process by `agent/start_agent_terminal.sh` (via `setsid ... &`), not inside a visible terminal — output goes to `/tmp/decurix-startup.log` inside the container. Don't reintroduce a foreground/`xfce4-terminal --hold` launch; it makes the agent visible as a window on the VNC desktop instead of running silently.
- `decurix_agent/state.py`'s module attributes (`current_task`, `waiting_for_query`, etc.) are the agent's only cross-module shared state. Mutate them as `state.current_task = x` after `from decurix_agent import state` — never `from decurix_agent.state import current_task`, which copies the value instead of sharing it.
- `EnsureImages` no longer pulls. `decurix-desktop:*` are local-only tags that exist in no registry, so the old `ImagePull` could only ever fail with "pull access denied" on a fresh machine; it now just reports which images are missing and points at `--build-images`. Don't reintroduce a pull unless the images actually get published somewhere.
- `embed.go` sits at the module root on purpose — `go:embed` cannot reference parent directories, and the desktop build context spans `docker/` and `agent/`. Anything a desktop image needs at *docker build* time must be under one of those two trees and matched by an `embed.go` pattern, or the image builds fine from the repo and fails from a released binary. `go:embed` also silently skips names starting with `_` or `.`, which is what keeps `agent/__pycache__` out — but would equally skip a real file you name that way.
- **`go:embed` also skips `agent/thebot`, silently, because it is a Go module of its own** (a directory with a `go.mod`). So a released binary's build context had no TheBot and `--build-images` failed at `COPY agent/thebot/go.mod` - found by the Windows app's first launch; the Linux/Mac scripts `docker build` from the repo and never met it. `go generate .` (`embed_gen.go`, `//go:build ignore`) packs it into `agent/thebot.tar.gz` (gitignored, picked up by the `agent` pattern) and `desktop.tarBuildContext` unpacks it back to `agent/thebot/...` in the stream. Everything that builds a binary to hand out runs it first (`scripts/release/release.*`, `scripts/windows/build-electron.ps1`, `docker/Dockerfile`), **before `GOOS` is set** (the generator runs on the build machine). A binary built without it says so (`errNoTheBotSource`) instead of failing in Docker, and `TestTheEmbeddedContextHasEverythingTheDockerfilesCopy` checks every Dockerfile `COPY` source against the embedded context (it skips when the archive was not generated).
- **`go:embed` also skips the agent's `_`-named files** (`decurix_agent/__init__.py`, `computer/__init__.py`, `computer/__main__.py`, `tools/__init__.py`, `browser-agent/*/_pathfix.py`): a directory pattern drops names starting with `_`, so every desktop image the app or a released binary built had no `computer/__main__.py`, and `gui` - every engine's way to the screen - failed with "No module named decurix_agent.computer.__main__" (found 2026-10-07; the scripts' `docker build` from a checkout never met it). `embed.go` names them by pattern, and `TestEveryAgentFileIsEmbedded` walks the checkout's `agent/` for any `_` file the context lacks.
- **`--build-images` rebuilds an image built from other sources, not only a missing one** (`desktop.contextHash`, label `decurix.context`). It used to skip any image that existed, so a freshly built app went on creating desktops from the image an earlier binary had built - agent code and all. The desktop image's hash covers the whole embedded context except the tools Dockerfile; the tools image's, its own Dockerfile only. The classic builder's layer cache keeps an unchanged layer, so a rebuild after an agent change is minutes, not the first build's tens. An image built by the scripts' `docker build` has no label and is rebuilt once by the app.

A hosted model distils the exchange into one standing instruction, or nothing: a bare yes/no/retry/skip and a yes or no to an approval are never looked at (a standing approval would be the worker switching off its own gate); "the second one, she works at Infosys" is this run's alone; a secret (the question asks for a password/code, or the reply looks like a credential) is neither kept nor sent to be read. With no model the exchange is kept as said, except a replay's or a skill run's own questions (a value, a stuck step), which would fill the memory with one-off values. It goes to worker memory through `messaging.remember` (category `lesson`): on the card's learned-memory list, in `~/.decurix/memory`, and so in every engine's context on every later task. On a taught task the question and answer are also kept on the skill itself (`run_answers`, read by `_criteria` beside `corrections` and the lesson's dialogue).
  - **Not asked again.** Before a person is paged with an engine's question (`kind: query` from an engine - never an approval, never a question a replay, a lesson, a skill's own run, a ticket or a web lookup asked), the hosted model is shown it beside everything the person has said - this task's lesson and the kept lessons - and a confident (0.8) "already answered" is given to the engine as the reply, said in the chat ("Not asking you - you already told me: ..."), at most twice a task. Checked on the real model: the person's "which Akshit Gupta?" is answered from "choose the first one"; an error on the page, a language nobody mentioned and a verification code are not.
  - **Used when reading a request.** `request_reading` is shown the kept lessons too, and a value may come from one that plainly says what to use.
  - A skill's memory entry (`skill_task._remember`) now carries the lesson's summary and each question asked and answered when it was taught, word for word.

- `desktop.Manager`'s, `conversation.Store`'s, `stepimages.Store`'s, `tasks.Store`'s and `schedule.Store`'s mutexes each guard one struct's own state — hold the lock for the whole read-modify-write, not just parts of it. `querynotes`/`memory`/`claudeauth`/`suggest` have none: each of their operations is one SQL statement (`suggest`'s embedding cache write is `INSERT OR IGNORE`, so a duplicate concurrent attempt is a harmless no-op, not a race).
- **`sqlitedb.Open`'s pool holds `maxOpenConns` (8) connections, not one** — WAL journal mode lets any number of readers run alongside whichever connection is writing at a given instant, and `busy_timeout(5000)` absorbs the rare case of two connections writing at once, so the pool no longer needs to be held to one connection for that. What one connection *was* also doing for free — serialising every `Exec`/`Query` call against every other one — is not something WAL replaces: a store that reads a row and writes it back (`schedule.Store.MarkRun`/`SetEnabled` is the one example so far) now needs its own mutex for that read-modify-write to stay atomic, the same pattern `tasks`/`conversation`/`stepimages` already use for their in-memory state. `sqlitedb.OpenMemory` (tests only) stays pinned to one connection on purpose — a second connection to a `file::memory:` database is a *second, empty* database, not a shared one, so tests that want real multi-connection behavior (a concurrency regression test, say) need `sqlitedb.Open` against a temp file instead, the way `schedule`'s `TestConcurrentMarkRunAndSetEnabledDoNotLoseAnUpdate` does. **No query may run while a `*sql.Rows` is still open** remains the rule regardless of pool size — on a connection pool of 1 it silently deadlocked instead of erroring, and on a larger pool it silently burns a second connection instead (or holds back WAL's checkpoint on a long-open read) — every store reads rows to the end (and closes them) before its next statement; keep it that way.
- **Every transaction is `BEGIN IMMEDIATE`** (`_txlock=immediate` in `sqlitedb.Open`'s DSN). A deferred transaction that read and then wrote after another pooled connection had committed failed at once with SQLITE_BUSY_SNAPSHOT (517, "database is locked"), which `busy_timeout` never retries: found by `bench/screen/teach_e2e.py`, where a finished lesson's outcome was lost and its task stayed "running" for good. `TestAReadThenWriteTransactionIsNotLostToAConcurrentCommit` reproduces it. Stores open transactions only to write, so taking the write lock up front costs nothing.
- A schema change is a **new step appended** to that component's `schema` slice, never an edit to an applied one: `sqlitedb.Migrate` records how many steps each component has run and only runs the rest.

- **The chat model is chosen for this machine, not hardcoded** (`internal/ollama` `select.go`, `autoselect.go`, `resources.go`). Unless `OLLAMA_MODEL` names a model, `EnsureReady` calls `SelectModel`: `ProbeResources` reads RAM (`/proc/meminfo` `MemAvailable`, capped by a cgroup limit; `vm_stat` on macOS; `GlobalMemoryStatusEx` on Windows), CPU busy over a 400 ms sample, and an NVIDIA GPU via `nvidia-smi` (Apple Silicon counts its unified memory as VRAM; AMD/Intel GPUs are not probed, which errs small). The budget is **(free - used by everything else) * 0.5** (`BudgetFraction()`, default `0.5`, tunable via `DECURIX_MODEL_BUDGET_FRACTION` - kept well under 100% so spinning up a model doesn't starve the desktops, the browser and the OS), applied to RAM, VRAM and free cores, minus a reserve for the embedding model. **Ollama's own loaded model is added back to "free"** (`ollamaHeld`, from `/api/ps`): otherwise a model that fit would stop fitting the moment it was loaded, and every re-check would shrink the pick. A model fits if its weights plus KV/runtime overhead (`NeedGB`; for an installed model the KV cache is exact - `kvsize.go` reads layers x KV heads x key/value width from `/api/show`, which never loads the model, once per digest, per-layer head arrays summed, times `OLLAMA_KV_CACHE_TYPE`'s element size; the old `0.06 x params` guess overstated a MoE model's cache several times) are inside the VRAM budget (GPU speed), or inside the RAM budget *and* it decodes at least `DECURIX_MODEL_MIN_TPS` on the free cores (`cores * DECURIX_MODEL_CORE_GBPS / GB read per token` - CPU decoding is memory-bound, and a mixture-of-experts model reads only its active parameters, which is why `qwen3:30b` beats a dense 14B on a big CPU-only box). Among fits the highest `Quality()` wins (parameters x a family factor; MoE = geometric mean of total and active). Those constants are estimates, loosely calibrated on this repo's measurements, not benchmarks - tune them by env var. - **Prompt evaluation, not generation, is what makes a desktop feel slow**, and `keep_alive` is the lever. Measured on an ordinary CPU-only laptop with `qwen2.5-coder:3b`: the agent's 545-token system prefix took **31.8 seconds** to read cold and **0.6 seconds** with the model still resident. The corollary: **keep the system prefix byte-identical across calls**, which is why both halves of the Ollama harness go through `ollama_client.build_system_messages` rather than assembling their own, and why `num_ctx` is a fixed 8192 everywhere — changing it makes Ollama reload the model and discard the cache.
- **Warm the Ollama the desktops actually use, at the context size they use.** `ollama.Manager.EnsureReady` used to start the bundled `decurix-ollama` container and preload the model *there* whatever `OLLAMA_URL` said, and without `num_ctx`. Measured on a 7.6 GB CPU-only host with `OLLAMA_URL` pointing at the host's Ollama: the preload held 2 GB of RAM on a server nobody talked to, the real one loaded cold in 210 s inside the first request's 300 s timeout, and even a correctly-aimed 4096-context preload would have been thrown away by the agents' first 8192 request. It now preloads `ollama.DesktopURL()` with `ollama.NumCtx`, and touches the bundled container only when `OLLAMA_URL` is `ollama.BundledURL`. The same rule is why TheBot's `[code]` steps must really be code: `internal/coding` asks for a 32768 window, and one such request used to reload the shared model for **every** desktop (161 s, measured) and then reload it back the moment an ordinary chat turn followed it - Ollama treats the same model at two different `num_ctx` values as two separate loaded runners, and by default only keeps one resident at a time. `ollama.maxLoadedModels` now sets `OLLAMA_MAX_LOADED_MODELS=2` on the bundled container - exactly the two context sizes actually in play system-wide, never more - so both runners can stay loaded instead of trading places; `codeGenKeepAlive` (5m, against the chat runner's 30m `OLLAMA_KEEP_ALIVE`) is what then gives the rarely-used long-context runner's memory back promptly rather than both simply staying resident forever. Same caveat as the seccomp profile and the wallpaper below: the env var is only set at container *creation*, so an already-running `decurix-ollama` needs recreating to pick it up. It only ever applies to the bundled container - an external Ollama named by `OLLAMA_URL` is not this control plane's process to configure, and needs `OLLAMA_MAX_LOADED_MODELS=2` set by hand for the same fix to apply there.
- A **backend failure ends the task** (`write_final_reply(..., kind="error")`), it does not pause it with `ask_for_query`. The note tells the human to send the request again, and a paused desktop routes the next request to `continue_after_query` — measured live, a new task was taken as the "reply" to a greeting that had timed out, and reported under the greeting's Task. The exception is a failure inside `continue_after_query` itself, where a resend of the reply should still carry the original task.
- The reasoning model is not the only model. `nomic-embed-text` is a **separate dependency** that only the `thebot` harness needs, and Ollama will not embed with a chat model. Nothing pulled it, and the failure was invisible in the worst way: soul kept answering questions while every write to its Data RAG, its L1 long-term memory and its negative-feedback store failed with `model "nomic-embed-text" not found`. An agent that cannot record what it learned still looks like it works — it just never improves, and repeats the same failure next time. `ollama.EnsureReady` now ensures both models (the embedding one best-effort, since the other two harnesses never embed), and `scripts/linux/lib/ollama-setup.sh` (shared by `build.sh` and `rebuild.sh`) does the same for a host or remote Ollama the control plane does not manage.
- A model that asks a query before running a single command has not tried anything, and `task_runner` pushes back exactly once (`PREMATURE_QUERY_NUDGE`). This is what "hello, whats your desktop name?" needed: it came back as a query asking the human *why they wanted to know*, blocking the desktop on a question. Two things keep the pushback honest — it fires only once, so a second HELP is always delivered, and its last paragraph explicitly invites a safety pause (payment, outgoing message, real-world consequence) to be re-sent unchanged. Verified against the real model: a bogus HELP becomes `DONE: kiolo`, while "pay the 400 dollar invoice" and "email my landlord" still escalate.
- **A reply with no marker is still an answer.** `parse_agent_response` returning `invalid` used to re-prompt with a generic restatement of the format, up to the 50-step limit, and then tell the human the agent "may be stuck in a loop". Measured live: asked how many files are in `/etc`, the model ran the right command, read the right number and replied `241` — finished at step two — then spent forty-eight more steps being lectured about markers before paging a human about a task it had already completed. Two fixes, both load-bearing: `invalid_format_nudge` quotes the model's own opening back to it (the generic version produced another bogus HELP; the quoting version produced `DONE: 241`), and after `MAX_INVALID_RESPONSES` tries `salvage_unmarked_response` delivers the text as the final answer rather than raising a false alarm.
- **A repeated command is how the Ollama loop actually runs out of steps**, and `task_runner` catches it deterministically rather than trusting the prompt to forbid it. The model writes `COMMAND:` and a *predicted* `DONE:` in the same reply; `parse_agent_response` correctly takes only the command, the prediction is dropped, and the model - which considers itself finished - sends the identical pair again. Measured on "what is the current kernel version?": `uname -r` fifty times. An identical consecutive command now gets `repeated_command_nudge` (the output it already produced, and an instruction to answer), and if it repeats again the task ends with `final_answer_from_command`. That reports **what the command actually printed, never the agent's own trailing DONE:** — on step one of that very case it predicted `5.10.124-microsoft-standard-WSL2` before running anything, and the real answer was `6.6.87.2`.
- `parse_agent_response` matches uppercase markers anywhere in the response, then falls back to a line-anchored, case-insensitive pass for `Help:`, `**DONE:**` and `HELP :` (all seen live). The two passes are not interchangeable: a lowercase `help:` mid-sentence is ordinary English, so accepting it anywhere would truncate a real DONE answer at the word "help:". Keep the loose pattern anchored and second.
- What a human reads when an engine fails must not be the engine's own words. `messaging.backend_failure_note` rewrites `context deadline exceeded` / connection refused / missing-model errors into what happened and what to do, keeping the raw text underneath — the note used to hand someone `ollama: request failed: Post "http://host.docker.internal:11434/api/chat": context deadline exceeded` as the entire explanation for why their desktop stopped. `thebot_harness._escalate` applies the same rewrite to failures TheBot words in its own voice ("could not reason about the failure (...) - stopping here").
- `thebot_harness` sends **the task and the standing context as separate fields** (`prompt` and `context` on soul's `/api/chat`), never one string. They used to be glued together, and soul classified, planned, stored in session history and answered the whole blob: "hello, whats your name?" spent 97 seconds in a planning call and came back as `NEEDS_APPROVAL: Before sending any real-world consequences...` — an answer to the safety rule — and "what is the current kernel version?" became a plan to search the web for the weather in New York. The context now only ever reaches soul's system frame; classifiers, the planner and history see the task alone. Measured before/after on `qwen2.5-coder:3b`, CPU only: the greeting went from 148 s (wrong) to 56 s (right), the kernel version from 205 s (wrong) to 45 s (`uname -r`), and creating a file in the work dir from a failed recovery that tried to `chmod /home/headless` to 18 s.
- soul is **deterministic before it is clever**: `atomizer.Triage` routes a request without a model call, and only a genuinely compound request (`looksCompound`) is sent to the planner. The removed layer asked the model "is this a task or a question?" for every request no classifier claimed — the single most expensive and least reliable call in the agent. Keep new routing rules in `triage.go`, deterministic, with a `triage_test.go` case; a chat answer that turns out to need the machine replies `NEEDS_TOOLS` and the scheduler reroutes it to the operator, so a triage miss costs one short call, not a wrong answer.
- soul keeps **one paused job per session** (`server.paused`). `thebot_harness.perform_task` sends `reply: false` (drop any paused job — this is a new request) and `continue_after_query` sends `reply: true` (resume it). A resumed approval runs the exact command it stopped before; a resumed question hands the human's words to the operator's saved transcript. Don't restate the task in a reply — the checkpoint already has it, and restating it makes the operator start over.
- The prompt frame's **volatile sections are chat-only**: live counters (`selfStats`) and the time of day go into a conversational job's frame and nothing else; every other job gets the date alone. With the counters in every frame, the job-log count — which goes up by one per job — changed the bytes right before the operator's contract and made every job re-read it cold.
- **A question for a web app is asked there, not worked out** (`ask_task.py`). Live: `chatgpt "where is addid ababa"` was triaged by TheBot as chat, rerouted to the operator, which ran `... | xargs curl -s https://www.google.com/search?q=` on the basic image (no curl), and the person was paged "Install curl using `sudo apt-get install curl`". The request already is the plan: each supported service takes the question in its URL (ChatGPT `?q=` submits it, logged out too), so the watcher opens that URL and a per-site reader polls the page until the answer stops changing. What the readers rely on was checked on the live pages in 2026-09 and is written beside each one - ChatGPT's classes are generated, but `li[data-message-role=assistant]`, `data-message-complete` and `[data-assistant-content-reference]` (source pills) are stable; Wikipedia's paragraphs moved into `<section>`s. ChatGPT marks a reply complete a moment before it marks its source pills up, so a reply can be read with "W / Wikipedia / +1" in it as words: `strip_source_pills` takes that shape out (the letter must be the source's own first letter, so an answer of "B" survives). Supported: ChatGPT, Google (AI overview + top results), DuckDuckGo, Wikipedia, YouTube. Not: Perplexity (logged out it shows a sign-in page, no answer), Bing (titles hidden behind redirects), anything that needs a sign-in. The name must lead the request (`what does google say about x` goes to the engine), another product is not a query (`google docs ...`), a job for the desktop after the answer (`... and save it to notes.txt`) goes to the engine, and a question holding a credential (`privacy.credential_in`) is never sent. A request that is only a list of quoted questions (`chatgpt "a", "b" and "c"`, `QUESTION_LIST`) is asked one question at a time, each in its own tab, with every answer in one reply; a refusal stops the rest and says which were not asked. Live, the whole list went to ChatGPT as one prompt. **With a hosted brain, the shortcut steps aside for a service a person taught and explained** (`ask_task.taught_for`: a ready skill whose goal/title/explanation names the service and has an explanation, and `llm_client.available()`), so the model follows the person's words. For that the model gets: `gui ask SERVICE "QUESTION"` (one question, `ask_task._ask`, taught in `operator.go` and in the context); TheBot's triage sends a request that leads with a web app's name to the operator (`webAppLeadRe` - it used to be a "question" answered by the chat skill, which has no tools, from the model's own knowledge); and `thebot_harness.taught_context` puts every ready skill (name order, up to 8, so the frame stays stable) with what the person said into soul's standing context.
- **A person's explanation from `/learn` is shown to every model as theirs, whole** (`skills.explanation`: `explanation`, else `done_when` for older skills): `gui skills`/`gui skill`, the Office engine's procedures, the skill's worker-memory entry, TheBot's context. It used to reach only the grounding prompt of a stuck step, and elsewhere its non-step part was shown as "finished when" - "I will send you a list and you query them one by one" is how to do the task, not what done looks like. A challenge page or no answer in time ends the task as an error that quotes the page, never a guess. A recorded `chatgpt "who is x"` demonstration is not mimicked in its place: its one fixed word, "chatgpt", is also in a control it clicked ("Chat with ChatGPT"), so `mimic.align` finds no shape to match and returns None - `/skill <name>` still runs such a skill by name. When a site changes its markup the reader times out with the page's text in the reply - fix the reader, and re-check it live (`docker exec -i -u headless -e PYTHONPATH=/opt <desktop> python3 -` with `cdp.Page` and the reader's JS).
- **What soul logs is not what the chat shows** (`thebot_harness.readable_step`). soul's job log is for debugging soul; forwarded verbatim, the card's "Working on" line and the chat's live box showed `scheduler: "chatgpt \"where is x\"" [general] -> skill=general model=qwen2.5-coder:3b`. Plumbing lines (the dispatch line, empty L1/skill-library lookups, rerouting, RAG ingestion, raw model replies) are dropped, the rest rewritten ("Running: uname -r", "The command failed (exit 1): ..."); every raw line still goes to `/tmp/decurix-startup.log` as `TheBot: ...`. A new soul log line reads as itself with its `component:` prefix stripped - add a rewrite only when that is not readable.
- **TheBot's browser route gives up on a browser extension that is not there** (`skills.BrowserSkill`, `defaultPickupTimeout` 30 s). The extension's listener claims work every few seconds; a request still `pending` after that means none is running (the prewarmed Chromium from `start_agent_terminal.sh` is started without `--load-extension`), so it is withdrawn (`/requests/<id>/cancel`) and the step is rerouted to the operator. It used to wait out the whole 16-minute budget, measured live. Triage keywords only count as words of their own (`atomizer.matchesWord`): "content-**type**" is a header, and it sent a terminal request to the browser. A request that names the terminal/shell/command line is never a browser task.
- **The terminal skill runs what was named, not the sentence around it** (`trailingProseRe`): "run curl -sI https://x in the terminal and tell me the content-type header" ran as that whole sentence. **Exit 127 (program not installed) is handed to the operator** with a `rerouteNote` saying so (the scheduler appends it to the rerouted step), never to the failure-reasoning model - which, measured live, chose `sudo apt-get install curl`, then on the next run asked the person. That model's prompt now also says nothing can be installed (no sudo password).
- **An answer nothing printed is not taken** (operator `ungroundedDoneNudge`, `repeatedCommandNudge`; `task_runner.repeated_command_nudge`). Live: python3 with a missing `requests` module failed twice, the repeat nudge said "if that answers the task, reply with DONE", and the model reported a Content-Type header nothing had printed (`text/html; charset=utf-8`; the real one is `text/html`). A repeated *failed* command now says the answer is not known yet, and a DONE when every command so far failed is pushed back once - a failure that is itself the answer ("no such file") is taken when said again. `missingProgramHint` also names a missing Python module and points at the standard library.
- **Stopping, restarting or deleting a desktop also closes its chat turn** (`conversation.Store.EndTurn`, from `closeOpenTasks`). The task record was closed, the agent's "interrupted" report was then refused as already closed, and nothing ended the turn: the card counted "Working on ... 12m" over nothing and the next request's steps were added to the dead turn.
- **A query note is shown as its task and its message** (`querynotes.QueryNote.Task/Message`, `ParseMessage`/`ParseTask` - also what `httpapi.agentReplyFromNote` uses; `/api/querynotes*` add `task`/`message`). The note's text opens with "DECURIX QUERY REQUEST / Desktop: / Desktop ID:", and that boilerplate was all the rail's card showed. The rail and the Queries page lead with a kind label (Needs your answer / Needs approval / Failed / Done), the task, then the agent's words; the whole note only for a note in no known shape.
- **An operator HELP straight after a failed command is pushed back too** (`failureQueryNudge`, at most `maxFailureNudges` = 2, the Ollama harness's rule), and it says never to ask the person to run or install something. When the failure is a program that is not there (`missingProgramHint`: `command not found`, or a launcher such as xargs/env/sh saying `No such file or directory` - `cat: notes.txt: No such file` is a missing *file*), the command's own result already says so and names what to use (python3's urllib for curl/wget). `curl` is now also in the basic image; the hint still matters for every other tool.
- **An operator HELP straight after a successful command gets one grounded push back** (`successQueryNudge`) unless it asks for something only a person can give (`humanOnlyRe`). Measured live: `ls -l /etc | wc -l` → exit 0, `118` → `HELP: It seems there was an error. Please try running the command again.`; and `uname -r` → the correct kernel version, delivered under `HELP:`. Both would have paged a human about finished tasks. Set `THEBOT_LOG_MODEL_REPLIES=1` on the container to see raw operator replies in the job log.
- **The operator's transcript keeps only the command, never the answer the model guessed beside it.** A 3B model writes `COMMAND: df -h DONE: 1.8T total, 20G used, 1.6T available` before anything runs; kept in history, it reads that guess back and reports it — measured, word for word, against a real `df` of 1007G/121G/835G. The same leftover guess made it call the real kernel version "not what was expected". (The Ollama harness's `task_runner` appends the raw response the same way.) Likewise `atomizer.scrubInventedContent` strips quoted content the planner wrote into a write step that follows research, unless the human typed it: the planner put `write "The newest Go version is v1.20.5"` behind a search that found 1.27, and file-write saved the guess.
- An abandoned Ollama request is **not** cancelled: when a caller times out or disappears mid-prompt, this Ollama keeps evaluating it, and the next call queues behind it with its own timeout already running — which is how one oversized prompt turned into a chain of `context deadline exceeded` failures on unrelated small requests. Prompt size is therefore a correctness issue on CPU hosts, not just speed: `THEBOT_WEB_PAGES` / `THEBOT_WEB_PAGE_CHARS` (set to 2 / 2500 by `start_agent_terminal.sh`; soul's own defaults of 3 / 6000 assume a GPU) keep a web step's synthesis prompt under the timeout — at 3 × 6000 it took more than 300 s to read and timed out.
- `thebot_harness` sends `sessionId` (the desktop ID). soul keeps real per-session history and threads it into every turn, but `session.Store`'s `Append` and `History` are both no-ops for an empty id — which is what this harness used to send, making TheBot the only harness with no memory of the request before last.
- `scripts/windows/build.ps1`/`rebuild.ps1` mirror `build.sh`/`rebuild.sh` step for step, including the Ollama-selection block, which - like its Linux counterpart - lives in a shared lib file (`lib/Ollama-Setup.ps1`, dot-sourced by both, mirroring `lib/ollama-setup.sh`) rather than being duplicated in each script. Three things in it are specific to Windows PowerShell 5.1 (the PowerShell every Windows machine has), and each one breaks the script without failing loudly:
  - The Python probes go into `decurix-desktop:basic` **on stdin, with their inputs as arguments**, never as a `-c` string, because 5.1 mangles double quotes in arguments to native programs.
  - `.env` is written as **UTF-8 without a BOM, with LF endings**. 5.1's `Set-Content`/`Out-File` add a BOM or write UTF-16, which hides the first key from `godotenv`.
  - A function's array output is unrolled, so a one-model list must be wrapped in `@()`. Otherwise `[0]` returns the name's first character.

  Each script's own `finally` tears its own stack management down only when it did *not* leave through `Exit-Build` - that covers Ctrl+C and the tunnel exiting on its own - but the two scripts' `Invoke-Cleanup` do different things on purpose: `build.ps1`'s just reports that the tunnel stopped and Decurix is still running (it never tore anything down to begin with, matching `build.sh`), while `rebuild.ps1`'s tears the whole stack down (matching `rebuild.sh`'s signal trap), since an interrupted rebuild must not leave a stack half old, half fresh. A failed build or a missing `cloudflared` leaves a running Decurix alone either way (that path always goes through `Exit-Build`).
- Windows `.ps1` twin steps with no Linux equivalent are platform fixes, not drift: `build.ps1`/`rebuild.ps1` check that Docker Desktop is actually running, and on Windows the loopback-only Ollama fix is a user environment variable plus an app restart rather than a systemd drop-in.
- The desktop agent binds `:8081` *before* waiting on its reasoning backend (`app.py` runs `harness.wait_for_backend` on a background thread). It used to call `wait_for_ollama()` inline, so an unreachable Ollama meant the port was never bound at all — and since `desktop.Manager.SendRequest` POSTs there, every human request from the chat, the Requests page and a query reply came back as an unexplained HTTP 500 while the desktop looked healthy in the dashboard. Keep the request channel independent of the model: a task that arrives with the backend down fails *inside* the harness, which reports it through `ask_for_query` as a reply the human can actually read. `wait_for_backend` also belongs to `harness.py` for the usual reason — `app.py` must not learn which engine is running.
- A request that arrives before the reasoning backend is up is **queued, never failed**. `watchers.command_watcher` leaves the file sitting in `COMMAND_DIR` while `state.backend_ready` is False and picks it up on a later pass, the same way it already defers a request that arrives mid-task; `harness.wait_for_backend` sets that flag once the engine answers. Dispatching into a backend that is still starting is what turned "Ollama is 20 seconds from ready" into a query asking a human to fix something that was about to fix itself. Every branch of `wait_for_backend` must mean *reachable*, not *launched* — `thebot` waits on both the shared Ollama and soul's own `/api/health`, because soul reports an unreachable Ollama as a reasoning failure that reads like a real one.
- The command watcher claims the task slot (`state.current_task = content`, under `state.state_lock`) *before* starting the harness thread, not inside `perform_task`. Otherwise the loop tests `current_task` again for the next queued file before the thread it just started has run a line, and dispatches a second task on top of the first — rare when requests trickled in one at a time, routine once a queued backlog can be released all at once.
- Don't hardcode a Cloudflare quick-tunnel URL as anyone's default. Quick-tunnel hostnames are regenerated on every `cloudflared` restart, so a checked-in one is dead code the day it's written — `buildDesktopEnv`'s `OLLAMA_URL` default was one, and every desktop created after that tunnel died was structurally brainless. Tunnel URLs belong in `.env` (or `internal/tunnel`, set at runtime), never in a literal.
- **`internal/lanaccess` only ever gates the second listener, never the primary one.** The primary listener (`:8080`) is what `CONTROL_PLANE_URL` points every desktop agent's callbacks at, so putting a login page in front of it would make every `POST /api/querytext`/`/api/agent/events` from inside a container fail closed the moment the control plane started, with no human anywhere to type a code. `cmd/decurix/main.go` builds two independent `*http.ServeMux`s from the one `Server` (`RegisterRoutes` called on both) precisely so a bug in the gate can never touch the primary listener's routing — the two are different `net.Listener`s on different ports, not one mux with some paths exempted. `RegisterLocalRoutes` (the code itself, and the rotate button) is the one asymmetry: registered only on the primary mux, so the code is never fetchable over the very listener it protects.
- **`lanaccess.Store`'s lockout degrades to one shared bucket for anything reverse-proxied into the gated listener**, not a per-attacker throttle: `cloudflared` (or any other reverse proxy) forwards every connection through its own local process, so every request the control plane sees through it carries the same loopback `RemoteAddr` regardless of who is actually on the other end — `recordFailure`'s per-source key can't tell a legitimate retry from an attacker in that case (a genuine direct-LAN connection, by contrast, gets AO's real per-device lockout). This is why the access code is 10 characters from a 54-character alphabet (`passwordChars`: no `0`/`O`/`1`/`I`/`l`, kept readable and typeable on a phone) rather than AO's 8: the code's own entropy is carrying weight the lockout can't, on that one path. `build.sh`/`rebuild.sh` deliberately tunnel *into* the gated listener, and only it (the `lan_tunnel_url` tunnel — see "Two listeners, one process, one set of routes" above), so this shared-bucket degradation is the normal case, not an edge case someone opted into by proxying it themselves; it is exactly the path the code's extra length was sized for. `lanaccess.RunAutoRotate`'s 48-hour automatic rotation is the other half of that same trade: entropy and a lockout that can't fully do its job are backstopped by the code simply not staying valid very long.
- **A paired device outlives the access code; an ordinary session does not.** The gate's "Remember this device" (on by default when `lanaccess.Store.SetDevices` has a registry) sets a second cookie, `decurix_lan_device`, holding a token from `internal/devices`; `Rotate` (the button and the 48 h timer) still drops every *session* but leaves paired devices alone - pairing is how a person keeps their own phone signed in across rotations. A device is revoked by name from the Mobile menu or signs itself out (`POST /__decurix_access/forget`). The list and revoke routes are primary-listener only like the code itself (`TestHostRoutesAreOnlyOnThePrimaryListener`), so a paired phone cannot see or unpair the others. The one-click link pairs too with `&remember=1` (name from the User-Agent unless `&name=`).
- **The Mobile menu adds a pairing link; it replaces nothing.** On top of the tunnel/LAN addresses, the access code with its "New code" button, the paired devices and the Admin access section, it shows one link to share: the free quick tunnel's address (the LAN address when no tunnel is up) with the code in it - `/__decurix_access/authenticate?code=...&remember=1`; `build.sh`/`rebuild.sh` (and the `.ps1` twins, via `lib/lan-tunnel.sh`/`Lan-Tunnel.ps1`) print it too. **Opening it never pairs on the GET**: it shows a "Pair this device" page (`renderPair`: the name, one button) whose POST goes through the typed form's own path. A chat app fetching the link for its preview, or a browser prefetching it, used to pair an unnamed "Device" next to the real phone. `pairDevice` also skips a request that already carries a valid device cookie, so opening the link again on the same phone does not list it twice. Costs of the free tunnel: forwarding the link hands over access, and its address changes whenever `cloudflared` restarts, so a paired device needs the new link and pairs again (its cookie belonged to the old hostname). The named-tunnel setup form was taken out of the menu (people did not know what to put in it); `internal/cftunnel` and `/api/cftunnel*` are kept for a later version that provisions the link without asking anyone.
- **A linked Android phone's apps run on the phone and show in a VM** (`internal/phonehost`, `internal/phoneagent`, `httpapi/phones.go`, `web/templates/phoneapp.html`). **It is set up from the phone itself** (`httpapi/phonelink.go`, `web/templates/phonelink.html`): an Android phone that pairs is sent to `/phone/link` (`lanaccess.SetAfterPair` -> `Server.PhoneLinkAfterPair`, by User-Agent), which asks whether to use its apps in VMs; on yes it gets a one-time setup token (`/api/phones/setup-token`, paired devices only, `phoneSetupTTL` 15 min) and one command to paste into Termux - `pkg install -y curl && curl -fsSL '<origin>/phone/setup.sh?t=..&b=<origin>' | sh`. The script installs `android-tools`, downloads the phone build **from this control plane** (`/phone/decurix`; `phoneBinaryPath`: `DECURIX_PHONE_BINARY`, else `decurix-android-arm64` beside the running binary - `docker/Dockerfile` builds it, the release scripts put it in every control-plane bundle) and runs `decurix --phone-setup BASE TOKEN` with the keyboard as stdin (`</dev/tty`, the pipe is the script). That claims the link's own sign-in (`/api/phones/claim`, spends the token; `devices.Store.AddToken` - a second token on the **same** device, so the phone is listed once and revoking it ends both), opens Developer options (`am start`), finds Wireless debugging's pairing and connect ports with `adb mdns services` (asking for them only when Termux cannot hear multicast), asks for the 6-digit code, pairs, moves ADB to `localhost:5555` (`adb tcpip`), writes a Termux:Boot script, and links. Those three setup paths are let past the gate (`lanaccess.SetOpenPaths(httpapi.PhoneSetupOpenPaths...)`) because Termux has no cookie; each checks the setup token itself. What Android does not let any app do - install Termux, show Developer options (Build number x7), switch Wireless debugging on, read its code - the person does, and the page says so. Termux comes from **`/phone/termux.apk`**, a redirect to the latest official arm64 build on Termux's GitHub releases (`termuxLatest`, looked up at most every 6 h, `termuxFallbackAPK` pinned when GitHub cannot be read): F-Droid finds nothing until its first catalogue download finishes (people searched an empty store), and the Play Store build cannot run a downloaded binary. A Termux already installed from F-Droid is signed differently, so the GitHub build will not install over it - that person skips step 1. **Nothing is set up until the person accepts a warning** (the red box on `/phone/link`, and a tick that enables "Yes"; `phoneSetupTokenHandler` refuses a token without `understood=1`, so it cannot be skipped by calling the API): linking is full control of the phone, by the person and by the agents, anyone with the dashboard or the pairing gets it too, and how to undo it (Revoke, Wireless debugging off, uninstall Termux). **A phone app is buttons in the VM, not only a picture** (`phoneagent/tree.go`, `phonehost.OpTree`, `phoneapp.html`'s `#ax`): the phone reads what the app's display shows from Android's own accessibility tree with `uiautomator dump --windows` (Android 11+: AOSP change 89f367d; the plain dump reads only the phone's own screen) - one dump covers every display (Android allows one reader at a time anyway), soon after input, every 1.5 s while someone is using an app, every 6 s otherwise - keeps the display scrcpy logged (`New display: WxH/dpi (id=N)`, read off the server's output; else the only non-zero display with the package), and turns it into controls: a clickable row is one button named by the text inside it, an unlabelled control is named by its resource id (`com.whatsapp:id/send` -> "send"), an `EditText` is a field named by its hint, `password=true` stays a password. The XML shape was read from `AccessibilityNodeInfoDumper` and the test dump is written from it, **not captured from a phone**. The viewer lays them over the picture as invisible, real elements (`role=button` + `aria-label`, `<input>`), so `cdp.observe` reads a phone app like a web page and **the approval gate stops a tap on its Send/Pay** (`approval.check` on the label; Enter too, the window being titled with the app's name). A click on one is a tap at its middle; typing into a field taps it, then sends text (replacing: Ctrl+A, Delete). Elements are reused while the phone reports the same role and label - rebuilt ones made an agent's click fail as "detached" - and after any input the page carries `data-decurix-busy` until a tree read after that input arrives (`Tree.Fresh`); `cdp.observe` waits for it, so the gate judges what is on the screen now. Not readable, and the viewer says "Picture only": Android 10 and older, and apps that draw their own screen without labels. **The phone's picture needs H.264 in the VM's browser**: the base image's Chromium 112 shipped `chromium-codecs-ffmpeg` (no H.264) and answered yes to every support check, failing only when a decoder was made; the desktops now run Google Chrome, which decodes H.264 itself (the codec swap script is gone; `TestAPhoneAppIsButtonsInARealDesktop` decodes a real frame in it). Its phone is a fake; step 2's `intent:` carries `S.browser_fallback_url=/phone/termux.apk`, so with Termux not yet installed Chrome opens the download instead of Google Play (whose Termux cannot run the helper); closing it would need the phone's own UI tree (uiautomator over ADB) fed to the gate - not built. The page is three steps (download, one "Copy & open Termux" button that copies the line and opens Termux with an `intent:` URL, the pairing code), and the pasted line and the script feed `yes |` to `pkg`, which on a fresh Termux can stop to ask about a package's settings file. The phone link reconnects ADB on its own after a network change or restart (`Reconnect`: `localhost:5555`, else Wireless debugging's connect port by mDNS) and keeps retrying while it is off. By hand it is still `decurix --phone "<pairing link>"`. The phone dials out and holds one WebSocket to `/api/phones/connect`, authenticated by its paired-device cookie (`devices.Store.Lookup`; on the tunnel's listener the gate checks the same cookie first). Nothing on the phone listens on a network, so it works over the free tunnel from mobile data as well as the LAN. The create dialog's app list asks every linked phone for its apps first (`refreshPhoneApps`, then `desktop.SetExtraHostApps` adds them from the hub's cache as `ModePhone` entries with `HostCmd` `android:<device>/<package>`); `packDynamicApp` writes a launcher that opens `/phone-app/view` in the VM's Chromium, signed with `winhost.Token(secret, id, "android:"+device, package)` - checked by the page and its WebSocket (`phoneAppAuthorised`), both primary-only and `hostGUIDirectOnly` like the host-app viewer. A phone app is never swapped for its web version (WhatsApp has one): picked from the phone, it runs on the phone. **On the phone**, one scrcpy server per open app (v4.1, pinned: its protocol is internal to scrcpy and changed in v4 - the video socket now opens with the codec id alone and a 12-byte *session packet* with the top bit set carries the display size; every layout here was read from v4.1's `control_msg.c`/`develop.md`/`Streamer.java`, not remembered) on `new_display=WxH/dpi`, then the app is started with the `START_APP` control message (16; `start_app` is not a server option). Also unverified: apps starting on a virtual display while the phone is locked, Doze with the screen off despite the wake lock, and banking apps (`FLAG_SECURE`) - expected to show black. iPhones cannot do any of this (no background process, no ADB).
- **Under WSL2 the local-network link is Windows' address, forwarded into WSL** (`scripts/linux/lib/lan-address.sh`, `decurix_lan_ip`, used by `build.sh` and `rebuild.sh`). In WSL's default NAT mode the address `ip route get` gives (172.x) is reachable from Windows only, so a phone handed it got nowhere. The scripts ask Windows for its own LAN address (`Get-NetIPConfiguration`, the adapter with a default gateway), and when no `netsh interface portproxy` rule already maps it on the gated port to WSL's current address, run one elevated PowerShell (`Start-Process -Verb RunAs`, the commands passed as `-EncodedCommand` UTF-16LE base64 so no quoting survives the hop) that replaces the rule and adds an inbound firewall rule `Decurix LAN access (<port>)`. One UAC prompt, then none until either address changes. Only the gated port is forwarded, never 8080. Declined or failed, the script says so and reports WSL's own address; mirrored networking (the two addresses equal) needs nothing. `DECURIX_WSL_LAN_FORWARD=0` in `.env` skips it. No `.ps1`/Mac twin: native Windows (Docker Desktop publishes on the host itself) and macOS have no WSL NAT to cross. **A quick tunnel's address is hyphenated words**: every script pattern requires `https://word(-word)+.trycloudflare.com`, and `httpapi.tunnelAddress` refuses `api.trycloudflare.com` - cloudflared names that host in the error it logs when a quick tunnel cannot be created, and a script that took it for the tunnel handed out a pairing link that answered "method not allowed".
- **"Your own link" (`internal/cftunnel`) routes only the gated listener, and only the person can set it up.** `/api/cftunnel*` are primary-only *and* `humansOnly`: the API token can create tunnels and DNS records on the person's account, and the connector token would let anything holding it run a connector that receives some of the link's visitors (and the access codes they type) - so a desktop, which can reach the primary listener, must never read either. The API token is never returned by any route; an empty token on a re-run reuses the saved one. `pointCNAME` never overwrites a DNS record it did not make (an A record, or a CNAME without its `Decurix tunnel` comment): it refuses with `ErrNameTaken`. `Disable` only stops the connector and forgets the setup; the tunnel and record stay in Cloudflare, and setting up again reuses them. The control plane runs `cloudflared` itself - the released binary needs it on PATH (the setup scripts install it) and says `missing` otherwise; the compose image does not ship it while the setup form is out of the menu, so add it to `docker/Dockerfile` when bringing that back - so the scripts' `start_lan_tunnel`/`Start-LanTunnel` skip their quick tunnel when `/api/cftunnel` says one is configured, and `GET /api/tunnel` reports the fixed link as `lan_tunnel_url` over any quick-tunnel URL a script posted. A fixed, public hostname is easier to find than a random trycloudflare one, and the gated listener's lockout is one shared bucket for all tunnel traffic (see below); the 10-character code is what holds. Put Cloudflare Access in front of the hostname for a second factor.
- **`idlepause` never guesses "idle" from task history alone.** `Checker.idleSince` takes the *latest* of the desktop's own container start time (`desktop.Desktop.StartedAt`, read off `container.Inspect`'s `State.StartedAt` in `List`/`Get`), its last task activity (`tasks.Store.LastActivity`, `MAX(updated_ns)` over that worker's tasks), and `desktop.Manager.LastViewed` (bumped by `Screenshot` and `resolveProxyTarget` — a card's thumbnail poll or an open screen tab) — never just one signal. A desktop with old task history that was just started fresh, or one with no tasks at all but someone actually looking at its screen right now, must not be stopped out from under them — idle-pause is on by default, so this is the ordinary case, not an edge case someone opted into. `idleSince` returns `ok=false` (leave it alone, never "assume idle") when `StartedAt` itself can't be parsed, which is Docker's own zero-value RFC3339 string for "never started" — a container inspect briefly failing is not evidence of anything.
- **`idlepause.Checker.Run` returning immediately when `Threshold <= 0` is load-bearing, not an optimization.** `cmd/decurix/main.go` calls `go checker.Run(ctx)` unconditionally, every startup, passing whatever `idleStopThreshold()` returns — including `0` after an explicit `DECURIX_IDLE_STOP_MINUTES=0` opt-out. The type has to be safe to start with a non-positive `Threshold` because of this, not as a defensive extra: it is the only thing that makes the opt-out actually opt out, rather than `main.go` needing its own enabled/disabled branch that could drift from `idleStopThreshold`'s own idea of "disabled".
- **`idlepause.Checker.sweep` checks up to `sweepConcurrency` (8) desktops at once, not one at a time.** A burst of desktops crossing the idle threshold in the same tick used to mean stopping them sequentially, and one `Stop` can itself take up to `DESKTOP_STOP_TIMEOUT_SECONDS` (10s default) waiting for a graceful shutdown — with many desktops idle-eligible together (the ordinary case idle-pause is *for*, at scale), a sequential sweep could take minutes and leave the rest of that tick's candidates idle-but-unstopped until the next one. Each `checkOne` only touches its own desktop's state, so nothing here needs a lock beyond the semaphore bounding how many run at once.
- **A stopped desktop no longer fails a request — `httpapi.deliverRequest` starts it and waits, up to `autoStartTimeout` (90s), before giving up.** This is what makes idle-pause's default-on behavior actually mean "works only when a task is assigned" instead of "silently breaks until a human notices and clicks Start": `desktop.Manager.SendRequest` itself stays a fast "send now, fail if not running" primitive (`ErrNotRunning`), and the wait-and-retry policy lives in `httpapi` — `sendRequestHandler` and `recordTaskHandler` are the two callers, both already about to block the human/automation on the desktop's reply anyway. The retry loop tolerates both `ErrNotRunning` (container still coming up) and `ErrAgentUnreachable` (container up, `vm_server.py` hasn't bound `:8081` yet) as "keep waiting", and returns immediately on anything else. Measured live on this repo's own dev host: a cold `ollama`-harness `basic` desktop took ~20s from stopped to accepting a request — comfortably inside the timeout, but real time a human or an API caller now waits out rather than seeing an error.
- **`desktop.Manager.SendRequest` reaches the agent by the container's address on `decurix-network`, not its name** (the same address `resolveProxyTarget` uses for the screen and recordings). The name resolves only for a control plane on that network (compose); the released binary on the host has no Docker DNS, and every chat request it sent failed as `lookup desktop_<id>: no such host`. Found by the Azure benchmark run on 2026-09-29.
- `progress.emit` is decoration and must stay that way: it never blocks, never raises into a harness, and drops lines when its bounded queue is full. A desktop reporting what it is doing must never be able to slow down or fail the task it is describing — which is also why `agentEventHandler` answers a malformed event with 200 rather than an error the agent would then have to handle.
- **Steps nobody asked for are filed under their own entry once a request follows them** (`conversation.Store.AppendUserRequest`, `thread.openedBySteps`, `UnrequestedActivity`). A step with no running turn still opens one, so a person demonstrating, or a `gui` command run by hand, stays visible. A request arriving while such a turn is open used to be treated as queued behind it, and its reply carried the demonstration's clicks as if the agent had done them. A turn opened by a request always has that request as its latest entry, so no new state is stored.
- **A turn's last step can arrive after its reply.** Steps go out on `progress`'s background queue, but the reply is POSTed directly, so TheBot's final log line ("wrote … verified on disk") reached the control plane under a millisecond *after* the answer — and `AppendStep`, seeing no running turn, opened a new one that nothing ever closed: the chat showed "Working…" forever over a finished task. Two guards: `messaging.send_query` calls `progress.flush()` (bounded) before sending, and `conversation.AppendStep` attaches a step arriving within `lateStepWindow` of an agent reply to that reply instead of reopening a turn — the second is what covers desktops built from an older image.
- `DESKTOP_ID` (what a desktop calls itself on every callback) and `Desktop.ID` (what the dashboard lists it as, derived from the container name) must produce the same string, since query notes and chat entries are keyed by it. Both now go through `sanitizeName`; they diverged for any name containing a character only `sanitizeName` rewrites (`my.box` stayed `my.box` in the env var while the desktop was listed as `my-box`), and that desktop's callbacks matched no desktop the dashboard knew. Use `desktop.SanitizeID` from outside the package.
- A dashboard card's preview is a JPEG from `/api/desktops/screenshot`, **never an embedded screen**. It used to be `<iframe src="/desktop/<id>/">` — a whole noVNC client per card, measured at 83 requests plus a WebSocket each, all against the control plane's single origin, which a browser serves over at most 6 concurrent HTTP/1.1 connections. Two desktops saturated that pool (178 requests over 7 connections, ~950ms stalls) and the VNC handshake for a screen a human had actually opened queued behind the thumbnails — 11s in one run, "Failed to connect to server" in the next. That is why "spin up two VMs and you can't work on both" was a browser-side bug with a clean server: the Go proxy served 120 concurrent requests with zero errors. `desktop.Screenshot` reads RFB directly instead (~8KB, ~80ms), and `index.html`'s `shotLoop` refreshes cards in one *sequential* sweep so the dashboard never has more than one thumbnail request in flight whatever the desktop count. Don't reintroduce a per-card iframe, and don't parallelise that sweep.
- `desktop.Screenshot` connects as a *shared* RFB client (`ClientInit` shared=1) and only ever sends a FramebufferUpdateRequest — a thumbnail must stay invisible to whoever is using the screen. It offers `Raw` as the only encoding, so the server cannot answer with a compression scheme there is no decoder for, and it reads `VNC_PW` off the container rather than the control plane's `DEFAULT_PASSWORD`, so a desktop created before that value changed still has a readable screen.
- The chat renders `content` through `textContent` only, never `innerHTML` — the text in a bubble is written by a model that can be told to emit anything. `renderContent` builds real `<pre>`/`<code>` nodes for fenced and inline spans and leaves everything else literal; keep that property when extending the formatting.
- `internal/webui/render_test.go` executes every page template. Templates are data to the Go compiler, so a typo'd action or a renamed field is invisible to `go build` and shows up as a panic or a 500 on the first request — add new pages to that test.
- `httpapi.agentProxyHandler` (`/agent/<id>/`) still proxies TheBot's own UI on port 4900, but nothing in the control plane's UI links to it any more: the chat page talks to TheBot through `decurix_agent` like every other harness, so it picks up worker memory, the safety preamble and the approval path, none of which soul's own UI goes through. Keep it as a debugging surface; don't wire it back into the UI as a second way to command a desktop.
- The base image ships `/home/headless` as `root:root` — anything that needs to write directly under it at **build time** (not runtime, where the real entrypoint/volume-mount semantics differ) needs an explicit `chown headless:headless /home/headless` first, same as the existing `RUN ... chown -R headless:headless /home/headless/.config` step. This bit the `claude` native-binary install (`~/.claude`, `~/.local`) until fixed in `docker/desktop.developer.Dockerfile`/`docker/desktop.ai.Dockerfile`.
- **Chromium in a desktop runs sandboxed**, which takes two halves that must both be present. `desktop.Manager.Create` gives every new desktop `internal/desktop/seccomp-desktop.json` — Docker's own default seccomp profile with `clone`/`setns`/`unshare` opened, nothing else — because Chromium's sandbox is built from user/PID/network namespaces that the stock profile forbids (the base image's answer was a hardcoded `--no-sandbox`, and the "unsupported command-line flag: --no-sandbox" bar on every window). And `agent/chromium-browser.init` probes `unshare --user --pid --net` at each browser launch and only adds `--no-sandbox` back when namespaces really are unavailable — a desktop created before the profile existed, or a daemon without seccomp (`desktopSecurityOpt` checks `SecurityOptions` and skips the profile there, since such a daemon rejects the container outright). **A desktop created before this change keeps showing the warning until it is recreated**: the seccomp profile is fixed at container creation. The warning is left visible in that fallback on purpose — the browser really is unsandboxed there.
- Desktops run with **core dumps off** (`desktopUlimits`, plus `ulimit -c 0` in `chromium-browser.init` for desktops created earlier). The `core.<pid>` files that filled a TheBot desktop's `~/Desktop` were not TheBot's: parsed out of the ELF notes, every one was a Chromium utility process (`--utility-sub-type=data_decoder` / `unzip`) dying with `*** stack smashing detected ***` in a restart loop, ~50 MB every fifteen seconds, landing in `~/Desktop` because that is where the XFCE menu starts the browser. `start_agent_terminal.sh` deletes existing ones, matching both the `core.<digits>` name and the ELF `ET_CORE` header.
- The chat renders a sent request **the moment Send is pressed** (`desktop.html`'s `pending` list), then drops that local copy as soon as a transcript snapshot contains the server's own (the first new user entry with the same text that was not in the transcript at send time). The server stays the only record — `sendRequestHandler` still appends only after the desktop accepts the request (measured at 5–12 ms) — and a failed send stays on screen with Retry and Edit.
- **The Cloudflare quick tunnel does not deliver the chat's event stream.** Measured through a `trycloudflare.com` tunnel: `/api/desktops/chat/stream` returns its headers and then *no body bytes at all* — not the snapshot the handler flushes on connect, not a request sent a second later — for as long as it was watched (40 s), while the same stream on localhost delivered the request in 70 ms. The chat used to fall back to polling only on a stream *error*, and a held stream never errors, so on a phone a sender's own request appeared only when the agent's reply finally pushed something through: the "my request only shows up with the response" bug. `connect()` now closes a stream that has not delivered its first frame within `FIRST_FRAME_MS` (4 s) and polls instead; over the tunnel a sent request shows in ~70 ms (locally rendered), the server's copy in ~2 s, and live steps from ~2 s. Anything else that relies on SSE through the tunnel needs the same fallback.
- `NEEDS_TOOLS` is taught **only to the chat skill** (`prompt.ChatRule`, appended to the frame by `GeneralSkill`), never in the shared `Persona`: with it in the persona, the operator answered "ping - just reply pong" with `HELP: NEEDS_TOOLS`, which a human received as an entire query. The operator also treats that marker as a malformed reply.
- The XFCE desktop wallpaper is set by baking `agent/decurix-desktop-wallpaper.xml` (pointing at `agent/decurix-wallpaper.svg`, copied to `/opt/decurix-wallpaper.svg`) into `/home/headless/.config/xfce4/xfconf/xfce-perchannel-xml/xfce4-desktop.xml` at image build time, in all three desktop Dockerfiles — otherwise XFCE generates its own default (the base image's stock `xfce-shapes.svg`) the first time it starts with no config present. Since `/home/headless` is the container's persistent named volume, this file only seeds *new* desktops (an empty volume on first start); it has no effect on a desktop created before an image rebuild.
- **The taskbar (`agent/decurix-panel.xml`, seeded into the `xfce4-panel` xfconf channel the same way as the wallpaper above) replaces the base image's own top-menu-bar-plus-autohide-dock layout with a single bottom bar, so a Windows user recognizes it immediately**: a Start button (`xfce4-whiskermenu-plugin`, search-as-you-type, installed alongside the theme packages) with pinned Files/Browser/Terminal launchers at the left, running windows shown icon-only and kept roughly centered by a pair of expanding separator plugins on either side of that group (imperfectly — the fixed-width tray+clock on the right isn't mirrored on the left, so the group sits a little left of true center; this is the same trade-off Windows 11 itself makes when tray content is present), and the system tray plus a stacked time/date clock (`digital-layout=0`, confirmed live against this xfce4-panel build — other values render date-only or time-only, not both) on the right. `decurix-xfwm4.xml`'s `button_layout` is set to `|HMC` to match: minimize/maximize/close grouped on the right, no window-menu button on the left. Same persistence rule as the wallpaper: only seeds *new* desktops, and an existing one keeps its old panel until recreated.
- **A launcher plugin's `.desktop` file is looked up by the panel *plugin's own ID*, never by the desktop-file's name.** `xfce4-panel` reads a pinned launcher's entry from `~/.config/xfce4/panel/launcher-<plugin-id>/<anything>.desktop` — found live by seeding a `decurix-panel.xml` whose launcher plugins referenced desktop-id filenames with no matching `launcher-<id>/` directory on disk, which silently rendered a generic fallback icon instead of erroring. `decurix-panel.xml`'s launcher plugins are hardcoded to IDs 3/4/5, so `agent/decurix-launcher-{files,browser,terminal}.desktop` must land at `launcher-3/`, `launcher-4/`, `launcher-5/` respectively (each Dockerfile's `mkdir -p`/`COPY` block) — renumbering one side without the other reproduces the same silent fallback.
- **Editing a live desktop's `xfce4-panel.xml` (or any xfconf-seeded file) by hand while `xfconfd` is already running does nothing**, and *looks* like it worked because the file on disk really does change: `xfconfd` only reads a channel's perchannel-xml file at the moment that channel is first touched by *this daemon process*, then serves everything from memory and writes back to the same file on every property change — so a `cp` over that file mid-session is invisible until `xfconfd` itself restarts. Verified live: killing only `xfce4-panel` and relaunching it kept the old panel, because the original `xfconfd` (running since container start) was still alive and still serving the old config from memory; killing `xfconfd` too (and letting the panel respawn it) picked up the new file. Also, `xfconf-query`/any manual panel restart from a `docker exec` shell must export the *session's own* `DBUS_SESSION_BUS_ADDRESS` (read off a running session process's `/proc/<pid>/environ`, e.g. `xfce4-session`) — without it, `dbus-launch` silently opens a throwaway private bus with its own empty `xfconfd`, and both reads and writes against it are talking to nothing the real session ever sees.
- **The base image sets `NO_AT_BRIDGE=1`**, which silently turns off every GTK app's AT-SPI bridge: the accessibility tree was empty until the desktop Dockerfiles set `ENV NO_AT_BRIDGE=0` (and `computer.session.ACCESSIBLE_APP_ENV` sets it for anything the layer launches). Thunar's windows belong to the XFCE session's Thunar *daemon*, so on a desktop created before that ENV change they stay invisible until the daemon is restarted — which is why `bench.py` runs `thunar --quit` before a file-manager task. Like the seccomp profile, the ENV is fixed at container creation: an existing desktop needs recreating.
- **LibreOffice misreports where it draws.** Under XFCE its AT-SPI extents for everything VCL paints (the document, table cells, toolbars, sheet tabs) are often reported too high, by an amount that depends on its state, not a constant: 27 px on one desktop; on another a freshly opened Calc was 25 px off (the menu bar's height), right again once the pointer crossed the window, and off again after a no-op window move. The frame's own extents cannot tell (it reported (0,0) with the window at (0,36)). Only the native GTK menu bar is always right, and VCL's first toolbar is drawn directly below it, so `atspi.libreoffice_offset` measures the offset every observation as how far the topmost toolbar is reported above the menu bar's bottom edge, and `_correct_libreoffice_boxes` shifts everything but the menu bar by it (none when no toolbar is shown). This is what `calc-rename-sheet` (double-click on the sheet tab) failed on. So the layer never clicks LibreOffice content by coordinates: text goes into a Writer cell or paragraph through `Atspi.Text.set_caret_offset` (`atspi.place_caret`), and a Calc cell is reached by coordinate through the Name Box shortcut (Ctrl+Shift+F5, the reference, Enter — `core._goto_sheet_cell`), because LibreOffice 24.2 does not expose the Name Box over AT-SPI at all. A Calc sheet MANAGES_DESCENDANTS with 2^31 children and is never walked; its visible used range is read cell by cell through the Table interface (`atspi._sheet_cells`). Writer's document sets the same flag with a handful of children and *is* walked — the rule is the child count, not the flag.
- **A ref means "the element at this path"**, not "the Nth element of this observation" (`elements.assign_refs`). Paths are rooted at the window title with a leading `*` stripped (an editor's unsaved-changes marker) for AT-SPI, and at the **site** (host:port), not the page title, for Chromium — so a navigation link keeps its ref on every page of a site. Renumbering per observation made "e12" point at something else after one row was inserted.
- A GTK list/tree cell's AT-SPI action is `activate` — *open the file*, not select it — so `core._perform` clicks cells, list items and icons by position instead of invoking their action. Every other widget prefers its own action over a coordinate click.
- **The browser's DevTools port (9222, `agent/chromium-browser.init`) is how pages are read and worked**, bound to 127.0.0.1 inside a container with no published ports. It is also a way for any process in that desktop to drive the logged-in browser — the same trust the agent's unrestricted shell already has, not a new one. A Chromium started *without* the port (before this change, or by hand) cannot be read; `observe` says so in a note rather than returning an empty page. Chrome accepts a DevTools websocket with no Origin header (cdp.py sends none), and since 136 refuses remote debugging on its *default* profile - which is why the launcher always passes `--user-data-dir` (see below).

The gate guards against a model's mistakes, not a hostile model: an engine with a shell could write the grant file itself, exactly as it could run xdotool directly.

- **A dispatched request file is renamed to `*.txt.done`** (`watchers._mark_handled`). `state.processed_commands` is memory and `COMMAND_DIR` is the persistent volume, so every desktop restart used to replay every request the desktop had ever received — found by the GUI benchmark, which restarts a desktop between tasks: each task queued behind replays of all earlier ones, and a spreadsheet task was answered with questions about signing in to an admin panel. A request deferred behind a running task or a backend that is not up yet keeps its `.txt` name until it is actually dispatched.

And an approval task only passes when the gate itself fired (a step with `outcome: needs_approval`), not when the agent merely raised a query for some other reason — which leaves the invoice unpaid too.
- **A demonstration tells the person from the agent by input device, not by timing.** XInput2 raw events name their source device: a person using noVNC arrives as Xvnc's `TigerVNC pointer/keyboard`, every xdotool action as `Virtual core XTEST pointer/keyboard` (measured: devices 6/7 vs 4/5), and `demonstration.py` drops XTEST. The client must announce XInput **2.2** (`XIQueryVersion`) — only from 2.1 are raw events delivered while another client holds a grab, i.e. inside an open menu or a drag. python-xlib 0.33 parses XInput device events but not raw ones: the recorder registers a raw-event struct with `Display.ge_add_event_data` (a method of the high-level `Display`, not `display.display`) and matches `ge.GenericEventCode`, since `X.GenericEvent` does not exist there.
- **A press the recorder read late is not named from a screen that changed after it** (`demonstration.Recorder._lag`, `LATE_SECONDS`, `LATE_NOTE`; `processing.CARRIED` carries `happened`/`late`; `replay.compile_program` takes no picture for a `late` event). Found live on a 1-vCPU worker (2026-10-07): a click on the web app's Save, read ~20 s late, was named from a look taken after the save - when the same spot had become "Submit" - and a skill taught from it would have submitted the invoice. The X server's own timestamp on each raw event gives how far behind the reader is (the smallest clock gap seen counts as on time); a press read more than 0.5 s late, whose last look at the screen was taken after it, is recorded with no target and that note, and `/learn` asks about it like any position-only click. Still open: the pointer position itself is read when the event is handled (raw events carry none), so under the same lag a press can land in the recording a little off - a row's "Accepted Qty" was recorded as "Rate" and a click as a drag in that run; the lesson's Q&A is where a person corrects such steps.
- **A pause that ends on the screen it began on records no private step** (`demonstration.UNCHANGED_SCREEN`, `Recorder._resumed`). The toolbar pauses while a Reason is written, and every resume used to write a `manual` event - so a taught application task ended with "29. a private step done by hand", which `/learn` kept even after the person said it was only the note. A real private step (a sign-in) changes the screen and is still recorded.
- **Xvnc changes the keymap while someone types.** It maps the keysyms a VNC client sends onto keycodes on the fly and types a capital by toggling Caps Lock around it, announcing both with `MappingNotify`. The recorder refreshes its keymap on that event, names keys from its own `KEY_NAMES` table (python-xlib's `keysym_to_string` returns None for Shift_L, Caps_Lock and every other named key), and reads the Lock state back from the server whenever a key goes down with nothing held. Measured before each fix: "Human Co" recorded as four runs split by `keycode_66`, then as "hUMAN cO" when an earlier session had left Caps Lock on.
- **A typing run keeps its field until something moves focus** (`demonstration._focus_after`), and text typed into a field that cannot be told is withheld whenever a secret field is on screen. Both close a leak found live: an unrecognised key split a password's typing in two, the second half had no element, and it was stored as plain text.
- **A demonstration's "what changed" is discarded when the person's next input landed before the screen was read** (`change_missing`). Observing takes a second or two and people do not wait: a sign-in click's "Welcome back" was recorded as what the typing before it did, and a replay would have waited for it after the wrong step.
- A replay is **refused (409) while the desktop has a task running, queued or waiting** (`tasks.Store.Busy`), rather than routed: sent to a paused agent the watcher takes it as the reply, and queued behind a running task it is absorbed as the reply if that task pauses. A replay's parameters travel only in the request body to the desktop and live in `replay_task`'s memory until it runs — the chat, the task record and the command file see `/replay <id> [from=N]`, never a value.

- **Everything the agent keeps for itself lives under `~/.decurix`**: `config`'s command/querytext/final/memory dirs, the computer layer's `computer/` and `recordings/` (an `audit/` from before recordings is imported into them once at startup by `recording.import_legacy_audit`, with its typed secrets withheld), and TheBot's `WORKSPACE_ROOT` (`ai/`). `~/work` is the only directory it adds to the top of the home, because that is where tasks run and what a human browses. `start_agent_terminal.sh` moves an older volume's `~/command`, `~/helptext`, `~/final`, `~/memory`, `~/audit` (and `~/ai`, on a TheBot desktop only) into place before the agent or soul starts, never overwriting an entry already there - a second step then renames a `~/.decurix/helptext` it finds (freshly moved, or already there) to `~/.decurix/querytext`. A container keeps the image it was created from, so a desktop created before the move still runs an agent that reads `~/memory` — which is why `desktop.Manager.PersistMemoryFile` writes there while it is that desktop's only memory directory.
- **A ticket is opened the same way any request is, but Record/Stop/Continue/Reason/End are not command files.** `record_task.py` keeps the open ticket as its own module-private state (`_ticket`, the way `replay_task.py` keeps `_held`) rather than in `state.py`, because nothing outside the module reads it directly — the GUI toolbar's begin/pause/resume/end calls go straight into `record_task.begin()` etc. over HTTP, bypassing the command directory and the watcher entirely, since they only ever act on whatever ticket is already open. `tasks.Store.Busy` is still what keeps a second ticket (or a replay) from being opened while one is: `perform()` occupies the task slot for the ticket's entire lifetime, exactly like an agent's task would.
- **`httpapi.callAgent`'s payload parameter is `any`, and a nil `map[string]string` boxed into it is not the untyped `nil` the function tests against** — Go's classic typed-nil-in-an-interface trap. `ticketActionHandler` hit this for `begin`/`resume`/`end` (no fields to send): a `var payload map[string]string` left nil and passed straight through would satisfy `payload != nil` anyway, and `json.Marshal` would send the literal `null` as the body — which the agent's `_body()` rejects (`json.loads("null")` isn't a dict) as 400 rather than sending no body. Pass the bare `nil` literal itself for a call with no fields, not a nil-valued typed variable.
- **The ticket toolbar's own poll must not rebuild the panel when nothing changed.** It reads GET `/api/desktops/ticket` every 2.5s the way `desktop.html`'s chat polls the transcript, but unlike the chat's whole-snapshot renders, rebuilding this panel on every tick would wipe out a task name being typed into the `+` input mid-keystroke (new `<input>`, empty value) even though the ticket state hadn't actually changed. `refresh()` compares the fetched ticket against the last one (`JSON.stringify`) and skips the render entirely when they're equal; a create-ticket **failure** (busy desktop, dropped request) also preserves what was typed, via a `draftTask` variable read back into whatever `<input>` gets rebuilt next, so a rejected submission doesn't make someone retype it.
- **End does not wait for `record_task.perform()`'s own thread to clear the ticket, so its HTTP response can still show the ticket "open" for an instant.** `end()` sets `demonstration.stop()` (if capturing had started) and signals `_ended`, then returns immediately — `perform()`'s background thread wakes and clears `_ticket` a moment later, off this request's critical path. Trusting that response's `ticket` field for the toolbar's post-End render would flash the ticket panel once more before the next poll corrected it; the toolbar's `act("end", ...)` special-cases the answer instead — captures `session_id` for the download link if the response carried one, sets its own `ticket = null` unconditionally, and renders the "recording saved" view right away.
- **The dashboard card has no Record button of its own** — `index.html`'s `.dcard-actions` only opens the chat and the screen (plus restart/stop/delete); *making* a recording lives solely in the ticket toolbar inside the screen itself. Don't re-add a card-level Record: the toolbar is the one thing that already knows whether a ticket is open, recording, or paused, and a second, unsynced entry point would just be another place for that state to go stale. What the card *does* have is a **Recordings dropdown** (running desktops only, `data-rec-list`): the finished demonstrations, oldest first, each with Replay / Learn / Download, read from `GET /api/desktops/recordings` when the list is opened and calling the same `/api/desktops/recordings/{replay,learn,export}` the recordings page does. Replay there sends no parameters, so a recording that typed a secret halts and asks; the full page (`/recordings/<id>`) is where values are given.
- **"Your task is done" is announced on every page** (`theme.html`'s `announce`). A finished task leaves no query note, so `queryTextHandler` also records it in an in-memory feed (`httpapi/finished.go`, last 50, `GET /api/tasks/finished?after=<seq>`; a first call without `after` returns only the latest seq, so a page never replays old news). Notes and finished tasks are told the same way: a toast when the page is in front (not on that desktop's own chat, which shows the reply), a system notification when the bell is on, otherwise a dot in the tab's title until it is looked at. Notes are titled by kind ("finished", "could not finish", "needs your approval", "needs you").

Only notes of kind `query`/`approval` are resolved that way: a finished task's report is not answered by a reply and stays open until someone resolves it. A note from before `kind` existed has none, so it is never auto-resolved. The Queries page polls (4 s) to drop cards answered elsewhere.
- **The "Recording saved" view of the ticket toolbar offers Replay, Learn and Download**, the same calls the recordings page makes (`/api/desktops/recordings/{replay,learn,export}`). Replay and Learn are refused (409) while a task is open, and End answers before the ticket's own task has finished closing, so `startFromRecording` retries a 409 a few times before showing the reason. Neither is given values: a recording that typed a secret halts and asks.
- **A saved skill is written into the desktop's learned memory.** `skill_task._learn_reply` calls `messaging.remember` on a `save` decision, which POSTs `/api/desktops/memory` (category `skill`): the entry shows in the card's learned-memory list and is written back into `~/.decurix/memory`, so every harness reads that the skill exists and how to run it. A draft, a discard or an unclear answer records nothing. Best-effort - a failed post never fails the lesson. Corrections a later run learns are not recorded there, only the skill file keeps them.
- **A request that is a recorded task done again is done the way the person did it: mimic first, intelligence only for the difference** (`computer/mimic.py`, `skill_task.mimics`/`perform_mimic`, dispatched by `watchers.command_watcher` before the harness, no backend needed). The desktop's model is small, so what a person recorded is the plan. The request is compared word by word (`difflib`) with the task every finished demonstration was recorded for (its `task`, else its title) and every ready skill's `goal`. Every ticket word that is not filler, not something the person typed or clicked, and not a value (a number, a quoted phrase, a capitalised name) is the task's shape and must be there unchanged - so `bing X` after a ticket for `google X` is another task, and nothing reads meaning into "google". What differs is put where the recording has it literally: into what was typed, a clicked control's name (its recorded path dropped), a page opened. Window titles and expected results take a changed typed value *whole* (`step_spans`/`value_spans`): the lone word "koustubh" must not rename the window "Koustubh - Chrome" (a browser profile) the steps were recorded in. Only a value the recording typed in another form ("5 March" typed as `05/03/2026`) asks the model one fixed question (`adapt_values`: recorded task, what was typed, new task -> what to type), and the person when there is no model; a model that would type everything unchanged means it is another task, as does a difference with nothing typed to adapt, and a second job in the request (`SECOND_JOB`: "... and email it") - those go to the engine. A recording nobody taught is built into a skill for that run only (`learning.build`, `one_off`: never saved, no experience recorded); a taught skill is preferred over its own recording and its saved steps are never rewritten - substitutions go into the run's expanded copy. The same request as recorded replays as recorded.
- **A skill has a name a person can give it, and its goal survives a rename.** `/learn <ids> name="Search Google"` (quotes allowed; `skill_task.learn_request` and `httpapi.learnContent` build the same string) makes the skill's `title` that name and its file name a free slug of it (`skills.unique_name`: naming a skill after one that exists never overwrites it). The goal (what `mimic.plan` matches against) is the recording's `task`: `recording.update` keeps the first title as `task` the first time a recording is renamed, so a friendly name does not lose the words typed for the ticket. The name box is on the card's Recordings list (the title, edited in place), the ticket toolbar's "Recording saved" view, and the recordings page's Teach form.
- **A replay puts the screen back to the size its point clicks were recorded at** (`replay._fit_screen` -> `screen.set_size`, xrandr `--newmode/--addmode/--mode`, as noVNC's remote resize does). A screen's size follows whoever viewed it last: a demo recorded at 1527x727 met 1280x720 after a restart and halted at its first click, although the same size lays the window out pixel for pixel. Only when every point step shares one recorded size. `screen.grab`/`size` read the live geometry every time: the old per-process cache kept capturing the size the agent started at after noVNC resized the screen.
- **A point click whose picture fails because this run typed something else is matched by kind** (`visual.make_kin`/`find_kin`, `replay._find`/`_kin`/`_first_change`). Recorded as a search for `koustubh is great`, the first result's title "Kaustubha" was clicked at 352,544; searched for `who is rama`, the first result is "Rama", 58 px higher, and the look correctly finds nothing. A *kin* describes what kind of thing was clicked: a line of text in a coloured ink (a link), its height, the column it starts at, and which of those it was counting from the top; the replay clicks the same-numbered one now (measured on the real frames: (353, 487), on "Rama"). Only when **all** hold: the look is `missing` (never `ambiguous`), an earlier step of this run typed something other than what was recorded (so the picture was expected to change), the step is not `consequential`, and two consecutive looks at the screen agree on the spot (a page still loading is not clicked). Ink is judged by hue, chroma and brightness, not RGB distance: anti-aliasing keeps a thin letter's hue, and dark teal text on a pale highlight (Google's AI overview) is close to a link's blue in RGB. Black or grey text is never described ("the third black line" means nothing). The kin is read from the step's recording frame at run time (`step["session"]` + `event`), so skills taught before this get it too, while their recording is on disk. The run reports it ("clicking the 1st line of text in its colour and size in that column"). Not handled: an ad or another result type pushed in above the first result is what gets clicked, since it is the first of that kind.
- **A "kin" must look like a line of text** (`visual._looks_like_text`: at least `KIN_MIN_ASPECT` times as wide as tall, and on a plain ground above and below that is not the ink). Found live on a skill that searched in a host Chrome: for another search, a 5-px sliver of a portrait's blue backdrop at the results' column was taken for "the first link" and clicked. Now the run finds no kin there and goes on to the engine or the person, never the picture.
- **The first `/learn` question also invites an explanation in the person's own words** (`learning._answer_goal`). The whole reply is kept as `skill["explanation"]`; each sentence naming a step ("step 6 clicks the first search result") goes on that step as `intent` (shown in the overview as "you said: ..."), and the rest is `done_when`. `Ladder(explanation=)` puts both into the engine's grounding prompt, and a stuck step's question repeats the step's `intent`. It is one question, not a new one, so every scripted lesson in the tests is unchanged.
- **A desktop icon is opened by its launcher, not by its picture** (`computer/launchers.py`, `replay._open_desktop_icon`). Found live on a skill that searched Google in a copied host Chrome: the recorded picture of the icon was mostly xfdesktop's hover tooltip, and at replay time the icon was drawn selected, so step 2 never matched - and `skip` then stopped step 3 because the window it opened was not there. A click or double click recorded on the bare desktop (no window in front, no element) whose expected result is a window W is done by the one `.desktop` launcher (in `~/Desktop` or `~/.local/share/applications`) whose Name is W with its "(Host)"-style tag dropped - never a guess between two - or by raising W when it is open already. A step recorded *in* W while W is not in front raises it or opens it the same way, once, before halting (`_find`). A drag on the bare desktop of at most `DESKTOP_NUDGE_PIXELS` (40) only nudged an icon (XFCE keeps them on a grid): the replay does nothing for it and `/learn` leaves it out (`learning._tidy`, after the burst folding, which still takes a nudge inside a burst of presses). **An app found open, or a kept host app its launcher reconnects to, is in whatever state it was left in**, not the fresh one the recording's next steps were made in: when a later step in that window cannot find its target before any step there has worked, the run's result carries `reopen` and the question offers `restart` (`skill_task.RESTART_RE`): close W with `_NET_CLOSE_WINDOW` (`screen.close_window`, what its close button does - never a kill), wait for it to go, and run again from the step that opens it. Only on a person's word: whatever is open in W goes with it. **A point click after the run typed something else, whose picture and "kin" both miss, asks the person to click it and reply `done`** (`after_change` on the result): measured on a real Google page whose first result was below a large AI overview, scrolling and taking the first thing that looked alike matched a link inside the overview first, so the replay does not scroll-and-guess.
- **A browser window is opened by the browser's own icon, whatever it is called** (`launchers._opens_the_browser`): since the desktops run Chrome the icon is "Google Chrome" while a page's window keeps its canonical "... - Chromium" title, so no name matched and a taught search's first step (double-clicking that icon) fell back to its picture and halted. A launcher whose command is the browser (and not a web app's `--app` window) now opens a browser-titled window; a host app's launcher named for the window still wins. `bench/screen/teach_e2e.py` checks both halves: with the icon covered by the open browser the run uses it, and with the icon gone and the browser closed it stops and asks (20/20).
- **Workflows are similar, not the same: a skill run leaves out steps that dealt with something this run never meets** (`computer/detour.py`, `escalation.Ladder.detour`, `replay._recover`). Found live: a person recorded a Google search, Google showed a CAPTCHA, and they clicked "I'm not a robot", three picture tiles and Verify before the result; replayed with another search Google showed none, and the run halted at "I'm not a robot". When a step's target is not found (a `_Halt` with `missing`), the live screen is compared with the recording's screens *before* that step and before each of the next `MAX_AHEAD` (8) in the same phase - only while the steps between are `skippable` (click/key/scroll/drag, never consequential, typed, by hand, `open` or `manual`). If a later step's screen is clearly closer than this step's own, the steps between are left out and the run goes on there. The comparison is **by where content is, not by pixels**: 16 px cells with edges, overlap with one cell of slack, minus cells busy in every frame (a pixel diff ranked the mostly-white CAPTCHA page *closer* to a white results page, 0.85 vs 0.77; by content 0.43 vs 0.69), and, when OCR is available, the words on each screen minus those typed into the task and those every screen shares; the text may only lower the margin. Measured on the real frames (fixture `agent/tests/fixtures/detour/captcha-search.json`, cells and OCR lines only - the frames themselves are 3 MB and the CAPTCHA page printed the user's IP address, stripped): step 5 -> step 10, margin 0.22 with text, 0.34 by layout alone; the CAPTCHA on screen, a half-solved grid and a results page at the results step all leave everything alone. Not learned into the skill: each run decides afresh.
- **A point click whose picture and kin both miss can be placed by the engine reading the screen** (`computer/ocr.py`, `Ladder.ground_point`). The recording's frame is OCR'd for the line under the click (and the lines around it); the live screen for its lines; the engine is asked which line plays the same part now (`POINT_SYSTEM`, "the same kind of thing in the same role, not the same words") or 0, and a choice under `GROUND_CONFIDENCE` places nothing. Never for a strict step (approval-gated, optional). **OCR needs `tesseract-ocr`**, now in all three desktop images; without it (a desktop from an older image) both OCR rungs are skipped and detours fall back to layout alone. - **A `NEEDS_APPROVAL:` the model wrote in its own answer is a pause in Decurix only** (`thebot_harness._written_pause`). soul finished that job as `answered` and holds no checkpoint, so the reply sent with `reply: true` resumed nothing and was run as a request of its own: `google "sanmayee is great"` -> "NEEDS_APPROVAL: I want to Google..." -> "proceed" -> "I can't assist with that request". - **The screen is the control plane's page, not noVNC's** (`httpapi/screen.go`, `web/templates/screen.html`). `/desktop/<id>/` renders the viewer itself (for a stopped desktop too, `desktop.Manager.ScreenAccess` reads name + `VNC_PW` off the container); only the WebSocket (`/desktop/<id>/websockify`) and noVNC's own `vnc.html` are still proxied. A desktop whose X session ends restarts its container on its own (exit 0, `unless-stopped`); the task it was on stayed "running" for good ("Working..." over nothing). The started-and-unfinished task is kept in `~/.decurix/active-task.json` (not `/tmp`, which a restart empties) and reported as an `error` with `interrupted: true`; `queryTextHandler` records it only while `tasks.Store.IsOpen` says the task is still open, so a restart through the API (which already closed it) gets no second note. A request saved while the agent is waiting on a question gets `-reply` in its file stem (`messaging.REPLY_MARK`); one that finds no question waiting (the agent restarted in between) is answered with a note instead of being run as a new request - "keep" used to go to TheBot as a chat message. `ask_for_query` sets `waiting_for_query` before posting the question, not after, so a reply that beats `send_query` back is still a reply.
- **The command watcher cannot die and cannot hang silently.** One pass is `watchers._pass()`; the loop catches `BaseException` (logging can itself fail). The approval store's `flock` waits at most `approval.LOCK_TIMEOUT_SECONDS` (10) and raises `TimeoutError`, which every caller already handles as an `OSError`. `watchers.watchdog` logs every thread's stack and a chat step when a pass has not started in `STALL_SECONDS` (45): a reply once sat unhandled for four minutes with nothing in the log, and the process was gone (container restart) before it could be inspected.
- **End records everything done before it** (`demonstration.py`). The recorder grabbed a full-screen frame on its input thread for every keystroke; on 1 vCPU typing a phrase put it 10-20 s behind, and End (SIGTERM) stopped reading at once - " breeding season" and the Enter after it were lost. Now only the first key of a burst (`KEY_BURST_SECONDS`) captures a frame, SIGTERM sets `stop_requested` and the reader drains what is already on its X connection (bounded by `DRAIN_SECONDS`, even under continuous input) before `stopping`, and `_process` empties the queue before its last flush.
- **`/learn` tidies a demonstration before asking about it** (`learning._tidy`; the recording itself is untouched, `/replay` still does what was recorded). A burst of presses on one spot within `REPEAT_SECONDS` that contains a double-click - clicks, a press that barely moved (a ≤`REPEAT_PIXELS` drag, even one that nudged a desktop icon), more clicks while a slow app starts - becomes that double-click, expecting what the last press produced: replayed as recorded it opened the app three times. Every click recorded only as a position is then **one grouped question** (`coordinates:s1+s2+...`): `keep`, `manual`, or exceptions like `manual 1, skip 5` / `skip 2 and 4` / `manual 1-2` (`_coordinate_choices`; a number outside the question or a conflict is asked again, twice unclear is `manual` for all). A step a person chose to do by hand reads "you do this by hand: ..." (`step["by_hand"]`), not "a private step". Verified end to end: record a search through the viewer clicking the icon impatiently, `/learn` (every answer back in ~1 s), run the skill with a new value (Chromium shows the new search), and with the browser already covering the icon the run stops rather than clicking blind and `skip` finishes it.

- **A card's pill is a traffic light**: green running and free, yellow (`--busy`) working / recording / needs you / provisioning, red crashed. Crashed is `desktop.Desktop.Crash` (`crashReason`): state `dead`/`restarting`, or exited with a code other than 0/143, or 137 with `OOMKilled` - 0, 143 and a plain 137 are how `Stop` (SIGTERM, then SIGKILL after its timeout) ends one. `Status` stays `stopped` so nothing reading it changes meaning. `/api/desktops/activity` carries `status`/`crash` from the cached `List`, so a card turns red or green without a reload.
- **A desktop's card says what it is doing** (`GET /api/desktops/activity?ids=a,b`, `httpapi/activity.go`; `index.html`'s `pollActivity`, 2.5 s, one request for every card): the request its running turn was opened for and the latest step, read off the chat snapshot so the card can never disagree with the chat; a `/record` turn is a ticket ("Recording: <task>"). The pill reads needs you > recording > working > running, and a finished task's report left open in the rail (`kind` done/error) no longer hides that the desktop is busy again. A ticket also narrates itself in the chat: Record, Stop, Continue and End each emit a step (`record_task`), where it used to say "Ticket open" and then nothing until the first click.

- **A result check follows a changing value into window titles too** (`learning.CHECK_TEXT`, `replay.unmet`, `skills.expand`). A browser search comes back as a window titled "<what was typed> - Google Search - Chromium"; `_follow_param` only rewrote element names, so a taught search halted at its last step, after the search had worked, waiting for the demonstration's title. `window`/`active_window` checks now hold `{typed_text}` like element checks do. A skill taught before this keeps its literal title check until it is taught again.

Measured on a 1-vCPU desktop: a click took 10.3 s to reach the chat, the typing after it waited behind that (~15 s), and Stop took 15-20 s to finish; now ~3 s per click and Stop is immediate. What remains is the settle wait (up to `core.SETTLE_SECONDS`) while a page loads: typing followed by Enter on Google reached the chat ~12 s after Enter end to end.

What a demonstration typed comes back in what the screen then says ("Saved Initech"); baked in as recorded, every run with another value halted asking whether the result was fine. When a person says a typed value *changes*, any element check whose name contains the demonstration's example becomes `Saved {customer_name}` and `replay.unmet` fills it from the run's values. A placeholder with no value stays literal so it fails rather than passes on something never seen, and `skills.expand` renames it per item for a list parameter, the way it already renames a value check. A value said to stay the same leaves the check alone.
- **A demonstration's typing replaces the field on replay only if the field was empty, and the recorder must not misread its own typing as content.** `demonstration._entry` sets `append` from the element's value in the last settled look at the screen - which is normally taken *after* the typing, so a field that had been empty read as holding exactly what was typed and was recorded `append: true`; every later run then added to whatever the field held (`InitechUmbrella Corp`). A value equal to the typed text now counts as empty-before; a value holding more than the typed text is still an append. Found live, not in the unit tests: the fake recorder never took its look after the typing.
- **A finished recording is a `quiet` callback, not a Query rail note.** `record_task._report` calls `write_final_reply(..., quiet=True)` on success: no file in `querytext/` (its watcher would send it as a note) and `quiet: true` on `POST /api/querytext`, which `queryTextHandler` honours by skipping `QueryNotes.Add` while still closing the task and answering in the chat. Failures (`did not finish`, `nothing in it`, `nothing was recorded`) are still ordinary notes — something went wrong and a person should see it.
- **The ticket toolbar's tab is a drag handle, not just a click target.** Pointer-down on `#decurix-ticket-tab` starts tracking; past `DRAG_THRESHOLD` (6px) it "pins" the toolbar (`decurix-pinned` class, cancelling the default centered `transform`) to an explicit `left`/`top` clamped to the viewport, so it can be moved off whatever it's covering on the desktop underneath. A drag's terminal `pointerup` still fires a `click` on the tab — the same handler that opens/closes the panel — so the click listener checks the `dragged` flag first and swallows that one click rather than also toggling the panel.
- **Every rewrite in the proxy's `ModifyResponse` chain writes UTF-8, but the proxied container's own `Content-Type` never says so.** `rewriteDecurixBranding` (always first) now sets `Content-Type: text/html; charset=utf-8` explicitly. It has to be there and not later in the chain: `injectTicketToolbar` splices its own copy in right before `</body>`, far past a browser's ~1024-byte `<meta charset>` sniffing window, so by the time that text exists in the document the browser has already committed to whatever encoding it guessed for the whole thing. Without the header, a guess other than UTF-8 turns every non-ASCII byte added anywhere in the chain to mojibake — this is what an em dash in the toolbar's own copy needs the header for, not anything wrong with how that string is written in Go.
- **A note written while paused stays paused; whether to continue afterward is the toolbar's call, not `demonstration.note`'s.** `note()` no longer refuses a call while paused (that used to be its only guard on `_running()`'s state) — it writes the note into whatever pause it finds, active or not, and always (re-)pauses after with its own summary as the reason. The toolbar's Reason button pauses *before* opening its text box (not after submitting, like Stop), and only follows a successful submit with an explicit `resume` when its own click is what caused that pause (`reasonAutoPaused`, reset on every path that leaves the box) — never when Reason was opened on top of a pause already in effect, since that pause may be covering exactly what the note is warning about, and auto-continuing would hand it straight back to the recording.
- **Triggers are one page (`/triggers`, `web/templates/triggers.html`), not one page per kind.** A trigger is anything that sends a request without a person pressing Send: a repeating schedule, a one-time run, an email rule - its "New trigger" form is a segmented picker whose JS `kinds` table has one entry per kind (label + `create`), so a new kind is one radio and one entry. It lists schedules, email triggers, mailboxes and the jobs email started; the keep-awake panel sits on top because every kind needs the machine awake. The requests page's compose form offers the same three (repeat / once / "Run when an email arrives"); the list of existing triggers is on the Triggers page only. What both pages share - the email-rule fields and `window.Triggers` (mailbox loading, rule create/test, the list rows) - is `web/templates/triggerparts.html`, parsed only for those two pages (`webui.templatePaths(page, triggerParts)`).
- **A schedule (`internal/schedule`) is a fourth door onto `submitRequest`, set up from the requests page or the Triggers page, never from the chat.** Creating one never sends the request immediately — its first run is the next time the cron expression matches (or, for a one-time run, the future time it was given), same as cron itself never fires the instant a job is added. `Runner.fire` appends `\n\nTIME:{<RFC3339 UTC>}` to the request text on every trigger and always advances the schedule afterward, whether or not the submit itself succeeded — a desktop that is unreachable this minute must not turn every following tick into a retry of that same stale run, and a control-plane outage across several missed occurrences produces one catch-up run on the next tick, not a replayed backlog. Cron fields are matched in UTC regardless of the host's own timezone, and `cron.go` is a small hand-written parser (no external dependency) rather than a library, matching this repo's `modernc.org/sqlite`-over-cgo preference for a static, dependency-light binary. A schedule whose expression can no longer match anything (day 31 in a month field restricted to February, say) disables itself on the next `MarkRun` instead of being checked forever.
- **A one-time schedule (`Schedule.RunOnce`, created by `Store.CreateOnce` with a future run time instead of a cron expression, `cron_expr` left `""`) fires exactly once and then disables itself** — `MarkRun` special-cases `RunOnce` to skip the cron-based "next occurrence" computation entirely (there is no cron expression to recompute from) rather than trying to `Parse("")` and erroring. `createScheduleHandler` (`internal/httpapi/schedules.go`) accepts either `cron` or `run_at` (RFC3339) on the same `/api/schedules/create` endpoint, never both — the requests page's "Repeat on a schedule" and "Run once at a future time" checkboxes are mutually exclusive for the same reason. Re-enabling (`SetEnabled(id, true)`) a paused `RunOnce` schedule that has *not* fired yet keeps its original run time rather than recomputing one (there is nothing to recompute from), which means a run time that passed while paused fires as an immediate catch-up on the next tick, same as a cron schedule that missed occurrences during an outage; re-enabling one that *has* already fired errors, since firing is `RunOnce`'s terminal state and there is no second occurrence to resume into.
- **No automated sender reaches a busy desktop, and none can race a person** (`httpapi/sendlock.go`). A request reaching an agent that waits on a question is taken as the *answer* (`tasks.Plan`, `watchers.command_watcher`): an email's "yes, pay it" must never become a person's approval, nor a schedule's run land as someone's reply. `Server.Submit`/`SubmitTracked` - the doors schedules, DAG nodes, email triggers and `/api/channels/inbound` use - are `submitWhenFree`: under the desktop's **send lock** they check `tasks.Store.Busy` and send, or refuse with a `*DesktopBusyError`, which callers outside httpapi recognise by its `DesktopBusy()` method (they cannot import httpapi) and treat as "try again later": a schedule is held (`Schedule.Waiting`, shown on the Requests page) without advancing, a DAG node is released, an email job goes back to pending with the reason. Every person-initiated send takes the same lock (`submitRequest`, and the replay / `/skill`/`/learn` / ticket handlers around their own Busy check), so a check-then-send is atomic against all of them. A person may still send to a busy desktop - that *is* how they reply. Verified live: a second invoice email arriving while the agent waited on a question was held ("Waiting: the agent is waiting for your reply"), and went out as its own task 10 s after the first finished.
- **A mailbox is read by UID, which is what makes sleep safe.** Connecting records UIDVALIDITY and UIDNEXT, so mail already there never fires; each poll reads UIDs above `last_uid` (at most `maxPerPoll`), and `RecordPoll` saves the new position *and* the jobs in one transaction - a crash, a dropped connection mid-poll or a laptop sleeping mid-poll neither loses an email nor queues it twice (`TestAFailedPollNeitherLosesNorRepeatsAnEmail`). A connection is opened per poll, never kept: a socket does not survive a sleep. `Runner.noticeSleep` compares *wall-clock* gaps between ticks (`Round(0)`; the monotonic clock stops while asleep) and polls every mailbox at once on waking. A new UIDVALIDITY rebaselines rather than firing on the whole folder.
- **A From line proves nothing; `verifySender` reads the provider's own verdict.** Only the *topmost* `Authentication-Results` counts (a sender can write any such header into its own email; the provider's is added above it), and for Gmail only one whose authserv-id is `mx.google.com`; it must show `dmarc=pass header.from=<domain>` or `dkim=pass header.i/d=<domain>` for the From domain. `VerifiedOnly` (default on in the page) records an unverified match as `skipped`, and "Send anyway" retries it. Email sent to yourself is usually not verified. Verified live through Dovecot: a spoofed "Acme CEO" invoice (`dmarc=fail`) was skipped while a genuine one ran.
- **The Triggers page (`/triggers`, and `/email`, which now redirects to it) and `/api/mail*` are refused to the desktops** (`httpapi/humansonly.go`, 403). An agent - or a prompt injected into one - must not read someone's inbox headers or add a rule. A container is recognised by address: inside a Docker network desktops use (`desktop.Manager.ContainerNetworks`, cached a minute) and not its gateway - a browser reaches the control plane from loopback (binary on the host) or from the gateway (compose's published port). Verified live under compose: from `desktop_mailbot`, `/email`, `/api/mail` and `rules/create` answer 403 while its own callbacks work, and the host's browser gets 200. Not covered: the released binary on Docker Desktop (macOS/Windows), where a container's call to `host.docker.internal` arrives on loopback like the browser's. `/api/keep-awake` stays open (the host script needs it; it reveals nothing).
- **An email-triggered request writes the email out as plain delimited text and says the task again after it** (`mailtrigger.Render`, `emailStart`/`emailEnd`). Measured on the desktops' own model (qwen2.5-coder:3b, Ollama harness, a real desktop, real email via Dovecot): an `EMAIL:{...}` block like a schedule's `TIME:{...}` was read as a shell variable - `grep ... <<< "$EMAIL"`, against a variable that does not exist, in 3 of 6 runs. The text is marked as the sender's (information, not instructions), `---` in it is broken up so it cannot fake the end marker, and the request after the email keeps a sender's "ignore all previous instructions" from being the last thing the model reads. A request starting with `/` is sent as written.
- **The Ollama loop no longer reports work it never did** (`task_runner.UNRUN_COMMAND_NUDGE`, `UNGROUNDED_DONE_NUDGE`, `TASK_WANTS_CHANGE_RE`, `WRITES_RE`). Found by the email tests on a real desktop: the model replied `HELP: ... COMMAND: echo INV-7001 >> ~/work/invoices.txt DONE: ...`; the parser rightly took the HELP, the plain pushback then got `DONE: The invoice number is INV-7001.`, and the task was recorded done with nothing written (3 of 3). Now a HELP carrying a command is answered by naming that command as not run (the model must send it itself, so every command check still applies; the guessed DONE beside it is not kept), and a DONE is pushed back once when the model proposed a command it never ran, or when the task asks for a change (append/write/save/create/delete/...) and no *successful command that can change something* (`WRITES_RE`: a redirect into a file, `tee`/`cp`/`mv`/`rm`/`mkdir`/`sed -i`, a script) has run - "extracted the number, then said DONE" was the next failure measured. A question is never pushed back, and a second DONE is taken. **Commands deliberately stay in `/bin/sh` (dash)**: running them in bash so the model's `<<<` works made 8-email runs worse (2 and 3 of 8 against 6 of 8) - see the note above `commands.run_command`.
- **In a task that says to append, the Ollama loop never runs a command that would overwrite a non-empty file** (`task_runner.overwrite_target`, `OVERWRITE_NUDGE`). Measured live: asked to append an invoice number, the model wrote `echo "INV-9802" > ~/work/invoices.txt` and the line the previous email's task had appended was gone - the run itself looked fine; the loss showed a task later. Such a command is refused before it runs and the model told to use `>>`; after `MAX_OVERWRITE_NUDGES` (2) the person is asked. It recognises a plain `> file` onto an existing non-empty file only (not `/dev/*`, not `2>`), in both `perform_task` and `continue_after_query`: a net for one measured mistake, not a sandbox.
- **Mailbox passwords are encrypted at rest** (`mailtrigger/secret.go`: AES-256-GCM, key in `DECURIX_DATA_DIR/mail.key`, 0600, created with `O_EXCL`). It keeps the password out of a copied `decurix.db`, not away from someone who can read the whole data directory. A plaintext password (from before the key) is sealed at startup; a key that no longer opens one makes the mailbox "Password needed" rather than failing.
- **Email jobs are sent at most once, and retried only when nothing was sent.** A job is claimed (`pending` -> `sending`, a compare-and-swap) before it is sent, so two dispatchers - the tick and a "Check now" - cannot both send it (`TestTwoDispatchersNeverSendTheSameEmailTwice`). A failed send is retried after 1, 5 and 15 minutes, then failed; a busy refusal is not an attempt. A job left `sending` by a control plane that stopped is marked failed with "check the desktop's chat" (`Store.RecoverInterrupted`), never resent on its own: its task may already have run, and may have consequences.
- **A mailbox whose password is refused is not polled again until a person gives a new one** (`Account.NeedsPassword`, `Runner.due`): repeating a refused login is how an account gets locked. "Check now" still tries once. A mailbox that keeps failing otherwise (network down) is polled at doubling intervals up to 15 minutes. A poll works through up to 500 new emails in batches of 50; a mailbox or rule deleted while a poll runs leaves no jobs behind (`RecordPoll`).
- **Keep-awake is held only while it is wanted, and only stops *idle* sleep.** Lid close, Sleep from the menu and a flat battery still sleep the machine - no application can veto them - and the page says so. It is wanted while a mailbox is polled, an email job waits to be sent, a schedule or DAG cron is pending, or a desktop has a task running or queued (`tasks.Store.Working`) - not for a task waiting on a person, which can wait for days. The host scripts ask with `?holder=script`, which is how the page knows whether anything is actually holding the machine in a container deployment (`State.Script`; it says "Nothing is keeping this computer awake" otherwise). Verified live on this repo's WSL host: `powercfg /requests` lists a SYSTEM request from `powershell.exe` while held and none after release, for the Go helper, `lib/keep-awake.sh` (also against the real compose deployment) and `Keep-Awake.ps1`. A `docker pause` of the control plane for 2m36s stood in for a sleep: on thawing it logged the gap, polled at once, and the email delivered meanwhile was read within a second and ran. Every child of the WSL loop gets `3>&-`: a `sleep` that inherited the helper's pipe kept the request alive 30 s after the loop was killed. The host is on S3 standby, where a SYSTEM request fully blocks idle sleep; on Modern Standby (S0ix) laptops Windows may still drop to standby once the screen is off - not verified.
- **Windows apps run on the host and show in the VM** (`internal/winhost`, `httpapi/hostgui.go`, `desktop/hostapps.go`'s `hostGUILauncher`). Copying a Windows app to a VM writes a launcher that opens `/host-gui/view` in the VM's own Chromium (`--app=`), not a `host-run` that would open the app on the person's own screen. The app itself is started by `bridge.ps1` on a **private Win32 desktop** (`CreateDesktop` + `CreateProcess` with `lpDesktop`): it renders normally but is never on the visible desktop - `FindWindow` from the interactive desktop finds nothing, and a count of the app's windows on it stays where it was (checked for Character Map, Paint, Chrome, Bruno, VS Code). What the viewer shows is **every visible top-level window of the app composited in z-order** (`Native.Compose`: menus, drop-downs, tooltips and dialogs are separate top-level windows, so a single-window capture made them invisible and unclickable), each captured with `PrintWindow(PW_RENDERFULLCONTENT)` and cropped to `DWMWA_EXTENDED_FRAME_BOUNDS` (Windows' invisible resize border captures black; a popup's shadow margin does too, so near-black is drawn transparent over the window beneath); a click is hit-tested against the topmost window at that point. Input is **window messages, always posted** (`WM_LBUTTONDOWN/UP`, `WM_CHAR`, `WM_KEYDOWN` to the innermost child under the point, keyboard to `GetGUIThreadInfo`'s focus window of the topmost window) - never `SendInput`, which only reaches the visible desktop, and never `SendMessage`, which does not return until the app has handled the message: a click that opens a modal dialog runs a nested message loop and froze the whole session.
- **Modifier keys need the input queue's key-state table, not just messages.** `GetKeyState` (how an app learns Ctrl/Shift/Alt is held) reflects hardware input only, so a posted `WM_KEYDOWN` carries no modifiers and Ctrl+S or Shift+click do nothing. `WithModifiers` runs the event on a helper thread that has called `SetThreadDesktop(private desktop)` and `AttachThreadInput` to the app's thread, sets the shared key-state with `SetKeyboardState`, posts the messages, and holds ~80-150 ms so the app dequeues them under that state (a toolkit that handles shortcuts in its message loop, like WinForms, only sees posted messages). Verified by the test app's own `KeyDown`/`MouseDown` handlers reporting `ctrl`/`shift`. The viewer sends the browser's `keyCode` (it is the Windows virtual-key code) with `mods` (`c`/`s`/`a`) for named keys and any Ctrl/Alt shortcut, and the text a key produces (`type`) otherwise - AltGr arrives as Ctrl+Alt and is treated as text.
- **The clipboard is the person's own** (it belongs to the window station, which the private desktop shares). So *paste* (the viewer's `paste` event) is typed into the app line by line (`Session.Paste`) and never touches the host clipboard, and *copy* (Ctrl+C/X in the viewer, `Session.Copy`, only vk 67/88) presses the key in the app and reads the host clipboard only if `GetClipboardSequenceNumber` changed, then puts back what was there when it was plain text or empty. An app's own Copy menu item is not noticed. The VM's clipboard is set with `execCommand('copy')` on a hidden textarea, because `navigator.clipboard` needs a secure origin and the viewer is plain http.
- **What can and cannot be hidden.** A packaged app is either a full-trust desktop program that ships in a package (Notepad, Paint, Terminal: `EntryPoint="Windows.FullTrustApplication"` plus an execution alias) - `Resolve-Packaged` finds the alias and runs it like any program - or a **true UWP app (Calculator, Camera), which Windows only activates on the visible desktop and which cannot be hidden**; that is refused with an explanation rather than leaking a window. `shell:AppsFolder\{known-folder GUID}\x.exe` resolves to its real path, and a classic app listed as `shell:AppsFolder\<AppUserModelID>` (Chrome, Brave, Discord) is found through its Start menu shortcut by the name `Get-StartApps` gives it. A Chromium browser or Electron app (recognised by `icudtl.dat` beside the executable or one folder down, plus a name list) would hand a second launch to the copy already running - on the person's own desktop - so it gets a **persistent private profile** (`%LOCALAPPDATA%\Decurix\hidden-profiles\<desktop>-<app>`): a sign-in made inside the hidden app survives, and the person's own profile (locked by the running copy) is never what is shown. Browsers also get `--no-first-run --no-default-browser-check`: on a private desktop nobody can answer a modal first-run or "make me your default" dialog, and a modal dialog swallows the keyboard for the whole window (which read as "typing does not work" until the composited frame showed the dialog). A `.lnk` is resolved to its target first. Not supported, and why: **audio** (the desktop containers have no sound device and noVNC carries none, so there is nowhere in a VM to play it), file drag-and-drop, an app that ignores synthetic window messages, and Notepad-style apps show whatever state they restore (Windows 11 Notepad reopens its saved tabs).
- **The helper launches the app with a clean environment** (`CleanEnvironment`): `ELECTRON_*`, `VSCODE_*` and `NODE_OPTIONS` are stripped. A helper started from inside an Electron program (or VS Code's extension host, whose `ELECTRON_RUN_AS_NODE=1` reaches Windows through WSL interop) otherwise hands it to the app, and an Electron app started that way runs as plain Node, rejects its own `--user-data-dir` and exits with code 9 - which looked exactly like "VS Code cannot run on a private desktop" until the environment was checked. The working directory defaults to the app's own folder for the same family of reasons (a `\\wsl.localhost\` UNC cwd breaks Electron apps).
- **Access to the host-gui API is by signed launch token, and never through a tunnel** (`winhost.Token`, `httpapi.hostGUIAuthorised`, `hostGUIDirectOnly`). The API lets a caller see and drive a program on the host, and it is on the unauthenticated primary listener, so a session id (`<desktop>-<app>`, guessable) is not enough: each launcher carries `token=` = HMAC-SHA256 over the session id, the program and its arguments, keyed by a secret in `DECURIX_DATA_DIR/hostgui.key` (0600, so launchers survive restarts). `start` validates the token against exactly what it launches (a launcher edited to run something else has no valid token), remembers it for that session, and every later request (frame, stream, input, stop) must present it. Requests carrying `Cf-Connecting-Ip`/`Cf-Ray`/`X-Forwarded-*`/`Forwarded`/`X-Real-Ip` are refused: the viewer runs in a window of the VM and reaches the control plane directly, never through the tunnel. `desktop.Manager.HostGUISecret` and `httpapi.Server.HostGUISecret` are both set by `main` from `winhost.LoadSecret`. Launchers written before tokens existed stop working; copy the apps again.
- - **"Is this Windows" (`desktop.IsWSLOrWindows`) never rests on a `/mnt/c` folder existing.** `docker-compose.yaml` always creates that mount, and the Linux scripts mount the host's own `/` there, so on a Mac or an ordinary Linux machine it is an empty folder or a Linux root, and the check used to say Windows: the control plane then ran the Windows Start Menu query (whose last resort starts a container) and tried to warm a helper it can never have. The kernel (`/proc/version`, `WSLENV`) decides, or a drive that really holds a `Windows` folder (`hasWindowsInstall`). `queryWindowsStartApps` returns nothing at all off Windows.
- **Native Windows has no bash and no POSIX modes.** `createHostCmd` runs a signed command as the program itself (no `bash -c`, which on a WSL install would run it inside Linux), and `/api/host-bridge/open` uses `rundll32 url.dll,FileProtocolHandler` so no shell parses the link's `&`. `hostbridge open` waits `hostOpenWait` for the opener to fail and reports it (`startAndWatch`); it used to answer success for a control plane in a container with no `xdg-open`, which is the ordinary Mac/Linux compose case: opening a link on the host from a desktop is honestly unavailable there. `hostgui.key`'s 0600 does nothing on Windows; its folder's per-user ACL is what protects it.
- **Bridge gateways are bound on Linux only** (`cmd/decurix/main.go`). On Docker Desktop (macOS, Windows) the bridge gateway addresses exist only inside its VM, so binding them fails, and `host.docker.internal` already reaches a loopback listener.
- **`scripts/mac/lib/host-mounts.sh` points compose's host mounts at real folders.** Compose defaults `DECURIX_HOST_HOME`/`DECURIX_HOST_MNT_C` to `/home` and `/mnt/c`, which a Mac does not have and Docker Desktop for Mac does not share; the Mac scripts export the user's home and an empty folder. It has no `.ps1` twin: `scripts/windows/` leaves the defaults, which Docker Desktop for Windows resolves inside its own WSL VM - not checked on a real Docker Desktop for Windows.
- Tests that stand bash in for the Windows helper, or run the bash launchers a VM would run, skip on Windows (`requireBash`); the native-Windows behavior has its own tests in `internal/httpapi/hostgui_windows_test.go`, built only for Windows.
**Apps can be copied into a desktop that already exists**: `POST /api/desktops/host-apps/copy` (`id`, `host_apps` comma-separated IDs from `/api/host-apps/detect`) runs the same `MigrateHostApps` creation does - to add apps later, and to overwrite launchers an older build wrote. There is no dashboard control for it yet; the dashboard's app picker lives in the create dialog.
- **The copy-apps picker lists only what a VM can really show, and says how** (`HostAppItem.Mode`, `desktop.vetHostApps`). A listed entry is one of: `web` (a service whose web version opens in the VM's own Chromium - the description says you sign in there), `host_gui` (a Windows program the host has *confirmed* it can run hidden), `data` (credentials/settings copied as files) or `helper` (the host-run bridge). Everything else is left out rather than offered with a caveat: Linux and macOS apps (their only launcher was `host-run`, which opens on the host's own screen, and the DISPLAY-tunnelling that would draw it in the VM was never verified), the chrome/edge/firefox/vscode/youtube defs (same launcher, plus profiles the VM has no app to use - Windows browsers encrypt cookies with DPAPI), and audio/video apps (`needsSound`: the VMs have no sound device). `host_gui` is decided by the bridge itself: `winhost.Check` sends `check <target> <args>`, which runs the very `Resolve-Launch` a real `launch` runs but starts nothing, so the list and a launch cannot disagree. It refuses what is known to fail or to leak a window onto the visible desktop: true UWP apps, shell-only targets, folders, non-programs (`.msc`, `.cpl`), WSLg shortcuts (the "(Ubuntu)" entries - Windows shows those itself), programs whose manifest asks for administrator rights (the prompt cannot be answered on a hidden desktop) and shell/script-host stubs (`control.exe`, `cscript.exe`...). Measured on a real host: 110 of 174 Start-menu apps refused. **"Confirmed" means the host can start it, not that its window is proven to render** - that would need launching every app, and a scan must not start Outlook. Verdicts are cached per target until a forced rescan (a full check took ~8-25 s), and `MigrateHostApps` only honours IDs the current scan offered. Without a checker (`desktop.SetHostAppChecker`, installed by `httpapi.NewServer`), or when the helper fails, no Windows program is offered: an app that could not be asked about is not one that can be promised.
- **A copied app that only opens a local web page opens that page in the VM's own browser** (`winhost.Manager.LocalPage`, `desktop.localPageLauncher`, `vmPageURL`). The bridge already recognised such a launcher (a small program whose text holds `--app=http://localhost:PORT`, e.g. the the web app launcher) and ran its browser on the hidden desktop - where the worker got a picture: no fields, coordinate-only demonstrations, a password field not known to be one. `check` now reports the launcher (a seventh field; `launchr` carries it too, so a fast launch still starts the server), and the VM launcher tries the page at `host.docker.internal:PORT` first, in an app window of the VM's Chrome; when nothing answers it asks `/api/host-gui/start` for the app (whose launcher starts the server) and waits; only a page the VM still cannot reach is shown through the viewer. The picker says "A web app: opens in the VM's browser". Works when the server listens beyond the host's loopback (a WSL container, as the web app is); a Windows process bound to 127.0.0.1 only falls back to the viewer.
- **A host app's controls are real elements in the VM, read from Windows' accessibility tree, with a vision model as the fallback** (`bridge.ps1`'s `Tree`/`ReadControls`, `winhost.Controls`, `httpapi/hostcontrols.go`, `hostgui.html`'s `#ax`). The viewer was a canvas, so to a worker every Windows program was a picture. The helper's `tree` walks the app's visible windows with UI Automation on a thread attached to the private desktop (it works there: Character Map, Excel, a hidden Edge measured) in one cached request (~0.5 s), maps each control into the picture's pixels by the rule `Compose` cuts the picture by (`Geometry`, worked out afresh: with nobody watching nothing is composed), and answers at once with the last read while the next runs beside the input, saying whether that read began after the latest input (`fresh`). The viewer asks over its WebSocket (`{"kind":"controls"}`), lays the controls over the picture as invisible buttons, links, tabs, options, cells, checkboxes and `<input>`s (`type=password` for a password field) and carries `data-decurix-busy` from an input until a fresh read - the phone viewer's design - so `observe`, `act`, the approval gate, privacy and the recorder work on a Windows app as on a page. Chromium (browsers, Electron) is started with `--force-renderer-accessibility`, or its page is four title-bar buttons. A browser page's root Document says it is read-only and is left out; a RichEdit field is a Document that says nothing and is a field (Character Map's "Search for"). **When an app reports no usable control** (`Controls.Actionable`: not text, images or the title bar's buttons) and a hosted brain reads pictures, `sessionControls` has it list the controls of the current picture (`visionSystem`, at most every `visionEvery` and only for a changed picture; boxes checked and cut to the picture, a password field's value dropped, no `focused`), and the viewer says "Controls read from the picture by the vision model". Verified live in a worker through a dev control plane: Character Map driven by name (a checkbox, a field typed into, a button), and an owner-drawn WinForms form with no accessibility at all filled and saved through the vision read. Not done: Excel cells are `gridcell`s to click, not fields to type into; a vision read costs a model call per changed picture while a viewer is open.
- **A click on a DPI-unaware Windows app landed short** (`ClientLParam`). Windows rescales the point of a mouse message posted from the (system-aware) helper to a DPI-unaware window - measured at 125%: (269, 96) arrived as (215, 77) - and the helper scaled it as well. It now sends the physical client point and lets Windows convert.
- **Nothing on a private desktop may outlive what is showing it, because the person cannot see it to close it.** `Shutdown` first posts `WM_CLOSE` to the app's windows and gives them ~2.5 s, and only then terminates what is left - an app that is simply terminated leaves a "did not shut down correctly" flag and Chrome greets the next start with a Restore prompt. Three independent guarantees, each of which had a real bug found by testing it: the app runs in a Job object with `KILL_ON_JOB_CLOSE` (the struct must match `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` exactly - an extra field silently disabled it and a `quit` before the window existed left the app running), `Shutdown` also terminates the launched process and every process that owns a window on the desktop, and stdin closing (the control plane dying, `docker restart decurix`) ends the helper. A session with no viewer for `idleStop` (90s) ends itself, so a viewer that stays connected while the picture is static must keep it alive: a connected viewer (`Session.Watch`, held by the WebSocket) counts as watching, and closing the viewer window (`pagehide`) stops the session at once.
- **The helper is reached through the same `docker run --privileged --pid=host ... nsenter` hop `createHostCmd` uses when the control plane is in a container** (`hostShellCmd`, with `-i` so stdin stays open), and the script reaches Windows through `/tmp`, which `docker-compose.yaml` mounts from the host: `hostGUIStarter` writes `/tmp/decurix-winhost/bridge.ps1` and runs it from `$(wslpath -w ...)`. It works where there is a Windows to run it on: through WSL (that hop), and on Windows itself, where `nativeHostGUICmd` runs Windows PowerShell directly on `bridge.ps1` in `%TEMP%\decurix-winhost` (no shell, no `wslpath`, no docker). On a Mac or an ordinary Linux machine there is no private Win32 desktop, so `hostGUIStarter` refuses with a plain message and the picker offers no Windows programs (the web apps and data copies still work). Native Windows was verified by running the real helper and the real picker scan from a Windows build of the tests; Mac was verified only to compile, vet and behave as "no Windows apps". The helper must never open a network listener: an earlier draft used an `HttpListener` on all interfaces, which would have let anything on the network click and type into a host app.
- **A VM showing a host app is in use even though nothing proxies its screen**, so `httpapi.markDesktopViewed` calls `desktop.Manager.MarkViewed` for as long as its viewer's frame request is open; without it `idlepause` paused the desktop out from under an open viewer. The launcher passes `desktop=${DESKTOP_ID}` for this.
- **A copied Windows app is kept running on its private desktop, ready, not started when it is opened** (`winhost.Manager.Keep`/`Forget`/`ForgetDesktop`, `httpapi.startHostGUIAppAhead`, `RestoreHostApps`). The launcher write (`packDynamicApp` -> `startHostAppAhead(desktopID, id, ...)`) keeps it; when it ends - the person closed it inside the viewer, closed the viewer window (`pagehide` -> stop), or it crashed - a fresh one is started `keepRelaunch` (2 s) later, so the viewer's `start` joins a running app and the "Starting ... on the host" line (shown only after 700 ms now) never appears. A kept app nobody has opened yet is never reaped for being unwatched; once opened and left, `idleStop` ends it and a fresh one replaces it. A launch that fails is retried with backoff (30 s doubling to 30 min). The kept list is saved in `DECURIX_DATA_DIR/hostgui-apps.json` and restored at startup for VMs that still exist; deleting a VM forgets its apps. Cost: every copied app holds its memory on the host all the time (a hidden Chrome is a few hundred MB). `Start` never joins a session that is closing (`Session.ending`) and waits for one `Manager.Stop` is still ending (`stopping`): both would use the same private desktop, whose shutdown closes every window on it. The viewer closes its own window when the app closes (`appClosed`: `window.close()`, which Chromium allows for an `--app` window with one history entry), instead of saying "The app was closed" and needing a second close. `start_agent_terminal.sh` keeps looking for `*-host.desktop` launchers for 5 minutes before deciding not to pre-warm Chromium, because a new VM's apps are copied in while it boots.
- **Why a host app is fast, and what not to undo** (measured on this repo's dev host, Chrome, before -> after). *Start* 5.7 s -> 1.6 s: the helper's C# is compiled once to `%LOCALAPPDATA%\Decurix\bridge\Native-<hash>.dll` (a fresh `Add-Type` was ~2-4 s of every start), a warm spare helper waits (`Manager.Warm`/`keepWarm`, let go after `spareTTL`), and what a check finds a program to be (`Get-StartApps` and the Start-menu walk were ~3 s of every launch) is kept on the **Go side** (`Manager.resolved`, keyed by target): `check` replies `OK<TAB>exe<TAB>args<TAB>dir<TAB>own<TAB>base` and a launch sends `launchr` with exactly that, so nothing is looked up and the cache survives every helper being replaced (a program that has since moved gets `ERR Not found`, is forgotten, and is launched through the full lookup once). **Nothing the person will need should be built while they wait**: `Manager.Warm` is called when the control plane starts (the DLL compile finished ~14 s after start, long before any desktop), when the create dialog fetches `/api/host-apps/detect`, and when `MigrateHostApps` begins (i.e. while the VM itself is still spinning up) via `desktop.WarmHostApps`; each call also restarts the spare's `spareTTL` (now 2 h), so a helper people keep asking for is never let go. Measured with the DLL cache deleted and the control plane just started: launches of 1.9 s, 0.8 s and 0.6 s, the second and third in replacement helpers. The only launch that can still wait is one made within ~14 s of the control plane itself starting. `Start` is single-flight per id (a viewer that loads twice must not open the app twice). *Pictures*: the helper has a capture thread of its own and **pushes**: it compares each capture with the last one it sent (`memcmp` by row, then by 16-px column) and sends only the changed rectangle, grown to 16-px blocks so a JPEG patch has no seam, or the whole picture when over 55% changed, when the size changes, or on `keyframe`. Nothing changed means nothing sent, so an idle app costs almost nothing; it used to encode, base64 and ship a full picture every 120 ms for as long as a viewer was open. Capture runs every ~15-40 ms for 0.7 s after any input (`Kick`) and backs off to 250 ms, and only while `viewers > 0`. Pictures are raw bytes after a header line (`FRAME W H x y w h whole n`), not base64, and everything the helper says goes through one locked writer (`Native.Reply`) because a picture must never be split by an answer. *Transport*: one WebSocket (`/api/host-gui/ws`) carries patches down and input up, both ordered - the old design made a fresh HTTP request per picture and per input, one in flight. In the VM a keystroke now reaches pixels in a median 85 ms (p90 114 ms), a typical update is a ~7% patch, and an idle app costs the desktop ~6% of one core (measured while that desktop was CPU-throttled to its 1 vCPU). A slow viewer loses its backlog and waits for the next whole picture (`Session.publish`) rather than paint patches on a picture it never got, and the viewer drops queued decodes when a whole picture arrives. Do not go back to a streamed `<img>` (MJPEG: Chromium did not paint the first frame of a static app) or to per-request polling. What is still slow is outside this bridge: the VM's own Chromium cold-starting on 1 vCPU (11-15 s the first time on a new desktop, ~1 s after) and Xvnc re-encoding whatever the canvas repaints. Not measured: the compose deployment, where each new helper also pays a ~1 s `docker run ... nsenter` hop (the warm spare hides it).
- **A browser's first start in a VM imports the person's profile, and must not be timed out as a hung helper.** `Initialize-PrivateBrowserProfile` (bridge.ps1) runs inside `launch`/`launchr`, which now wait `launchRequestTimeout` (15 min, `Session.DoTimeout`) instead of the 20 s every other command gets: at 20 s the helper was killed mid-copy, the marker never written, and both the hot start (`Keep`, now given `keepStartTimeout`) and the person's click failed with "the host helper stopped answering". The import copies only the active profile plus top-level files, skips caches and downloaded components (`$ProfileSkipDirs`; Chrome's Service Worker CacheStorage was 1.6 GB), and runs `/MT:16`: measured 7.8 s / 367 MB, was ~1 GB and past the timeout. robocopy's exit 8 (files the running browser holds locked - its cookie file, so sign-ins do not carry over while the person's own Chrome is open) is not failure; only 16 is. The VM launcher (`hostGUILauncher`) raises an open viewer, ignores clicks while one is opening (flock), and the `.desktop` has `StartupNotify` + `StartupWMClass=<control plane host>__host-gui_view` (Chromium's class for the viewer's `--app` window) for a busy cursor; the viewer shows a spinner, and after 6 s says a first start can take a minute. Existing VMs keep their old launcher until their apps are copied again.
- **A hidden Chrome must not show "Restore pages?"**, because that bubble takes the keyboard for the whole window (typing looked dead while clicks worked). The hidden profile persists between sessions, and a session ended without ceremony (control plane restart, helper death, `KILL_ON_JOB_CLOSE`) leaves Chromium's "did not exit cleanly" mark in it. `Resolve-Launch` therefore passes `--disable-session-crashed-bubble --hide-crash-restore-bubble` to the browsers it recognises, and `Clear-CrashMark` rewrites `exit_type`/`exited_cleanly` in the profile before each start. Verified by killing Chrome hard and restarting: no bubble. The old `pagehide` beacon also sent no token, so its stop was refused and closing the viewer window never ended the app until the idle timer did; it sends the token now.
- **`EVENT closed`**: when the app has had a window and then has none for 2 s, the helper says so and the session ends, and every viewer gets `{"closed":true}` - before, the viewer sat on the last picture of an app that was gone.
- **A launcher's host command is split with Windows rules and passed as separate quoted words** (`splitWords`/`shellWords`, `windowsTarget`): pasting a `cmd.exe /c start ...` line into a bash script let bash eat the backslash in `shell:AppsFolder\Microsoft...`, so the host was asked to open a name that does not exist and answered `success: true` anyway (`/api/host-bridge/exec` replies as soon as a GUI app has *started*, before it has run, so it cannot report a launch that later fails). `host-run` uses `python3`, not `curl` (the desktop images do not all ship curl), and every wrapper calls it by absolute path (`~/.local/bin` is not on the basic image's PATH).
- Tests for the launcher must never run a real browser: `hostGUILauncher` execs the first of `chromium-browser`/`google-chrome`/`chromium` it finds, so a test that runs the generated script has to put a stand-in first on PATH (`TestHostGUIWrapperOpensTheViewerForThisDesktop`) - an earlier test launched this machine's real Chromium and hung. `desktop.Manager.BeginProvisioning` returns a **snapshot** of its provisioning record, never the live one (`runProvisioning` keeps rewriting it under `provisioningMu` and the create handler serialises what it is given without that lock - a data race that `TestCreateDesktopAsyncAndStatusPoll` reported under `-race` and `TestBeginProvisioningReturnsASnapshotNotTheLiveRecord` now pins without it).
- **On this repo's own 8 GB Windows host the scarce resource is not CPU, it is memory the WSL VM has not touched lately.** `.wslconfig` gives the VM `memory=8GB` on a machine with 8 GB, so Windows keeps ~0.6-1.2 GB free and hands memory back to the VM slowly: measured, first-touching a fresh 1 GB in the VM took 62 s (later 128 MB took 32 s), while raw disk reads ran at 255 MB/s. That is what a "cold model" costs: `qwen2.5-coder:3b` took **170-320 s to load** (Ollama: `llama runner started in 166 seconds`; the same call is 2 s when resident) and `llama3.2:3b` 324 s. It is why a 7B+ model is out of the question here (4.7 GB would be ~5 min to load and starve Windows), and why every rule below is about *never reloading*. Setting `memory=` lower in `%USERPROFILE%\.wslconfig` (needs `wsl --shutdown`) is the one lever outside this repo.
- **`OLLAMA_NUM_PARALLEL=2` does not keep two desktops' prompt caches apart** (`bench/ollama_parallel/probe.py`, a private Ollama on its own port, never the shared one). Measured on Ollama 0.24.0: a repeated prompt costs 0.06 s against 17 s cold, but prompt A after prompt B is 17 s again with one slot *and* with two - the second slot does not hold A's prefix, while every slot reserves its own KV cache. Leave it at 1. Judge a cache hit by `prompt_eval_duration`, never `prompt_eval_count`: 0.24 counts cached tokens as evaluated.
- **Anything that reloads the model is minutes, and Ollama treats a different `num_ctx`, `num_thread` or `num_batch` as a different runner.** `ollama_client.model_options()` is the single source of the options every request carries and `ensure_model_resident`'s preload sends the same ones; the control plane (`ollama.preloadModel`) and TheBot send `num_ctx 8192 / num_thread OLLAMA_NUM_THREAD / num_batch 512` too, and `buildDesktopEnv` always hands the desktops the control plane's thread count so the defaults cannot diverge. **Never poke the shared Ollama by hand with other options** (a probe with `num_thread` 3 instead of 4 evicted the resident runner: 203 s load + 157 s prompt evaluation before anything answered) - set `OLLAMA_NUM_THREAD=4` in your shell, or use `model_options()`. For the same reason `TestOllamaChatAgainstRealServer` in TheBot is opt-in (`TEST_OLLAMA_MODEL`); it used to load a model on the real server on every `go test`.
- **Warming is `ollama.WarmAsync()`; the thing to protect is the prompt-prefix cache.** `WarmAsync` is debounced (90 s), single-flight, off until `main` calls `ollama.EnableWarm()` (so tests never dial an Ollama), and called from start/unpause/restart, opening `/view/<id>` and `submitRequest`, so a cold load overlaps with the desktop booting or the person typing. It asks `/api/ps` whether the model is loaded at the agents' `num_ctx`, preloads if not, and **does nothing at all if it is**. That last clause was measured, not assumed: a version that sent a resident model a one-token "touch" (to page its weights back in) took 3 s itself and made the *next* chat spend 199 s evaluating its prompt, because the touch's 2-token prompt replaced the cached prefix. On this host the agent's ~900-token prompt costs 75-200 s to evaluate from scratch and ~1 s from cache (five consecutive chats: 1-4 s each after the first), so **nothing but an agent's own request may ever be sent to the shared Ollama while agents are in use** - probes included. What *does* pay the cold cost in the background is `ollama_client.prime_prompt_cache()`, run by `harness.wait_for_backend` on a thread after the backend is ready (Ollama harness only; the hook is `_after_ready`): it sends this desktop's real system messages (same options, `num_predict` 4) once at boot, skipping if a task is already running, so a person's first request finds the prefix cached (a fresh desktop: priming took 138 s, and the first request afterwards 35 s instead of 188 s). On the agent side `ensure_model_resident()` runs before every native request: a cold model is loaded with its own `OLLAMA_LOAD_WAIT_SECONDS` (900) budget and "Loading the model into memory..." steps in the chat, instead of the request's 300 s timeout expiring on a load and reporting "accepted the request but did not finish answering". `KEEP_ALIVE` is 60 min (was 30) for the same reason. Generation is ~4.5 tokens/s here, so every token of reply and every wasted step (~20 s) counts.
- **A new tab that comes late is taken, not asked for again** (`cdp._new_tab_after`, `NEW_TAB_WAIT_SECONDS` 30). On a 1-vCPU desktop just restarted with the web app open, DevTools' `/json/new` answered after its 10 s timeout: `gui open` failed "could not open a new tab: timed out", the tab appeared a moment later, and each retry by the engine opened another. On a timeout the tabs are watched for the new one, which is used.
- **A new tab keeps its address exactly** (`cdp.navigate`): DevTools' `/json/new?<url>` decodes its query once, so the URL is escaped whole (`safe=""`). It kept `%` unescaped, `%2B` arrived as `+`, and ChatGPT was asked "what is 7 8?" for "what is 7+8?" (every `gui ask` with a `+` before this).
- **The Ollama loop pushes back on a mislabelled HELP, and never on a real one.** After a command that *succeeded*, a HELP gets `SUCCESS_QUERY_NUDGE` once (measured: `ls -la /etc | wc -l` → `123` → `HELP: It seems there was an error`); after one that *failed*, `FAILURE_QUERY_NUDGE` up to `MAX_FAILURE_NUDGES` (2) times (`df -h | grep "root"` matched nothing, exit 1, and a human was paged that "the command failed... check the path or permissions"); before any command, `PREMATURE_QUERY_NUDGE` once. What is never argued with: `APPROVAL_RE` (approval, secrets, payments, outgoing messages) and, for the pre-command case, `CONSEQUENTIAL_RE` ("are you sure", delete, irreversible...) - the pre-command pushback used to talk the model out of `HELP: Are you sure you want to delete all files in /etc?` and got `DONE: I am ready to proceed.` `CHOICE_RE` ("which one", "do you want") is only exempt after a command: "do you want to know" is the very false HELP the pre-command nudge exists for, so it must not be in that list. The regexes are not interchangeable and the "permission" alternative is phrase-anchored on purpose: the model's own boilerplate ("check the path or permissions") is not a request for permission. A bare `HELP`/`DONE` with nothing after it is never salvaged as the answer (`salvage_unmarked_response`) - a person was once handed the word "HELP" as the result of their request. A marker-less code block gets a nudge saying nothing was written or run and showing a heredoc `COMMAND:`.
- **The transcript keeps only the command, never the answer the model guessed beside it** (`command_only`), and an empty successful output is rendered `exit_code: 0 (succeeded)` / `(no output) - this is normal` (`format_command_result`): to a 3B model a blank looks like failure, and after `echo banana > hello.txt` it answered with the system prompt's own HELP example. Do not put a worked HELP in `SYSTEM_PROMPT` that reads like a plausible answer.
- **`commands.dangerous_reason` is a deterministic net under the model, not a replacement for its judgement**: recursive `rm` of `/`, a system directory or the whole home, `mkfs`, `dd` onto a device, a fork bomb, `find / -delete`... pause the task before the command runs (`pause_for_dangerous_command` -> `ask_for_query(kind="approval")`) and a *clean* yes (`approval.is_approval`, and none of "but/except/not/instead...") runs exactly that command once (`resume_approved_dangerous_command`, called by `continue_after_query`). It is narrow on purpose (`rm -rf build/`, `rm -rf /tmp/x` and `echo rm -rf /` run) and `..` traversal is not resolved. It exists because the only defence against "delete every file in /etc" used to be a question the model could be talked out of.
- **API errors are the caller's mistake unless proven otherwise.** `httpapi.jsonError` maps `desktop.ErrNotFound` to 404 and `memory.ErrInvalid` to 400 (it still never echoes `err.Error()`), and `desktop.Manager` turns Docker's "no such container" into `ErrNotFound` (`notFound`) for start/stop/restart/pause/unpause/delete - these were all 500s. `POST /api/desktops/send` to a desktop still being created says so (503, `errStillProvisioning`) instead of "no longer exists", and `deliverRequest` waits (up to `autoStartTimeout`) for the agent of a desktop that *just* started (`recentlyStarted`), not only for a stopped one: a request typed the moment a new desktop turns green used to be a 503. Memory entries are length-capped (a worker's memory is read into every prompt it builds). The create/memory/send APIs are **form-encoded** (`r.FormValue`); a JSON body is ignored and, for create, silently makes a desktop with a generated name - fuzz them with `application/x-www-form-urlencoded`.
- **Follow-ups to the above.** (1) `thebot_harness.wait_for_backend` now also waits for `ensure_model_resident()` (a cold model outlives soul's own per-call budgets, and the request should queue, not fail as "could not reason") and `warm_after_ready` loads the embedding model in the background; TheBot is still the slow harness on this host (a greeting took >400 s on a fresh desktop; its prompt frame is unprimed and evicts the Ollama harness's cached prefix, and vice versa) - prefer the `ollama` harness. (2) `SYSTEM_PROMPT` lists reliable commands for the common cases (`df -h /`, `ls -A DIR | wc -l`, `ls -S`, `curl -s ifconfig.me`, `printf`/heredoc for files) and forbids telling the human to run something; measured on qwen2.5-coder:3b it fixed the public-IP task and the wrong disk figure (2/2). (3) `failure_nudge` adds "create the file first with a heredoc" when a command fails on a missing file (`python3 fib.py` with no `fib.py` used to end in a query to the human). (4) `/api/host-bridge/clip` answers 501, not 500, when the host has no clipboard tool.
